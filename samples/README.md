# Samples

Small, self-contained programs, each showing one wiring end to end. The package READMEs explain what a piece is; these show what you actually write.

## How these are meant to be read

**Numbered directories.** Reading order is a property of the set, so it is written down rather than implied. Later samples assume you have read the earlier ones and skip what they already showed.

**Three of the Bicep samples run the same sandbox image**, [`images/bicep-sandbox`](../images/bicep-sandbox/) — sample 01 imports it into an Azure sandbox group, sample 02 builds it on the machine you are sitting at with `wslc build`, sample 05 builds it with `docker build`. That is what makes their output comparable at all: one compiler, one lint rule set, a different backend underneath. Its README carries the build, push and import command lines. Sample 09 is the fourth Bicep sample and runs no image either — its backend is a host work directory and a real `bicep` subprocess, so it compiles with the same CLI and the same `bicepconfig.json` as the three above and its output is comparable with them; the bicep binary the images bake in is installed on the host instead.

**All four CodeAct samples run the same image too**, but nobody in this repository builds it: `mcr.microsoft.com/devcontainers/python:3.13-bookworm`, a standard Microsoft Container Registry image, used by reference. Sample 03 imports it into an Azure sandbox group as a disk image; samples 04, 06 and 08 pull it directly, the way any `docker run` does. Each README says once why a dev-container image is bulkier than this workload strictly needs.

**The docker samples (05, 06, 07, 08) are for everyone `wslc` leaves out.** `wslc` needs Windows and WSL; a Docker-compatible engine is on macOS, Linux and Windows-with-WSL alike, and on every GitHub Actions Linux runner. Sample 05 is the local-machine Bicep story for those hosts; sample 06 is the CodeAct one, and it is also the first sample whose live verification runs a real container on this repository's own runners — see below. Samples 07 and 08 are the two that move a file back out, one by writing a kind and one by configuring the packaged one.

**Sample 07 is the one that builds a kind to read a file back out.** Where 05 and 06 write into a container and read its stdout, 07 pulls a rendered PNG out through `FILES_OUT` and lands it in host storage — and it defines its own `render_diagram` kind in [`diagram_kind.py`](07_docker_diagram/diagram_kind.py) rather than installing a workload package, so it doubles as the worked example of writing a kind against the published protocol alone — that file is the one to open if the question is *how do I write a kind*. Its guest is [`images/diagram-sandbox`](../images/diagram-sandbox/), a Debian base with Graphviz and nothing else, built with `docker build`.

**Every image here is sample-grade, chosen for prototyping.** The dev-container image is a convenience, and even the purpose-built Bicep image is only a pinned CLI on a stock base. A production deployment replaces them with hardened images your organization builds and owns — minimal base, digest-pinned, nothing installed the workload does not use, scanned and rebuilt on your patch cadence — supplied through the same `image`/`image_id` spec fields; nothing else in a sample's wiring changes.

**Each sample installs from PyPI**, not from this workspace, and says so itself. Every `agent.py` carries a [PEP 723](https://peps.python.org/pep-0723/) `# /// script` block naming what it needs, so the whole of running one is:

```bash
cd samples/01_acas_bicep && uv run agent.py
```

[uv](https://docs.astral.sh/uv/) reads that block, resolves it against the index and builds a throwaway environment — nothing is installed into yours, and no list on this page can drift from what the sample actually imports.

That the wheels come from PyPI is deliberate. A sample that only ran inside this repository would demonstrate something a consumer of the published wheels does not get: an import that resolved because every sibling package happened to be on the path.

**Two model clients, and the split is deliberate.** Every sample but three uses `OpenAIChatClient` against an Azure OpenAI deployment with `DefaultAzureCredential` — no key anywhere in the tree, and the same wiring a host is likely to deploy. **Samples 02 and 04 keep `OpenAIChatCompletionClient`** with a key and an optional `OPENAI_BASE_URL`, because they are the local-model road: chat-completions is the surface a local server (Ollama, vLLM, LM Studio) implements well, where newer-API support is often partial in ways that surface as an empty final answer. They pair that with `wslc`, so together they are the sample you can run with nothing rented — a container on your own machine and a model on your own machine. **Sample 09 keeps `OpenAIChatCompletionClient` too, and is the one sample that uses it for both**: Azure OpenAI in CI, reached with `DefaultAzureCredential`, and a local Ollama endpoint by default, reached with a placeholder key the server ignores — one client class, branched on a single environment variable, because its backend is the host and there is no billable sandbox to reach either way.

**No secrets in the tree.** Configuration comes from environment variables, and authentication is whatever the sample's own stack uses — `DefaultAzureCredential`, which an `az login` session satisfies, wherever Azure is involved. Each sample's README lists the variables it reads.

**They are not tests.** Samples are not uv workspace members and are not in the root `testpaths`, so `uv run pytest` does not collect them. They *are* covered by `uv run ruff check .` and `uv run ruff format --check .`, so they cannot rot into non-idiomatic code without CI noticing.

No pull request runs them. Gating every PR on a real subscription and a preview service would trade a great deal of flakiness for a little assurance — so instead `verify-live.yml` runs them on demand and once after each release ([#33](https://github.com/sokolaidev/maf-extensions/issues/33)), where a billable sandbox per run is proportionate and a red is about the released set rather than a contributor's diff.

**Ten of the twelve have a job there. Six pair up**: 01 with 05 on the Bicep workload, 03 with 06 on the CodeAct one, 07 with 08 on reading a file back out. Each pair is one workload against a billable Azure microVM and against a Docker container on the runner, so a red on one side while the other is green names the backend rather than the workload. **Four pair with nothing**, and each drops something the others need. 09: its backend is the host, so there is no sandbox to pay for and no container to build — only the bicep CLI on the runner and the model's inference. 10: no sandbox and no model either, since everything it shows is decided at attach — the first of the three jobs carrying neither an `environment:` nor a `permissions:` block, because there is nothing to look up and no token to mint. 11: a container but still no model, because the router's own decisions need no inference to demonstrate. 12: the same, for the disposal end of those decisions.

So the cost picture is three tiers rather than two. Only the **two ACAS jobs** create a billable sandbox. The **six docker jobs** (05, 06, 07, 08, 11, 12) and 09 create nothing billable — a container on the runner, or for 09 the host itself. And **10, 11 and 12 pay for no inference at all**, which every other job does; where a model is involved it is reached with a federated credential, so there is no stored secret either.

**The two artifact samples assert on something stdout cannot show.** The sink hands the model a sentence saying where a file landed, and a model can write that sentence whether or not one did — so sample 07's check reads the landed PNG's own header and sample 08's reads the summary on disk. A run that answers perfectly and lands nothing goes red.

**Sample 10's job is the cheapest here by some distance.** It reads no configuration and calls no service — no model, no sandbox, no registry — so it is the only one with neither an `environment:` nor a `permissions:` block: nothing to look up and no token to mint. It is not offline: like every job here it checks out the repository and lets `uv` resolve its dependency from the index, per the PEP 723 note above. What it does not do is reach anything at run time. Its check is also the only strict one: with no model between the library and stdout, the printed values are `maf-sandbox`'s own answers rather than a retelling of them, so it compares them exactly.

**Samples 02 and 04 have no job, and that one is structural**: `wslc` needs Windows and a WSL that ships it, which the Linux runners are not, so a break in either is invisible until someone runs it by hand. Nothing similar hides under the docker samples — `test_docker_e2e.py` runs a real container on **every** pull request (the Linux runners have Docker), `FILES_OUT` path included, which is a first for this family: the wslc and acas live paths never could.

**What no sample covers yet** — `FILES_OUT` on a second backend and a multi-turn author → validate → fix loop — is tracked in [#191](https://github.com/sokolaidev/maf-extensions/issues/191) rather than listed here. A roadmap inside a README ages without anything failing; an issue can be closed.

**`Capability.FILES_LIST` is missing on purpose, and will stay missing.** It is the one gap above that is not a "yet". Enumeration — *tell me what is in this directory* — is a separate capability from `FILES_OUT`, which stats and reads a path the spec named, and that split is the load-bearing decision in [`files-out.md`](../docs/design/files-out.md). Only `maf-sandbox-acas` serves it; the docker backend cannot, because Docker has no engine-level enumeration primitive and reaching for one means an in-image shell. No packaged kind requires it — CodeAct says so in its own words, that both its output roads end in literal paths and it therefore requires `FILES_OUT` and never `FILES_LIST`, so it runs on every backend serving the first.

A sample showing a kind enumerating a directory would teach the opposite of what that decision decided. The trap it would teach is specific: a kind requiring `FILES_LIST` when it does not need one has made itself ACAS-only in the worst direction — a host running Docker locally and ACAS in production sees the tool refused at attach on a developer machine and attached in production. `FILES_LIST` is for a kind that must discover a name **nothing told it**; a name unknown when the tool is built can still be known before collection runs, because the model names its files in the call or the program writes a manifest the kind reads. Both end in literal paths, which is all `FILES_OUT` needs.
