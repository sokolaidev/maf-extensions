## How these are meant to be read

**Numbered directories.** Reading order is a property of the set, so it is written down rather than implied. Later samples assume you have read the earlier ones and skip what they already showed.

**Three of the Bicep samples run the same sandbox image**, [`images/bicep-sandbox`](../images/bicep-sandbox/) — sample 01 imports it into an Azure sandbox group, sample 02 builds it on the machine you are sitting at with `wslc build`, sample 05 builds it with `docker build`. That is what makes their output comparable at all: one compiler, one lint rule set, a different backend underneath. Its README carries the build, push and import command lines. Sample 09 is the fourth Bicep sample and runs no image either — its backend is a host work directory and a real `bicep` subprocess, so it compiles with the same CLI and the same `bicepconfig.json` as the three above and its output is comparable with them; the bicep binary the images bake in is installed on the host instead.

**The CodeAct samples all run a Python interpreter, but from two different places.** Sample 03 names the service-provided prebuilt image `python-3.13` — the service keeps it Ready for every sandbox group, so the sample imports nothing. Samples 14 and 15, and the container-based samples 04, 06 and 08, use `mcr.microsoft.com/devcontainers/python:3.13-bookworm`, a standard Microsoft Container Registry image nobody in this repository builds, used by reference: 14 and 15 boot it from a disk image imported into an Azure sandbox group, and 04, 06 and 08 pull it directly, the way any `docker run` does. The container-based sample READMEs say once why this dev-container image is bulkier than the workload strictly needs.

**The docker samples (05 through 08, and 11 through 13) are for everyone `wslc` leaves out.** `wslc` needs Windows and WSL; a Docker-compatible engine is on macOS, Linux and Windows-with-WSL alike, and on every GitHub Actions Linux runner. Sample 05 is the local-machine Bicep story for those hosts; sample 06 is the CodeAct one, and it is also the first sample whose live verification runs a real container on this repository's own runners — see below. Samples 07 and 08 are the two that move a file back out on this backend, one by writing a kind and one by configuring the packaged one; sample 14 is 08 again on a remote backend, which is what makes that channel's portability something the set demonstrates rather than asserts.

**Sample 07 is the one that builds a kind to read a file back out.** Where 05 and 06 write into a container and read its stdout, 07 pulls a rendered PNG out through `FILES_OUT` and lands it in host storage — and it defines its own `render_diagram` kind in [`diagram_kind.py`](07_docker_diagram/diagram_kind.py) rather than installing a workload package, so it doubles as the worked example of writing a kind against the published protocol alone — that file is the one to open if the question is *how do I write a kind*. Its guest is [`images/diagram-sandbox`](../images/diagram-sandbox/), a Debian base with Graphviz and nothing else, built with `docker build`.

**Every image here is sample-grade, chosen for prototyping.** The dev-container image is a convenience, and even the purpose-built Bicep image is only a pinned CLI on a stock base. A production deployment replaces them with hardened images your organization builds and owns — minimal base, digest-pinned, nothing installed the workload does not use, scanned and rebuilt on your patch cadence — supplied through the same `image`/`image_id` spec fields; nothing else in a sample's wiring changes.

**Each sample installs from PyPI**, not from this workspace, and says so itself. Every `agent.py` carries a [PEP 723](https://peps.python.org/pep-0723/) `# /// script` block naming what it needs, so the whole of running one is:

```bash
cd samples/01_acas_bicep && uv run agent.py
```

[uv](https://docs.astral.sh/uv/) reads that block, resolves it against the index and builds a throwaway environment — nothing is installed into yours, and no list on this page can drift from what the sample actually imports.

That the wheels come from PyPI is deliberate. A sample that only ran inside this repository would demonstrate something a consumer of the published wheels does not get: an import that resolved because every sibling package happened to be on the path.

**Every sample declares the same `maf-sandbox` floor: the current released minor.** Read it as "this is the version these were written against", not as a compatibility range — a sample has no consumers to keep compatible, and a floor claiming two minors of support would be a claim nothing here runs. That matters because `uv` resolves the *newest* admissible version, so a floor that is too low is never exercised and never fails: it bites only a reader whose resolution is capped elsewhere, and it can bite quietly. Three of these samples once declared a floor permitting a core whose default working directory was different, where the Bicep compiler simply never finds `bicepconfig.json` and the model reports diagnostics produced without the configured rules. The floors move together after every core release, in the pull request that moves the packages' range, and `tests/test_sample_metadata.py` fails when one falls behind.

**Two model clients, and the split is deliberate.** Samples 10, 11 and 12 call no model at all and so have neither client. Of the eleven that do, seven use `OpenAIChatClient` against an Azure OpenAI deployment with `DefaultAzureCredential` — no key anywhere in the tree, and the same wiring a host is likely to deploy. **Samples 02 and 04 keep `OpenAIChatCompletionClient`** with a key and an optional `OPENAI_BASE_URL`, because they are the local-model road: chat-completions is the surface a local server (Ollama, vLLM, LM Studio) implements well, where newer-API support is often partial in ways that surface as an empty final answer. They pair that with `wslc`, so together they are the sample you can run with nothing rented — a container on your own machine and a model on your own machine. **Samples 09 and 13 keep `OpenAIChatCompletionClient` too, and use it for both roads**: Azure OpenAI in CI, reached with `DefaultAzureCredential`, and a local Ollama endpoint by default, reached with a placeholder key the server ignores — one client class, branched on a single environment variable, so the sample runs on a laptop with nothing rented and still verifies against a real deployment in CI. Sample 09 makes that split inline; sample 13 factors it into a `build_client` and says so in its own docstring.

**No secrets in the tree.** Configuration comes from environment variables, and authentication is whatever the sample's own stack uses — `DefaultAzureCredential`, which an `az login` session satisfies, wherever Azure is involved. Each sample's README lists the variables it reads.

**They are not tests.** Samples are not uv workspace members and are not in the root `testpaths`, so `uv run pytest` does not collect them. They *are* covered by `uv run ruff check .` and `uv run ruff format --check .`, so they cannot rot into non-idiomatic code without CI noticing.

No pull request runs them. Gating every PR on a real subscription and a preview service would trade a great deal of flakiness for a little assurance — so instead `verify-live.yml` runs them on demand and once after each release ([#33](https://github.com/sokolaidev/maf-extensions/issues/33)), where a billable sandbox per run is proportionate and a red is about the released set rather than a contributor's diff.

**Twelve of the fourteen have a job there. Six pair up**: 01 with 05 on the Bicep workload, 03 with 06 on the CodeAct one, 08 with 14 on the file channels. Each pair is one workload against a billable Azure microVM and against a Docker container on the runner, so a red on one side while the other is green names the backend rather than the workload. **Six pair with nothing**, and each drops something the others need. 07: it lands a file the way 08 does, but through a kind the sample writes rather than the packaged one, and only on Docker — `wslc` cannot serve the pull surface at all, and nothing imports a Graphviz image into a sandbox group. 09: its backend is the host, so there is no sandbox to pay for and no container to build — only the bicep CLI on the runner and the model's inference. 10: no sandbox and no model either, since everything it shows is decided at attach — the first of the three jobs carrying neither an `environment:` nor a `permissions:` block, because there is nothing to look up and no token to mint. 11: a container but still no model, because the router's own decisions need no inference to demonstrate. 12: the same, for the disposal end of those decisions. 13: the only job that runs more than one turn, so it is the only one where the model's second answer is under test rather than its first.

So the cost picture is three tiers rather than two. Only the **three ACAS jobs** (01, 03 and 14) create a billable sandbox among the samples — `verify-live.yml` carries one further billable job that is not a sample at all, `acas-e2e`, which runs the backend's own live suite against the real service. The **seven docker jobs** (05, 06, 07, 08, 11, 12, 13) and 09 create nothing billable — a container on the runner, or for 09 the host itself. And **10, 11 and 12 pay for no inference at all**, which every other job does; where a model is involved it is reached with a federated credential, so there is no stored secret either.

Sample 14 is the third billable job and the newest, so it is worth saying what buying it answers. The other two run a command and read stdout, which means no ACAS run had ever pulled a file — the backend's `stat_file` and `read_file` were exercised by unit tests against a fake group client, over payload fixtures copied out of a live run once and frozen. That is the seam where a preview service's SDK and its actual payload have twice disagreed, so it is the seam worth a sandbox.

**No check can be satisfied by the model's prose.** Each one gates on at least one thing the model did not write — a tool's own output, a file on disk, a number the host counted — and those arrive either inside a fenced block or on a line the sample tagged `[measured]`. Some also read the reply, on purpose and always *in addition*: a value has to reach the model and not merely the log, so 03, 06, 08 and 14 all check that the answer appears in what the model said. That check can fail a healthy run whose reply is worded oddly; it can never pass an unhealthy one on its own. The samples that judge a tool's answer print a fenced block of what it returned — the framework records that beside the call, so the model does not write it — closed by a tagged line. The three that judge a landed file print no such block, deliberately: they read the file itself, and off the tag they read what the router disposed, plus for 08 and 14 what the sink took this turn. Every reply is filtered before printing, so a line of one beginning with that tag comes out quoted. A model can write the heading; it cannot close the block, and it cannot answer for the host.

For 08 and 14 that reply check is the grand total, looked for anywhere in the transcript rather than on a tagged line. It is not what proves a program ran. The landed summary is — not because its numbers are unguessable (they are printed in sample 08's README, and the CSV is six rows anyone can add up) but because of how a file gets into `out/` at all: the sink is host-side code, and the only road to it runs through a real call to the tool and a real artifact pulled back out of the sandbox. That was worth doing because the alternative was wrong in both directions at once: `main.bicep` names both rule ids and both severities in its own comments, so a run that never called the tool could satisfy a check made over prose, and three healthy releases went red because a model wrote `**error**` where the pattern wanted `[error]` ([#314](https://github.com/sokolaidev/maf-extensions/issues/314)).

**The three artifact samples go one further, and assert on something stdout cannot show.** The sink hands the model a sentence saying where a file landed, and a model can write that sentence whether or not one did — so sample 07's check reads the landed PNG's own header, and one script reads the summary on disk for both 08 and 14. A run that answers perfectly and lands nothing goes red. What those runs are *also* read on is the host's own and carries the `[measured]` tag for the same reason everything else here does: all three print what the router disposed, and 08 and 14 print what the sink took this turn — a list sample 07 has no counterpart for, since its kind lands one file by a name the sample chose.

**Sample 10's job is the cheapest here by some distance.** It reads no configuration and calls no service — no model, no sandbox, no registry — so it is one of the three jobs with neither an `environment:` nor a `permissions:` block, alongside 11 and 12: nothing to look up and no token to mint. It is not offline: like every job here it checks out the repository and lets `uv` resolve its dependency from the index, per the PEP 723 note above. What it does not do is reach anything at run time. Its check is also the only one that compares values *exactly*. Every check here now reads something the model did not write, but the others read a tool's rendering and so must tolerate what drifts inside it — a day count, an API-version list. Nothing stands between this library and stdout, so a mismatch is a behaviour change rather than a paraphrase.

**Samples 02 and 04 have no job, and that one is structural**: `wslc` needs Windows and a WSL that ships it, which the Linux runners are not, so a break in either is invisible until someone runs it by hand. Nothing similar hides under the docker samples — `test_docker_e2e.py` runs a real container on **every** pull request (the Linux runners have Docker), `FILES_OUT` path included, which is a first for this family: the wslc and acas live paths never could.

**Host-tool calling on a *local* backend** — so the price of a round trip that is not an HTTP call can be read beside sample 15's remote one — is now `SAMPLE_BACKEND=docker` on sample 15 above ([#519](https://github.com/sokolaidev/maf-extensions/issues/519)); `maf-sandbox-docker` had declared `Capability.HOST_TOOLS` since sample 15 landed, and the same sample now reads it on either backend. The umbrella tracking the wirings still missing is [#191](https://github.com/sokolaidev/maf-extensions/issues/191) rather than a roadmap here — a roadmap inside a README ages without anything failing; an issue can be closed.

**Two capabilities are missing on purpose, and will stay missing.** Neither is a "yet".

**`Capability.FILES_LIST`.** Enumeration — *tell me what is in this directory* — is a separate capability from `FILES_OUT`, which stats and reads a path the spec named, and that split is the load-bearing decision in [`capabilities.md`](../docs/sandbox/capabilities.md). Only `maf-sandbox-acas` serves it; the docker backend cannot, because Docker has no engine-level enumeration primitive and reaching for one means an in-image shell. No packaged kind requires it — CodeAct says so in its own words, that both its output roads end in literal paths and it therefore requires `FILES_OUT` and never `FILES_LIST`, so it runs on every backend serving the first.

A sample showing a kind enumerating a directory would teach the opposite of what that decision decided. The trap it would teach is specific: a kind requiring `FILES_LIST` when it does not need one has made itself ACAS-only in the worst direction — a host running Docker locally and ACAS in production sees the tool refused at attach on a developer machine and attached in production. `FILES_LIST` is for a kind that must discover a name **nothing told it**; a name unknown when the tool is built can still be known before collection runs, because the model names its files in the call or the program writes a manifest the kind reads. Both end in literal paths, which is all `FILES_OUT` needs.

**`Capability.FILES_DELETE` is the same shape, mirrored.** Only `maf-sandbox-docker` serves it — `maf-sandbox-acas` and `maf-sandbox-wslc` declare neither — so a kind putting it in `requires` is Docker-only in exactly the direction the paragraph above warns about, and the two backends it locks out are the remote one and the Windows one. No packaged kind requires it and none needs to: a kind built on `sandboxed_tool` has its call directory removed through `Sandbox.reclaim`, which every backend implements and no capability gates. `remove` takes a path a model named and owes it the parent walk; `reclaim` takes a directory this stack created and owes none. That is why one carries the capability and the other does not. There is nothing here a sample could show that would not be teaching the trap.
