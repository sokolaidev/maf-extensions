# Container image security checks

The [Image security workflow](https://github.com/sokolaidev/maf-extensions/actions/workflows/image-security.yml) builds the eligible profiles listed below on Linux/amd64, inventories each built image with Syft, and scans that retained inventory with Grype. It runs on pull requests for affected profiles, daily at 06:35 UTC, and by manual dispatch with a choice of all profiles or one profile. Tag changes and same-tag digest refreshes select every consumer of the changed declaration. Main-branch pushes retain code, workflow, lint, type and CodeQL checks without an additional image-build matrix. Antivirus builds run on source changes and manual dispatch; host-managed signatures remove the need for daily antivirus rebuilds. Other daily builds use the reviewed image digests and refresh package-manager inputs; they are new candidates, not rescans of an earlier release's exact bytes. The [dependency inventory](../../images/DEPENDENCIES.md) records update ownership, compatibility lines and native manifest coverage.

Scanners use the versions and archive checksums pinned in [`install_container_scanners.py`](../../scripts/install_container_scanners.py). Workflow jobs fetch release assets through the authenticated GitHub API and verify their checksums before installing the executables. Installation and download failures fail the scan job.

Failures outside pull requests open or update the workflow's tracking issue through the repository's existing reporter. The scanner jobs have read-only repository permissions; separate failure and recovery reporters have issue-write permission and never run on pull requests. A manual all-profile run on the default branch automatically closes the tracking issue with a recovery link after all profiles complete their scans successfully in the same attempt. Scheduled runs omit antivirus and cannot close this shared tracker. Single-profile runs, branch runs, scans superseded by a newer default-branch commit and deferred Hyperlight scans cannot close it. A tracker updated after the successful attempt started stays open for a later full run, so earlier recovery cannot dismiss a newer failure.

The README badge shows the latest scheduled workflow status on `main`. Passing means every eligible profile in that scheduled run built, its inventory and scan completed, and no applicable High or Critical findings remain after the reviewed component decision below. Raw Grype findings remain available. Manual scans do not update this badge; it does not establish scan freshness or the status of an already published image.

Image publication is the mandatory image gate: its workflow builds the selected profile, retains its exact OCI bytes, checks runtime behavior, produces SBOMs and refuses applicable Critical findings including unfixed ones before maintainer approval. Publication rechecks freshness, and independent signature, anonymous-pull and runtime verification precedes completed release evidence. PR checks validate builds and runtime behavior while reporting applicable vulnerability findings as warnings with retained scan evidence. Findings do not block merging reviewed source, and a green PR check does not establish release eligibility. Python package publishing and PRs, including version PRs, do not depend on live image availability, compatibility qualification or security state. Independent consumer qualification and published-image live verification still require authenticated compatible images; a package release alone makes no image compatibility claim.

PR image selection excludes the two exact MXC experiment records in `EXPERIMENT_RECORDS` in `scripts/select_image_security.py`: image builds and checks consume neither `HOST_PUBLICATION.md` nor `cross-active-results.json`. The selector and its two test modules in `SELECTION_TOOLING` are covered by code checks and portable workflow behavior tests without rebuilding unchanged images. Mixed changes still select every profile affected by the other files. Image-security workflow changes, build and evidence helpers, unknown scripts and neighboring experiment files retain their normal scan coverage. Scheduled scans and image publication gates are unchanged. A successful no-scan check reports selection only; it does not establish image security or clear an existing vulnerability finding.

Core-only edits to `.py` files under `packages/maf-sandbox/src/` select Hyperlight runtime validation through the selector's separate `hyperlight` output, without selecting an AKS probe image-security scan. Package dependency metadata, lockfiles, image recipes, build helpers and non-Python payload changes retain their scan coverage, including when mixed with core edits. Core source remains an image release input, and scheduled/manual scans and publication still scan the probe image. This selection boundary does not clear vulnerabilities found in an existing image.

## Release-needed issues

Bicep scans default to `bicep_route=policy`. The reviewed per-profile policy in `scripts/image_scan_policy.py` currently selects the patched `source` route for `bicep`, `bicep-avm` and `bicep-docker-sbx`. Manual dispatch can still select `upstream` for diagnostics; its findings remain visible in the scan and operational failure tracker. A diagnostic route cannot create component replacement requirements or supersede a replacement scan. The job summary identifies the selected route and purpose. Release dispatch remains an explicit, independently approved choice; a published route differing from the replacement policy is itself a replacement requirement.

Before accepting a Bicep candidate, the reporter verifies its runtime profile, image identity, compiler route and patched-package inventory against the retained scan evidence. Component requirements retain their route and original evidence. For an existing requirement from another route, reconciliation re-reads the original trusted run and checks its attempt, observation time, inventory hash and exact component delta against the authenticated published baseline. When a newer release is current, the reporter finds the original profile/digest in the catalogue and verifies that historical release's immutable evidence and signatures before comparing the old delta. A legacy requirement without route provenance can recover a mismatching scan link from complete trusted run history only when exactly one retained candidate matches its original timestamp, inventory hash and full delta. Only a proven incompatible-route requirement is withdrawn, with the verified scan link and both comparison and current digests retained in the issue. Missing, ambiguous, expired or mismatching evidence preserves the requirement; source changes and published-image vulnerabilities remain independent. A request with no remaining requirements closes as not planned without claiming a replacement release. A later matching or clean scan alone cannot clear a valid component requirement.

The [Image release tracking workflow](https://github.com/sokolaidev/maf-extensions/actions/workflows/image-release-needed.yml) runs after main-branch image scans, published-image monitoring and image release attempts, or by manual dispatch. It maintains at most one open issue per affected profile. Known High/Critical findings on the published digest or an explicit replacement-route policy mismatch use `Image release needed: <profile> (replace <current-version>)`. Source-input and installed-component changes alone use `Image refresh available: <profile> (current <current-version>)` for maintainer review in the next planned release; they do not establish a vulnerability in the published image or require immediate publication. The same issue changes classification when a required replacement reason appears or is resolved. The maintainer chooses the next release number. Resolved requests use `Image release needed: <profile> (resolved at <current-version>)`, including source-only resolutions that need no replacement. Reconciliation updates active issue titles and refreshes their current version. Closed issues stay closed; a remaining or later release need creates a new issue. It starts with profiles that have a completed, delivered release; choosing a profile's first release remains a maintainer action. No committed release history means there is no replacement baseline and no automatic release request.

The reporter verifies immutable release evidence, all three release attestations and the indexed assessment before comparing against the latest completed release. Input comparison covers image contexts, known image builders, prepared Terraform dependencies, Hyperlight wheel packages and its copied probe, and the proxy context. Publishing/reporting scripts and tests do not by themselves request refreshes. The exact consumer paths in `CONSUMER_GUIDES` in `scripts/select_image_security.py`, plus `images/README.md`, are ignored because the image recipes and build helpers do not consume them. Unknown guides and nested files retain their normal build-input classification. Workspace Python metadata and lock files affect only `hyperlight-aks-probe`, which installs workspace wheels and locked dependencies; package metadata affects that profile only for its three wheel packages. Parsed package-version-only changes and matching editable-workspace lock versions are ignored. Recheck these boundaries when recipes consume new inputs. Scheduled scans still cover every eligible profile.

The shared release catalogue is compared by profile membership when its schema and shared settings are unchanged. The build dispatcher is compared by literal profile branches when both revisions use the recognized non-fallthrough shell structure; heredoc contents stay attached to their branch. Shared shell changes, unsupported syntax and unrecognized catalogue structures retain all-profile coverage. The Bicep builder is compared by profile membership only when both revisions declare a single-line literal `PROFILES` set used solely by the recognized membership guard and all text outside that set is unchanged. Renaming another profile does not request a refresh for an unchanged member. Changes to profiles passed as fixed arguments to the shared route validator affect every Bicep image. The release tracker additionally ignores route-error wording and equivalent combined/separate rejection guards when all guards and the rest of the parsed builder remain unchanged; unknown validators and messages with executable expressions retain coverage. Other builder edits retain coverage for every Bicep profile. Missing Git history fails reconciliation instead of guessing that a refresh is available.

Each issue carries the current version/digest, changed inputs or component versions, CVEs and available fixes, and evidence links. Component comparison ignores SBOM IDs, locations and timestamps; a different image hash alone is not a reason to release. A candidate with applicable High/Critical findings remains pending remediation in tracking. Only applicable Critical findings block publication; a High-only candidate may be released while the remediation request remains open. A passing candidate still needs the full release-preparation and approval gate. Failed or missing candidate assessments do not create replacement requests on their own; workflow failures retain their separate operational trackers, and previously known component and vulnerability requirements remain open. Source reasons are recomputed from the verified release source to the current checkout.

Reconciliation holds the same catalogue lock as release and monitor history writers throughout planning and issue updates, and manages only marked issues authored by GitHub Actions. It updates the body when actionable state changes or a newer candidate observation advances the saved ordering timestamp; candidate profile jobs must complete strictly later than release completion and the saved observation to replace that state. Build records identify their run and attempt, and both build collection and artifact creation must fall within the producing job. Evidence links and ordering use that job attempt, so rerunning another profile cannot refresh retained evidence. Older artifacts without attempt identity remain unavailable until a fresh scan. Timestamp ties keep the previously accepted state. Before accepting a scan event, the reporter reads complete retained Actions run history and rejects profiles with newer or tied profile-job completions from trusted completed runs, across all rerun attempts, even when no release-needed issue exists. A newer failed profile attempt also prevents an older scan from becoming current, even when its build or identity step produced no artifact; incomplete run or job history stops reconciliation. It preserves component and vulnerability reasons across unavailable scans, produces no daily reminder comments, and creates a new issue for release needs after the previous issue was closed. Repeated runs update that new active issue, including after an uncertain creation response. The title and body are machine-maintained; add maintainer notes as comments. Component and vulnerability requests close only after a different, completed and delivered digest has authenticated evidence, no remaining source-input differences, addressed component-update requirements and no outstanding known High/Critical findings for that replacement. Each component or vulnerability requirement records the published digest it was observed against; a requirement discovered on a replacement needs a further replacement, even when the issue predates that image. A matching candidate scan cannot clear a pending component requirement. A component-update requirement is satisfied when every recorded addition is present and every recorded removal is absent, comparing component type, name, version and package URL exactly. A higher APK `-r` revision also satisfies an addition when its upstream version, component name and package URL identity (including namespace, qualifiers and subpath) match. Other inventory changes do not prevent closure; other version differences are not assumed to satisfy the request. A source-only request can instead close as not planned when a fresh comparison against the authenticated release finds no relevant build-input differences, including a reverted change or corrected profile classification. Its body records that no replacement was required; this does not claim publication or new runtime qualification. Resolved requests carry a resolved status and discard pending candidate links and findings while retaining their observation timestamp. Reconciliation also repairs stale pending statuses on already resolved requests. A candidate scan cannot silently dismiss an unresolved request. Manual closure leaves the historical issue closed; requirements that remain unresolved after verified reconciliation are carried into a new issue. Evidence retrieval, signature, history-race or issue-state errors leave requests unchanged and report tracking as unavailable. This reporter has issue-write permission but no publication, package-write or signing permission.

During an adjacent core release transition, the Hyperlight profile is deferred when the checkout core cannot satisfy its dependent ranges; the job summary records that no image or security evidence was produced. The other selected profiles still run. A green badge during this transition does not establish Hyperlight image coverage. Invalid or non-adjacent dependency ranges still fail the preflight.

The inventory must contain components and identify the exact built image. For `terraform-random`, `opentofu-random`, `terraform-avm` and `opentofu-avm`, the daily/manual build scan also requires every provider in the selected manifest, at its approved registry, version and platform path. Each unpacked provider executable must expose its Go main module and standard library; source-built providers must match the manifest's Go compiler version. An engine-only inventory or a provider ZIP without catalogued binary components fails this check. All findings remain in the reports. Applicable High/Critical findings, including unfixed ones, warn on pull requests and fail scheduled/manual scans. Only applicable Critical findings block image publication; High findings remain in the assessment and raw reports and still require remediation. Build, runtime, inventory, scanner and evidence-upload errors fail every run; no step or job uses blanket error suppression. Scanner ignore rules and filtered reports remain forbidden. A passing result does not establish the absence of malware, backdoors, uncatalogued software or unknown vulnerabilities.

## Reviewed SQLite library applicability

The sole component exception is `CVE-2026-119586` matched through `nvd:cpe` to Wolfi's Linux/amd64 `sqlite-libs 3.54.1-r0`. The [original disclosure](https://abraxaslabs.tech/research/sqlite-cli-recover) identifies the SQLite CLI recovery/restore pipeline and explicitly excludes `libsqlite3`; SQLite documents the [CLI and library distinction](https://sqlite.org/cli.html#sqlite_command_line_program_versus_the_sqlite_library). This is a non-applicability decision for specific library bytes, not an assertion that SQLite is patched or that every image containing it is safe.

[`sqlite_vulnerability.py`](../../scripts/sqlite_vulnerability.py) requires the exact package URL, matching scanner/SBOM artifact identity and locations, reviewed package file list, and image-bound ELF evidence for `/usr/lib/libsqlite3.so.3.54.1` with SHA-256 `7c8f466fe08716da0c3ce29ef451e8443313b296717fd8ef98b020030fb282f7`. Missing or changed evidence, a detected SQLite CLI, another package or distribution, and other CVEs remain blocking. The decision is valid for assessments from 2026-11-04 until 2026-12-04 00:00 UTC; promotion refreshes an assessment when its exception expires, even inside the ordinary 24-hour freshness window. Maintainers must review any replacement bytes or extension of that deadline.

The same assessment function applies to PR scans, release preparation, promotion revalidation, published-image monitoring and release-needed evidence. `grype.json` is unchanged and retains the High finding; `assessment.json` records the exact component, image ID, library digest, reason, source and expiry under `notAffected`. The approval summary displays that decision alongside the raw severity counts. Monitoring health and public status become stale when any decision expires, even within the ordinary 48-hour freshness window and without another monitor run. A passing applicability assessment does not substitute for image qualification, approval or publication.

The reviewed evidence is [failed preparation 41906526189](https://github.com/sokolaidev/maf-extensions/actions/runs/41906526189/job/126849896784), source `7979755cb77a841dc18bcc3df16221112920468d`, configuration `sha256:be4a792579b8625eb361f50a2492373e681954b7bdaee3d54bbdfde26abda75d`, manifest `sha256:59a4acf431e523079a5261657b2ae5f221436cf66d7c8f2829cd651ff02287e0`. Its retained SBOM and scan identify only the SQLite library package. An independent download of `sqlite-libs-3.54.1-r0.apk` from the configured Chainguard repository has SHA-256 `5ea68a7dad00791dbc5eff42aad9022b0984f82e271058811a4d72181e450144`; its library bytes match the retained SBOM hash and its payload contains no CLI. The reduced [regression fixture](../../tests/fixtures/sqlite-library-match.json) preserves that component and file evidence. Replaying these reports validates the classification; it is not a fresh scan or a published replacement for [#2465](https://github.com/sokolaidev/maf-extensions/issues/2465).

The scan covers the built runtime filesystem. Build-stage-only packages, other architectures, custom image arguments, externally supplied images, upstream device-plugin images and different prepared dependency manifests are outside this inventory. In particular, the broader OpenTofu AVM catalog and OpenTofu platform/provider/multiversion variants require separate scans. Applying the `sbx` template to another base also creates an unassessed image. Image scanning does not qualify sandbox confinement or backend lifecycle behavior.

The Bicep, shell, Graphviz, Draw.io, Terraform/OpenTofu and Hyperlight recipes use digest-pinned Wolfi bases with signed APK packages. Wolfi is a rolling distribution, so package updates and native-runtime compatibility are assessed by each build and scan. ACAS consumer recipes omit build-time device nodes from their final layers and rely on runtime-provided devices. Release preparation rejects special files in every saved layer of ACAS-targeted profiles before OCI retention and records the built image identity and checked layer count in `image-layers.json`; this does not establish live ACAS import or execution. OpenTofu is rebuilt from a pinned upstream commit with explicit Go dependency updates; its retained source-build records distinguish it from the upstream release binary. These images still require deployment-specific qualification, including live AKS/ACAS checks where applicable.

## Reading the evidence

Each matrix job that reaches image identity recording retains an `image-security-<profile>` Actions artifact for 30 days, including when vulnerability findings fail the scan:

- `build.json`: source commit, profile, platform, observation time, run URL and immutable local image ID.
- `image-inspect.json`: Docker's metadata for that exact built image.
- `declared-images.json`: tagged, digest-pinned external Dockerfile references from the assessed checkout.
- `runtime.json`: the selected profile's runtime or packaging qualification, with its own scope limits.
- `sbom.syft.json`: the component inventory, source-image metadata and Syft version.
- `grype.json`: findings, Grype version and vulnerability-database metadata.
- `grype.yaml`: the empty configuration used to prevent repository-discovered exclusion rules.

A scanner failure may leave an incomplete artifact. Missing inventory or scan output is missing evidence, not a clean result. Inspect the job's conclusion and steps as well as its files. Actions artifact downloads may require a GitHub login; job summaries identify each target without downloading the artifact. Retain the original reports elsewhere before their expiry if an assessment depends on them.

The local image ID identifies the image configuration and its content-addressed filesystem layers. It is not a registry manifest digest and cannot be substituted into a registry pull command. These checks do not publish images or retain the complete built image. Rebuilding the same source can produce different bytes; use these results only for the recorded local image ID.

## Planned distribution

The agreed registry is GitHub Container Registry, under `ghcr.io/sokolaidev/maf-extensions/`, with packages linked to this repository. The [accepted image release contract](container-image-releases.md) defines names and independent versions for all eleven Linux/amd64 profiles, maintainer-approved publication of the exact assessed bytes, signed provenance and SBOMs, and daily monitoring of released digests. It requires a release scan no more than 24 hours old, stale status after 48 hours, and 90 days of continued monitoring after a release is superseded.

Interrupted publications are registered before the registry write. Incomplete or abandoned candidates remain visibly blocked and monitored for as long as they remain public, even if no release completes. Consumers require an authenticated completed catalogue record for the selected profile, version and digest, even when image attestations pass. Abandonment permanently retires the version; it does not delete the image automatically or start the completed-release 90-day window.

Implementation of that contract is pending. Public publication is not enabled by the scanning workflow: it grants no package-publishing or signing permissions. Published candidates will need their own registry manifest digests, retained reports and signed provenance.
