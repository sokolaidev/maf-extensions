# Manual platform remediation rehearsal

The [rehearsal workflow](../../.github/workflows/platform-image-remediation-rehearsal.yml) implements an isolated manual entry point for the [remaining qualification plan](platform-remediation-qualification-2026-11-09.md#remaining-qualification-plan). It qualifies current authenticated platform evidence or an explicitly selected historical replay case and can exercise App delivery with an isolated draft PR while normal platform automation stays disabled. Update cases deliver the qualified dependency diff; rebuild cases deliver a test receipt. [Qualification evidence on #2517](https://github.com/sokolaidev/maf-extensions/issues/2517#issuecomment-6768000540) records successful historical rebuild, App recovery and draft receipt CI. Hosted qualification of positive Bicep/OS updates, actual dependency-diff delivery and production operation remain pending.

## Select a case

Dispatch from `main` after this workflow is merged. The [reviewed case manifest](../../scripts/platform_rehearsal_cases.json) defines the required finding type, planner outcome and aggregate result. The request receipt binds the manifest hash, source SHA, workflow run and attempt to the selected case.

| Case | Required authenticated finding | Required result |
|---|---|---|
| `current-rebuild` | Bicep/.NET `source-pin-sufficient`, with no proposed source edits | Ordinary builds and all inherited runtime/inventory checks pass; targeted findings absent; `release-needed` |
| `bicep-update` | Compatible Bicep/.NET patch producing a source update | Each selected finding is observed in a baseline and absent from every applicable candidate; aggregate `ready` |
| `apk-pinned` | Compatible vendor APK fix producing a source pin update | Signed vendor-repository installation, all affected builds/runtime/inventory checks, baseline matches and candidate removal; aggregate `ready` |
| `apk-unpinned` | Compatible vendor APK fix handled by the existing upgrade recipe, with no source edits | Vendor availability and ordinary rebuilt images prove targeted removal; aggregate `release-needed` |
| `replay-bicep-update` | Hash-pinned historical cryptography findings and a reviewed test manifest at `10.0.10` | Generate the NuGet update to `10.0.13`, reproduce baseline matches and remove them from all three Bicep candidates |
| `replay-apk-pinned` | Hash-pinned historical Graphviz glibc finding, current vendor metadata and a reviewed test recipe at `2.44-r14` | Generate the compatible pinned APK update, prove signed vendor installation, reproduce the baseline match and remove it from the candidate |
| `historical-rebuild` | Pinned historical Bicep/.NET `source-pin-sufficient` findings, plus separate authenticated current delivery authority | Fresh ordinary builds and runtime/inventory checks for all three Bicep profiles; targeted findings absent; `release-needed`; evidence explicitly labelled historical replay |

Acquisition, planning, source checks, ordinary image builds, vendor checks and final qualification reuse the production implementations. Except for the explicit `historical-rebuild`, `replay-bicep-update` and `replay-apk-pinned` cases, the selected case must exist in current authenticated monitoring. Missing cases, deferred acquisition, stale current inputs and unresolved targeted findings fail the rehearsal; they cannot produce a successful empty qualification. All affected profiles in the acquired plan are checked, including unrelated planned updates in an update case. Rebuild-only cases refuse plans containing source edits. Raw residual findings, including ignored matches, remain in the scan artifacts.

There is no automatic fallback from a missing current case. Select `historical-rebuild` explicitly to exercise the App lifecycle when current published images no longer contain the old Bicep findings. Select `replay-bicep-update` or `replay-apk-pinned` explicitly for historical findings with reviewed vulnerable fixture inputs and real fixture dependency updates. Current `bicep-update` and `apk-pinned` cases still require compatible current findings. Hosted qualification of positive updates remains separate acceptance work; `historical-rebuild` proposes no dependency update.

## Run qualification and optional delivery

Leave `exercise_delivery=false` to perform read-only qualification. To exercise the App lifecycle, explicitly select `exercise_delivery=true` on the manual dispatch. The workflow uses the existing remediation App client ID/private key and Docker Sandboxes credentials described in the [platform contract](container-image-releases.md#bicep-and-os-package-remediation). It mints the App token only after all scan jobs, the source gate, aggregation and retention of qualification evidence succeed.

With delivery selected for `bicep-update` or `apk-pinned`, the App delivers the actual qualified package changes on `bot/platform-remediation-update-rehearsal-<run-id>`. It recomputes the bounded proposal from authenticated current evidence and requires the exact file hashes recorded by qualification. Empty proposals, rebuild-only results and historical evidence cannot enter this path. Existing source PRs, including Dependabot and the production remediation PR, prevent delivery when they touch the proposed files; the check repeats before branch and PR writes and excludes only this rehearsal's own branch.

The `replay-bicep-update` and `replay-apk-pinned` cases use the same update branch prefix but deliver only the qualified fixture dependency files described below. Their historical findings drive planning; independent current evidence authorizes delivery. They cannot deliver production package changes. Competing-PR checks apply to the fixture destinations.

The `current-rebuild`, `apk-unpinned` and `historical-rebuild` cases change only the tracked [test receipt](../../tests/fixtures/image_dependencies/platform-rehearsal-receipt.json) on `bot/platform-remediation-rehearsal-<run-id>`. The receipt binds the qualified result hash and retained artifact URL. All delivery cases leave the production remediation branch untouched and create a draft marked **do not merge**. Update drafts use `build: rehearse qualified Bicep and OS dependency updates`; receipt drafts use `test: retain platform remediation rehearsal evidence`. Keep the draft available for inspection; close it when its evidence has been reviewed. Human edits, a human-closed PR, an unexpected head or conversion out of draft prevent automated refresh.

For a new run, the harness deliberately stops the first PR-creation request after the signed branch write. It verifies the hosted orphan's App identity, signature, parents, tree and file hashes, records the signed commit, then exercises two read-only refusal probes against unsigned and altered copies of that commit response. These probes do not modify hosted ownership records. Recovery uses the shared publisher with current-evidence checks before writes. It creates one draft PR and repeats delivery, requiring the same PR URL and unchanged head. A later execution against an existing draft records `refresh-passed`; it does not claim another interruption/recovery exercise.

Production source, scoped release/assessment and latest-monitor freshness checks remain active throughout. Unrelated publication can proceed; a change that invalidates the acquired evidence causes refusal. Each run has an isolated branch and concurrency group. No catalogue writer lock is held for the duration of the builds, and this workflow neither publishes images nor changes `PLATFORM_IMAGE_REMEDIATION_ENABLED`.

### Controlled positive replay

The two `replay-*` cases use native package inputs retained under `tests/fixtures/image_dependencies/platform-positive/`. The request binds their hashes, and the committed case manifest pins every consumed historical monitor member. Historical findings and current write authority are acquired independently; the production entry point refuses these rehearsal receipts. The Bicep build fixture keeps NuGet vulnerability diagnostics as warnings so the intentional vulnerable baseline can compile. The production builder and publication policy remain unchanged; fresh baseline/candidate Grype reports, exact package inventories and runtime checks are still required.

Each worker overlays the selected fixtures only for its operation and restores the original production bytes on success or failure. The `checks` command runs the source gate, Markdown checks and trackers inside the candidate overlay. A positive replay must generate a nonempty bounded proposal. Its App draft changes only the corresponding fixture package file using the exact candidate bytes; the supporting Bicep Dockerfile is never a delivery target. Delivery retains both native build-input hashes and fixture destination hashes, and uses the same signed interruption recovery, ownership refusals and unchanged-repeat checks as current proposals.

These results use `evidenceMode: controlled-positive-replay` and `productionRecovery: false`. They demonstrate the selected planner, build and fixture-diff delivery paths; they do not demonstrate a live production dependency proposal, current published-image recovery or normal automatic operation. Inspect normal CI at the generated draft's exact head separately. Keep the draft unmerged so its vulnerable baseline remains an explicit test input, and record the evidence and remaining operational acceptance on #2517.

## Inspect and retry

Current cases and `replay-apk-pinned` retain vendor security feeds alongside the plan. When an exact vendor fix resolves a stale NVD match, `caseMatches` counts the remaining unresolved findings and `rawCaseMatches` preserves the original counts. The platform aggregate records `vendorResolvedFindings`; raw scanner reports and assessments still show the match. `historical-rebuild` retains its original evidence rules; `replay-apk-pinned` revalidates current vendor feeds independently of its pinned historical monitor bytes.

Artifacts are retained for 30 days and include the workflow attempt in their names:

- `platform-rehearsal-plan-<attempt>`: request, authenticated acquisition receipt, evidence and deterministic plan, or acquisition failure. Historical runs also retain the independent current acquisition under `current/`.
- `platform-rehearsal-<variant>-<profile>-<attempt>`: baseline/candidate build, vendor, runtime, inventory and scan evidence.
- `platform-rehearsal-qualification-<run-id>-<attempt>`: acquired input and all image results, plus `rehearsal-qualified.json` on success. This artifact is uploaded before App token creation.
- `platform-rehearsal-delivery-<run-id>-<attempt>`: delivery progress and any failure record. `payload` distinguishes `dependency-diff` from `receipt`, and `files` binds the delivered bytes. Successful `delivery-passed` includes the interruption's signed commit, identity, ownership, injected-read refusals, delivered PR/head and unchanged repeat. `refresh-passed` covers only an existing draft's refresh.

Inspect the records, not just the workflow conclusion. `rehearsal-qualified.json` states `productionRecovery: false`; delivery evidence states `ci: not-verified`. After creation, inspect the draft's normal PR workflows at its exact head and retain their URLs/results separately, including any approval hold or failure. Receipt delivery cannot qualify a real package-update diff. An update draft needs its own successful hosted delivery and normal PR CI before that acceptance criterion is met; availability of this path is not hosted qualification.

Use **Re-run all jobs** to retry the same run. Downloaded receipts and artifacts are attempt-bound, so rerunning only failed jobs cannot reuse the previous attempt's acquisition. Fresh acquisition must still match the dispatch source; if `main` advanced, start a new manual run. A retry on the same run reuses its isolated branch and verifies signed ownership before recovery. Preserve failed attempt evidence when comparing a recovery. Unclaimed unsigned branches, key changes and human edits require investigation; the workflow never force-updates them.

Record hosted results separately from the dated [Bicep rebuild evidence](platform-remediation-qualification-2026-11-09.md). Automatic enablement, image publication and issue closure remain separate maintainer actions.
