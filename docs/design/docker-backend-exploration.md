# A plain-Docker backend: what it would buy, and what it honestly is

> **Status: EXPLORATION — analysis only, nothing here is shipped.** No package, module, class or test named in this document exists, and nothing here has been prototyped. This is the analysis half of a pair: the normative design that follows from it is [`docker-backend-proposal.md`](docker-backend-proposal.md). The vocabulary it argues in — the isolation ladder, the capability set, the egress declaration — ships today and is described in [`sandbox-architecture.md`](sandbox-architecture.md), with its proposed evolution in [`two-axis-sandbox-policy.md`](two-axis-sandbox-policy.md) and the out-door specified in [`files-out.md`](files-out.md).

The question this document answers is narrow: should the `maf-sandbox` family grow a backend that runs sandboxes as **plain Docker containers on the developer's own machine**, and if so, what exactly would such a backend be entitled to claim? It is deliberately *not* about Docker's own "Docker Sandboxes" micro-VM product, which is a different thing with a different isolation story and gets its own section below. We reach a positive answer, with one important honesty constraint carried throughout: a plain container is a `container`-rung boundary, it will never be anything else, and the value of the backend depends on us saying so plainly rather than on rounding it up.

## Why — the two-backend gap

Two backends ship today, and between them they leave most developers with nothing.

- **`maf-sandbox-acas`** (`AcasSandboxBackend`, `packages/maf-sandbox-acas/src/maf_sandbox_acas/_backend.py`) declares `Isolation.MICROVM` and `Egress.ALLOWLIST`. It is the reference conformant backend and it meets the router's default floor with nothing configured — but `AcasSandboxConfig` requires an Azure Container Apps Sandboxes endpoint, and every sandbox it creates is billable compute in someone's subscription. It is not a thing you reach for to run the test suite on a laptop.
- **`maf-sandbox-wslc`** (`WslcSandboxBackend`, `packages/maf-sandbox-wslc/src/maf_sandbox_wslc/_backend.py`) declares `Isolation.CONTAINER` and is exactly the local-machine answer — no subscription, no daemon, no login, sub-second creates. Its requirement, stated in `packages/maf-sandbox-wslc/README.md` under "Requirements", is **Windows with WSL 2.9.3 or later**: `wslc` is WSL's own container CLI, every call spawns `wslc.exe`, and the host's event loop must be one that can start subprocesses (asyncio's Proactor loop on Windows).

So the set of developers with a working local sandbox backend is "Windows users who have WSL". A developer on **macOS** has nothing. A developer on **Linux** — including every Linux CI machine and every Linux container in which someone runs an agent — has nothing. A **Windows user without WSL** has nothing. That is not a marginal population; it is most of the people who would evaluate this family at all, and for all of them the only way to exercise a real sandbox today is to provision Azure.

The second half of the gap is ours rather than theirs: **no backend can run end to end on GitHub Actions hosted runners.**

- `.github/workflows/tests.yml` — the whole gate on every push and pull request — runs on `ubuntu-latest`.
- The one live-backend test module in the repository, `packages/maf-sandbox-wslc/tests/test_wslc_e2e.py`, carries a `pytestmark` that skips unless `shutil.which("wslc")` finds the binary *and* `MAF_SANDBOX_WSLC_E2E_IMAGE` names an image. On Ubuntu neither holds, so the module skips in full, silently and correctly.
- `.github/workflows/verify-live.yml` does run samples against a real ACA sandbox, but it is a separate workflow: OIDC-federated into Azure, pinned to a `live-verify` environment, serialised by `concurrency: verify-live`, and deliberately never triggered by a pull request because each run creates billable compute.

The consequence is that the family's central claim — a *kind* written against the protocol runs unchanged on any backend — is proved on every PR against fakes (`InProcessSandboxBackend` in `maf_sandbox.testing`, which is `Isolation.PROCESS` and runs nothing in a boundary at all), and proved against a real container only on a maintainer's Windows machine, by hand. Every command line the wslc backend emits is pinned by offline tests; whether a real engine agrees with those beliefs is checked out of band.

Worth noting: the repository has been writing cheques against a Docker backend for a long time. The protocol module's own docstring (`packages/maf-sandbox/src/maf_sandbox/_protocol.py`) says "a backend (ACA Sandboxes today; local Docker or an in-process fake later) decides what actually boots"; `SandboxSpec.image`'s docstring says "a Docker backend would hand it to `docker run`"; `CONTRIBUTING.md` describes the portability guarantee as "the same tool run on Azure, on Docker, or on the in-process fake". The forward references are already in the source. Nothing implements them.

## What "Docker" reliably means

"Requires Docker" is a weaker and more portable statement than it sounds, and getting precise about it is what makes the rest of the analysis possible. What a backend would actually depend on is **a `docker`-compatible command-line client talking to a Docker-API-compatible socket** — not Docker Inc.'s daemon specifically, and not any particular installation shape.

That contract is honoured today by Docker Desktop on all three platforms and with either of its Windows backends, by native Docker Engine (rootful and rootless), by [Colima](https://betterstack.com/community/comparisons/docker-desktop-alternative/) and [OrbStack](https://betterstack.com/community/comparisons/docker-desktop-alternative/) and [Rancher Desktop](https://dev.to/pickuma/docker-desktop-alternatives-orbstack-vs-colima-vs-rancher-desktop-2af1) on macOS, and by [Podman's docker-compatible socket](https://oneuptime.com/blog/post/2026-03-18-configure-docker-socket-compatibility-podman/view), which is [rootless by default](https://codersera.com/blog/podman-vs-docker-2026/) and is now the [default container engine on RHEL 10, Fedora and AlmaLinux](https://www.alekseialeinikov.com/en/blog/topics/devops/podman-2026-rootless-daemonless-containers-without-docker). Targeting the contract rather than the binary is not an abstraction we would be inventing; it is the state of the ecosystem.

**What the contract does imply**, uniformly enough to design against: container lifecycle (`create`/`run`/`start`/`stop`/`rm`), `exec` with a working directory and an argv, `cp` streaming a tar over stdin or stdout, labels at create and label filters on listing, and the basic network drivers — [`none`](https://docs.docker.com/engine/network/drivers/none/) and [`bridge`](https://docs.docker.com/engine/network/drivers/bridge/) and user-defined networks. It also implies that the kernel-enforced hardening flags behave the same everywhere they are accepted: capability drops, `no-new-privileges`, the [default seccomp profile](https://docs.docker.com/engine/security/seccomp/), read-only root filesystems, `--user`, and the cgroup resource limits are enforced by whatever kernel is running the container, which is the daemon's kernel whether that daemon sits on bare metal or inside a virtual machine.

**What the contract does not imply**, and where a design that assumed uniformity would break:

- **Host-level network and firewall behaviour is not uniform.** Some of these daemons run inside a VM (Docker Desktop on every platform, Colima, OrbStack, Rancher Desktop, `podman machine`) and some do not. Anything expressed in host firewall rules has a different meaning, or no meaning, depending on which. This is the single most important non-implication and the egress section below is built around it.
- **Per-tool API and CLI parity is claimed, not verified.** Each of these projects advertises Docker compatibility; we have not measured how far it extends for the specific verbs and output formats a backend would depend on. That is a smoke-test matrix to build, not a property to assume — it appears again under Risks.
- **Daemon-level configuration differs by install.** Rootless mode and user-namespace remapping are properties of how the engine was set up, are [alternative models rather than complementary ones](https://oneuptime.com/blog/post/2026-02-08-how-to-use-docker-with-user-namespace-remapping/view), and a backend cannot detect or promise either.
- **Listing output formats drift.** Field names and shapes emitted by `--format` have varied across engine versions, and Podman's docker-compat listing is not byte-identical to Docker's. Parsing has to be defensive.

One field-tested piece of prior art on locating the socket at all: **testcontainers is environment-variable-first**. It honours `DOCKER_HOST`, falls back to the current Docker context from `~/.docker/config.json`, and offers an explicit socket override, with [Colima](https://golang.testcontainers.org/system_requirements/using_colima/) and [Podman](https://golang.testcontainers.org/system_requirements/using_podman/) supported by pointing `DOCKER_HOST` at their sockets. The relevant observation for us is that a backend driving the real `docker` CLI as a subprocess inherits every one of those mechanisms for free, because the CLI already implements them; a backend speaking the HTTP API itself has to reimplement the lookup and keep it current.

## Host matrix

| Host | What provides the socket | Honest caveat |
|---|---|---|
| macOS (Apple Silicon or Intel) | Docker Desktop, OrbStack, Colima, Rancher Desktop, `podman machine` | Every option is VM-backed; containers share that VM's kernel. Parity between them is claimed, not measured. |
| Linux | Docker Engine (rootful), Docker Engine (rootless), Podman's docker-compatible socket | The only shape where the daemon's kernel *is* the host kernel. Also the only shape where `--runtime=runsc` or Kata are even available. |
| Windows with WSL 2 | Docker Desktop, WSL 2 backend | The default and recommended configuration; containers run in the WSL 2 utility VM. |
| Windows without WSL, Pro or Enterprise | Docker Desktop, Hyper-V backend | Supported rather than deprecated: Docker's install page lists Hyper-V among its Windows backends and names [WSL 2 "the default"](https://docs.docker.com/desktop/setup/install/windows-install/), without calling Hyper-V legacy or announcing a removal. Requires an all-users install and the Hyper-V and Containers Windows features, which are Pro/Enterprise only. This is the honest no-WSL path: second-class, not disappearing. |
| Windows Home without WSL | *nothing* | Home cannot enable Hyper-V, so it is forced onto WSL 2; "no WSL and no Hyper-V" is not a configuration a plain-Docker backend can serve. |
| Windows containers mode | out of scope | The target is Linux containers throughout. |

Two things follow. First, a plain-Docker backend serves macOS and Linux — the two populations with nothing today — completely, and Windows-with-WSL alongside them; Windows-*without*-WSL is deliberately deferred: the Hyper-V route is documented by Docker but is not its default, nobody in this project's loop runs it, and claiming a host nobody verifies would be the kind of rounding-up this document refuses elsewhere. Second, the deferred user is precisely the one Docker's own micro-VM product can serve: Docker Sandboxes uses the Windows Hypervisor Platform rather than WSL. That is an argument for a second, separate backend later, not for stretching this one.

## Driving Docker from async Python

Everything in this family is `async`, and every backend method a workload reaches is a coroutine. That constrains the driver choice more than it first appears.

| Option | Async | New runtime dependency | Assessment |
|---|---|---|---|
| `docker` (docker-py) 7.2.0, [PyPI](https://pypi.org/project/docker/) | No — `requests`-based, sync | `docker` (and its transitive HTTP stack) | Actively maintained and the most-used option, but every call would need `asyncio.to_thread` in a library whose whole surface is async. Its `exec` support has [no timeout](https://github.com/docker/docker-py/issues/2651) (an open feature request), with known [exit-code](https://github.com/docker/docker-py/issues/2450) and [stdout/stderr separation](https://github.com/docker/docker-py/issues/704) problems, and `put_archive` has long-standing failures on [larger payloads](https://github.com/docker/docker-py/issues/1808) — the two operations a sandbox backend does most. **Rejected.** |
| `aiodocker` 0.27.0, [releases](https://github.com/aio-libs/aiodocker/releases) | Yes, natively | `aiodocker` **and `aiohttp`** | Genuinely async and the closest fit on paper. It pulls `aiohttp` into a package whose only dependency today is `maf-sandbox` itself, and its release cadence is low. It also speaks the API directly, so socket discovery, context handling and version negotiation become ours. **Rejected on dependency weight.** |
| `python-on-whales`, [PyPI](https://pypi.org/project/python-on-whales/) | No | `python-on-whales` | Sync, so the same thread-offload problem. But it is worth citing rather than dismissing: it is explicitly *not* a reimplementation of the API — it shells out to the real `docker` binary, and its authors argue in a [Docker guest post](https://www.docker.com/blog/guest-post-calling-the-docker-cli-from-python-with-python-on-whales/) that doing so is what keeps it feature-complete and compatible. That is the philosophy we would be adopting; we would simply not need the wrapper. **Rejected as redundant.** |
| The `docker` CLI over `asyncio.create_subprocess_exec` (standard library) | Yes, natively | **none** | Zero new runtime dependencies. Inherits the CLI's own compatibility across Desktop, Colima, OrbStack, Rancher Desktop, rootless engines and Podman, including `DOCKER_HOST` and context resolution. Argv lists mean nothing is ever handed to a shell. Machine-readable output comes from `--format` and `inspect`. **Preferred.** |

The subprocess route is also the one this repository already knows how to test. `WslcSandboxBackend` funnels every provider interaction through a single private coroutine, `_wslc()`, which builds an `asyncio.create_subprocess_exec` call, bounds it with `asyncio.wait_for`, and kills and reaps the child on any abnormal end — and the offline test suite replaces exactly that one seam with a fake. A Docker backend with a `_docker()` seam of the same shape gets the same testability for free: every command line it emits is assertable without an engine present, and a configurable `docker_path` (defaulting to `"docker"`, pointed at `podman` when that is what is installed) is the same knob as `WslcSandboxConfig.wslc_path`. The seam's third behaviour transfers too, since it is a property of spawning subprocesses from Windows rather than of `wslc`: a selector event loop raises a bare `NotImplementedError`, so the seam catches it and says the Proactor loop is what the backend needs — which a Docker backend driven from a Windows host wants for exactly the same reason.

The dependency argument is not aesthetic. `maf-sandbox-wslc` has one runtime dependency, `maf-sandbox`, and the repository enforces the honesty of that declaration with a per-package test that walks every top-level import and refuses anything outside the standard library, the declared dependencies and the package itself. Keeping a Docker backend at zero new dependencies keeps that test meaningful and keeps `pip install` cheap for people who wanted a container, not an HTTP stack.

## Egress, honestly

The router will not attach a workload's tool to a backend that cannot confine egress: `SandboxRouter._refuse_unless_backend_can_serve` (`packages/maf-sandbox/src/maf_sandbox/_router.py`) reads `backend.egress` through a `getattr` defaulting to `Egress.UNRESTRICTED` and raises `SandboxEgressNotEnforced` unless it is `ALLOWLIST` or `CLOSED`. So the egress question is not a feature question; it decides whether the backend is usable at all.

There are exactly two honest ways to confine egress that hold across every host in the matrix above.

**Closed.** `docker run --network none` puts the container in a network namespace with nothing but loopback. It is enforced inside the container's own namespace by the kernel running it, which means it behaves identically on Docker Desktop, Colima, OrbStack, native Engine, rootless Engine and Podman — there is no host configuration that could weaken it and no client cooperation involved. See the [`none` driver documentation](https://docs.docker.com/engine/network/drivers/none/). This maps to `Egress.CLOSED`, and it is what a spec with an empty `egress_allow` deserves.

**Allowlist, by topology.** The workload container joins an internal network only (`docker network create --internal`), and a second container — a filtering CONNECT proxy — is dual-homed onto both that internal network and a bridged one. The workload gets `HTTP_PROXY` and `HTTPS_PROXY` pointing at the proxy; the proxy opens a tunnel only to the `host:port` pairs the spec allowed. This is precisely the topology `WslcSandboxBackend._ensure_egress`, `_ensure_network` and `_ensure_proxy` already build, and the proxy itself already exists in this repository as source rather than as a published image: `packages/maf-sandbox-wslc/src/maf_sandbox_wslc/_proxy/proxy.py` is a stdlib-only `ProxyServer` that never decrypts TLS, resolves the target hostname on the egress side rather than inside the sandbox, and — via `_peer_is_global` — refuses to complete a tunnel to an allowlisted *name* that resolves to a private or link-local address, which is what keeps a cloud metadata endpoint out of reach. Its `Dockerfile` pins `mcr.microsoft.com/azurelinux/base/core` by digest, because the image is a security boundary. The same pattern is used outside this repository for the same purpose, for instance by [INNOQ](https://www.innoq.com/en/blog/2026/03/dev-sandbox-network/) and in [published recipes for network-isolating coding agents](https://shaharia.com/blog/run-claude-code-docker-network-isolation/).

Following wslc, the declaration would be **config-derived rather than per-spec**: `Egress.ALLOWLIST` if and only if a proxy image is configured, `Egress.CLOSED` otherwise. `WslcSandboxBackend.egress` carries the reason in a comment — it is a statement about what the backend *can* enforce, not about what any one sandbox got — and `acquire` still closes a spec that allows nothing outright, because `--network none` denies everything for free without burning a network and a proxy on allowing the same nothing.

**The honesty limit, stated plainly.** `HTTP_PROXY` and `HTTPS_PROXY` are **advisory**. They are conventions that well-behaved clients read; a binary that ignores them, or model-written code that opens a socket directly, is not constrained by them in the slightest. What actually enforces the allowlist is the **topology**: the workload sits on an internal network with no route off it, so the proxy is not the polite path out, it is the only path out. The environment variables exist so that ordinary tools find the proxy without configuration, not so that they are prevented from leaving. Any documentation of this backend that describes the proxy variables as the enforcement mechanism would be describing a security property the design does not have.

**A second limit, identified rather than measured.** On a user-defined network the engine puts an embedded DNS resolver at `127.0.0.11` in the container, and Docker's [networking overview](https://docs.docker.com/engine/network/) states that it "forwards external DNS lookups to the DNS servers configured on the host" — a forward the daemon performs, outside the container's own namespace. Whether it still does so on a network created `--internal` is not something Docker's documentation states either way, and if it does, name resolution is a low-bandwidth channel off a network that otherwise has no route off it. So it is named here as engine behaviour to verify against a real engine, not as a hole we have measured and not as one we have closed. The obvious lever if it turns out to be open is pointing `--dns` at the proxy or at a blackhole address, and either way a negative control that only tries TCP would pass on a topology that leaks — a DNS case belongs in it.

**And the non-portable alternative we are explicitly not taking.** Allowlisting egress with host-level `iptables` rules is not part of the portable contract and cannot be made so. Two independent reasons: under rootless Docker the rules land in the wrong network namespace ([moby issue](https://github.com/moby/moby/issues/43781), [forum thread](https://forums.docker.com/t/using-iptables-to-block-internet-access-from-containers-doesnt-work-running-docker-as-rootless/150761)), and on macOS and Windows the daemon is inside a VM whose namespaces have no relationship to anything the host firewall can express. The `DOCKER-USER` chain is a Linux-daemon-specific facility ([firewall guide](https://oneuptime.com/blog/post/2026-02-08-how-to-set-up-docker-containers-with-custom-firewall-rules/view)). A Linux-only enforcement path that silently does nothing on two of three platforms is worse than not having one, because the declaration would be identical in both cases.

Two related things a Docker backend must **not** invent while it is in this neighbourhood. It must not declare `Capability.NETWORK`: no shipped backend declares it, including in allowlist mode, and the capability's meaning is still a mapping exercise rather than a checked contract. And it must not introduce a general environment-variable channel: `Sandbox.exec` in `packages/maf-sandbox/src/maf_sandbox/_protocol.py` takes `command`, `working_directory` and `timeout` and nothing else, a per-exec `env` channel is described in `two-axis-sandbox-policy.md` as *a protocol addition* that does not exist, and the only environment variables a backend has business setting are the two proxy ones that make its own topology usable.

## Where plain Docker sits on the ladder

A plain-Docker backend declares **`Isolation.CONTAINER`**, unconditionally, with no configuration that raises it. The rung's own definition in `packages/maf-sandbox/src/maf_sandbox/_protocol.py` is "Shared-kernel namespaces and cgroups: the host kernel is in the attack surface" — which is a description of what `docker run` produces, without qualification.

The interesting part is the argument against rounding up, because there is a tempting move available. On macOS and on Windows the containers do not run on the host kernel at all; they run inside a virtual machine. Does the hypervisor between the container and the user's laptop lift the backend toward `microvm`?

No, and the standard says why. `two-axis-sandbox-policy.md` defines `microvm` as a four-part conformance bar, and a backend may claim it only if **all four** hold:

1. **A hardware virtualization boundary** — the guest executes behind a hypervisor, not behind shared-kernel namespaces. Plain Docker **fails this categorically**. One VM hosts *every* container on that machine, and they share its kernel with each other. The boundary between a sandbox and the user's host may be a hypervisor, but the boundary between a sandbox and the next sandbox — and between a sandbox and the daemon that controls all of them — is namespaces. The rung describes the boundary a workload actually sits behind, not the strongest boundary anywhere in the stack.
2. **No ambient identity reachable from inside** — achievable, and the design should meet it: `--network none` reaches nothing at all, and the allowlist proxy already blackholes private and link-local addresses.
3. **Confinable egress** — achievable, per the section above; a backend that could not confine egress would be capped below `microvm` outright anyway.
4. **An explicit guest-host surface** — achievable, and it is the reason to forgo bind mounts, host-path sharing and any form of `/var/run/docker.sock` passthrough. Files go in as a tar over `docker cp`, results come back as command output, and nothing else crosses.

Meeting three of four legs is not a claim to the rung; it is a design discipline worth keeping anyway, and worth being explicit that it is self-imposed. The router does not enforce legs 2 and 4 on a `container`-rung backend — nothing checks that a backend declaring `container` refrained from mounting the host filesystem. The conformance probe suite that would give the standard teeth is described in `two-axis-sandbox-policy.md` as **designed but parked**; today the standard is enforced by normative text and honest self-declaration, which is exactly why the self-declaration has to be honest.

There is also a precedent, and refusing to round up is what keeps it consistent. `wslc` containers run in the WSL 2 utility VM — one shared kernel behind a hypervisor, structurally the same shape as Docker Desktop's VM — and `WslcSandboxBackend.isolation` returns `Isolation.CONTAINER`. Classifying Docker Desktop's containers any higher would say that two identical architectures sit on different rungs because of who shipped the VM. (This is an argued classification: the repository states the wslc rung, and the general principle that a shared-kernel VM does not lift a container is our reading of the standard rather than a sentence already written down in it.)

**What about hardening the runtime?** On Linux, `docker run --runtime=runsc` swaps in gVisor's userspace kernel, which the ladder ranks at `hardened_container` — and per the standard that ceiling "is the standard working, not a gap". It is genuinely interesting future work, and it is genuinely not v0: gVisor is [Linux-only and needs KVM for its KVM platform](https://gvisor.dev/docs/user_guide/quick_start/docker/), so it cannot exist on macOS Docker Desktop at all, and [Kata](https://kata-containers.github.io/kata-containers/installation/) is likewise Linux-only. More importantly, a backend must not raise its declared rung off a configuration string it cannot verify. `isolation` is read by `SandboxRouter._resolve` at construction and is the basis of every posture claim a deployment makes; a backend that returned `HARDENED_CONTAINER` because someone typed `runsc` into a config field would be laundering an unchecked string into a security guarantee. If that rung is ever claimed it needs a verification story first.

**What this means for a host, concretely.** A `container`-rung backend sits below the router's default floor of `Isolation.MICROVM`, so constructing a router over it with nothing configured raises `SandboxBackendNotPermitted`. The host opts down explicitly, with the same single line `wslc` users already write and which `samples/04_wslc_codeact/agent.py` already contains:

```python
router = SandboxRouter([backend], min_isolation=Isolation.CONTAINER)
```

That is the entire mechanism, and it is worth being precise about what it is not. There is **one knob**, `min_isolation`; there is no development-versus-production profile system, no environment detection, and nothing that lowers the floor on a host's behalf. `packages/maf-sandbox/README.md` puts it flatly in "Upgrading from 0.4.x": there is no longer a value meaning "anything goes" — a host that wants the weakest rung names it.

Equally worth being precise about: **registering a Docker backend alongside an ACAS one does not give you per-workload routing.** `SandboxRouter._resolve` picks `self._backends[0]`, or the backend whose `name` matches `selected=`, and checks *only* the floor against that one choice; capabilities and egress are then checked against the already-chosen backend in `_refuse_unless_backend_can_serve`. The "first registered backend satisfying floor and capabilities and egress" selection described in `two-axis-sandbox-policy.md` is proposed, not implemented. A host that wants both backends today picks one with `selected=` and gets its purge fan-out across both — `dispose` and `dispose_scope` do ask every registered backend — but not per-spec selection.

Finally, the capability declaration: `frozenset({Capability.EXEC, Capability.FILES_IN, Capability.FILES_OUT})`. The first two match both shipped backends; the third is specified in [`files-out.md`](files-out.md) — which supersedes the `two-axis-sandbox-policy.md` sketch — and this backend is written into that specification twice over. First as the reason for its load-bearing split: `FILES_OUT` is *stat and read a path the spec declared* (`stat_file`/`read_file`, both served against an image with no shell — the engine stats a named path via `HEAD /containers/{id}/archive`, and the tar stream from `docker cp <name>:<path> -` carries size, type and link target in its first header block), while open-ended *enumeration* is a separate `FILES_LIST` capability precisely because Docker has no engine-level primitive for discovering what names exist — requiring enumeration would have made this backend either image-dependent or cap-hostile, so a kind that cannot name its outputs is refused here and served by ACAS, which is the capability match working. Second as the rollout's **acceptance gate**: "Docker, first", before ACAS, its e2e chosen to prove the protocol because it is the only suite a pull request can run. The declaration is therefore `FILES_OUT` from day one and `FILES_LIST` never — and the members it declares against are no longer only on paper: the protocol surface and the collection glue have since been implemented in `maf-sandbox`, so nothing about the declaration waits.

## What CI gains

This is the strategic reason to prefer a Docker backend over any other way of closing the host gap, and it should be argued as a **new capability** rather than presented as something the repository already does. It does not. There is no live-backend end-to-end test in CI today, on any backend, for the reasons set out at the top.

A Docker backend changes that, because `ubuntu-latest` already has an engine. The shape would be the one `test_wslc_e2e.py` established — a module gated on the binary being present and an image being named in the environment, skipping cleanly everywhere else — except that on this backend the gate would be *satisfied* on the repository's own runners, so `tests.yml` could set the environment variables and the module would run on every pull request. Deliberately lightweight, though: a tiny image and no model in the loop, so the pull-request gate keeps its quick turnaround — the full sample end-to-end, model included, belongs to the release-time verification workflow, not to PR CI.

What that would actually prove, none of which any offline test can:

- That a one-entry tar written to `docker cp - <name>:/`, with the entry name carrying the full path, really does create the intermediate directories — the trick `_WslcSandbox.write_file` depends on.
- That an argv passed to `docker exec -w <dir>` reaches the process without a shell, and that exit codes and the stdout/stderr split come back as the backend believes.
- That warm reuse, restart-after-stop and adopt-on-name-conflict behave against a real engine, which is where the acquire-race invariant in `SandboxBackend.acquire`'s docstring actually lives.
- That `--network none` denies what it claims to deny, and that the allowlist topology allows an allowed host and refuses a denied one — a positive *and* a negative control, which is the only way a network test is worth anything.
- That label filters return the containers a purge needs, which is the multi-replica leak defence.
- That a declared output stats and comes back byte-identical through the tar stream, that an over-cap output is refused before its content moves, and that a symlinked output is refused at stat and again on the tar entry's type bit — the round trip and negative controls [`files-out.md`](files-out.md) assigns to exactly this suite, whose rollout runs "Docker, first and as the acceptance gate" for the same reason this section argues: it is the only live suite a pull request can run.

Two operational details worth settling now rather than after the first red build. **Images should come from a registry that will not rate-limit a shared runner IP.** Docker's own usage documentation puts unauthenticated pulls at [100 per six hours per IPv4 address or IPv6 /64 subnet](https://docs.docker.com/docker-hub/usage/), and hosted runners share addresses, so a Hub-based e2e is a flaky test waiting to happen; `mcr.microsoft.com` is the registry this repository already pins its proxy base image against, and GHCR is the fallback — GitHub documents that [usage is free for public packages and that a workflow authenticates to the registry with `GITHUB_TOKEN`](https://docs.github.com/en/packages/learn-github-packages/introduction-to-github-packages), which is what makes it frictionless in Actions, though it publishes no pull-limit number for public images, so "no limit" is not a claim we can make on its behalf.

**And a Docker CodeAct sample would be the first whose live verification runs on this repository's own runners.** That, rather than "needs no cloud", is the property that distinguishes it: samples 02 and 04 need no cloud either — they need Windows and a WSL that ships `wslc`, which the Linux runners do not have. What a Docker equivalent of sample 04 adds is a sandbox needing no Azure subscription and no billable compute, on a runner that already has the engine: `samples/03_acas_codeact` and `samples/04_wslc_codeact` both run `mcr.microsoft.com/devcontainers/python:3.13-bookworm`, and `ubuntu-latest` can run it directly. It would still need a model endpoint and a key, and this repository holds no model secret today — the proposal's samples section is where that is worked through rather than here.

For a consumer, the same property is a two-line story: an agent using this family in its own GitHub Actions workflow gets a working sandbox on `ubuntu-latest` with no setup step, and gets nothing on `windows-latest` or `macos-latest` for the reasons in the runner matrix. That asymmetry should be documented rather than discovered.

One line on the cloud shape, for completeness: [e2b](https://e2b.dev/docs/) gives agents Firecracker micro-VMs behind an HTTP API. It is a hosted service rather than a local engine, so it belongs in the same conversation as ACA Sandboxes — a possible future backend at the `microvm` rung — and not in this one.

The lifecycle split between llm-sandbox and epicbox is the one design question prior art actually settles for us. Per-call containers are simpler and stricter; session containers are what an agent's fix-round loop needs, because a cold create every iteration turns a seconds-long loop into a minutes-long one. This family already made that choice — `acquire` is get-or-create with warm reuse — and llm-sandbox arriving at the same answer from the same workload shape is a useful confirmation.

## Docker Sandboxes, the product — and why not yet

Docker shipped its own agent-sandboxing product — announced with micro-VM isolation [at the end of January 2026](https://www.docker.com/blog/docker-sandboxes-a-new-approach-for-coding-agent-safety/), which is the date we can source rather than a general-availability milestone Docker states as such — and it is a genuinely different thing from what this document proposes. Each session gets a **dedicated micro-VM with its own private Docker daemon inside it** — "each sandbox gets its own Docker daemon, filesystem, and network", in Docker's words ([Docker Sandboxes](https://docs.docker.com/ai/sandboxes/)) — so nested `build`, `run` and `compose` work without ever mounting a socket. Docker wrote [a proprietary VMM from scratch rather than using Firecracker](https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/), specifically so it could run natively on all three desktop platforms, and its own [prerequisites and install commands](https://docs.docker.com/ai/sandboxes/get-started/) say what each needs: macOS Sonoma or later on Apple silicon (`brew trust docker/tap` then `brew install docker/tap/sbx`), Windows 11 on x86_64 with "Windows Hypervisor Platform enabled" (`winget install -h Docker.sbx`) — note that WSL 2 appears nowhere in that list — and Ubuntu 24.04 or later with KVM enabled and the user in the `kvm` group (`sudo apt-get install docker-sbx`). The same page states plainly that "Docker Desktop is not required to use `sbx`". It has its own `sbx` CLI, and "Sandbox Kits" are declarative YAML describing tools, environment, credentials, files, startup commands and **allowed network domains** ([product page](https://www.docker.com/products/docker-sandboxes/)).

Read against the micro-VM standard, that is a serious candidate for the `microvm` rung — which is exactly where `two-axis-sandbox-policy.md`'s design map already places "Docker Sandbox". Its platform matrix is still settling, though, and Docker's own [release notes](https://docs.docker.com/ai/sandboxes/release-notes/) are the evidence: the CLI is still on a `0.x` line, and a mid-2026 release shipped with no Linux/ARM64 builds at all "due to stability issues". So any platform claim about it should be re-verified against Docker's documentation at the time it is written rather than repeated from here.

It is out of scope for this exploration for three reasons, in order of importance. It is a **different isolation rung**, so folding it in as a configuration flag on a `container`-rung backend would mean one backend whose `isolation` property depends on how it was configured — the exact laundering the ladder exists to prevent. It has a **different CLI and a different lifecycle vocabulary**, so almost none of the command-line surface would be shared. And it is **new**, in a way a `container`-rung backend built on a fifteen-year-old command surface is not.

The right relationship between the two is therefore: a **second backend package**, at the `microvm` rung, behind the same `SandboxBackend` protocol — which is the whole point of having a protocol. A host would move from one to the other by constructing a different backend and deleting a `min_isolation` argument, and every kind would run unchanged. It is also, per the host matrix, the eventual answer for the one user a plain-Docker backend cannot serve: Windows without WSL, where Docker Sandboxes uses the Windows Hypervisor Platform directly.

None of that argues against a plain-Docker backend now. Plain Docker is already installed on the machines and runners in question, costs nothing, works identically on macOS and Linux today, and — being a `container`-rung backend — is honestly positioned as the developer-machine option rather than as a production posture.

## Risks and unknowns

**Per-tool API and CLI parity.** Docker Desktop, Colima, OrbStack, Rancher Desktop and Podman all advertise Docker compatibility, and the specific verbs a backend would depend on — `cp` from a tar on stdin, `--format` output shapes on `ps`, `network create --internal`, `network connect`, label filters, `--pids-limit` — have not been measured across all five by us. Compatibility claims are the right prior, not the right assumption. The available mitigations are a defensively-parsed listing and an honest support boundary — the proposal scopes official support to Docker itself and leaves the compatible engines best-effort — and the risk is not "it will not work" but "it will work on four of five, and we will find out from a user".

**Registry rate limits.** Docker Hub's documented unauthenticated ceiling of [100 pulls per six hours per IPv4 address or IPv6 /64 subnet](https://docs.docker.com/docker-hub/usage/) is a real CI hazard on shared runner addresses. Pointing at `mcr.microsoft.com` mitigates it, but we should be careful about how strongly we state the mitigation: MCR's own rate-limit policy is not documented in a form we could confirm, so "MCR has no limits" is an assumption, not a finding. GHCR is the fallback if MCR ever pushes back, and the same care applies to it — GitHub documents that public packages are free and that a workflow authenticates with `GITHUB_TOKEN`, which is the part that makes it painless in Actions, but it publishes no pull-limit figure for public images, so an unlimited-pulls claim would be ours rather than theirs.

**Exec-timeout ergonomics.** `_WslcSandbox.exec` discards the whole sandbox when a command times out, and its docstring explains why: the timeout bounds the host-side call, killing the client process does not reach the process it started inside the container, and there is no per-command handle to kill. Docker offers a backend nothing better here in any portable way, so a Docker backend would inherit the same behaviour — a timed-out command costs the sandbox, and the next `acquire` pays a fresh create. For a fix-round loop where one call hangs and the rest are fine, that is a real ergonomic cost. One could imagine wrapping each exec in an in-container supervisor that records a pid so a later exec could kill it, but that changes the exec contract, adds an in-guest component, and is not a v0 decision.

**Hyper-V backend drift.** The Windows-without-WSL path rests on the backend that is not the default. Docker's [Windows install page](https://docs.docker.com/desktop/setup/install/windows-install/) names WSL 2 "the default", and it does not call Hyper-V deprecated or announce a removal date — "supported, but not the path most users are on" is as far as the source goes, and stronger readings of it are ours rather than Docker's. The design consequence is modest and unchanged: nothing load-bearing should rest on that row, and it is the row most likely to move first if Docker's Windows story consolidates.

**The daemon that is not running.** The dominant local failure mode is not exotic — it is Docker Desktop installed but stopped, which turns every command a backend runs into a connection error rather than a sandbox. A backend whose entire surface is subprocesses has to name that condition instead of letting it surface as an unexplained transport failure, and the proposal specifies the actionable error for it: a `RuntimeError` naming the client path that was run and carrying the engine's own message, raised at acquire, since nothing probes at construction time.

**Daemon-configuration variance we cannot see or promise.** Rootless engines and user-namespace remapping change the security properties of a container materially, and are properties of the installation rather than of anything a backend passes on a command line. Docker Desktop's default user-namespace posture in current releases is something we did not confirm. The safe posture is to make no claim that depends on either, and to state the hardening we *do* apply as flags on the create command line, whose effect is verifiable.

**Listing-format drift.** The output of `docker ps --format` has varied across engine versions, and Podman's docker-compat output is not identical. This is a mundane, high-probability, low-severity risk, and the mitigation is the one the wslc backend already models: parse defensively, treat a failed listing as "found none" only where that is safe, and keep a fixture of real captured output in the test suite so a format change shows up as a failing test rather than as a purge that silently selects nothing.
