# Kinds

> What a *kind* is: a workload written against the sandbox protocol and nothing else, the pattern the first one set, and how a spec grows from what the kind declares. Sources of record: [`../research/sandbox-architecture.md`](../research/sandbox-architecture.md) and [`../research/files-out.md`](../research/files-out.md).

**These pages own the architecture-facing contract of each kind — the spec it declares and why, its security pattern, its portability story. Each package's own README owns install and usage, and is linked rather than duplicated.** Someone deciding whether a kind fits a deployment reads here; someone wiring it up reads there. Where the two would say the same thing, the package README is the one that gets to say it, because it ships with the code.

## A kind is a workload, never a vendor and never a backend

A kind is one thing: a tool factory that asks a `SandboxRouter` for a sandbox and gets back `write_file`, `exec` and the pull surface. It names no backend, imports no provider SDK, and contains no lifecycle code — acquiring, keying, disposing and confining egress are all [`../architecture.md`](../architecture.md)'s, and reclaiming a call's files is [`../tool-call.md`](../tool-call.md)'s, written once. What is left over is what is genuinely workload-specific: the command templates, the accepted inputs, the parsing of what comes back, and the hosts this particular work needs to reach.

That division is a portability claim, and it is test-enforced rather than asserted:

| Test | Where it lives | What it pins |
|---|---|---|
| `TestZeroDependencies` | `packages/maf-sandbox/tests/test_sandbox_router.py` | the protocol modules import nothing outside the standard library. Scoped to `_PROTOCOL_MODULES`, not the whole distribution, because the dist does declare `agent-framework-core` for `maf_sandbox.maf` — a scan that kept claiming "nothing here imports anything" would have had to be deleted rather than narrowed |
| `TestNoDirectAzureImport` | each kind's own suite | no `import azure` anywhere under the package. Strictly redundant with the row below, and kept anyway: its failure message names the property that actually broke — the workload reaching around `maf_sandbox` for a provider — where "undeclared dependency" would not |
| `TestOnlyDeclaredDependencies` | every package | every import is one the package's own `pyproject.toml` declares. This is the defect class that otherwise first reproduces on a clean install, where the workspace is no longer there to satisfy it |

The direction of the boundary matters as much as its existence: **kinds and backends never import each other**, in either direction. A kind that reached for a provider would stop being portable; core reaching for a kind would make the protocol a registry of workloads. Both talk only to the router in the middle.

The payoff is one sentence per kind: the same tool runs unchanged on ACA Sandboxes, a Docker container, a WSL container or an in-process fake ([`../backends/README.md`](../backends/README.md)) — and a backend that cannot serve it is refused at attach, not at first call.

## The pattern the first kind set

`bicep_validate` was written first, against real infrastructure code an agent wrote, and the shape it settled on is what every later kind follows.

- **Fixed command templates, with nothing but a validated path interpolated.** No agent-authored text reaches a command line. Where a kind can use an argv sequence it does, and the backend quotes it; where it genuinely needs a shell line — `|| true`, a redirection — the template is a module-level constant and the one `{path}` in it has already been through validation.
- **The caller's file listing is the injection pin, and now also the label channel.** Only a name present in `CallerContext.list_files` is ever substituted, so a name the model invented, or read out of a poisoned file, has nowhere to go. A failure to enumerate is a *refusal*, never an empty listing: empty would look like "the store has no files" and refuse every name individually with the wrong reason.
- **Sanitized error surfaces.** Provider and transport text can carry endpoint, subscription and tenant ids, and a tool result is persisted into a transcript. That detail goes to the log; the model gets a fixed sentence. What this stack authored itself is safe to surface verbatim, and is.
- **One egress mode, chosen inside the set the kind accepts.** A spec carries a single `Egress` mode — `CLOSED` by default, so a kind that says nothing about the network gets none — and `egress_allow` is the payload of an `ALLOWLIST` run rather than a field with a life of its own; naming hosts in any other mode is refused where it is written. Each kind guards the set of modes it will accept **at construction**, so the posture a deployment may choose is bounded by the kind rather than by the backend it happens to have wired. What the *kind itself* needs to function stays fixed in the package — bicep's four hosts are the kind's, not a deployment's — because a deployment able to widen that could undo the containment the design rests on; where a kind lets a deployment add hosts of its own (codeact does), they are added to the kind's half and never in place of it. The router then serves that exact mode on a backend that enforces it, or refuses at attach — never a more open substitute, which would silently widen what the workload reaches, and never a more isolated one, which would hand it a posture it was not built for. See [`../network.md`](../network.md).
- **T2, not T0 — and a degrade that says so.** The point of running the work is that a compiler, an interpreter or a test runner answers instead of the model checking its own output; a model that reads its own work and agrees with itself has added no information. Every degrade path therefore returns the run to T0 *visibly*: an unconfigured host attaches no tool at all (the agent keeps the ungrounded behaviour it already had, and is never shown a capability it lacks), while a host whose backend cannot honour the spec **raises** — nothing-configured is a choice, can't-confine is a misconfiguration, and quietly shipping the workload without its containment is the one outcome not on offer.

## The spec is where the posture questions are answered

Everything a host needs to decide about a kind is in its `SandboxSpec`, which is why each page below leads with one. `kind` names the workload and is half of a sandbox's identity; `egress` says which of three network postures it runs in and `egress_allow` names the hosts when that posture is `ALLOWLIST`; `requires` says what it cannot run without; `requires_os_family` says what shape of guest its commands are written for, and both shipped kinds leave it `None`, which asks nothing and is refused by nothing; `min_isolation` says whether it raises the host's floor, and most kinds should not ([`../policy-isolation.md`](../policy-isolation.md)); `declared_outputs`, `files_in` and `files_out` say what moves and how much.

**`requires` grows from what the kind declares, in both directions.** A spec that declares any output — of either disposition — is *refused* without `FILES_OUT`, because the capability match is the only thing standing between that spec and a backend with no pull surface, and it only ever runs on what `requires` names. A spec that declares no outputs should not require `FILES_OUT` at all: every capability a kind asks for is a backend it can no longer run on, and asking for one it does not use is portability given away for nothing. The vocabulary and the match are [`../capabilities.md`](../capabilities.md).

## Writing a kind that collects artifacts

The six rules, from [`../research/files-out.md`](../research/files-out.md) § *Writing a kind that collects artifacts*:

1. **Declare your outputs** — literal relative paths, each with a disposition, a media type, and `required` set honestly.
2. **Tell the model where to write.** The output path has to appear in the tool's description; a program that saves its PNG somewhere else produces nothing collectable and no error.
3. **Do not put bytes in the result.** Return the references `deliver` gave you.
4. **Require `FILES_LIST` only if you truly cannot name your outputs.** It is refused on Docker and wslc, so a kind that requires it without needing it has made itself ACAS-only. "The model decides at run time" is *not* that case — set `outputs_named_at_call_time` and pass the names to `collect_outputs(outputs=...)`.
5. **Grow `requires` from what you declare** — the rule above, applied.
6. **Do not combine a sink with an explicit `declarations=`.** It is refused, because the two disagree about what the tool's information flow is.

The same document carries a worked example — a `render_diagram` kind, the smallest workload that exercises every rule above — and its spec is the shortest statement of the whole pattern: `egress_allow=()` because rendering is computation, no `FILES_LIST` because the kind names its own output, `max_files=1` because one call renders one graph, and `required=False` because a renderer failing on malformed input is a diagnostic the model should act on rather than a transport error.

## Writing a kind that declares its information flow

What a kind may claim about the result it hands back, and why the claim is not about who wrote the bytes. [`../information-flow.md`](../information-flow.md) is the design and carries the reasoning; these are the rules it holds a kind writer to.

1. **Declare nothing until you can say what makes the claim true.** No declaration hands the question to the framework's input-label join, which is where a workload running model-authored code belongs. It is not a shortcut to *untrusted*: the join propagates whatever labels your arguments carry, so a trusted labelled argument yields a trusted result, and the fallback applies only where the join finds no labels. Neither shipped kind relies on that fallback: both declare `untrusted`. They *would* have landed on it, because every value they take is a plain unlabelled string — `execute_code` receives its program directly as `code: str`, not only file names — but that is a property of their signatures rather than a promise the rule makes you, which is why they say it instead. This is a supported answer and the common one, not an omission for a later commit to fill in — and it is what the library gives you for saying nothing: `source_integrity` defaults to `None` on both `sandbox_tool_declarations` and `sandboxed_tool`, so a `"trusted"` claim has to be written where a diff can see it.

   **But it is a delegation, not a fail-safe, and two routes take it to trusted.** If your visible arguments could carry trusted labels while an unestablished source still reaches your result out of band, tier 3 hands back a *trusted* result with no declaration written anywhere — laundering that source exactly as a false `trusted` would. And the fallback itself is the host's `default_integrity`, a constructor argument rather than a constant, so a host that raised it gets a trusted result out of your tool whatever your arguments look like: that route asks nothing of your signature and nothing in your package would notice. **Declare `untrusted` explicitly wherever an unestablished source may survive into your result.** It is a tier-2 declaration, so it overrides the join and the default alike, and it puts the claim where the framework reads it. Delegating is an answer only where the delegate cannot answer trusted.
2. **List your result's real sources before you declare `trusted`, and clear every one.** Not just the arguments: the file store you read, an allowlisted host your program may fetch from, a registry it may call back through. The framework's input-label join sees only the arguments, so it is a lower bound and never the answer — a trusted labelled argument settles one channel and says nothing about the others, and a source the join never observed is still a source. A **`trusted`** declaration is honest only where every surviving source is established **as trusted**, or where nothing of them survives into your result — as text, as a number, or as the presence of a line. Establishment alone is not enough: a registry fold can establish a source as *untrusted*, and that counts against you exactly as an unestablished one does. Where a source does not clear that bar, you do not declare `trusted` — and rule 1 decides what you do instead: an explicit `untrusted` where the join might still answer trusted, or nothing where it cannot.

   **The library now holds you to this one, from what your spec says.** `sandbox_tool_declarations` refuses an explicit `source_integrity="trusted"` over a spec that opens a channel it cannot establish *as trusted* — `Capability.FILES_IN` in `requires`, an `egress_allow` naming hosts or an `unrestricted` run, `Capability.HOST_TOOLS` in `requires` — and names each one by the field and value that opened it, so a `requires` assembled out of shared sub-specs still points you at the composition site. Host tools are the one channel a spec can also *establish*: a sealed `HostToolAggregate` on `SandboxSpec.host_tools` folding to `trusted`, or to `None` where no registered tool brings anything external in, settles that channel and no other. A fold of `untrusted` has settled the channel and is refused all the same — known-untrusted and unknown fail together, because neither licenses a `trusted` claim. Requiring the capability while carrying no surface settles nothing, and is refused too. **Where a channel is open and nothing from it survives into your result** — you write host-authored fixtures in and answer with a fixed sentence — say so with `nothing_survives_from=(SourceChannel.FILE_STORE,)`. That is a claim about your body's result, which no spec holds and nothing here can check; it is yours the way `also_carries_out` is, and it exists so the claim lives in an argument a test can pin rather than in a comment. Naming a channel your spec does not open is refused, so a deployment that opens one later asks you again instead of finding the question pre-answered. An explicit `declarations=` mapping is read for that one key too: it is still written verbatim, but a check the derivation alone held would be walked past by exactly the hand-built mapping this rule exists for.
3. **Authorship licenses nothing.** That your package formatted the string, or that a first-party compiler emitted it, says nothing about what it was formatted from. A compiler is deterministic about a template the model wrote, and its diagnostics quote that template's identifiers back verbatim.
4. **Know that declaring overrides rather than floors.** `source_integrity` tells the middleware to disregard the input side of that call, so a declaration is not a hint reconciled with what the framework otherwise knows — it is an instruction to stop knowing it.
5. **Split a mixed result instead of choosing one label for it, and label each item on its own derivation.** An item is trusted only where its value **and its presence** are both independent of every source not established **as trusted** — the same test as rule 2, applied per item, and a source established as untrusted counts against the item just as an unestablished one does. Authoring it does not qualify it, and neither does no guest having run: a count, an exit status, a size or a line emitted only on failure all carry something unestablished, and putting one in an item of its own changes the granularity rather than the derivation — split that way, it launders the influence instead of containing it. What qualifies is standing guidance you emit on **every return path** — refusals and error surfaces included, true on all of them — saying nothing about this call. `execute_code` renders one under `withhold_guest_output=True` and nothing else does; `bicep_validate` renders none, which is why it splits nothing.

   **And an item's label is both axes, not just integrity.** `ContentLabel` defaults confidentiality to `public`, so an item you labelled for derivation alone arrives *public* — measured. You cannot invent a confidentiality value: they are the host's vocabulary, carried verbatim and never ordered here. **So label as little as you can.** An item you leave unlabelled takes the call's own label, confidentiality included, and the combined result is the most restrictive across every item — which is what keeps the host's classification when one item is labelled and the rest are not. Build the labelled one with `labelled_result_item`, return the rest as plain `Content`, and never label every item: `sandboxed_tool` refuses that result, because nothing in it is left to carry the call's. `labelled_result_item` refuses `untrusted` for the same reason from the other side — the untrusted item is the one holding what the call produced, and `public` on it is a claim you cannot make. Where the join might answer trusted, rule 1's explicit `untrusted` belongs to the whole tool, which leaves the confidentiality resolution alone.

   **And this rule is executed rather than read.** `sandboxed_tool(..., standing_guidance=(…))` takes the sentences at attach, where a reviewer sees them and a test can pin them, and the wrapper holds every call's result to that **sequence**: the labelled items must be the last items of the result, in the committed order, one carrying each committed sentence. Text, count, order and placement are fixed together, because a set would leave the last three free — one sentence emitted twice, two swapped, or guidance moved ahead of the derived half are each a bit a body can vary on whatever it likes. Once anything is committed a bare `str` answer is refused too — a string on the refusal path beside a split result on the success path is the presence leak this rule names, spelled as a result shape. A kind that commits nothing is unchanged, so the check costs a tool that does not split anything at all.

   **One substitution, and only one.** A committed sentence may carry `{call_id}`, which the wrapper renders from the call it is running inside. That exists because a sentence naming this call's landing folder does qualify — a host-minted `uuid4` owes nothing to the arguments or to what the program did — and yet is not a constant, so equality alone could not express it. Every other value a body could interpolate is either derived from the call or is the guest's, which is why the vocabulary is closed at one and the wrapper does the rendering rather than trusting the body's. A `{call_id}` sentence on a body that awaits nothing is refused at attach: it runs inside no call, so there would be no id to render.

   **The refusal names a position and never the text.** A raise from the wrapper propagates through `LabelTrackingFunctionMiddleware.process`, whose `try` runs `call_next` and `_label_result` with no `except` between them, so labelling is skipped and MAF answers with an *unlabelled* error result — carrying the exception text wherever the host set `include_detailed_errors`. The mistake being caught is a kind labelling guest text as trusted, so quoting it would hand that text back out on the one path that labels nothing.
6. **Read the aggregate when you serve host tools.** A registry's `HostToolAggregate.result_integrity` is the weakest level over its registered sources, and an unstamped tool fails safe to untrusted. A kind that serves host tools derives from whatever they returned, so its own construction has stopped describing its result.
7. **Two different things keep the join uninformed, and you need both.** Your arguments are *visible but unlabelled* — a plain `str` carries no label, whether it is a file name or, as in `execute_code`, the model's program itself. The content behind a name is *out of band*: read from the store inside your body, never seen by the join at all. Either way the framework takes its separate no-labels branch, because nothing was inspected rather than because anything was traced. The first failure a caller could fix by labelling its arguments; the second nothing can fix *there* — `AgentFileStore` takes a `str` and returns a `str`, so the type it holds cannot hold a label, and the framework fills it with content it was hiding a moment earlier: a variable reference passed as the `content` of the host's file-write tool is expanded into the real bytes before that tool's body runs. What answers this is the listing *beside* the store rather than the store itself — rule 9 below — and it does not lift the ruling. **If your result may derive from what you read out of the store, declare `untrusted` — rule 1's explicit form, not silence** — because an entry the host established nothing about reads `None`, and a store no host kept a record for reads `None` for every file in it. You are labelling from what you know about your own construction, and nothing downstream will catch you getting it wrong.
8. **Do not pair an explicit `declarations=` with a sink.** It is refused, for the reason rule 6 of the artifacts list above gives: the two disagree about what the tool's information flow is.

9. **Read the label the listing gives you; never infer one from the name.** `CallerContext.list_files` answers with `ListedFile` entries — a name and what the host knows about the bytes at it — and `SandboxToolSession.read_file` hands you the content as a labelled item rather than a bare `str`. Four things follow, and none of them is new: they are rules 2, 5 and 7 applied to a channel that can finally answer.

   **The name and the label are different channels, and a label never licenses echoing a name.** Learning that a file is `trusted` tells you nothing about the string that pointed at it: the label is about the bytes, and the argument may be content the framework expanded into your call. So what decides how a verdict renders is not the label but the *hidden-content* verdict — pass both the argument position and that verdict to `echoed_name(name, at=..., hidden=...)`, which quotes an ordinary name and switches to the position only where the framework rewrote the argument. Ask once per call, before your first await, with `positions_holding_hidden_content`; a verdict belongs to a position and never to a value.

   **Fold across the files you actually read, weakest first.** `weakest_integrity` is that fold and it uses `INTEGRITY_RANK`, so a new member cannot be added without being ranked. `None` wins over everything: a file the host establishes nothing about disqualifies a `trusted` claim exactly as an untrusted one does, which is rule 2's "establishment alone is not enough" seen from the reading side.

   **The fold does not change your declaration, and cannot.** `source_integrity` is written when the tool is *attached* and the fold exists only per call, so a kind that may read a model-written file declares for that possibility once — rule 1's explicit `untrusted`, per rule 7 — and the fold never lifts it. Passing `nothing_survives_from=` remains what it always was: a claim about your result, not about a listing.

   **Where it does decide something is per item.** Under rule 5 an item is trusted only where its value and its presence are independent of every source not established as trusted, and the fold is how you now *know* which sources those were. An item deriving only from files that folded to `trusted` may carry a label; everything else stays unlabelled and takes the call's own. No kind derives an item's label from a file's integrity yet. That is narrower than "neither kind splits": `execute_code`'s withheld route already answers with a labelled item beside an unlabelled one, driven by `withhold` rather than by what any file was worth, while `bicep_validate` does not split at all. [`bicep.md`](bicep.md) and [`codeact.md`](codeact.md) track where each stands.

Then say what you decided and why, in one row of your kind's page and one paragraph of your package README. A declaration whose reasoning lives only in a code comment is how two kinds reasoned from the same sentence to opposite answers.
