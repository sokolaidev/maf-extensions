# `acas` — ACA Sandboxes

> The reference conformant backend: hardware-isolated micro-VMs on Azure Container Apps, the only one that can enumerate, and the only one whose isolation rung the router's default floor already admits. Install and configuration: [`packages/maf-sandbox-acas/README.md`](../../../packages/maf-sandbox-acas/README.md).

## What it declares

Acquire also checks shell invocation for `EXEC` and batches the shell, `mkdir`, `mv` and `nohup` prerequisites for `HOST_TOOLS`. Successful checks are kept with the sandbox's registry entry; failed checks are retryable. A new sandbox refused for missing commands is disposed, while a warm one keeps its identity and existing results. These command checks supplement the observed-removal gate below and do not change its inconclusive-result policy. Neither gate grants deletion authority. See [the ceiling and probe contract](../guest-platform-and-commands.md#decision-3--a-static-ceiling-matched-at-attach-and-a-probe-at-acquire).

The five below `isolation` are fields of this backend's `declarations`.

| Declaration | Value |
|---|---|
| `isolation` | `Isolation.MICROVM` |
| `capabilities` | `EXEC`, `FILES_IN`, `FILES_OUT`, `FILES_LIST`, `FILES_DELETE`, `HOST_TOOLS`, never `RUN_CODE`. `FILES_IN` uses guest authority and requires permission and transfer utilities at each write. Three are a ceiling: a failed guest removal probe withdraws `FILES_OUT` and `HOST_TOOLS`, and any result without an observed removal withdraws `FILES_DELETE` |
| `egress_modes` | `{Egress.ALLOWLIST, Egress.CLOSED}` |
| `limits` | 32 MiB per file, 128 MiB total, 128 files — the same `TransferLimits` in each direction |
| `os_families` | `{OsFamily.POSIX}` — a constant rather than a read: every sandbox the service boots is a Linux microVM, from the prebuilt catalogue and from an imported disk image alike. It is what `exec`'s `shlex.join` quoting and this backend's `posixpath` arithmetic rest on |
| `isolation_scopes` | `{IsolationScope.CONVERSATION, IsolationScope.CALL}` — see [one sandbox per call](#one-sandbox-per-call) |

The byte ceilings sit well under what a streaming backend could offer, because this one cannot stream: the SDK's `read_file` buffers the whole response, so a per-file ceiling bounds **host memory** rather than transfer cost. `max_files` is comparatively high because a `FILES_LIST` kind fetches each file in a round trip of its own.

## Two modes, one mechanism, built from the spec

`egress_modes` is `{ALLOWLIST, CLOSED}`, and the two are the same mechanism at two settings. Every create passes an `EgressPolicy` with `default_action: "Deny"`, full traffic inspection, and exactly one `Allow` host rule per name in `spec.egress_allow`. A spec running `ALLOWLIST` names hosts and gets exactly those; a spec running `CLOSED` names none and gets Deny with nothing allowed. Nothing in this backend's configuration widens the list: the deployment chooses the mode, the spec carries the hosts.

The held instance records its egress mode and case-insensitive host set. Equivalent policies reuse it; changed hosts or mode on a usable instance raise `AcasEgressPolicyConflict` before resume. This exception subclasses `SandboxEgressNotEnforced`. Refusal retains ownership and does not alter the original policy. Coordinate active calls, await `router.dispose_kind(key, spec.kind, timeout=60)` and require `True` before changing policy, or use a new key. Direct backend callers can await `backend.dispose(key, kind=spec.kind)` and require `None` (no disposal failure). Refusal also applies to stale held records until explicit disposal. Capture-invalidated instances instead require successful deletion before replacement, including when the requested policy changes. Refusal avoids deleting an instance another caller may still use. The live suite verifies the refusal, continued reach under the original policy, and denial after explicit disposal followed by a `CLOSED` acquisition.

**Method matching is measured and not yet established.** ACAS's advanced SDK rules can restrict methods, and the live service denied every verb the rule did not name, custom verbs included. It matches case-insensitively, which core's vocabulary no longer asks about: methods are uppercase tokens and a case distinction is not expressible. What remains unmeasured is the rest of the surface — redirects, rule precedence, wildcard overlap and the non-TLS path — so the backend withholds `EGRESS_METHODS` and refuses such specs on direct acquisition as well as through the router. GET request content also reaches the origin. [The live record](../research/acas.md) carries the setup, controls and remaining scope of [#377](https://github.com/sokolaidev/maf-extensions/issues/377).

`UNRESTRICTED` is absent and could not be added — the group's policy denies by default and cannot be told to allow everything. A workload that asked to run open is therefore **refused here rather than served something narrower**, which is the resolution rule doing its job: a mode is enforced as asked or not at all. The axis and what a host may state on it are in [`../network.md`](../network.md).

**The policy is measured now, not only built.** `test_acas_e2e.py` acquires one more sandbox with `ALLOWLIST` and a single allowed host, and runs the shared `assert_egress_conformance` probe inside it: a host on the list answers, a host off it does not. Until that leg, everything this backend could show for `ALLOWLIST` was the `EgressPolicy` it constructed before sending — nothing had watched the service apply one, on the backend where what the SDK reports and what the service does have already diverged twice. Its gate is the suite's own plus an imported image carrying `curl`, and it costs the module's fourth billable sandbox, so it runs where the rest of that suite runs — the `acas-e2e` job and the nightly conformance run — and never on a pull request. The deny here is L7, the group's proxy answering rather than the network being cut, which is why the shared probe reads the outcome and not the mechanism ([#402](https://github.com/sokolaidev/maf-extensions/issues/402)).

## The reference conformant backend

This is the backend the micro-VM standard was written against: a hardware virtualization boundary, host-owned group identity configuration, confinable egress, and an explicit guest↔host surface. The deployment owns the identity and permissions intended for its sandbox group, as [the configuration contract](#sandbox-group-identity) describes. It is remote into the bargain. What that role means in practice is that it defines what the file surface should *look* like — it is the only backend that can serve `FILES_LIST` — while [`docker`](docker.md) decides whether the surface actually works, because Docker is the one a pull request can run. Keeping reference and gate apart is what stops the richest backend from quietly setting requirements the portable ones cannot meet. The standard itself is in [`../policy-isolation.md`](../policy-isolation.md).

## Exec bytes and capture prerequisites

Exec returns exact `stdout_bytes` and `stderr_bytes`, with safe UTF-8 text views for display. ACAS requires writable `/tmp` and compatible `sh`, `mkdir`, `mkfifo`, `head`, `cat`, `wc`, `dd`, `base64`, `rm` and `rmdir` for EXEC/HOST_TOOLS. Acquisition checks this separately from removal compatibility. Guest FIFO readers retain at most the configured limit plus one byte per stream and drain inherited writers; encoded chunk retrieval and cleanup also run as the guest. No file-plane read or delete participates in exec capture.

`exec_output_limit_bytes` defaults to 1 MiB per stream. Overflow, reader failure, invalid framing, interrupted retrieval or an exception during scratch removal raises without returning partial output. These failures, timeout and cancellation invalidate and attempt to delete the whole sandbox, including concurrent commands. The narrow timeout exception is a deadline reached while the Azure SDK sleeps on an HTTP 429 `Retry-After`: the throttled request answered and no retry started, so the sandbox stays reusable. Another retryable status remains ambiguous and still disposes it; direct cancellation during the 429 sleep does too. The command deadline includes retrieval and the scratch-removal attempt; deletion after failure has up to `min(30, read_timeout_seconds)` additional seconds. A failed deletion stays retryable and the invalidated instance cannot be reused.

After complete retrieval, a scratch-removal response with a nonzero exit code or unexpected output instead logs a warning naming the guest directory and returns the captured bytes and program exit status unchanged. Scratch may remain until sandbox disposal, and the sandbox remains available under its existing capability checks. Cleanup never falls back to the privileged file plane. See [the output contract and migration](../exec-output.md).

## `HOST_TOOLS` rests on a live measurement

`HOST_TOOLS` is the one capability with no method behind it. What it asserts is that **`exec` detaches** — a process started by one call outlives it and is observable from the next, because the sandbox is a micro-VM the group keeps between calls rather than a session torn down per `exec` call. That is what the host-tool transport is built on: the launcher returns at once and the exit-code file is the run's only witness. Here it could not be taken on faith, since every call is an HTTP round trip to a remote control plane, so `test_acas_e2e.py` measures detachment against the real service rather than reading it off the SDK. It is **not** a claim about the image: the shipped launcher wants `sh`, `nohup`, `printf`, `mv`, `mkdir`, `rm` and `kill`, and a kind wants whatever interpreter it names — none of which this backend chooses, since the spec's image does. One property of the image it does read is the next section's, and it is the one that decides whether this capability can be served at all.

## A non-root image is refused at acquire, and says so there

The service file plane acts as root, while `exec` runs as the image's `USER` and the SDK exposes no selector to raise it. The SDK's native `write_file` lands files as `0:0`; the backend's workload `write_file` always uses guest execution. So on an image whose guest is not root, every directory the file plane creates arrives root-owned and `0755`, and the guest program can create nothing inside one — not the run directory the host-tools launcher `mkdir -p`s, not the pid and exit markers it writes beside it, and not a declared output it was supposed to produce. Measured on `python-nonroot:3.13` (`uid=10001`), where the launcher fails on its first two writes and the run never starts ([#722](https://github.com/sokolaidev/maf-extensions/issues/722)). Neither SDK route closes it: `mkdir` is single-level and answers `parent directory not found` for a chain, and `write_file(mode=...)` accepts `"777"` and reads it as **decimal**, landing a root-owned `0411` file whose one special bit is **sticky** — decimal 777 is `0o1411`, and sticky on a regular file does nothing on Linux — with the created directory still `0755`, while `"0o777"` is a 400. Closing it properly needs a file plane that can create a directory the guest owns, which is a service capability rather than something this backend can compose. That half is an upstream ask, filed as [microsoft/azure-container-apps#1820](https://github.com/microsoft/azure-container-apps/issues/1820).

`acquire` checks removal compatibility: the file plane writes a file into a fresh root-owned directory directly under `/`, then the guest attempts `rm -- <guest_file>` over `exec`, also from `/`. The backend verifies the file before the command, and verifies its absence and the continued presence of the scratch directory afterward. Stdout is ignored. An image-provided privileged wrapper can pass this check without giving ordinary workload code equivalent authority, so the observation never licenses a host-plane `remove`. The scratch directory is removed through the file plane in `finally`, including on cancellation. Preparation, execution and observation share a 30-second bound; cleanup has a separate 30-second bound. A cleanup failure leaves the probe incomplete and retryable.

The result describes **removal compatibility**, not a numeric uid or a security guarantee. An observed removal with a successful exit serves all three capabilities. A file that remains after `rm` exits 1 refuses `FILES_OUT` and `HOST_TOOLS` and serves `EXEC` with a warning: the functional gate conservatively refuses workloads requiring guest-written outputs or host-tool markers after failed removal. The warning does not claim that other destinations are unwritable; each `write_file` runs as the guest and requires permission at its destination. An inconclusive probe serves that functional pair without a warning. `FILES_DELETE` retains a conservative refusal on either failure or an inconclusive probe. Each actual `remove` executes as the guest and independently verifies absence through the file plane.

The probe runs only when a spec requires `EXEC`, `FILES_OUT`, `HOST_TOOLS` or `FILES_DELETE` and the sandbox has no completed verdict. Warm reuse reads that sandbox's own verdict, and transient failures leave it unprobed for the next acquire. An image-level hint answers only the refusal before a create; it never licenses a newly created sandbox, because the same reference can resolve to a different image. Hints expire 60 seconds after a completed probe, using a monotonic clock. Cached refusals, warm reuse and dropped probes do not extend the deadline. After expiry, the next cold acquire creates and probes again; a fresh refusal starts another 60-second window. This trades up to a minute of delayed recovery for avoiding a create on every rejected acquire. Concurrent cold acquires on different keys can still create separately; the timer is not a global create rate limit. Repointing an image does not change a warm sandbox: dispose it before acquiring a replacement, allowing any hint to expire first. An inconclusive result preserves an earlier concrete hint only until that hint expires; the remaining limitation is tracked in the Status table.

**The wall is a directory the file plane made**, not the working directory as such: `/tmp` is `0o1777` on the measured non-root image and the guest writes there freely. Every shipped kind reaches the guest through an upload that creates its call directory. A kind taking `FILES_OUT` with no `FILES_IN` and no host tools could create its own outputs under a world-writable `work_dir` and is conservatively refused anyway. The refusal lands at acquire rather than attach because no image is running when the router matches a capability set.

**Which images are in the gate:** images whose guests cannot remove the probe file, and, for `FILES_DELETE`, images whose removal probe is inconclusive. The prebuilt images and shipped `bicep-sandbox` and `diagram-sandbox` images run as root; they still have to pass the observation. An image needs a working `rm` for the probe, independently of the commands its workload needs.

## `run_code` answers, and what it answers is a refusal

`run_code` is a `Sandbox` method rather than an optional extra, so this backend implements it — as a raise. Not for want of an interpreter, since the image may well carry one, but because *which* runtime an image carries is a property of the image, and this backend resolves an image reference without looking inside it. Declaring `RUN_CODE` would be a claim about someone else's artefact. A workload that wants a runtime by name invokes it through `exec` and owns that assumption itself; the router refuses a spec requiring the capability before any caller arrives, so the `NotImplementedError` is the honest floor under a caller that skipped the check. It is the same asymmetry `remove` sits on the other side of, further down: a mechanism may exist and stay undeclared, and a capability may never be declared without one.

## The pull surface is read past the SDK

Confinement depends on being able to tell a symlink from a regular file, and the SDK's typed `FileInfo` **drops both** of the fields that would say so. The backend therefore reads the data plane's raw stat and list payloads itself, for `isSymlink` and `isDir`, and a payload that omits either flag is **refused** — `AcasEntryPayloadIncomplete`, never read as a regular file — because those two booleans are the whole of this backend's symlink refusal and a service that stops sending them has to break the read loudly rather than degrade confinement to nothing. `mode` is not consulted: it carries permission bits with the type bits stripped. That the reference backend's defence rests on an undocumented preview shape it reaches past its own SDK for is acceptable only stated plainly, and it is filed as [#136](https://github.com/sokolaidev/maf-extensions/issues/136).

A symlinked *parent* is invisible in the final entry's stat, so every one of `stat_file`, `read_file`, `list_dir` and `remove` first checks the components from the filesystem root down through `maf_sandbox.paths.refuse_symlinked_ancestors`, over this backend's own **unconfined, no-follow** stat. Only a link is a confinement failure there; any other non-directory is an ordinary `ENOTDIR`.

## Native reads retain a confinement residual

The backend retains `FILES_OUT` and `FILES_LIST` with native host-authority operations. Each method checks the path, then asks the service to resolve its spelling again. The guarantee is refusal of links observed by the check; no method holds that observation through the operation.

| Method | Final-component behavior | Remaining redirection |
| --- | --- | --- |
| `read_file` | A classified link is refused, but the read follows a link installed afterward | Parent or final-file swaps can return outside bytes, including bytes unavailable to the guest |
| `stat_file` | Describes the final link itself | A parent swap can return outside metadata under the requested path |
| `list_dir` | Checks that the listed directory is not a link before listing | Ancestor or listed-directory swaps can return outside children under the requested prefix |

**Measured 2026-09-13**, with Python 3.13.12 and `azure-containerapps-sandbox==0.1.0b4` against the service in `swedencentral`: `TestReadSurfaceResidual` passed ten live cases across the configured root and non-root images. Four controlled swaps per image returned the outside fixture's result: read through a parent, read through a final file, stat through a parent, and listing through the replaced directory. The test waits for the real stat response, runs the guest rename/link command, then lets the original backend operation continue. These tests characterize the residual; passing them does not certify confinement.

The target file was a synthetic, data-plane-created `0600` file inside the same sandbox. On the non-root image, guest `cat` failed with no returned bytes, while both redirected backend reads returned the target bytes. That image still failed the ordinary `FILES_OUT` acquisition gate, as expected; its direct methods remained callable. Root output acquisition passed. The tests also retained size-cap refusal, and both fixture scopes were verified empty after disposal.

**Disposition:** keep native capabilities with the stated residual. Replacing the surface with guest-side operations would add shell utilities or an interpreter to the image contract; running as the guest bounds authority but does not itself hold a path. A trusted descriptor-relative helper needs a trusted runtime and descriptor lifetime, not separate shell checks. Withholding `FILES_OUT` and `FILES_LIST` would remove existing artifact retrieval and native enumeration; it is not the compatibility policy chosen here. The removal probe cannot authorize host reads, returned path-prefix checks cannot detect an alias, and a second stat leaves another window.

A supported atomic service operation is tracked in [microsoft/azure-container-apps#1831](https://github.com/microsoft/azure-container-apps/issues/1831): bind resolution to a trusted directory boundary and read/stat/enumerate that object without following replaced components. [#136](https://github.com/sokolaidev/maf-extensions/issues/136)'s metadata repair does not supply this guarantee. Suspending the sandbox is already measured unsuitable: the stopped data plane refuses file operations, as recorded below.

A host requiring the working directory to remain a filesystem boundary must use a backend that holds it. Caps limit returned bytes, timeouts limit selected waits, and disposal limits lifetime; none binds a native read to its earlier check. Writes execute as the guest; this does not bound native read authority.

## Enumeration, and what a listing is allowed to say

`list_dir` is native here, and this is the only backend that declares `FILES_LIST`. Three rules keep the response honest, and each of them refuses rather than degrades. The `entries` key is **not defaulted to empty**: the service sends an explicit empty list for an empty directory, so an absent or renamed key means the payload shape changed, and defaulting would hide every output behind a listing that looks legitimately empty. Every returned entry path is lexically confined to the working directory *and* required to be a **direct child** of the path that was listed, because the protocol's listing enumerates one level — a sibling or a grandchild in the response is a payload this backend cannot read, not a path a caller asked to traverse. And each entry is classified by the same two flags a stat is, so an entry the service describes incompletely breaks the listing rather than arriving as a regular file.

## Regularity is not provable here

Refusing a symlink narrows an entry to *not a link and not a directory*. It does not prove a regular file, and FIFOs, sockets and device nodes are none of the three. **On ACAS, `EntryKind.FILE` means "not a directory and not a symlink"** — a kind author is entitled to know that, because a FIFO is reported identically to an empty regular file and reading one **never returns**. Nothing available closes it: `mode` has no type bits, and `exec` with `test -f` would reintroduce the in-image shell dependency the `FILES_LIST` split exists to avoid, on exactly the minimal images where the file API is most useful. So the read is **bounded by `read_timeout_seconds`**, turning an indefinite hang into a refusal in the output-error family — a failure no cap or reported size predicted. The missing signal is filed upstream as [microsoft/azure-container-apps#1807](https://github.com/microsoft/azure-container-apps/issues/1807).

## `FILES_DELETE` runs as the guest

`remove` executes `rm -f -- <guest_path>` or `rm -rf -- <guest_path>` through guest `exec` from `/`, after the file-plane path checks. A directory is refused without `recursive`, including an empty one, and the working directory and outside paths remain refused. A missing path is already success. Otherwise a successful exit must be followed by file-plane confirmation that the entry is absent; a nonzero exit or surviving entry raises `OSError`. The operation is bounded by `read_timeout_seconds`. The live suite runs the shared `assert_files_delete_conformance` probes against this declaration. What each capability obligates is in [`../capabilities.md`](../capabilities.md).

**The image controls its commands, so the probe cannot establish workload authority.** A setuid or file-capability `rm` wrapper could remove only probe paths and refuse other root-owned paths. Executing each requested removal as the guest keeps that wrapper's existing authority rather than granting the host file plane's authority. Parent checks are still a check rather than a hold: a component swapped after the check can redirect a guest command, but cannot turn it into a host-plane delete. The service reports no ownership for a per-path ownership gate. `write_file` follows the same authority rule: every workload write executes as the guest, as described below; `reclaim` refuses.

## `write_file` always runs as the guest

Every write uses `maf_sandbox.write_file_over_exec`, including cold acquisition, first `FILES_IN` use after a guest has run on a warm sandbox, and calls selecting an alternate absolute working directory. No guest-written probe output selects authority. The path checks reject observed symlinks but remain separate from the transfer: a later parent swap can redirect placement within the guest's existing reach. This is a guest-authority bound, not atomic confinement to `working_directory`; a root guest can still write wherever root can.

**Compatibility change:** the host-authority fallback is removed. A service-created root-owned `0755` base on a non-root image now produces `PermissionError` when the guest cannot write there. Missing `sh`, `mkdir`, `mv`, `rm` or `base64`, and missing commands required by bounded exec capture, cause a transfer or execution failure. Writes never retry through the host file API. `FILES_IN` remains declared: as with `EXEC`, each operation needs working image commands and permission at the requested path. Acquisition does not test base write permission or promise that every absolute working directory is writable.

This revises [#962](https://github.com/sokolaidev/maf-extensions/pull/962)'s compatibility choice explicitly. Preserving an input route does not justify granting a guest host-authority writes. Supply the transfer and capture utilities and an existing directory writable by the guest, then select it with `SandboxSpec.work_dir`; an alternate writable absolute working directory also works even if the storage base is protected. Merely choosing a missing path below `/tmp` is insufficient: acquisition creates missing base directories through the host plane, which may still make them root-owned. Bake the owned directory into the image or prepare it through guest execution under an existing writable parent. The backend does not change ownership or modes to make a refused write succeed.

[microsoft/azure-container-apps#1820](https://github.com/microsoft/azure-container-apps/issues/1820) requests guest-owned directory creation and remains relevant to that migration. It does not provide missing transfer utilities or bind a path check to a later operation. This policy needs neither an ownership oracle nor a no-follow service-write contract, so no new upstream write contract is required. Service metadata still cannot justify restoring the fallback. Work-directory preparation and the separate removal-compatibility probe continue to use the host plane; this decision bounds workload `write_file` transfers and does not claim that all ACAS file operations use guest authority.

**The road's cost is per chunk, not per write.** It runs two control commands plus one for every 48 KiB of content (`SHELL_CHUNK_BYTES`), so a file under that costs three guest commands — 0.44 s against the plane's 0.21 s, measured below — and one at this backend's 32 MiB `files_in` ceiling costs 685, sequentially. `read_timeout_seconds` bounds the whole transfer, so a large file on a slow link is refused where the plane would have taken it.

**Transfer failures retain their existing semantics.** A deadline that expires *between* commands takes the staged sibling back and raises `OSError` with the sandbox whole, because nothing was running. A command that fails *in flight* — its own timeout, a capture failure, an output overrun — invalidates and disposes the sandbox the way any `exec` failure does. A completed guest refusal preserves the sandbox and returns `PermissionError`, `IsADirectoryError`, `FileNotFoundError` or `ValueError`; other transfer failures return `OSError`. The HTTP 429 `Retry-After` timeout exception also preserves the sandbox when no command is in flight. `Sandbox.reclaim` refuses because safe ancestry cannot be established; withheld `RECLAIM` sends router-managed cleanup to disposal.

Verified on 2026-09-14 in `swedencentral` with Python 3.13.12 and `azure-containerapps-sandbox 0.1.0b4`. The focused ACAS live suite passed all 11 selected tests in 50.22 seconds, using an imported root image for the shared FILES_IN probes and `python-nonroot:3.13` for the permission checks. This verifies the selected guest-authority mechanism; it does not establish atomic placement or change the native-read residual.

Missing transfer utilities and cleanup failures remain deterministic unit-test coverage rather than live image mutations.

### Suspending the sandbox cannot close the window

Freezing the guest is what closes the same window on docker, where `pause` stops the container while `docker cp` keeps working ([#1130](https://github.com/sokolaidev/maf-extensions/issues/1130)). This service has suspend and resume and `acquire` already resumes, so it was measured rather than assumed. It does not work: the data plane serves a stopped sandbox nothing at all, and the price of the round trip is two orders of magnitude above the call it would protect. | `begin_stop()` until the control plane reports `Stopped` | 7.7 s |
| `ensure_running()` back to `Running` | 0.47 s |

## `reclaim` refuses; cleanup uses disposal

`reclaim` raises `NotImplementedError` before any service call. ACAS withholds `RECLAIM` and `SNAPSHOT`, so router-managed cleanup disposes the sandbox and the reclaim conformance suite refuses before planting. Direct callers must also dispose the sandbox instead of expecting call-directory reclamation.

The data plane's `delete_file` acts as the host and resolves linked parents, even though directly named and interior links are unlinked ([#708](https://github.com/sokolaidev/maf-extensions/pull/708)). It provides no ownership evidence to establish that the guest cannot replace an ancestor. A file-plane-created directory does not establish ownership of pre-existing ancestors, and `work_dir` may name a custom path. These constraints prevent this backend from establishing safe reach for a host-authority recursive deletion ([#710](https://github.com/sokolaidev/maf-extensions/issues/710)).

## Lifecycle

ACAS admission checks apply to direct backend callers as well as router users. Retained cleanup is retried before replacement; unsuccessful cleanup raises `SandboxOutputError` from acquire. Scope purge reports `ScopePurge(0, DisposalFailure("unknown", ...))` if acquisition for that scope and thread is active on this backend, so callers must retry after it finishes. Once purge is admitted, new acquires for that scope and thread raise `SandboxOutputError` until every overlapping purge finishes. Other scopes and threads remain available. This barrier is local to the backend object; hosts must stop new conversation work across replicas before purging.

**ACAS withholds `SNAPSHOT` and retains disposal.** `Sandbox.reset` refuses, so the cleanup ladder has no `RESET` rung on this backend. Warm reuse through reclamation requires explicit host opt-in and the backend's `RECLAIM` declaration, which ACAS also withholds. Kind confinement metadata is advisory. The service supports snapshot restoration; this backend deliberately withholds `SNAPSHOT` because the measurements below establish no consistent cleanup benefit. Acquisition retains its get-or-create mechanism.

The [M6 measurement on 2026-09-09](https://github.com/sokolaidev/maf-extensions/issues/978#issuecomment-5593743594) compared five disk-image creates and five snapshot restores per image in Sweden Central, using SDK 0.1.0b4. Median create-to-successful-exec time fell from 0.904 s to 0.479 s for Python, but rose from 0.943 s to 0.988 s for Bicep. First restores took 3.625 s and 2.605 s respectively; including them, snapshot means were slower for both images. Both cleanup strategies also pay the measured 5.646–7.103 s deletion time. This small sample establishes no consistent benefit across the two workloads sufficient to justify baseline ownership, recovery and reconciliation. Reconsider the decision when a representative measurement establishes a substantial, repeatable reduction in the whole cleanup cycle, or the service supplies an in-place restore.

M6 established that named snapshots survive source deletion, can be recovered by a fresh host process, and preserve process memory and disk. They require explicit deletion. SDK 0.1.0b4 rejects ownership labels on restore even though a direct service request accepts them, and restored lifecycle policy must be reapplied and verified. The snapshot quota and exact storage price remain unverified under [#978](https://github.com/sokolaidev/maf-extensions/issues/978); neither is assumed to be zero or unlimited, and neither blocks the decision to withhold the capability. The full measurement remains on that issue.

**Per-key disposal discovers sandboxes through service labels.** `dispose(key, kind=...)` selects sandboxes by the reserved scope, thread, agent and optional kind labels — plus the reserved `call` label when the key names a tool call, which is what keeps a call-scoped disposal off a sibling call's sandbox — so it reaches sandboxes another process created. Reserved labels are protected from caller overrides; the registry is a fallback for failed listing, not proof that the service holds no matching sandbox. `instance_id=...` narrows the service result to one ID; a failed ownership query refuses deletion. Disposal waits for the SDK deletion poller to confirm absence, and preserves failed IDs for retry.

**Auto-delete depends on successful policy configuration.** Creation and the later lifecycle update are separate operations. A sandbox left between them can have auto-suspend without auto-delete; suspension preserves resumable state and does not establish a deletion deadline. Recovery for that configuration gap is tracked separately from the deployment's scheduler. [`../operations.md`](../operations.md) describes an independent group sweep using the service's `Stopped` state and stop timestamp, with a one-day stopped retention policy for live verification.

**Warm resume over cold create.** Every acquire tries the registered sandbox first and waits up to 120 seconds for it to come back from suspension; a sandbox reclaimed by its auto-delete timer between rounds is expected, logged at INFO rather than warned, because it means the next call pays for a cold create and the reason is worth a line. **Labels are written at create** — scope, thread, agent, kind, plus the spec's own — and the sandbox is registered immediately after the create returns, before the lifecycle policy is configured, so it stays reachable by purge even if configuration fails. **`dispose_scope` selects from the service by label**, not from process memory, because a conversation delete lands on whichever replica serves it. Label values pass through when short and safe and become a `sha256-` digest otherwise — never a truncation, since two scopes sharing a prefix would let one conversation's purge delete another's sandboxes — and the same mapping runs on write and on query. **Get-or-create is serialised per key**, per running event loop, because a create names no sandbox and the service therefore has nothing to recognise a duplicate by; unserialised, both racing acquires get a running, billable sandbox and only one stays registered.

**The control-plane credential never enters the guest.** The default `DefaultAzureCredential` or a host-selected credential lives with its group client in the host process. [Host credential selection](acas-credentials.md) covers per-request grants, independent cleanup on another replica, bounded caches and loop-owned shutdown. It does not grant authority to guest code or enable the attached-identity capability.

## Sandbox group identity

ACAS supports managed identity attached through sandbox-group configuration. The host provisions the identity assignments, grants and intended sharing, and the adapter trusts that configuration. Cold and warm acquisition make no ARM assignment read, add no management-read permission requirement, and do not refuse a group merely because it has an attached identity. This applies independently to every host replica; no inspection cache or cross-replica verification state is introduced.

The host's ACAS control-plane credential and the group's attached identity serve different purposes. [Host-selected credentials](acas-credentials.md) authorize SDK operations from the host process. Group-attached identity is a supported platform feature. [M1](https://github.com/sokolaidev/maf-extensions/issues/1164#issuecomment-5647054734) measured guest token acquisition through the configured identity endpoint for its tested API, image and group configuration; the available guest surface depends on the deployment. The host chooses the permissions and sharing intended for the workloads it routes to that group. Sandbox deletion does not delete the group's shared principal; revocation of previously issued tokens was not measured.

The [M1](https://github.com/sokolaidev/maf-extensions/issues/1164), [M2](https://github.com/sokolaidev/maf-extensions/issues/1165), [M5](https://github.com/sokolaidev/maf-extensions/issues/1166), and [M7](https://github.com/sokolaidev/maf-extensions/issues/1167) measurements remain evidence about service behavior and limits. A possible management inspection mechanism is not a requirement to use it on every acquisition. [Lifecycle](#lifecycle) is applied separately: the adapter sends `AcasSandboxConfig.auto_suspend_seconds` and `auto_delete_seconds` to each newly created sandbox. An authentication or authorization failure refuses acquisition and attempts cleanup; another lifecycle update failure logs the missing confirmed timer and continues with the state left by the service, without a confirmed lifecycle policy. These intervals and failure paths do not establish the core contract's hard authority-retention bound, and do not disable configured group identity.

The library APIs remain unchanged. The adapter does not advertise the finer-grained `Capability.ATTACHED_IDENTITY` channel/scope/lifetime contract, and a workload requiring that capability is still refused by the router. Ordinary specs can use the group-configured identity without core identity opt-in or bounds. The host routes only workloads intended to share that authority to the configured group, using separately configured groups where authority must differ. Mapping group configuration into the declaration vocabulary remains a separate API decision; neither the default declaration nor an isolation-floor match certifies an identity-free Azure group.

## One sandbox per call

A spec asking for `IsolationScope.CALL` is served here rather than refused. This backend mints no name of its own — the service issues the sandbox id — so the whole of its call-scope identity is the **registry entry**, filed under `(scope, thread, agent, call, kind)`, and the **service label** a disposal selects on, `call`. Two acquires differing only in `call_id` miss each other in the registry and are two microVMs; a disposal that names a call selects that label and leaves the sibling call of the same assistant message running. That is the property `maf_sandbox.conformance.assert_call_scope_conformance` measures, and the live suite here answers it against the service.

**A conversation-scoped key carries exactly the labels it carried before.** The `call` label is written only when the key names a call, so a sandbox created by an earlier release is still reached by a selector that does not mention it.

**The conversation's purge is still the backstop.** `dispose_scope` selects on scope and thread alone, never on the call, so a per-call sandbox whose own delete did not land is reached when the conversation ends — which matters more here than elsewhere, because what is left running is billable.

**What it costs is a cold create per call**, and on this backend that is the most expensive cold start of the three: a warm resume is seconds where a create is minutes. The default is still `conversation`; a host raises the floor with `SandboxRouter(min_isolation_scope=...)` or a spec raises it for itself.
