# `docker` — plain containers

> Container-rung sandboxes on any Docker-compatible engine — the backend a contributor can run on the machine in front of them, and the one whose live suite is the repository's acceptance gate. Install and configuration: [`packages/maf-sandbox-docker/README.md`](../../../packages/maf-sandbox-docker/README.md).

## What "Docker" means here

A `docker`-compatible command-line client talking to a Docker-API-compatible socket — not Docker Inc.'s daemon specifically, and not any particular installation shape; the full argument for targeting the contract rather than the binary is [`../research/docker-backend-exploration.md`](../research/docker-backend-exploration.md).

## What it declares

The four below `isolation` are fields of this backend's `declarations`. Three are settled by the constructor; `os_families` is the one the daemon has to be asked for, and only `create` asks.

| Declaration | Value |
|---|---|
| `isolation` | `Isolation.CONTAINER` |
| `capabilities` | `EXEC`, `FILES_IN`, `FILES_OUT`, `FILES_DELETE`, `HOST_TOOLS`, `RECLAIM` — never `FILES_LIST`, never `RUN_CODE` |
| `egress_modes` | `{Egress.CLOSED}`; `{Egress.CLOSED, Egress.ALLOWLIST}` when an egress proxy image is configured. Never `UNRESTRICTED`: a container backend always cuts or proxies |
| `limits` | 64 MiB per file, 256 MiB total, 256 files — the same `TransferLimits` in each direction |
| `os_families` | `{OsFamily.POSIX}` when the daemon reports `linux`; `frozenset()` for every other answer, `windows` included. Read once by `DockerSandboxBackend.create`, and the plain constructor declares nothing |

## `container` is a constant

`isolation` is not a function of the config, in this version or any later one. A container shares the host kernel and no setting this package has can change that; a Docker Desktop or Colima VM does not lift the rung, because one shared VM kernel serves every container — the same shape as wslc's WSL 2 utility VM, which the ladder also classifies at `container`. A hardened runtime would be a different rung, but only with a way to *verify* it is in effect, and a runtime string a backend cannot verify must never become a security guarantee the router repeats. The rung sits below the router's default floor, so a host opts down explicitly with `min_isolation=Isolation.CONTAINER`; with nothing passed, construction raises. Three self-imposed constraints hold the guest↔host surface narrow — no bind mounts, no host-path sharing, and never `/var/run/docker.sock` passthrough — and they are self-imposed: nothing checks that a backend declaring `container` refrained from mounting the host filesystem.

## The guest family is read from the daemon, and only `linux` is declared

The `os_families` field of this backend's `declarations` comes from `docker version --format '{{.Server.Os}}'`, asked once by `DockerSandboxBackend.create` — an `async` factory, because `__init__` makes no engine calls and a blocking read in a constructor would do subprocess I/O on the caller's event loop, against a daemon that (measured) can hang rather than refuse. The plain constructor is unchanged and still declares nothing, so nothing that builds one today has to move.

**A `linux` daemon declares `POSIX`. Every other answer declares `frozenset()`, and `windows` is not a translation waiting to be written.** This backend's `exec` is `sh -c`, its removals are `rm -rf`, its guest paths go through `posixpath` against a `/` root, and core's `maf_sandbox.paths` refuses a backslash outright — so `OsFamily.WINDOWS` would be a guarantee no code path here backs, and reading one off a daemon would move the failure from the guest's first command to the router's certificate. A daemon that will not answer declares nothing for the reason a guess would be worse than silence: `frozenset()` refuses only a spec that names a family, which is what this backend did before it asked at all.

**The declaration is a snapshot, so a cold acquire re-asks.** The client resolves `DOCKER_HOST` and the active docker context on *every* invocation, and switching Docker Desktop to Windows containers moves the engine under a running host. The router matched the old answer at attach and cannot ask again, so `acquire` re-reads the daemon before it starts a container — ahead of the create, ahead of the restart and ahead of the egress scaffolding, so a refusal leaves nothing to dispose — and raises `SandboxOsFamilyNotSupported` when it changed. A backend that declared nothing asks nothing, and a daemon unreachable *now* is served: the acquire is about to fail on its own terms, and refusing on a transient would take a working deployment off the air.

**A restart is gated exactly like a create, and the reason is not symmetry.** `_restart` removes a container that will not start and falls through to a create, so a check asking *"does no container exist?"* would let that create through unchecked — and a restart that does succeed hands out a container from whichever daemon is answering now, which is the same claim a create makes. **A *running* container is the stated residual:** it is served without a round trip, because re-asking there would put one in front of every tool call, which is the path this backend exists to keep cheap. Reaching it takes a switch to an engine that is already running a container under the same derived name.

## The pull surface: one tar, read twice

**The supported file surface is the container's rootfs.** `work_dir` and declared outputs must remain on that filesystem. `docker cp` does not observe the running guest's mount namespace: a file the guest reads under tmpfs can receive the engine's ordinary absence message, so neither `stat_file` returning `None` nor `collect_outputs` reporting no output proves absence there. `/proc`, `/sys`, `/dev` and other unsupported mounts are outside this contract ([Docker's copy limitations](https://docs.docker.com/reference/cli/docker/container/cp/#corner-cases)). The backend adds no volume, mount or tmpfs flags in either network mode; it does not inspect or refuse every mount an image or guest might introduce. Supporting mounted output storage requires a pull mechanism that sees the same filesystem as the workload, or an explicit refusal of the affected work directory. The creation test pins the absence of mount flags, not the visibility of arbitrary mounted paths.

Stat and read are the **same `docker cp <name>:<path> -` tar stream**, which works against an image with no shell at all — the property that makes a file surface possible on a minimal image. `stat_file` reads the entry header, following PAX or GNU extended metadata when present. Ordinary names still cost one 512-byte block. Extended metadata is limited to a 64 KiB prefix and 32 headers; a copy that stops inside that prefix is retried with a larger bounded read under the same command deadline. Each copy is parsed independently, and stat stops before the file body. `read_file` uses the same parser, allowing at most `max_bytes` beyond the metadata, and rejects files whose declared size exceeds that cap or whose body is incomplete. Malformed metadata, oversized metadata and sparse encodings raise rather than being classified as an ordinary file. The child is killed and reaped rather than drained. A non-regular entry is refused twice independently — on the stat's entry kind, and again on the tar entry's type bit, since `docker cp` without `-L` tars a symlink as a link *entry* rather than the target's bytes. A hard link stays `EntryKind.OTHER`: it names an inode rather than a path, so it is no way out of the working directory, and it is refused as non-regular regardless. Every parent is classified first, from the filesystem root down, through the shared `refuse_symlinked_ancestors` check over this backend's own unconfined stat — one bounded metadata read per component. The residual that the check cannot close is stated rather than papered over: a guest that turns a stat-ed component into a link between the check and the read wins, since `docker cp` has no no-follow form.

**Absence is a verdict the engine has to reach, not what is left when a copy fails.** A failed `docker cp` reads as "the path is not there" only where the daemon said so about *that* path — `Could not find the file <path> in container <name>`, which sets the path off with spaces, so it is matched whole rather than as a substring of the message. Every other failure raises. That distinction is load-bearing because absence is what **ends** the component check — there is nothing below a component that is not there — and the words get borrowed by failures that name no path at all: a container removed from under the sandbox answers `No such container: <name>`, and an unreachable daemon can carry `no such file or directory` up from its socket. Read either as absence and the check ends over ancestors nobody classified, while the read half reports a transport failure to a kind as `FileNotFoundError` — the workload told it produced no output, rather than the caller told the read failed.

The tar header is the settled mechanism by maintainer ruling, in preference to `HEAD /containers/{id}/archive` and its `X-Docker-Container-Path-Stat`: the header carries the same daemon-provided answer one layer down, and it keeps the driver at zero dependencies where the HTTP endpoint would reintroduce exactly the socket and context handling the CLI-driver choice exists to avoid. The one field the header lacks is modification time, and nothing needs it yet.

## `FILES_IN`: guest ownership does not bound placement authority

`write_file` checks the path before sending a tar to `docker cp - <name>:/`. Extraction resolves parents with the daemon's root authority: a guest that swaps a checked parent for a symlink between those calls can land a file in a directory the guest program could not write. A symlinked final component is replaced rather than followed. The uid/gid stamp controls ownership of the landed entries, not the authority that places them, so the write direction of the check-then-act window remains outside the reach bound.

The REACH write probe reads what the write left behind: a file the guest can rewrite and a directory it can unlink that file from. Passing is necessary, not sufficient to establish placement authority. The probe measures the result of placement and does not exercise a concurrent parent swap. `FILES_IN` retains the tar plane so file transfer needs no shell or other guest-side writing utility; the residual is stated beside the declaration and in `write_file`'s docstring. Closing the window remains [#456](https://github.com/sokolaidev/maf-extensions/issues/456).

## No `FILES_LIST`, and that gap is why the split exists

Docker has **no engine-level primitive for enumerating a directory**. A *named* path can be statted and copied against an image with no shell; discovering what names exist would need either an in-container `ls`/`find`, which depends on the image having one while the copy path does not, or tarring a whole directory to read its entry headers, which transfers every byte a size cap exists to refuse. That is the backend the capability split was named for — *name the backend that lacks it; if none does, it is a comment, not a capability* — so a kind requiring `FILES_LIST` is refused here, which is the match doing its job rather than a defect. `list_dir` raises `NotImplementedError` with that reason: the router refuses such a spec before a workload runs, so the raise is the honest floor under a caller that skipped the check. See [`../capabilities.md`](../capabilities.md).

## `FILES_DELETE` is declared, over `rm`

`remove` runs `rm -f` — or `rm -rf` when `recursive` — after confining the path and checking its ancestors, because the engine has no delete primitive. `rm`'s exit codes are the contract rather than a re-implementation of it: `-f` makes a missing path succeed and refuses a directory without `-r`. The image dependency is the one the `EXEC` declaration already names, so nothing new is being assumed. The working directory itself is refused before the subprocess is built.

## Measuring a confinement claim

`maf_sandbox_docker.conformance.DockerFingerprintSubject` implements the shared `FingerprintSubject` seam. The host supplies a trusted local Python 3.12+ observer image; the subject pins its engine image ID before use. It measures one acquired, quiescent Linux container before a kind's call and after its cleanup. A nonempty initial `docker diff` or populated tmpfs refuses the probe before the callback runs. A non-Linux engine returns an unsupported result; core treats paths and process identities as opaque strings and imposes no POSIX assumptions on other backend subjects.

`docker diff` answers for rootfs changes. Mounted storage is read by a separate observer container sharing the workload's PID namespace, through `/proc/1/root` and kernel mount metadata. This replaces the proposal's `docker cp /dev/shm` approach: that copy reads the rootfs and misses tmpfs contents. The observer measures implicit `/dev` and `/dev/shm`, host-added `--tmpfs`, and engine-mounted regular files such as `/etc/hosts`. Declared writable mounts are refused from `docker inspect`; other writable directory mounts outside tmpfs are refused by the observer. It reads symlinks as entries, never follows workload-controlled path components, and never opens devices, FIFOs, or sockets for content. A changed mount inventory or container replacement fails. Kernel process IDs paired with start ticks distinguish surviving and replaced processes, without interpreting host-mapped UIDs on rootless engines.

The observer runs its own Python with isolated imports, a read-only filesystem, no network, no workload executable, and only `SYS_PTRACE` above an empty capability set. That capability permits the kernel namespace read; it is given to the observer, not the workload. The host must trust the observer image as it trusts its Docker client. The helper removes the observer after success, failure, timeout, and cancellation; workload disposal remains the test owner's responsibility. Byte and entry limits bound the storage read, and reaching a limit fails rather than returning a partial fingerprint. Shared PID namespaces and privileged workload containers are refused.

This is a conformance measurement, not a production file API or a proof against concurrent tampering. The workload must be quiescent at each measurement. Kernel state and open sockets are outside the claim. Mounted-entry fingerprints compare SHA-256 hashes of regular-file contents, symlink targets, device/inode identity, mode, ownership, link count, size, and nanosecond modification/change times. Access time is excluded because the observer can change it by reading. For Docker-managed regular-file mounts at `/etc/hostname`, `/etc/hosts`, and `/etc/resolv.conf`, the before/after comparison also excludes change time: Docker's archive setup resets their ownership even when it already matches. The exception requires an inspected source under the measured container's ID, a matching kernel mount-root suffix, and no declared mount at or above the path; an unverified mount retains change time. Change time remains part of every during-read consistency check. A mounted file restored to identical contents and compared metadata is accepted, including restored permissions on these network files; this measures final state, not an absence of temporary changes. Rootfs paths that the engine reports changed remain changed even if their original bytes return.

## `reclaim` is the same `rm`, without the confinement duty

Docker declares `Capability.RECLAIM` over its acquire-time reach check and existing guest-authority fallback. A kind's confinement declaration makes that cleanup rung available; a kind declaring nothing still resolves to disposal. Guest file access is refused through `maf_sandbox.guest_access.refuse_capabilities_the_guest_cannot_back`, an OS-independent helper whose caller supplies an established access fact rather than a UID.

`reclaim` is a required method, and this backend implements it with `rm -rf` through `_removal`: as root when the acquire-time ancestor check permits raised authority, otherwise as the image's user. `-f` makes an already-gone directory a success, as the contract requires; other failures raise for the caller to report. The framework chooses the call directory, but the reach rule still bounds removal through ancestors the guest could swap. The conformance suite requires the `RECLAIM` declaration before planting. `FILES_DELETE` is a separate declaration for model-directed removal. [WSLC](wslc.md) refuses both removal methods; [ACAS](acas.md) implements reclamation through its data plane.

## Who each command runs as

**The file plane is the host's, and what it writes is the container user's.** `write_file`, `read_file`, `stat_file` and the filesystem path check under them are all `docker cp`, which the daemon performs with root's authority; the image's `USER` never enters into *which process* copies. What the copied files are **owned by** is a different question: `write_file`'s tar entries carry the uid and gid the image's `Config.User` names — read once per container at acquire and cached with the other facts. A `uid:gid` pair is taken as-is; a bare uid or a named user is resolved against the container's own `/etc/passwd` — and a named group half (`app:devs`) against `/etc/group` — read host-side over the same pull surface, because the primary gid comes from those files and is not the uid's to guess — a bare `0` no more implies gid `0` than `10001` implies `10001`. `id` inside the container answers last, only for what those files left open and only when the image carries it. If no source resolves the uid, `acquire` raises `SandboxCapabilityNotSupported` for a spec requiring `FILES_OUT` or `HOST_TOOLS`: a root-owned call directory cannot promise guest-written outputs or transport markers. An unreadable `Config.User` is unresolved too; an explicitly empty value establishes root. Other workloads retain root-owned inputs with a warning that the guest may be unable to modify or reclaim them; an exec whose result is stdout remains usable. Unresolved facts are not cached, so the next acquire retries. The container remains registered for retry or explicit disposal. Give the image a numeric `uid:gid`, readable account files, or an `id` it can run to enable the writing capabilities. Docker creates an implicit intermediate as root whatever the entry says, so every **missing** directory from `work_dir` down to the entry's parent is sent as an **explicit entry** stamped with the resolved user — an existing one is left alone, since an entry would re-stamp its mode, and an absent ancestor above `work_dir` is docker's to create as root — that is what makes a call directory one the guest can modify what it was given inside of, and empty when `reclaim` comes ([#680](https://github.com/sokolaidev/maf-extensions/issues/680)). In-guest files are not security controls: the shim runs where model-written code can edit it, and every gate that matters — resolution, declaration checks, call caps, response ceilings — is host-side in the supervisor.

**`remove` and `reclaim` have no engine primitive** — what separates them from `list_dir` is that they borrow `exec` instead of refusing — and they ask for `--user 0` when the protocol's **reach rule** allows it.

**`exec` and `run_code` are the guest program's own** and name no user, so the image decides. Root there would hand a model-written program authority over the whole container — every file root owns, not only the ones beside it. On an image that identifies its user, that program can already rewrite what the host put beside it: the transport shim it imports, the request and response files, the inputs it was given. That is by design rather than an accident — in-guest files are not security controls, and the gates that matter are host-side — so what root adds there is reach, not a boundary; keeping `exec` at the image's user costs nothing on these images and never grants reach a model-written program did not have.

**A refused removal is retried as the image's user where the container holds no `CAP_DAC_OVERRIDE`.** `--user 0` is a uid, not a capability set: with that capability root empties anything, so a refusal is never about ownership and a less privileged retry could only fail again over the error that mattered. Without it root empties only what it owns, and an image that gives `work_dir` to its own user — the same hardening advice that produced the non-root `USER` — leaves it unable to; that is exactly the shape *that user* can empty.

Which case a container is in is **read from the container**, not taken from `cap_drop_all`. `acquire` reuses a container by a name derived from scope, thread, agent dir, kind and egress and never from the hardening, so a running one can predate a change to the setting and the setting would then describe a different container. It is one `inspect` at acquire, beside the ancestor read and cached with it; unknown counts as dropped, which costs an extra `exec` on a removal that failed anyway where the other direction costs the leak. What it is *not* read from is `rm`'s message, which belongs to the guest's `rm` and its locale.

**The reach rule decides, and the check answers it.** `Sandbox.remove`'s contract holds the *reach* of a swap rather than the mechanism that bounds it: a guest that turns a stat-ed component into a symlink between the check and the `rm` redirects the removal, because `rm` unlinks its own operand but resolves every parent. So root is for paths with no component the guest could have swapped — every directory on them root's, and writable by nobody else — which is what a `docker cp` creates and what an image's build leaves unless it hands `work_dir` to the user it runs as. Which uid the guest has never enters into it: a directory root owns and nobody else may write is beyond every other principal, and where the guest *is* root there is no authority to raise. Where a component *is* the guest's, the removal runs as the guest, and loses nothing by it: a directory the guest can swap is one it can empty. The check's walk is the filesystem path check `remove` already owes, read with `/` itself added: swapping the topmost checked component needs write on the root, and the same tar header carries the owner and the mode.

**`reclaim` uses an acquire-time reach check.** It does not run `remove`'s model-input confinement check. Its safety argument covers two swappable parts of the path. The operand is one: `rm -rf` unlinks a symlink operand rather than resolving it, so a link planted at the call directory takes the removal nowhere (measured, and the case #584 asks a probe for). The parents are the other: `work_dir` and above, and swapping one needs write on *its* parent, which no image here hands out — the guest-owned image gives away `work_dir` itself, not `/maf-sandbox`.

**That last half is checked rather than asserted, at acquire.** The ancestors above `work_dir`, and `/` itself — the parent whose write is what swapping any of them takes — are fixed before any guest runs, so the backend reads them once per container — through the same `docker cp` header the check uses — and `reclaim` is handed the answer instead of a claim. An image that does grant write above `work_dir` — or on the root — gets its removals run as the guest, the way `remove` already handles the same shape. It costs one header read per container, cached on `(container, image, work_dir)` because a container name is a digest of scope, thread, agent dir, kind and egress and never of the image. The cache cannot go stale in the direction that matters — the answer changes only if something writes those directories, and the answer itself is that only root can. Unreadable fails closed.

**The price, stated plainly.** On such an image the removal runs as the guest, and since #680's write half landed that removal **succeeds for everything `write_file` created**: the call directory and everything under it carry the container's resolved user, so the guest can empty its own tree. The one exception is the unresolved-identity fallback from the section above — an image that names its user but answers no identity probe leaves the writes at root's `0:0`, and a guest-authority removal then cannot take them; that is the same shape #680 documented rather than fixed, and the reason the fallback is logged. What the check still buys is the boundary — a root removal a guest could redirect is never attempted. Measured, a swapped `work_dir` sends `rm -rf` to the named leaf under wherever the link points, and it deleted a file the guest could not have touched; that is the shape this refuses, and the reason is logged at acquire.

It keeps a floor as well: it refuses a relative path, and one within two components of the filesystem root — both subsets of what `reclaim_guest_path` already refuses before dispatching, so the two cannot disagree except by refusing more. Relative matters because the removal runs from `/`: `etc/ssh` from a caller that skipped the dispatcher would be `rm -rf /etc/ssh`.

## `run_code` answers by refusing

`run_code` is a `Sandbox` method, so this backend implements it — as a raise naming the backend and the reason. Not for want of an interpreter, since the image may well carry one, but because *which* runtime an image carries is a property of the image, and this backend hands an unparsed reference to `docker run`. Declaring `RUN_CODE` would be a claim about someone else's artefact. A workload that wants a runtime by name invokes it through `exec` and owns that assumption itself; the router refuses a spec requiring the capability before any caller arrives, so the `NotImplementedError` is the honest floor under a caller that skipped the check — the same shape `list_dir` already has.

## `HOST_TOOLS` on a live measurement

As on ACAS, `HOST_TOOLS` has no method behind it and asserts that **`exec` detaches** — a process started by one call outlives it and is observable from the next, because the container *is* the sandbox and it stays up between calls. `test_docker_e2e.py` measures it rather than assuming it. It is not a claim about the image.

## Egress topology

Closed mode is `--network none`: a network namespace with nothing but loopback, enforced by whichever kernel runs the container. Allowlist mode is an **internal network with an unaddressed bridge, plus a dual-homed CONNECT proxy** — an `--internal` network created with `gateway_mode_ipv4=isolated` and its IPv6 twin so nothing on it has a route off it, a proxy container on that network carrying the spec's allowlist, its outbound leg connected to a second network, and the workload created with `HTTP_PROXY`/`HTTPS_PROXY` pointing at it. The proxy is recreated on every acquire rather than adopted, so a stale or half-connected one is never mistaken for a working one, and a failure to connect the outbound leg fails the acquire — a proxy without it would turn `ALLOWLIST` into `CLOSED` silently. Recreating it is also what makes its *record* perishable: the `ALLOW`, `DENY`, `DENY-NONGLOBAL` and `UNREACHABLE` lines it prints would go with the container it printed them in. So this backend implements `ObservesEgress` and drains them first — before the removal in `_ensure_proxy`, and before every removal `_purge` makes for a disposal or a scope purge — which makes the record cover one acquire's window rather than a sandbox's whole life. A window with nothing to report emits nothing, so an absent record is not by itself a loss — but it is not proof of quiet either: the window a live proxy is accumulating is unreported until something removes it, and one this process cannot attribute is never reported at all. A purge drains what this process can attribute and no more: `EgressObserved` needs a key, a purge is addressed by a conversation, and a container another replica created — or one from before this process started — has no key here, so that last window goes with it. `observes_egress` says this backend reports the windows it can attribute, which is what it acquired: a sandbox another replica created, or one from before this process started, has no key here and its window goes unreported. It reads a bounded tail, in lines and in bytes, and says when the window may be short of it — conservatively, since a full page back cannot say whether the line past the bound was a decision; a proxy that is simply not there reports nothing, and a read that failed is reported as a window nobody can account for. Nothing is read at all until a router with an observer hands over a reporter. `egress_modes` states what the backend *can enforce*, not what one sandbox got: with a proxy image it declares both modes, and a spec running `CLOSED` still gets a `--network none` container, because denying everything for free beats burning a network and a proxy on allowing the same nothing. Without a proxy image the set is `{CLOSED}` alone, and a spec running `ALLOWLIST` is **refused at attach** rather than served the closed run it did not ask for. What the modes *mean*, and who declares what, is [`../network.md`](../network.md); this section is what this engine does to honour them.

**`--internal` alone is not the confinement; the unaddressed bridge is.** Docker assigns an address to the bridge device of an internal network, and [documents what follows](https://docs.docker.com/engine/network/port-publishing/#gateway-modes): processes on the Docker host reach the network, and containers on it reach host services listening on that bridge address — including one bound to `0.0.0.0`, which never passes the proxy and so is outside the allowlist entirely. `gateway_mode_ipv4=isolated` leaves the bridge with no address, which closes both directions at once and leaves the two paths the topology needs untouched: the proxy is a sibling on the same network, and the engine's embedded resolver still answers there. Both address families are set, since a daemon with IPv6 enabled would otherwise keep the v6 half addressed. This is where the backend's own requirement comes from: **the mode arrived in Docker Engine 28.0.0**, so an older daemon rejects the option and the acquire fails naming it, rather than serving the workload on an addressed bridge — refuse rather than degrade, applied to a topology rather than to a mode. The floor binds only a sandbox that builds a network, which is an `ALLOWLIST` spec with hosts on the list: `CLOSED` and an empty allowlist both resolve to `--network none` and run on any supported engine. **Every network an allowlisted acquire will use is read back, adopted or created.** `network create` compares nothing but the name, so an existing network is adopted whatever it is; and a create the engine accepted is not evidence of what it built, since an option a daemon does not act on is stored and reported back like one it applied. What is read is the **effect** — the driver, the internal flag, and whether IPAM gave the bridge an address — and never the options the network carries, which are the request echoed back and so cannot tell an unaddressed bridge from an addressed one. A network that is not an internal bridge, or whose bridge holds an address, or that cannot be read at all, is refused either way: an adopted one is replaced along with the sandbox on it, because the workload holds an endpoint and the network cannot be removed around it, while one this acquire has just built is removed with the refusal, before the proxy or the workload joins it.

What enforces the allowlist is the **topology**, not the environment variables: `HTTP_PROXY` and `HTTPS_PROXY` are advisory conventions a binary can ignore, but the workload sits on a network with no other route off it, so the proxy is not the polite way out — it is the only way out. No TLS is decrypted and no name is resolved inside the sandbox. Host-level `iptables` allowlisting is deliberately not part of the contract and cannot be made so: under rootless Docker the rules land in the wrong namespace, and on macOS and Windows the daemon lives in a VM the host firewall cannot address. The live controls that ship are the shared `assert_egress_conformance` pair against a real engine — an allowed host reachable, a denied one refused, the same two probes ACAS and wslc answer — plus one this backend adds because its deny is L3: a denied host reports `000`, curl's no-connection status, which says the tunnel was never opened rather than that a proxy answered. The engine's embedded DNS resolver forwards external lookups from the daemon, outside the container's namespace, and whether it still does so on a network created `--internal` is engine behaviour this repository has identified rather than closed — and no control measures it, here or in the shared pair. The proxy source is a **byte copy** of wslc's, pinned identical by a test rather than hoisted into core — the maintainer ruling that keeps operational content out of a stdlib-only package.

## Lifecycle

Names are **derived** from a digest of scope, thread, agent dir, kind and egress identity, so acquire and dispose agree without a registry; the kind is in the identity because a sandbox carries its spec's image and egress policy and must never serve two kinds, and the egress identity is in it because a sandbox is only reusable by an acquire that wants the same egress. Every acquire takes a per-`(loop, key, kind)` lock and lands in one of four states: reuse a running container, `start` a stopped one (removing and recreating it if it will not start), create an absent one, or **adopt on a name conflict** — the second line of defence for a race in another process that the lock cannot see. **Labels are the durable truth**: written at create, selected on at purge, with values passing through when short and safe and becoming a digest otherwise — never a truncation, because two scopes sharing a prefix would let one conversation's purge delete another's containers, and the mapping must be identical on both sides or the purge quietly selects nothing. `dispose_scope` sweeps the engine by label, removing containers, then their proxies, then their networks; the in-process registry is a fallback for when the listing fails, never the truth. Teardown never raises, and `dispose` returns the reason a workload container is still there — a proxy or network left behind is logged instead, since neither holds guest data. A timed-out `exec` **discards the sandbox** — killing the client does not reach the process inside the container and there is no per-command handle — while a *cancelled* call reaps only the host-side child and leaves the sandbox running.

`reap(older_than: timedelta, *, scope=None)` is the operator's cleanup for a host that is no longer alive to dispose its keys. It reads the engine's creation times and the four sandbox identity labels, restricted to this backend's naming scheme, across every scope unless the operator names one. It does not need the dead process's registry. The positive duration is the operator's explicit maximum-lifetime policy: it permits terminating active sandboxes older than that lifetime and does not prove abandonment. An expired workload takes its proxy and network with it, including newer infrastructure. Without a workload, the proxy's age decides; a network alone uses its own age. A workload exactly at the cutoff is retained; an orphan group applies the same strict comparison to the resource whose age decides. This API supplies no scheduler. [operations.md](../operations.md) defines deployment-owned cleanup and the reference ACAS deployment; that example's stopped-time policy is distinct from this API's maximum creation age. The [package README](../../../packages/maf-sandbox-docker/README.md#explicit-age-based-cleanup) carries the API and an operator inspection command.

The inventory includes stopped containers, proxies without a workload and networks without containers. Deletions use the inspected IDs, so reusing a name cannot redirect an old removal to the replacement, and network removal refuses attached endpoints. After inventory, each expired group's age anchor is rechecked by ID; a vanished anchor leaves the group untouched. An unreadable inventory or anchor authorizes no deletion. `DockerReapResult` reports separate workload, proxy and network counts and every removal failure. Proxies are removed first, and a failed or already-absent container removal leaves the rest of its group for a retry, preserving workload age when a younger proxy fails. Networks follow containers because attached endpoints prevent network deletion. Eligibility is recomputed on each sweep; a recently rebuilt network left alone after a failed removal uses its own age and may not yet qualify for a retry. A proxy this process can attribute is drained by ID first; a fresh process has no attribution, the same limit as a scope purge. Reaping is backend-specific operator authority and adds no method to `SandboxBackend`.

## The acceptance gate

`test_docker_e2e.py` runs against a **real engine on every pull request** — the only real-backend suite a PR can run, with no subscription, no login and no disk-image import. That is why the `FILES_OUT` rollout put this backend first: ACAS is the reference for shape, Docker decides whether the surface actually works. What the suite proves that no offline test can: that a tar written to `docker cp - <name>:/` creates the intermediate directories, and that the explicit entries it carries for them land under the image user rather than root; that an argv reaches the process without a shell and the exit code and stream split come back as the backend believes; that warm reuse, restart-after-stop and adopt-on-conflict behave against a real engine, which is where the acquire-race invariant actually lives; that `--network none` denies what it claims and the allowlist topology reaches an allowed host and fails a denied one, through the shared egress probe as well as this backend's own stricter `000` check; that the label filters return the containers a purge needs; and that a declared output stats and comes back byte-identical while an over-cap one and a symlinked one are refused.
