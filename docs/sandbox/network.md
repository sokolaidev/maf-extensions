# Network and egress

> The egress model — what a sandbox may reach, who declares it, and how each backend enforces it. Sources of record: [`research/sandbox-architecture.md`](research/sandbox-architecture.md), [`research/two-axis-sandbox-policy.md`](research/two-axis-sandbox-policy.md) and [`research/docker-backend-proposal.md`](research/docker-backend-proposal.md).

## Three parties, three different sentences

Egress is settled by three declarations that never merge, because they are made by parties with different knowledge. **The spec names hosts** — `SandboxSpec.egress_allow`, a tuple of hostnames stated positively, written by whoever built the kind and the deployment that configured it, who alone know what the workload has to fetch. **The backend declares what it can enforce** — an `Egress` member, a statement about mechanism and not about any particular spec, because a backend either has a way to allow one host and deny another or it does not. **The router refuses dishonesty** — before the tool is ever attached, it compares the two and raises `SandboxEgressNotEnforced` when the backend cannot hold the spec's line.

Keeping them apart is what makes `egress_allow` a contract rather than a comment. Before the axis existed, a spec could name four hosts, a backend could ignore the field entirely, and nothing anywhere would notice ([#34](https://github.com/sokolaidev/maf-extensions/issues/34), closed). The router's check is one of four it runs per spec and is owned by [`policy-isolation.md`](policy-isolation.md) — in one sentence: only `ALLOWLIST` and `CLOSED` pass, silence is refused as silence, and confining *more* than the spec asked is permitted with a warning while confining *less* is refused. What each declaration **means**, and what each backend actually does to honour it, is this document.

## The four declarations

`Egress` is declared by the backend and read off it with `getattr`, so a backend written before the property existed keeps loading — and is refused, which is the point.

| Member | What the backend is saying | Why it exists |
|---|---|---|
| `allowlist` | Deny by default, allow exactly the hosts a spec names | The only declaration that can honour a non-empty `egress_allow` as written |
| `closed` | All or nothing: it can deny everything, it cannot allow one host and not another | A real mechanism — a namespace with no route out — and an honest one. It confines *more* than an allowlisting spec asked, so it passes with a warning naming the hosts that will be unreachable |
| `unrestricted` | It cannot confine egress at all; whatever the host reaches, the sandbox reaches | Refused. A backend has to be able to *say* this, or the only way to be honest would be to say nothing |
| `undefined` | Nothing was declared — not a rung on the scale above | Refused, with a different sentence |

**The asymmetry between the first two and the last two is the whole design.** Confining less than the spec asks silently widens what the workload was built to reach, and nothing downstream can detect the widening; confining more only makes the workload fail, loudly, at whatever it could not fetch. One of those is a security failure and the other is a bug report, so only the first is refused.

**`UNDEFINED` is a fourth member rather than a re-use of `UNRESTRICTED`, and it changes only the wording of a refusal.** That is worth a member because the wording is the whole content: a backend that never declared has made no claim, and reporting it as `unrestricted` would put a claim in its mouth that its author never made — most likely because the author predates the property. The refusal says *"declares no egress at all"* where the other says *"declares `'unrestricted'` egress"*, and a maintainer reading the first goes to add a declaration while a maintainer reading the second goes to argue about a mechanism. A backend may also set `UNDEFINED` **deliberately**, to say the question is unanswered rather than answered badly — a backend mid-port, or one whose egress depends on deployment facts it has not read yet. Both paths are refused alike ([#521](https://github.com/sokolaidev/maf-extensions/pull/521), closing [#264](https://github.com/sokolaidev/maf-extensions/issues/264)).

## `egress_allow` — the spec's list, stated positively

`SandboxSpec.egress_allow` is a tuple of hostnames, and **everything not listed is denied**. Nothing is subtracted from an implicit whole; the list *is* the reachable world. So an empty tuple — the field's default — means no network at all, and **a spec that forgets to mention egress gets the closed configuration rather than the open one**. A deny-list would have inverted the failure mode of forgetfulness, which is the failure mode that actually happens.

**Core does not validate the entries.** The field is a tuple of strings and the protocol holds no opinion about their shape; the hostname rules live where a malformed entry would do damage. In the CodeAct kind an entry that is blank, or that holds whitespace or a comma, is refused outright — no hostname contains any of those, and each is a way for the spec, the tool description the model reads, and the backend's comma-joined allowlist to end up disagreeing about what was allowed, with a bare `str` passed instead of a sequence being the sharpest case: it becomes one single-character host per character, the real endpoint unreachable and no refusal anywhere.

**A kind's own needs and a deployment's are different halves of the same tuple, and the spec carries the union.** CodeAct fixes its half at empty — nothing in `execute_code` fetches — and fixes it in code rather than in configuration, because a deployment able to widen what the *kind itself* requires could undo the containment the kind's design rests on. `bicep_validate` fixes four hosts, the ones an AVM module restore reads, in the spec. What a deployment adds on top is a real widening of a sandbox running model-written code: every allowed host is a way out for anything the program can read, files shared into the run included.

**What the tuple cannot say** is worth naming, because both gaps are load-bearing. It cannot distinguish "this kind needs no network" from "this kind was never asked", so a deployment-wide default has nowhere to live ([#403](https://github.com/sokolaidev/maf-extensions/issues/403)). And it speaks hostnames only: method-scoped entries — allow `GET` and nothing else — exist in the field, and neither the spec nor any backend declaration can express one ([#377](https://github.com/sokolaidev/maf-extensions/issues/377)).

## `Capability.NETWORK` and `Egress` — the ask and the answer

They read as one subject and are two, on the same split as everywhere else in the protocol: **`Capability.NETWORK` is the workload's ask, `Egress` is the backend's answer, and `egress_allow` is the spec's list.** Its docstring is deliberately narrow — *"any egress at all — how precisely it is confined stays in `Egress`"* — so it never becomes a second, weaker way of saying `allowlist`.

**Today nothing uses it.** Repository-wide, `Capability.NETWORK` appears exactly once outside prose: its own definition at `packages/maf-sandbox/src/maf_sandbox/_protocol.py:167`. No spec requires it, no shipped backend declares it, and no test asserts on it; its only other mentions are a docstring comment in `samples/09_inprocess_bicep/no_isolation_backend.py:234` and the sample's README, both explaining why the member is *not* being used yet. That is a real cost rather than a harmless spare: because the ask cannot be expressed, `Egress` has to carry a refusal that is not its job — every workload is refused an `UNRESTRICTED` backend, including the ones that would never open a socket ([#406](https://github.com/sokolaidev/maf-extensions/issues/406)). The intended repair is to make the member matchable and let `UNRESTRICTED` serve a spec that does not require it ([#265](https://github.com/sokolaidev/maf-extensions/issues/265)); until then sample 09's no-boundary backend wears `CLOSED` to pass a gate it cannot enforce, and says so in a comment. Silence on `capabilities`, unlike silence on `Egress`, is read charitably — the reasoning is in [`capabilities.md`](capabilities.md).

## Enforcement, backend by backend

| Backend | Declares | Mechanism |
|---|---|---|
| ACAS ([`backends/acas.md`](backends/acas.md)) | `allowlist` | Service-level `EgressPolicy` at create: `default_action="Deny"`, full traffic inspection, one `Allow` host rule per entry **from the spec, not from configuration** |
| docker ([`backends/docker.md`](backends/docker.md)) | `closed`; `allowlist` when an `egress_proxy_image` is configured | `--network none`, or an internal network plus a dual-homed CONNECT proxy |
| wslc ([`backends/wslc.md`](backends/wslc.md)) | `closed`; `allowlist` when an `egress_proxy_image` is configured | The same topology, verb for verb — the proxy source is a copy held byte-identical by a test |
| `InProcessSandboxBackend` (`maf_sandbox.testing`) | `allowlist` by default, constructor-overridable | None. It is a declaration and nothing else |

**ACAS enforces above the guest, which is why the declaration costs the backend nothing to keep.** The policy is a create-time argument to the sandbox service and the guest never participates in it, so there is no in-guest component to bypass and no proxy for a workload to route around. The rule set is derived from `spec.egress_allow` on every create — a deployment cannot widen it from configuration, which is the property that makes the spec the source of truth rather than a request. One consequence of reuse is worth knowing: an ACAS sandbox's registry identity is `(scope, thread, agent_dir, kind)` and does **not** fold in the allowlist, so a warm sandbox keeps the policy of the spec that created it, where docker and wslc fold the allowlist into the sandbox's name and a changed one yields a different container.

**docker and wslc enforce by topology, and the distinction between topology and cooperation is the honest part.** Closed mode is `--network none`: a namespace with nothing but loopback, enforced by whichever kernel runs the container. Allowlist mode gives each sandbox its own `--internal` network — nothing on it has a route off it — plus a filtering proxy container attached to *two* networks, the internal one and an outbound one, which is the only path between them. `HTTP_PROXY` and `HTTPS_PROXY` are set on the workload, and they are **advisory**: conventions a well-behaved client reads, binding nothing on a binary that ignores them or on model-written code opening a raw socket. What enforces the allowlist is that there is no other way out. The proxy is recreated on every acquire rather than adopted, so it always carries the current spec's allowlist and always has its outbound leg; if that leg fails to connect the acquire fails, because a proxy without it would turn `ALLOWLIST` into `CLOSED` in silence.

**An allowlist of nothing is closed, even where a proxy is configured.** Both backends fold the effective egress into the sandbox's identity, so a spec allowing no hosts resolves to `--network none` rather than to a proxy that would permit the same nothing — one fewer moving part, and no network slot spent. The same fold means a changed allowlist produces a differently-named sandbox instead of a warm one running yesterday's policy.

**What the proxy buys, and what it does not.** It accepts `CONNECT` and nothing else, to a host matching the allowlist (exact or `*.` wildcard, case-insensitively) on an allowed port — 443 alone by default. It tunnels bytes without decrypting TLS, which means it cannot inspect a request and does not have to be trusted with anyone's plaintext; the cost is that its unit of policy is a host, never a path or a method. It resolves the target hostname **on the egress side**, so the sandbox never performs an external lookup and cannot use one as a side channel. And it refuses to complete a tunnel whose resolved peer is not a globally routable address: an allowlisted name that resolves into a private or link-local range — through a corporate DNS search suffix, say — is denied rather than dialled. That last rule is where an egress mechanism discharges an isolation obligation, and it is the reason to read the two documents together.

**The metadata blackhole is condition 2 of the micro-VM standard, enforced here.** That standard's condition 3 is confinable egress — `ALLOWLIST` or `CLOSED`, or the backend is capped below `microvm` outright — and its condition 2 is that no ambient identity or cloud metadata endpoint is reachable from the guest, satisfied *either* by construction (no network device at all) *or* by an enforced block of the link-local and metadata ranges. The non-global refusal above is that block. Both conditions are stated and adjudicated in [`policy-isolation.md`](policy-isolation.md); what belongs here is that they are met by egress machinery, so weakening the proxy's address rule would silently lower an isolation claim, not just a network one.

**Two limits sit outside the portable contract, and are stated rather than papered over.** Host-level firewall rules are not part of it and cannot be made so: under rootless Docker the rules land in the wrong namespace, and on macOS and Windows the daemon lives in a VM whose namespaces a host firewall cannot address at all — so every enforcement claim this family makes is a flag on a command line whose effect can be checked, and nothing else. And the container engine's embedded DNS resolver forwards external lookups from the daemon, outside the container's namespace; whether it still does so on a network created `--internal` is engine behaviour this repository has identified rather than closed, and it would be a low-bandwidth way out of a topology that by construction has no other. The live control that ships is a CONNECT pair — an allowed host reachable, a denied one refused — against a real engine.

**Nothing portable checks any of this.** Every shipped backend declares `ALLOWLIST` in at least one configuration; the enforcement has been observed for one of them, in that backend's own live tests, and there is no shared probe a backend author can run to demonstrate their allowlist works — with the positive and negative controls a network test needs to be worth anything ([#402](https://github.com/sokolaidev/maf-extensions/issues/402)). The declaration is checked for honesty against the spec; it is not checked against reality.

## Choosing a posture

**Closed is the default and needs no argument; every host on the list needs one.** A deployment that names nothing gets a sandbox with no route out, on every shipped backend, and pays nothing for it — no proxy image to build, no network to create, no resolver question to worry about. Each entry added is a decision that the workload cannot do its job otherwise, weighed against the fact that an allowed host is an exit for whatever the sandbox holds, and it is best made where the reason can be written down: a kind's fixed half in code beside the behaviour that needs it, a deployment's half in the configuration that knows the endpoint.

**A closed backend serving an allowlisting spec is a supported combination, not a misconfiguration.** It is the "confines more" direction, so it attaches and logs a `WARNING` naming the hosts that will be unreachable — expect the workload to report what it could not fetch. The warning is emitted by `ensure_can_serve` and deliberately not by `acquire`, which runs on every iteration of a warm fix-round loop and would turn one wiring fact into a log flood. That is the argument for calling `ensure_can_serve(spec)` once at startup as a host's wiring test: it is where this warning, and every refusal, arrives before a conversation is in flight.

## What egress does not bound

**An attached identity does not have to cross the network path to be exercised.** A platform connector or a sandbox-scoped credential reaches services through the platform's own plumbing, so a tight `egress_allow` is not a bound on what a workload's *authority* can touch. That axis is `Capability.ATTACHED_IDENTITY` and `Identity`, in [`hosts.md`](hosts.md).

**A dispatched host tool's body runs in the host process, not in the sandbox.** What it reaches is bounded by the host's own network position and by what the host registered, never by `egress_allow` — the guest asks, the host acts. That is `Capability.HOST_TOOLS` and the `Identity` axis, in [`hosts.md`](hosts.md).

**A landing sink moves bytes to host state with no network at all.** An output declared `LAND` leaves the sandbox through the backend's file transport and arrives in the host's store, which is a confidentiality flow that `egress_allow=()` says nothing about — the reason the outbound cap is a separate declaration. Also [`hosts.md`](hosts.md); the transport itself is in [`backends/README.md`](backends/README.md) and the surface in [`architecture.md`](architecture.md).
