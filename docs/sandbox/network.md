# Network and egress

> The egress model — the one mode a workload runs in, who declares what, and how each backend enforces it. Sources of record: [`research/egress-resolution.md`](research/egress-resolution.md), [`research/sandbox-architecture.md`](research/sandbox-architecture.md), [`research/two-axis-sandbox-policy.md`](research/two-axis-sandbox-policy.md) and [`research/docker-backend-proposal.md`](research/docker-backend-proposal.md).

## Three parties, and a router that resolves rather than reconciles

Egress is settled by three declarations that never merge, because they are made by parties with different knowledge.

**The workload declares the one mode it runs in.** `SandboxSpec.egress` is a single `Egress` member — `UNRESTRICTED`, `ALLOWLIST` or `CLOSED` — written by the deployment that builds the spec, which alone knows what this run is for and what it is wired to. `egress_allow` survives as the **payload** of an `ALLOWLIST` run: the hostnames, read in that mode and in no other.

**The kind guards the set of modes it will accept as an ask.** Not a field on the spec — a check in the tool factory, spent at construction. `bicep_sandbox_spec(egress=…)` refuses a member outside `_EGRESS_MODES`; CodeAct never takes the argument at all and derives the mode instead. By the time a spec reaches the router the kind has already had its say, which is why resolution below is one test and not two.

**The backend declares what it can enforce.** `egress_modes: frozenset[Egress]`, a field of its `BackendDeclarations`, and a statement about mechanism rather than about any particular spec: a backend either has a way to cut the network, or to allow one host and deny another, or it does not. It is a **set** because one backend can genuinely have two mechanisms — a Docker daemon with a proxy image configured can deliver `ALLOWLIST` or `CLOSED` and says so in one declaration.

**The router resolves.** Before the tool is ever attached, `ensure_can_serve` runs one membership test, and `acquire` runs it again so a caller who skipped the wiring test is refused all the same:

> Serve at `spec.egress` **iff** `spec.egress in backend.declarations.egress_modes`. Otherwise refuse, with `SandboxEgressNotEnforced` naming the mode asked and the set enforced.

> ### Refuse, never degrade.
> The router never substitutes a mode for the one asked. Not a **more open** one — that silently widens what the workload reaches, the exact failure the axis exists to prevent. Not a **more isolated** one — that hands the workload a quietly different network posture than it and its kind were built around, and calls a half-run a success. There is no best-effort: a backend is never handed a mode it cannot deliver.

**The confines-more-with-a-warning path is gone, and it is worth saying why.** Until 0.19 a `CLOSED` backend served an allowlisting spec, attached, and logged a `WARNING` naming the hosts that would be unreachable, on the argument that confining more only makes a workload fail loudly. The argument is half right and the half it misses is the expensive one: what was actually served was a *different posture than the one asked for*, reported as a success, with the difference recoverable only from a log line nobody reads until an incident. A workload built around four reachable hosts and run with none of them does not fail loudly — it fails somewhere inside a template restore, in a traceback the deployment has to reconstruct. Refusing at attach costs one clear sentence at wiring time and buys the property that a served run is the run that was asked for. Nothing on the serve path emits a warning any more; every outcome is served-exactly or refused.

Keeping the three declarations apart is what makes egress a contract rather than a comment. Before the axis existed, a spec could name four hosts, a backend could ignore the field entirely, and nothing anywhere would notice ([#34](https://github.com/sokolaidev/maf-extensions/issues/34), closed). This check is one of five the router runs per spec, and the sequence is owned by [`policy-isolation.md`](policy-isolation.md); what each declaration **means**, and what each backend actually does to honour it, is this document.

## The axis — three modes, ordered by isolation

```
UNRESTRICTED  <  ALLOWLIST  <  CLOSED
(reach anything)  (named hosts)  (no network)
```

| Member | What it says | Where it is the right answer |
|---|---|---|
| `UNRESTRICTED` | No confinement: whatever the host reaches, the sandbox reaches | A backend with no boundary at all, serving a workload that has explicitly accepted that — a fixed compiler on a developer's machine, never model-written code |
| `ALLOWLIST` | Deny by default, allow exactly the hosts `egress_allow` names | The designed posture of any workload that has to fetch something: a module restore, a package feed, one audience's endpoint |
| `CLOSED` | No network at all. **The most isolated, and the default** | Everything else, including every spec that says nothing |

**`CLOSED` is the default because forgetfulness has a direction.** A spec that never mentions egress gets no network rather than an open one, which is the same fail-closed instinct `egress_allow`'s empty tuple already carried, moved onto the field that now decides the posture.

**The order is prose, not data — deliberately.** `Isolation` ships `ISOLATION_RANK`, a `Mapping` with an exhaustiveness test, because a floor is a *comparison*: the router has to know whether a declared rung is at or above a required one. Egress needs no such thing, because refuse-never-degrade means nothing is ever ranked against anything — the resolution is a membership test, and the ordering above exists to explain the axis to a reader rather than to be evaluated. The moment something wants to compare two modes, that ordering becomes data with a test, per this package's rule that orderings are data before anything ranks by them.

**`UNDEFINED` is gone, and its instinct is intact.** A fourth member used to exist so a backend that had declared nothing was refused *as silent* rather than reported as claiming `unrestricted` — a claim its author never made. That reading survives in a cleaner form: silence is now the **empty set**. A backend leaving the field unstated — or declaring no `BackendDeclarations` at all — is read as `frozenset()`, enforces nothing, and is refused every ask, including `CLOSED`, with the message ending *"it enforces nothing"*. Same verdict, same facts, one member fewer, and it generalises: a backend can now say "I enforce exactly one of these" instead of having to pick a single label that flattens what it does. The `UNDEFINED` rule was one release old when the resolution replaced it ([#521](https://github.com/sokolaidev/maf-extensions/pull/521) shipped in `maf-sandbox` 0.19.0; [#534](https://github.com/sokolaidev/maf-extensions/pull/534) removed the member) — a short life, and the tracker below says so rather than quietly dropping the row.

**A backend outside this repository may declare plain strings.** `Egress` is a `StrEnum`, so `BackendDeclarations(egress_modes=frozenset({"closed"}))` matches a `CLOSED` spec exactly as the member would. That is a property of the vocabulary rather than a leniency in the router, and it is pinned by a test.

## What a kind accepts, and why the two that ship differ

The kind's set is the footgun guard, and it lives at construction because that is where a deployment's argument is written and where a refusal can name the line that caused it.

**Bicep accepts all three, and names hosts a template *may* restore from.** `_EGRESS_MODES = {UNRESTRICTED, ALLOWLIST, CLOSED}`, with the factory defaulting to `ALLOWLIST` — its designed posture, restoring AVM modules from four fixed hosts (`mcr.microsoft.com`, `*.data.mcr.microsoft.com`, `aka.ms`, `live-data.bicep.azure.com`). A deployment that will not use modules lowers to `CLOSED`; one running on a backend that cannot confine at all raises to `UNRESTRICTED`. **Only the mode is the deployment's to choose — the hosts stay the kind's**, so egress can be lowered, raised or left alone, but never widened to somewhere Bicep has no business reaching.

That the same kind runs happily at `CLOSED` is exactly the case the old match refused. Naming hosts is not the same as requiring them: [`samples/05_docker_bicep`](../../samples/05_docker_bicep) compiles a module-free template on `--network none` and completes fully offline. Under a rule that matched a non-empty allowlist against a backend's single declaration, a working sample was a policy violation. Under resolution it is a spec that says `egress=CLOSED` and a backend that enforces `CLOSED`. If the *template* then references a module, the restore fails inside the sandbox and Bicep reports the shortfall — a template/posture mismatch surfaced loudly at run time, which is where it belongs.

**CodeAct accepts two and derives the mode, never `UNRESTRICTED`.** It runs model-written code, and model-written code that can reach *anything* is the exfiltration case an allowlist exists to prevent, so the open posture is not expressible: there is no argument to pass. The mode falls out of the allowlist union — a non-empty union runs `ALLOWLIST`, an empty one runs `CLOSED` — where the kind's own half is fixed at empty in code (nothing in `execute_code` fetches) and the deployment's half is whatever it named. Fixing the kind's half in code rather than configuration is the same instinct: a deployment able to widen what the *kind itself* requires could undo the containment the design rests on. Per-kind detail is in [`kinds/bicep.md`](kinds/bicep.md) and [`kinds/codeact.md`](kinds/codeact.md).

## `egress_allow` — the payload of an allowlist run, stated positively

`SandboxSpec.egress_allow` is a tuple of hostnames, and **everything not listed is denied**. Nothing is subtracted from an implicit whole; the list *is* the reachable world. A deny-list would have inverted the failure mode of forgetfulness, which is the failure mode that actually happens.

**A non-empty list requires `ALLOWLIST`, checked where it is written.** `SandboxSpec.__post_init__` raises when hosts are named under any other mode, naming them: a host list is the payload of an allowlisting run and has no meaning without one. Naming four hosts and running with no network is incoherent rather than resolvable, so it is refused at construction rather than reconciled later into a surprise — and the two halves cannot drift, because they cannot coexist.

**Core does not validate the entries.** The field is a tuple of strings and the protocol holds no opinion about their shape; the hostname rules live where a malformed entry would do damage. In the CodeAct kind an entry that is blank, or that holds whitespace or a comma, is refused outright — no hostname contains any of those, and each is a way for the spec, the tool description the model reads, and the backend's comma-joined allowlist to end up disagreeing about what was allowed. The sharpest case is a bare `str` passed instead of a sequence: it becomes one single-character host per character, the real endpoint unreachable and no refusal anywhere, so it is refused by type.

**A kind's own needs and a deployment's are different halves of the same tuple, and the spec carries the union**, because the union is what the backend enforces and what decides whether the tool is declared as carrying something out. Every host a deployment adds to a sandbox running model-written code is a real widening: an allowed host is a way out for anything the program can read, files shared into the run included. And a host that two conversations both list is a channel *between* them, not only out of each. The key separates sandboxes; it does not reach a host that stores what one guest sends and answers it to the next — a wiki, a package index, an artifact store — and no hostname says whether the host behind it does. [`research/readable-host-as-a-scratchpad.md`](research/readable-host-as-a-scratchpad.md) reads two public incidents of exactly that against this axis.

**What the tuple still cannot say** is worth naming. The mode field answered half of one gap — every spec now states its posture explicitly, so "needs no network" and "was never asked" are no longer the same sentence — but a *deployment-wide default allowlist* that a kind inherits still has nowhere to live ([#403](https://github.com/sokolaidev/maf-extensions/issues/403)). And the tuple speaks hostnames only: method-scoped entries — allow `GET` and nothing else — exist in the field, and neither the spec nor any backend declaration can express one *today*. The shape that would is designed — [#377](https://github.com/sokolaidev/maf-extensions/issues/377), a refinement of this payload rather than a new mode — and is set out under [Method-scoped allow entries](#method-scoped-allow-entries--the-designed-refinement) below.

## `Capability.NETWORK`, and why there is no longer such a member

The enum used to carry `NETWORK`, on the reading that the workload's *ask* and the backend's *answer* were two sides of one subject. It was declared by no backend, required by no kind and read nowhere in the router, and the reason it stayed empty is the reason it is gone: **the question it asked is not a fixed property of a kind.** Whether a Bicep validation needs the network depends on the template it is handed, which is a per-deployment and per-run fact, not a capability a factory could stamp on a spec. Wiring it up would have forced a yes/no where the honest answer is a mode.

That question now has a place to live — `spec.egress`, chosen per deployment inside the set its kind accepts — so the member was removed rather than given a reader ([#406](https://github.com/sokolaidev/maf-extensions/issues/406), closed as superseded; [#534](https://github.com/sokolaidev/maf-extensions/pull/534)). The physical-versus-precision split it argued for is real and is preserved one level up: the isolation ladder answers *is the boundary real*, and the egress mode answers *what is it set to*. Silence on `capabilities` is still read charitably, unlike silence on egress — the reasoning is in [`capabilities.md`](capabilities.md).

## Enforcement, backend by backend

| Backend | Enforces (`egress_modes`) | Mechanism |
|---|---|---|
| ACAS ([`backends/acas.md`](backends/acas.md)) | `{ALLOWLIST, CLOSED}` | Service-level `EgressPolicy` at create: `default_action="Deny"`, full traffic inspection, one `Allow` host rule per entry **from the spec, not from configuration**. A `CLOSED` run carries no entries, so the deny-default is the whole policy |
| docker ([`backends/docker.md`](backends/docker.md)) | `{CLOSED}`; `{ALLOWLIST, CLOSED}` when an `egress_proxy_image` is configured | `--network none`, or an internal network whose bridge holds no host address plus a dual-homed CONNECT proxy |
| wslc ([`backends/wslc.md`](backends/wslc.md)) | The same two shapes, from the same config field | `--network none`, or an internal network plus a dual-homed CONNECT proxy — the original, which docker's is a byte copy of, held identical by a test. It passes no bridge-mode options, and needs none for the guest's half: its bridges carry no host address either way, measured on 2.9.4 |
| `InProcessSandboxBackend` ([`backends/in-process.md`](backends/in-process.md)) | `{ALLOWLIST, CLOSED}` by default, constructor-overridable | None. It is a declaration and nothing else — the default is what lets an offline test attach as it would against a proxy-capable backend, and a test of the refusal passes a narrower set |
| Sample 09's no-isolation backend (`samples/09_inprocess_bicep/no_isolation_backend.py`) | `{UNRESTRICTED}` | None, and that is the declaration. It runs the Bicep CLI on the host, so open is the one mode it can honestly enforce |

**Neither container backend lists `UNRESTRICTED`, and that is a mechanism fact rather than a policy one.** Both always either cut the network or route it through a proxy, so neither can hand a workload the host's own reach even if asked. ACAS likewise: the group's policy denies by default and cannot be told to allow everything.

**Sample 09 is the shape of the whole rule, which is why it ships as a sample.** Before resolution it declared `CLOSED` — a claim it could not enforce — to get past a gate that refused `UNRESTRICTED` for every workload, and its own source called that a temporary misuse. Now the backend claims only what it enforces, the workload states in one argument that it accepts no confinement, and the router invents no middle ground. The honest declaration is finally usable, and the sample runs on it ([#534](https://github.com/sokolaidev/maf-extensions/pull/534)). It is still reachable only by a host that has explicitly lowered `min_isolation` to `NONE` — the ladder gates whether a boundary is real, and it runs first.

**ACAS enforces above the guest, which is why the declaration costs the backend nothing to keep.** The policy is a create-time argument to the sandbox service and the guest never participates in it, so there is no in-guest component to bypass and no proxy for a workload to route around. The rule set is derived from `spec.egress_allow` on every create — a deployment cannot widen it from configuration, which is the property that makes the spec the source of truth rather than a request. One consequence of reuse is worth knowing: an ACAS sandbox's registry identity is `(scope, thread, agent_dir, kind)` and does **not** fold in the allowlist, so a warm sandbox keeps the policy of the spec that created it, where docker and wslc fold the allowlist into the sandbox's name and a changed one yields a different container.

**docker and wslc enforce by topology, and the distinction between topology and cooperation is the honest part.** A `CLOSED` run is `--network none`: a namespace with nothing but loopback, enforced by whichever kernel runs the container. An `ALLOWLIST` run gives each sandbox its own `--internal` network — and, on docker, one whose bridge is given no host address, because `--internal` on its own leaves the bridge holding one and that address is a route off the network in both directions ([#868](https://github.com/sokolaidev/maf-extensions/issues/868), the mechanism in [`backends/docker.md`](backends/docker.md)) — plus a filtering proxy container attached to *two* networks, the internal one and an outbound one, which is the only path between them. `HTTP_PROXY` and `HTTPS_PROXY` are set on the workload, and they are **advisory**: conventions a well-behaved client reads, binding nothing on a binary that ignores them or on model-written code opening a raw socket. What enforces the allowlist is that there is no other way out. The proxy is recreated on every acquire rather than adopted, so it always carries the current spec's allowlist and always has its outbound leg; if that leg fails to connect the acquire fails, because a proxy without it would confine a workload to nothing while reporting the mode it asked for.

**An allowlist of nothing runs on `--network none`, even where a proxy is configured.** Both backends fold the effective allowlist into the sandbox's identity, and an `ALLOWLIST` run that names no hosts reaches exactly what a closed one reaches — so it resolves to a namespace with no route out rather than to a proxy that would permit the same nothing. One fewer moving part, no network slot spent, and no posture difference to account for: the reachable set is identical either way. The same fold means a changed allowlist produces a differently-named sandbox instead of a warm one running yesterday's policy.

**What the proxy buys, and what it does not.** It accepts `CONNECT` and nothing else, to a host matching the allowlist (exact or `*.` wildcard, case-insensitively) on an allowed port — 443 alone by default. It tunnels bytes without decrypting TLS, which means it cannot inspect a request and does not have to be trusted with anyone's plaintext; the cost is that its unit of policy is a host, never a path or a method. It resolves the target hostname **on the egress side**, so the sandbox never performs an external lookup and cannot use one as a side channel. And it refuses to complete a tunnel whose resolved peer is not a globally routable address: an allowlisted name that resolves into a private or link-local range — through a corporate DNS search suffix, say — is denied rather than dialled. That last rule is where an egress mechanism discharges an isolation obligation, and it is the reason to read the two documents together.

**The metadata blackhole is condition 2 of the micro-VM standard, enforced here.** That standard's condition 3 is confinable egress — the backend enforces `ALLOWLIST` or `CLOSED`, not merely `UNRESTRICTED`, or it is capped below `microvm` outright — and its condition 2 is that no ambient identity or cloud metadata endpoint is reachable from the guest, satisfied *either* by construction (no network device at all) *or* by an enforced block of the link-local and metadata ranges. The non-global refusal above is that block. Both conditions are stated and adjudicated in [`policy-isolation.md`](policy-isolation.md); what belongs here is that they are met by egress machinery, so weakening the proxy's address rule would silently lower an isolation claim, not just a network one.

**Two limits sit outside the portable contract, and are stated rather than papered over.** Host-level firewall rules are not part of it and cannot be made so: under rootless Docker the rules land in the wrong namespace, and on macOS and Windows the daemon lives in a VM whose namespaces a host firewall cannot address at all — so every enforcement claim this family makes is a flag on a command line whose effect can be checked, and nothing else. And the container engine's embedded DNS resolver forwards external lookups from the daemon, outside the container's namespace; whether it still does so on a network created `--internal` is engine behaviour this repository has identified rather than closed, and it would be a low-bandwidth way out of a topology that by construction has no other. The live control that ships is a CONNECT pair — an allowed host reachable, a denied one refused — against a real engine.

**A portable probe checks this now, and resolution leans on it harder than the old rule did.** `maf_sandbox.conformance` carries the egress suite beside the capability ones: `run_egress_probes`, and `assert_egress_conformance` which raises on a failure. Both are handed the URL of a host on the spec's `egress_allow` and the URL of one off it — a spec's hosts are the deployment's, never the module's — and measure the pair with both of the controls a network test needs to be worth anything: `an-allowed-host-is-reachable`, so a backend confining more than it was asked to cannot pass by severing everything, and `a-denied-host-is-refused`, the security property the declaration stands for. The measurement is made **from inside the guest**, through the backend's own `Sandbox.exec`: `curl` prints the status of each request and only a completed 2xx counts as reached. That reads the outcome and never the mechanism, deliberately — a connection that cannot complete (`000`) and an L7 proxy's `403` are the same verdict, so an internal network with no route off it and ACAS's deny-default policy pass the same suite. A stronger, mechanism-specific property is that backend's own to assert, and the two shapes are not equally covered today: docker's severed tunnel **is** asserted — `curl` reports `000` and `test_docker_e2e.py` pins exactly that beside the shared probe, as `test_wslc_e2e.py` does for the same L3 topology — while ACAS's `x-deny-reason` is a header its proxy sends that **no test asserts**; the ACAS egress class defers it to [#377](https://github.com/sokolaidev/maf-extensions/issues/377), where method-scoped allow entries live, so it is a property named here rather than measured anywhere. `curl` is a requirement of the harness rather than of the protocol, the parallel to `ln` for the filesystem probes.

**Every backend's e2e suite calls it now** ([#548](https://github.com/sokolaidev/maf-extensions/pull/548)), so an egress declaration is measured against a live backend wherever that backend's e2e runs — and those legs are not equal. docker runs it on **every pull request**, in `tests.yml`'s `docker-e2e` job, which builds the allowlist proxy from the package's own shipped context before the suite starts; that is the leg a regression is caught by before it merges. wslc runs it **only where the backend runs at all** — Windows with a WSL that ships `wslc`, which no offered runner is — so that leg is a developer's to run and CI has never executed it. ACAS runs it **against the real service**: nightly in `conformance-live.yml`, on demand, and after a release that could change what it exercises, since every sandbox there is a billable Azure resource and this leg acquires one more. That last leg is what [#402](https://github.com/sokolaidev/maf-extensions/issues/402) is really about — until it, `ALLOWLIST` on the reference backend was backed by the policy object built before it was sent and by nothing that watched the service apply it. docker and wslc keep their own stronger assertion beside the shared one, since a severed tunnel and a proxy's `403` are one verdict to a probe that reads only the outcome. What a suite measures is still the backend rather than the run in front of a caller: the router refuses rather than best-efforts, and a served run inherits the evidence of the leg that last exercised its backend.

## Method-scoped allow entries — the designed refinement

An allowlist entry names a host and opens it to every method. A workload that should *read* an API and never *write* to it cannot say so, and the CONNECT proxy above is structurally why: a tunnel hides the method behind TLS, so its unit of policy is a host and can be nothing finer. The refinement that closes this is designed and waiting on a backend that can enforce it — [#377](https://github.com/sokolaidev/maf-extensions/issues/377) — and it changes the `ALLOWLIST` payload rather than adding a mode. The argument in full is [`research/egress-methods.md`](research/egress-methods.md); the decided shape is here.

**The shape.** `egress_allow` widens to `tuple[str | EgressRule, ...]`: a bare string stays "this host, all methods," and `EgressRule(host, methods)` narrows to named ones. `EgressRule` is a frozen dataclass — exported at package level beside `Egress`, since a deployment writes it — and a method is kept **exactly as the caller spelled it** — RFC 9110 makes a method a case-sensitive token and this design admits custom verbs, so `get` and `GET` are two distinct methods and neither is rewritten into the other. Each must be a valid HTTP token (the RFC 9110 `tchar` grammar, which rejects `GET/foo` and other malformed entries while admitting every real verb) with **no verb whitelist** (WebDAV and custom methods are real; whether a given verb is enforceable is the backend's concern); duplicates within one host's methods are compared case-sensitively, since distinct tokens are distinct methods; and `methods=()` is refused as incoherent. The footgun is documented rather than engineered away: a rule for `get` matches only a literal `get` request and every mainstream client sends `GET`, so a lowercase spelling of a standard verb is almost certainly a mistake the author owns — the enforcing proxy compares the wire token to the rule token and nothing more. `EgressRule(host, None)` stays constructible — it means all methods, and a caller building rules programmatically wants to name a host before it knows whether it will narrow it — but **the canonicalization is `SandboxSpec`'s, not the rule's**: a frozen dataclass's `__post_init__` returns the instance or raises and cannot hand back a `str`, so it is the spec that rewrites every such rule to the bare `host` string, in the same pass that collapses and conflicts the tuple. An all-methods entry is therefore string-equivalent by the time anything reads it, never forces the capability, and never reaches a backend as a rule object — which is what keeps a backend written before the axis reading plain strings. Hosts are schemeless by **convention** — nothing enforces it today, and a scheme-qualified entry is at best a silently dead allowlist entry on the shipped backends — so the kind's refusals grow a `://` check in the adoption wave, one contract for bare and rule hosts alike, while core keeps holding no opinion on host strings.

**One entry per host, reached by collapsing rather than refusing.** Hosts are compared **case-insensitively** — hostnames are, and the CONNECT proxy already matches that way, so case variants of one host cannot carry two method sets that a backend lowercasing the name would silently combine. Equivalent entries then **collapse**: duplicate bare strings, case variants of one bare string, and an `EgressRule(host, None)` that the same pass has just rewritten to a bare string, fold into a single all-methods entry (the first spelling survives, since core rewrites no host string) — which is what the tuple already means today: `("example.com", "example.com")` builds a valid spec now and keeps doing so, since a change whose claim is that it breaks nothing cannot start refusing specs that work. Method equivalence between two entries for one host is **set** equality over the tokens, case-sensitively — order is presentation, not policy — so two rules naming one set in two orders collapse too, the first entry's spelling and order surviving, and the comparison is well-defined because each rule's tuple is already duplicate-free. A `ValueError` fires only where the shapes genuinely conflict — two genuinely different sets — and only for shapes this design newly makes expressible: one host carrying two of them, or a bare string beside an `EgressRule` that narrows the same host. There which one wins is unanswerable, and refusing it breaks nothing that could be written before.

**What core validates, and what it does not.** `EgressRule.__post_init__` validates the **methods only**: the token grammar per entry, a non-empty tuple or `None`, and the case-sensitive duplicate check. `SandboxSpec`'s hosts-require-`ALLOWLIST` guard ([above](#egress_allow--the-payload-of-an-allowlist-run-stated-positively)) survives with its message rendering made union-aware — each entry named by its host, a rule's methods in parentheses after it — so a method-scoped entry under any other mode is still refused with the documented `ValueError`, never a `TypeError` from joining a rule as a string, and a test pins exactly that. The **host** keeps today's exact contract — core holds no opinion on host strings ([above](#egress_allow--the-payload-of-an-allowlist-run-stated-positively)), bare or inside a rule, and the kind-level rules stay where they are, unchanged, applying to a rule's host exactly as they do to a bare string today: a kind that refuses a blank, whitespace-bearing or comma-bearing host refuses it wherever it sits. Unchanged in *rule*, that is — it costs the kind a widening in *signature*, in its adoption pull request rather than the core release: CodeAct's factories type `egress_allow` as `Sequence[str]` and validate each entry by calling `.strip()` on it, so until they widen an `EgressRule` is refused inside the kind before a spec exists at all. They take `Sequence[str | EgressRule]` and grow one `isinstance` branch — bare strings on today's path, a rule's `.host` through the same blank/whitespace/comma refusals with the rule passed through whole — while the kind's own fixed half stays bare strings, all-methods being its designed posture. The chain behind the factories widens with them: `_effective_egress` and `_codeact_spec` carry `str | EgressRule` through to the spec, and `_tool_description` renders a rule's methods beside its host, so the model reads the narrowing as policy rather than a dataclass repr — tests ride the same adoption pull request. The union's dedup stays equality-based, so a deployment that narrows a host the kind's fixed half names bare sends both shapes into the spec, where core's conflict rule refuses them — the designed answer to narrowing what the kind itself requires, with no new kind code. Bicep needs nothing: its factory takes a mode and no hosts. The asymmetry between core and kind is deliberate — method grammar is vocabulary this design introduces, so core owns it; host grammar predates it and stays owned where it already was.

**A capability, not a fourth mode.** Method scope is not a new posture on the `UNRESTRICTED < ALLOWLIST < CLOSED` axis — it is a thing a backend *can do* to an allowlist, so it is a `Capability.EGRESS_METHODS`, opt-in and absent from `DEFAULT_CAPABILITIES`, and a declarer publishes beside it the tokens its mechanism can hold, as data: `egress_method_tokens: frozenset[str] | None` — `None` means every core-valid token, a finite set means exactly those spellings. A spec carrying any method-scoped entry **derives** the capability into its `requires` at construction, and the router's existing capability match refuses a backend that lacks it — the derivation means a kind that names methods cannot forget to require the enforcement. The match's site and order are unchanged, and it gains one qualification: when method-scoped rules survive the spec's rebuild, every rule token must be a member — case-sensitively — of the serving backend's declared set. That qualification is the fit check (below) run at the router, and because `ensure_can_serve` and `acquire` run the same checks, attach preflight and acquire refuse identically, by construction. The egress mode still resolves independently, so a `GET`-only spec is refused, never widened to the whole host. The *mode* thus stays a capability rather than a fourth bare backend declaration — but the token set is a new qualified declaration read, so the declaration surface grows by one, which is the collapse signal [`research/sandbox-architecture.md`](research/sandbox-architecture.md) names firing again; collapsing that surface stays its concern, not this axis's.

**Narrows, does not close — and the vocabulary says so.** `GET`-only drops the common write and upload verbs (`POST`, `PUT`, `PATCH`, `DELETE`), so the routine ways of pushing bytes out are gone; it does not shut the channel, because a `GET` still exfiltrates through the URL, the query string and the headers, and HTTP forbids a body on no method. The `EgressRule` docstring states this where a caller reads it, the methods stay literal HTTP verbs, and there is no `read_only=True` sugar to be misread as a control.

**Where it can be enforced, and where it cannot.** Only at an API boundary before TLS — Hyperlight's wasi-http surface, whose `allow_domain(target, methods)` enforces per host and method natively ([`research/hyperlight-backend-exploration.md`](research/hyperlight-backend-exploration.md)) — though not this vocabulary verbatim, measured against the current wheels: registration accepts any token, matching is case-normalized (rules `get`, `Get` and `GET` all admit a `GET` request), and a token outside its fixed verb set fails only at first `run()`, host-side, as a runtime error — or an L7 MITM proxy such as ACAS's, which already answers a denied host with `x-deny-reason: <host>:GET`. **A declarer therefore owns a fit check**: every method token in every rule must be one its mechanism can hold **as written**, and a rule the mechanism would rewrite or explode on is refused up front — never normalized, never deferred to a runtime error. Its mechanism is the declared token set the router reads (above), not backend-local code: a backend-local refusal at acquire would wave a core-valid token through `sandboxed_tool`'s attach preflight and fail it at first acquire — attach and acquire disagreeing about one spec — whereas the published set decides the verdict at the router, from data only the backend could know, and the two refuse identically. For Hyperlight the declared set is the uppercase spellings of its verb list, published by the adapter since registration refuses nothing, each exclusion for the mechanism's own reason: a lowercase token stays out because the mechanism would enforce its uppercase rewrite — a different rule than the author wrote — and a token outside the verb list because the mechanism's own answer is the late error the membership check exists to prevent; the refusal of `get` then falls out of membership, `get` not being in `{GET, ...}`. One wrinkle rides with it, stated rather than hidden: the wire comparison is case-insensitive too, so a `GET` rule there also admits a hypothetical lowercase `get` request — wider than the literal token by exactly the case axis, a mechanism fact for the adapter's own documentation like the CONNECT pair's method-blindness, and unobservable with mainstream clients — while the guest's whole request surface at this version is the injected `http_get`/`http_post`, so the scope bounds a surface that is already narrow. The docker and wslc CONNECT proxies cannot see the method and so will never declare the capability; that is a mechanism fact, honestly expressed as the capability's absence rather than a claim they cannot keep. **The axis lands in three steps — a compatibility wave, then a release between core and adoption — which is the repository's own law rather than a preference.** Every shipped reader of `egress_allow` types it as strings, and the gate runs each package's strict pyright on every pull request, so the widening alone would turn all four consumers red — runtime capability gating narrows nothing statically. So compatibility chores go first, one per consumer package, covering production readers and each package's tests alike — the strict gate types both: each read renders its entries through `str()`, which type-checks under today's tuple and the widened union alike and changes no behavior, since a non-declarer never receives a rule object at runtime; each shim is tightened or retired in that package's own adoption pull request. Core then lands — `EgressRule`, the capability, the `SandboxSpec` plumbing and the conformance probe, `maf_sandbox.conformance` code that carries its own method-issuing subject seam rather than the curl harness — its target answering 2xx to `GET` and `POST` both, the probe taking two pre-acquired subjects, one per policy, acquisition staying the wiring suite's: a reached `POST` on the all-methods control stands as the positive control for the scoped denial on the `GET`-only subject — with the refusal case asserted boot-free at the router seam, unit-tested against the testing fake and wired only by declarers' e2e suites — shipped in a `maf-sandbox` minor: a floor may only name a version that exists, and CI installs every built wheel into a clean environment to prove it ([`AGENTS.md`](../../AGENTS.md)). Adoption then follows as separate package-scoped pull requests behind that released floor — the Hyperlight adapter declaring the capability, reading the methods and raising its floor; CodeAct widening its factories and the chain behind them (above); each declaring backend's e2e suite wiring the probe as its own chore — because the same document's attribution law puts every shipped file under `packages/<name>/` on that package's changelog, and a cross-package pull request mis-announces in both. A package's own `tests/` is the exception and attributes to nobody, so a probe wired only there needs no chore of its own. Meanwhile the adapter serves host-wide entries under plain `ALLOWLIST`, so nothing is blocked. **The capability being unclaimed for that one release is precedent, not a hole:** `RUN_CODE` and `ATTACHED_IDENTITY` both entered the vocabulary with no backend declaring them and are still listed as *nobody* in [`capabilities.md`](capabilities.md), because the vocabulary is what makes an honest `cannot` sayable in the first place — and refuse-never-degrade covers the interval exactly, since a method-scoped spec is refused on every backend until one declares, which is the right answer to an ask nothing can enforce rather than a regression against anything that worked before. A backend that serves a method-scoped spec reads `str | EgressRule` from `egress_allow`; where the methods land is reuse identity, and it differs by backend. **docker and wslc** fold the allowlist into the sandbox name (above), so that fold must grow to include the methods, or a `GET`-only and an all-methods sandbox for one host collide into one warm container. **ACAS folds no allowlist at all** — its reuse key is `(scope, thread, agent_dir, kind)` and a warm sandbox keeps the policy of the spec that created it (above) — so method scope inherits that same hazard and needs the same full-policy fix, not a fold it does not have. **Hyperlight sits in the same class, and is named because it is the first declarer**: allowed domains are registered before its warm snapshot, and the planned adapter's cache identity is explicit `(key, kind)` plus tool names, no policy fold — so reacquiring the same `(key, kind)` under a different method rule restores the older, possibly broader, policy from the snapshot. The fix is the same — the canonical egress policy, methods included, joins the cache identity, or reuse runs a policy-mismatch replacement check, with changed-policy reuse covered in its adoption tests — and it matters most there, because a stale broader policy on the very backend that enforces methods would be the axis refuting itself.

## Choosing a posture

**`CLOSED` needs no argument; every host on the list needs one.** A deployment that says nothing gets a sandbox with no route out and pays nothing for it — no proxy image to build, no network to create, no resolver question to worry about. Each entry added is a decision that the workload cannot do its job otherwise, weighed against the fact that an allowed host is an exit for whatever the sandbox holds, and it is best made where the reason can be written down: a kind's fixed half in code beside the behaviour that needs it, a deployment's half in the configuration that knows the endpoint.

**Pick the mode to match the backend you wired, and prove it at startup.** `router.ensure_can_serve(spec)` is one line in a host's own suite and is where every refusal arrives before a conversation is in flight — an `ALLOWLIST` run against a proxy-less Docker daemon, a `CLOSED` run against a backend that cannot cut the network, a spec against a backend that declares nothing at all. There is no longer a warning to catch: an outcome is either the mode asked for, enforced, or an exception naming both sides. A deployment that finds itself refused has a real choice to make — wire the mechanism, or run the mode it can actually have and say so in the spec.

## What egress does not bound

**An attached identity does not have to cross the network path to be exercised.** A platform connector or a sandbox-scoped credential reaches services through the platform's own plumbing, so a tight `egress_allow` is not a bound on what a workload's *authority* can touch. That axis is `Capability.ATTACHED_IDENTITY` and `Identity`, in [`hosts.md`](hosts.md).

**A host-tool call's body runs in the host process, not in the sandbox.** What it reaches is bounded by the host's own network position and by what the host registered, never by the sandbox's mode — the guest asks, the host acts. That is `Capability.HOST_TOOLS` and the `Identity` axis, in [`hosts.md`](hosts.md).

**The axis is outbound, and a guest can still `listen`.** No mode stops a program binding a port — `CLOSED` included, where a guest binds freely on loopback and even takes port 80 under `--cap-drop ALL`. What a mode decides is whether anything can *reach* that port, and it decides it by what the guest is attached to rather than by any rule about binding: on `--network none` there is no interface to reach, and on an allowlisted network it turns on whether the bridge holds a host address, which is [#868](https://github.com/sokolaidev/maf-extensions/issues/868) above. There is no `ingress` member on the spec and no `INGRESS` capability, deliberately: every kind that ships wants the same answer, and the reach varies with the egress mode rather than being a posture a backend could declare once. A backend that wanted to *offer* inbound — a preview server, say — would be declaring a feature, and ACAS is the one with a mechanism for it, an Entra-authenticated `ports/add` this suite never calls. Two things follow that the mode does not cover. A listener **outlives the call that started it** wherever `HOST_TOOLS` is declared, since that capability asserts `exec` detaches, so a later call of the same conversation reaches it over loopback; `IsolationScope.CALL` is what ends it. And a guest that cannot be reached can still *publish an address* in its result and invite a host-side component to fetch it, which is the untrusted-result boundary in [`information-flow.md`](information-flow.md), not this axis.

**A landing sink moves bytes to host state with no network at all.** An output declared `LAND` leaves the sandbox through the backend's file transport and arrives in the host's store, which is a confidentiality flow that `egress=CLOSED` says nothing about — the reason the outbound cap is a separate declaration. Also [`hosts.md`](hosts.md); the transport itself is in [`backends/README.md`](backends/README.md) and the surface in [`architecture.md`](architecture.md).
