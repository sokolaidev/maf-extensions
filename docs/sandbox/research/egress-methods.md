# Method-scoped egress: a refinement of the allowlist payload, not a fourth mode

> The proposal that argued method scope (`GET`-only against a host) into the egress vocabulary — an `EgressRule` beside the plain hostname, a backend `Capability` that says whether it can enforce one, and a refusal that falls out of the capability match already in the router. Tracked by [#377](https://github.com/sokolaidev/maf-extensions/issues/377). It is kept in the tense it was written, as the record of the argument; the decided shape lives in [`../network.md`](../network.md). It builds on the resolved-mode model argued in [`egress-resolution.md`](egress-resolution.md) and is adopted, a release later, by the first API-boundary backend, explored in [`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md).

---

## The gap

`SandboxSpec.egress_allow` is a tuple of hostnames, and `Egress` says how precisely a backend confines — `UNRESTRICTED`, `ALLOWLIST`, `CLOSED`. Neither can say *which HTTP methods* an allowlisted host is reachable by. A workload that should read an API and never write to it — grant `GET` and nothing else — has no way to ask for that, and a backend that could enforce it has no way to say so.

The refinement already exists one layer down. hyperlight-sandbox's `allow_domain(target, methods)` restricts an allowlist entry to named methods, enforced natively at the wasmtime-wasi-http boundary (read for [#371](https://github.com/sokolaidev/maf-extensions/issues/371); [`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md)). So the mechanism is real and shipping in a guest we intend to adopt; what is missing is the vocabulary for a spec to request it and for the router to refuse a backend that cannot deliver it.

## Why it is worth having, stated without overselling

`GET`-only against an API host drops the common write and upload verbs — `POST`, `PUT`, `PATCH`, `DELETE` — from the channel, so the routine ways of pushing bytes out are gone. It **narrows** the sink; it does not **close** it. A `GET` still exfiltrates through the URL, the query string and the headers, and HTTP does not forbid a body on any method (a `GET` may carry one, even if servers rarely act on it), so even the request-content channel is narrowed rather than shut. So the honest claim is *narrowing*, and every place the axis surfaces has to say so, or `GET`-only will be read as no-exfiltration by the first host that wants it to mean that. This is the single framing constraint the whole design bends around: literal HTTP verbs, no `read_only=True` sugar, and a docstring that states the limit where a caller reads it.

## The sharp constraint: method scoping is only honest at an API boundary

A network-layer proxy cannot see the method of an HTTPS request. A `CONNECT` tunnel hides everything past the handshake — which is exactly why the docker and wslc proxies' allowlists are host-level and can never be anything else. Method enforcement is honest **only where the request crosses an API boundary before TLS**: wasi-http in the Hyperlight guest, an SDK-level egress shim, or a MITM proxy (its own trust decision, not an implementation detail — the ACAS L7 proxy already inspects far enough to answer a denied host with `x-deny-reason: <host>:GET`).

So most backends will honestly never enforce this. The axis is not a gap to close in every backend — it is a refinement few backends will ever claim, and its central requirement is that **cannot** be declarable and refusable, not silently ignored. A backend that drops the methods and serves the host wide has degraded a `GET`-only spec into an anything-goes one, reported as a success — the exact failure [`egress-resolution.md`](egress-resolution.md) exists to refuse.

## Reframing the issue's forks against the shipped model

[#377](https://github.com/sokolaidev/maf-extensions/issues/377) was filed against the *old* egress model — a single `Egress` declaration on an asymmetry scale, where the router refused a backend that confined less than the spec asked. The model that shipped is different: a workload runs **one** `Egress` mode, a backend declares `egress_modes` (the **set** of postures it enforces), and the router does membership — `spec.egress in backend.egress_modes`, refuse otherwise. Method scope is **not a new posture**; it is a refinement of the `ALLOWLIST` *payload* (`egress_allow`). That reframing moves two of the issue's four forks.

### Fork 1 — spec-side shape: widen the element type

`egress_allow` becomes `tuple[str | EgressRule, ...]`. A bare string stays exactly what it is today — "this host, all methods" — and `EgressRule(host, methods)` narrows to named methods. Additive: every existing `("mcr.microsoft.com",)` keeps working unchanged, one field still carries the whole allowlist, and it is the issue's own lean. A parallel `Mapping` field would split one concept across two that must be kept in sync; forcing every entry to be an `EgressRule` is breaking churn for no gain.

### Fork 2 — backend-side declaration: a `Capability`, not a fourth `Egress` member

The issue proposed a fourth `Egress` member above `ALLOWLIST`, ordered the way `Isolation` is. Under the set model that reads badly: it would split "allowlist" into two postures and force `egress_modes` to carry a mode that is really an allowlist with an annotation. The refinement is a thing a backend **can do** to an allowlist — which is what `Capability` is for.

So: a new opt-in **`Capability.EGRESS_METHODS`**, not in `DEFAULT_CAPABILITIES`. A backend that enforces method scope at an API boundary declares it; one that cannot simply does not — the honest `cannot`, expressed as the absence of a capability rather than a claim it has to make and get wrong. This also avoids the fourth-bare-`getattr`-declaration trigger [`sandbox-architecture.md`](sandbox-architecture.md) warns about (a new `enforces_egress_methods` flag would be exactly that), because a `Capability` rides an axis the protocol already has.

### Fork 3 — router: no new logic

Because the declaration is a `Capability`, the refusal is the one the router already runs. A spec with any method-scoped entry **derives** `Capability.EGRESS_METHODS` into its `requires` at construction, and the existing capability match refuses a backend that lacks it with `SandboxCapabilityNotSupported` — no new `getattr`, no new exception, no new router branch. The egress **mode** still resolves independently (`ALLOWLIST` ∈ `egress_modes`); both axes must pass, so refuse-never-degrade holds on each and a method-scoped spec is never silently served host-wide. The derivation is the "cannot forget" guard: a kind that names methods cannot also fail to require the capability, because it does not write `requires` for this by hand.

### Fork 4 — normalization: core owns the method grammar and nothing else

`EgressRule.__post_init__` validates the **methods only** — the token grammar below, a non-empty tuple or `None`, and the case-sensitive duplicate check. The **host** field keeps today's exact contract: core holds no opinion on host strings, bare or inside a rule, and the kind-level rules stay where they are, unchanged, applying to a rule's host exactly as they do to a bare string today — a kind that refuses a blank, whitespace-bearing or comma-bearing host refuses it wherever it sits. The asymmetry is deliberate: method grammar is vocabulary this design introduces, so core owns it; host grammar predates it and stays owned where it already was.

- **Casing** — the caller's spelling is preserved **verbatim**. RFC 9110 makes a method a case-sensitive token, and this design admits custom verbs, so `get` and `GET` are two distinct methods and uppercasing one into the other would rewrite the rule the caller wrote. Duplicate detection within one host's methods therefore compares **case-sensitively**: distinct tokens are distinct methods. The alternative offered — accept `get` but refuse it as a noncanonical spelling of a *known* method — is refused too, because deciding which spellings are noncanonical means knowing which verbs are standard, which is the verb whitelist this design does not have, smuggled in through the validator. The footgun is documented instead of engineered away: a rule for `get` matches only a literal `get` request, and every mainstream client sends `GET`, so a lowercase spelling of a standard verb is almost certainly a mistake the author owns — the enforcing proxy compares the wire token to the rule token, and does nothing more.
- **Token shape** — each method is a valid HTTP token, the RFC 9110 `tchar` grammar, which rejects whitespace and separators (`/`, `:`, `,`, and the rest) so a malformed entry like `GET/foo` or `GET:foo` is refused, while every real verb is a token and passes. There is still **no verb whitelist**: WebDAV and custom methods are real, and whether a *given* verb is enforceable is the backend's concern, not the vocabulary's. This validates the *grammar*, not membership in a list of known verbs — and it is the only string grammar core takes an opinion on here.
- **Empty methods** — `EgressRule(host, methods=())` is a `ValueError`. `methods=None` means *all* (the bare-string equivalent); a non-empty tuple means *these*; an empty tuple would mean "allow this host for no method at all," which is incoherent — drop the host instead.
- **Unscoped rules collapse to strings — in the spec, not in the rule.** `EgressRule(host, None)` is exactly a bare `host` (all methods), and `methods=None` stays a legal thing to construct: a caller building rules programmatically wants to name a host before it knows whether it will narrow it, and a frozen dataclass cannot hand back a `str` from its own constructor in any case — `__post_init__` returns the instance or raises, and nothing else. The rewrite is therefore **`SandboxSpec.__post_init__`'s**, in the pass it already makes over `egress_allow` to collapse equivalents and refuse conflicts: it rebuilds the tuple, and every `EgressRule(host, None)` it meets is written back as the bare `host` string, which then participates in that same collapse as the bare host it became. So the tuple a backend reads **never contains an all-methods rule object**, and a method annotation survives only where it actually narrows. That is what keeps the capability derivation exact — any `EgressRule` still present after the rebuild carries real methods, so an all-methods entry never forces `Capability.EGRESS_METHODS` — and it is what keeps a backend written before the axis reading plain strings.
- **Scheme** — entries stay **schemeless**, as they are today. No `http://`/`https://` in the vocabulary, so nothing a spec spelled precisely can be silently widened across schemes; per-scheme behaviour is a backend's own (hyperlight registers both forms for a bare host, which is its normalization to make, not ours).
- **Duplicate host — collapse equivalents, refuse conflicts.** Hosts are compared **case-insensitively**: hostnames are (the CONNECT proxy already matches its allowlist that way), so `Example.com` and `example.com` are one host and cannot carry two different method sets that a backend lowercasing the name would then silently combine. What that comparison *does* on a repeat is the part worth getting right. Refusing every repeat is not additive — `egress_allow=("example.com", "example.com")` builds a valid `SandboxSpec` today, and a blanket "one entry per host" rule would break specs that work now, on a change whose whole claim is that it breaks none. So equivalent entries **collapse**: duplicate bare strings, and case variants of one bare string, become a single all-methods entry, which is semantically what the tuple already means today (the first spelling survives, since core rewrites no host string). A `ValueError` fires only where the shapes genuinely **conflict**, and every conflicting shape is one this design newly makes expressible: one host carrying two different method sets, or a bare string beside an `EgressRule` for the same host where the rule narrows. There the ambiguity is real — which one wins is unanswerable — and refusing it is safe precisely because the shape could not be written before.

## What each layer changes

- **`SandboxSpec`** — `egress_allow` widens to `tuple[str | EgressRule, ...]`. `__post_init__` keeps the existing "a non-empty `egress_allow` requires `egress is ALLOWLIST`" guard and does its rebuilding pass over the tuple: it **rewrites every `EgressRule(host, None)` as the bare `host` string**, collapses entries that are equivalent for one host, refuses the ones that conflict, and **auto-adds `Capability.EGRESS_METHODS` to `requires`** when any surviving entry is method-scoped. The guard's message rendering becomes union-aware in the same change: today it `", ".join`s the entries, which a rule object would turn into a `TypeError` before the documented refusal ever formed, so each entry is named by its host — a rule's methods in parentheses after it — and the refusal still quotes what the caller wrote while the error path stays the documented `ValueError`, pinned by a test that a method-scoped rule under `CLOSED` or `UNRESTRICTED` raises `ValueError`, never `TypeError`. Canonicalization lives here rather than in the rule because this is the pass that already rebuilds the tuple, and because a frozen dataclass cannot canonicalize itself into a different type. This is the one place the model derives rather than validates, and it is safe because `requires` is an additive set.
- **`EgressRule`** — a new frozen dataclass in `_protocol.py`: `host: str`, `methods: tuple[str, ...] | None = None`. Its `__post_init__` validates the methods and nothing else, as above; the host carries the contract it carries today, and the rule rewrites nothing — not the host, not itself. Its docstring is where the narrowing-not-closing honesty lives. And it is public API, not a private shape: a deployment writes one and consumers import `maf_sandbox`, never `_protocol`, so the class exports at package level beside `Egress` and `Capability` — `_protocol.__all__`, the package `__all__`, and a row in `TestPolicyVocabularyExports` — as part of step 1's core work.
- **`Capability`** — a new `EGRESS_METHODS` member, opt-in, absent from `DEFAULT_CAPABILITIES`. Declared only by a backend that enforces method scope before TLS.
- **The router** — unchanged. The capability match it already runs is the whole refusal.
- **The kinds** — a deployment reaches this axis through a factory, and today the factory refuses a rule before a `SandboxSpec` is ever built. `codeact_sandbox_spec` and `make_codeact_tools` both type `egress_allow` as `Sequence[str]` (`_tool.py:155`, `_tool.py:222`), and `_validated_hosts` calls `entry.strip()` on every entry (`_tool.py:445`), which an `EgressRule` has no answer to. So the documented feature would be unusable through the repo's one deployment-configurable kind unless the kind widens too: the two factories take `Sequence[str | EgressRule]`, and `_validated_hosts` grows a single `isinstance` branch — a bare string takes today's path unchanged, and an `EgressRule`'s `.host` is checked by the same kind-local rules (blank, whitespace-bearing or comma-bearing refused) with the rule itself passed through intact. The widening runs the whole chain, not just its mouth: `_effective_egress` and `_codeact_spec` widen their signatures to carry `str | EgressRule` through to the spec, and `_tool_description` renders a rule method-aware — the model reads the narrowing as policy, the host with its methods named, never a dataclass repr — with tests part of the same adoption pull request. The kind's **own** half, `_KIND_EGRESS`, stays bare strings: all-methods is its designed posture, and fixing it in code is what stops a deployment widening what the kind itself requires. `_effective_egress`'s `dict.fromkeys` dedup stays equality-based, and the authority on collapse and conflict stays `SandboxSpec.__post_init__`'s pass: a deployment that passes a narrowing rule for a host `_KIND_EGRESS` already names bare sends both shapes through the union, and core's conflict rule refuses the spec — the designed answer to a deployment narrowing what the kind itself requires, arrived at with no new kind code. Bicep needs nothing — its factory takes a mode and no hosts at all. **This is adoption work and sequences with the adoption pull requests below, not with the core release.**
- **The backends** — a backend that serves a method-scoped spec (so, one declaring the capability) sees `str | EgressRule` in `egress_allow` and reads the methods; a backend that does not declare it is only ever handed plain hosts, because the spec's rebuild has already turned unscoped rules into strings and any `EgressRule` surviving it forces the capability. **Declaring also carries a fit check at acquire**: every method token in every rule must be one the backend's mechanism can hold **as written**, and a rule the mechanism would rewrite or explode on is refused up front — never normalized, never deferred to a runtime error. That is the concrete form of the sentence above — whether a given verb is enforceable is the backend's concern, not the vocabulary's — and it adds no declaration and no router branch: the router's capability match stays the router's whole refusal, declarer or not, and the fit check is the same verdict decided where the knowledge lives, backend-local like every mechanism fact. Where the methods have to land is **reuse identity**, and it differs by backend. **docker and wslc** both fold the allowlist into the sandbox name ([`../network.md`](../network.md) records both), so that fold must grow to include the methods, or a `GET`-only and an all-methods sandbox for one host collide into one warm container. **ACAS does not fold the allowlist at all** — its reuse key is `(scope, thread, agent_dir, kind)` and a warm sandbox keeps the policy of the spec that created it — so method scope inherits ACAS's existing changed-allowlist hazard and needs the same fix (a full-policy identity, or a replacement check on reuse), not a fold it does not have. None **declares** the capability today: the CONNECT-tunnel pair (docker, wslc) cannot see the method at all, ACAS's L7 proxy could in principle, and the first real declarer is Hyperlight — where the fit check earns its keep at once. Measured against the current wheels, `allow_domain(target, methods)` validates nothing at registration — any token registers — and the mechanism's real rules surface late: matching is case-normalized, so rules `get`, `Get` and `GET` all admit a `GET` request, and a token outside its fixed verb set explodes host-side at first `run()` (`RuntimeError: invalid HTTP method: PROPFIND`). Its enforceable set is therefore the uppercase spellings of that verb list, and the adapter carries that knowledge itself, since there is no registration-time refusal to lean on: a lowercase or mixed-case token is refused because the mechanism would enforce its uppercase rewrite — a different rule than the author wrote — and a token outside the set because the mechanism's own answer is the late runtime error the fit check exists to prevent. One wrinkle is stated rather than hidden: the wire comparison is case-insensitive too, so a `GET` rule there also admits a hypothetical lowercase `get` request — wider than the literal token by exactly the case axis, a mechanism fact for the adapter's own documentation the way the CONNECT pair's method-blindness is, and unobservable with mainstream clients; an author who needs the literal-case distinction is refused by the only declarer, which is the honest outcome. Also honest: the guest's entire request surface at this version is the injected `http_get`/`http_post` ([`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md)), so method scope there bounds a surface that is already narrow.
- **Conformance** — a method-scope probe (a `GET` reaches a `GET`-only host, a `POST` to it is refused), extending [#402](https://github.com/sokolaidev/maf-extensions/issues/402)'s outcome probe — and its refusal case: a rule the declarer cannot hold as written is refused at acquire, probed against any declarer, so an adapter that normalizes or defers to a runtime error fails the suite. The probe is `maf_sandbox.conformance` code, so it lands in step 1's core release — unit-tested against the testing fake, which can declare the capability, and dormant in the live suites until a declarer exists — the same way `run_egress_probes` landed in core before any backend wired it.

## Sequencing

Fully additive; nothing is blocked on it. The Hyperlight adapter serves host-wide entries under plain `ALLOWLIST` on day one and adopts the refinement when the axis lands — a `GET`-only spec is simply refused on it until then, which is the correct refuse-never-degrade behaviour, not a regression.

**It lands in two steps with a release between them, because the repository's dependency law leaves no other order.** [`AGENTS.md`](../../../AGENTS.md) is explicit: a dependency floor may only name a version that exists, and CI installs every built wheel into a clean environment to prove it, so a core addition a dependent imports has to be merged *and released* before the dependent can adopt it. A core wheel built from the same branch still carries its pre-release version, so "land them together" does not go green — it resolves against nothing. Hence:

1. **Core lands and releases.** `EgressRule`, `Capability.EGRESS_METHODS`, the `SandboxSpec` plumbing — the widened field, the canonicalizing rebuild, the collapse and conflict rules, the capability derivation — and the conformance probe above, exercised against the testing fake, go in on their own title and ship in a `maf-sandbox` minor.
2. **Adoption follows as separate package-scoped pull requests, behind the released floor.** One has the Hyperlight adapter declare `EGRESS_METHODS`, read the methods out of `egress_allow`, and raise its `maf-sandbox` floor to the release step 1 produced; one carries the CodeAct widening above — the factories and the chain behind them, tests included; and each backend e2e suite wires the probe in as its own `chore:`. The split is [`AGENTS.md`](../../../AGENTS.md)'s attribution law rather than caution — every file under `packages/<name>/` attributes to that package, so a cross-package pull request mis-announces in two changelogs at once. All are gated by the same released floor, and none touches a second package.

**So the capability is unclaimed for one release, and that is this repository's own precedent rather than a hole.** `RUN_CODE` and `ATTACHED_IDENTITY` both entered the vocabulary with no backend declaring them and are still listed as *nobody* in [`../capabilities.md`](../capabilities.md); a vocabulary is what makes an honest `cannot` sayable at all, and it has to exist before anyone can decline it. Refuse-never-degrade covers the interval exactly: for that one release a method-scoped spec is refused on **every** backend, because none declares the capability — the correct answer to an ask nothing can enforce, not a silent widening, not a regression against anything that worked before, and not a claim a backend has to make and get wrong. What must never ship unexercised is an *enforcement* claim; the vocabulary that lets a backend withhold one can.
