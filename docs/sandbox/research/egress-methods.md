# Method-scoped egress: a refinement of the allowlist payload, not a fourth mode

> The proposal that argued method scope (`GET`-only against a host) into the egress vocabulary — an `EgressRule` beside the plain hostname, a backend `Capability` that says whether it can enforce one, and a refusal that falls out of the capability match already in the router. Tracked by [#377](https://github.com/sokolaidev/maf-extensions/issues/377). It is kept in the tense it was written, as the record of the argument; the decided shape lives in [`../network.md`](../network.md). It builds on the resolved-mode model argued in [`egress-resolution.md`](egress-resolution.md) and is adopted, a release later, by the first API-boundary backend, explored in [`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md).

---

## The gap

`SandboxSpec.egress_allow` is a tuple of hostnames, and `Egress` says how precisely a backend confines — `UNRESTRICTED`, `ALLOWLIST`, `CLOSED`. Neither can say *which HTTP methods* an allowlisted host is reachable by. A workload that should read an API and never write to it — grant `GET` and nothing else — has no way to ask for that, and a backend that could enforce it has no way to say so.

The refinement already exists one layer down. hyperlight-sandbox's `allow_domain(target, methods)` restricts an allowlist entry to named methods, enforced natively at the wasmtime-wasi-http boundary (read for [#371](https://github.com/sokolaidev/maf-extensions/issues/371); [`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md)). So the mechanism is real and shipping in a guest we intend to adopt; what is missing is the vocabulary for a spec to request it and for the router to refuse a backend that cannot deliver it.

## Why it is worth having, stated without overselling

`GET`-only against an API host drops the common write and upload verbs — `POST`, `PUT`, `PATCH`, `DELETE` — from the channel, so the routine ways of pushing bytes out are gone. It **narrows** the sink; it does not **close** it. A `GET` still exfiltrates through the URL, the query string and the headers, and HTTP does not forbid a body on any method (a `GET` may carry one, even if servers rarely act on it), so even the request-content channel is narrowed rather than shut. So the honest claim is *narrowing*, and every place the axis surfaces has to say so, or `GET`-only will be read as no-exfiltration by the first host that wants it to mean that. This is the single framing constraint the whole design bends around: literal HTTP verbs, no `read_only=True` sugar, and a docstring that states the limit where a caller reads it.

## The sharp constraint: method scoping is only honest at an API boundary

A network-layer proxy cannot see the method of an HTTPS request. A `CONNECT` tunnel hides everything past the handshake — which is exactly why the docker and wslc proxies' allowlists are host-level and can never be anything else. Method enforcement is honest **only where the request crosses an API boundary before TLS**: wasi-http in the Hyperlight guest, an SDK-level egress shim, or a MITM proxy (its own trust decision, not an implementation detail — the ACAS L7 proxy already inspects far enough to answer a denied host with `x-deny-reason: <host>:GET`).

So most backends will honestly never enforce this. The axis is not a gap to close in every backend — it is a refinement few backends will ever claim, and its central requirement is that **cannot** be declarable and refusable, not silently ignored. A backend that drops the methods and serves the host wide has degraded a `GET`-only spec into an anything-goes one, reported as a success — the exact failure [`egress-resolution.md`](egress-resolution.md) exists to refuse.

## Reframing the issue's forks against the shipped model

[#377](https://github.com/sokolaidev/maf-extensions/issues/377) was filed against the *old* egress model — a single `Egress` declaration on an asymmetry scale, where the router refused a backend that confined less than the spec asked. The model that shipped is different: a workload runs **one** `Egress` mode, a backend declares `egress_modes` (the **set** of postures it enforces), and the router does membership — `spec.egress in backend.egress_modes`, refuse otherwise. Method scope is **not a new posture**; it is a refinement of the `ALLOWLIST` *payload* (`egress_allow`). That reframing moves two of the issue's four forks.

### Fork 1 — spec-side shape: widen the element type

`egress_allow` becomes `tuple[str | EgressRule, ...]`. A bare string stays exactly what it is today — "this host, all methods" — and `EgressRule(host, methods)` narrows to named methods. Additive: every existing `("mcr.microsoft.com",)` keeps working unchanged, one field still carries the whole allowlist, and it is the issue's own lean. A parallel `Mapping` field would split one concept across two that must be kept in sync; forcing every entry to be an `EgressRule` is breaking churn for no gain.

### Fork 2 — backend-side declaration: a `Capability`, not a fourth `Egress` member

The issue proposed a fourth `Egress` member above `ALLOWLIST`, ordered the way `Isolation` is. Under the set model that reads badly: it would split "allowlist" into two postures and force `egress_modes` to carry a mode that is really an allowlist with an annotation. The refinement is a thing a backend **can do** to an allowlist — which is what `Capability` is for.

So: a new opt-in **`Capability.EGRESS_METHODS`**, not in `DEFAULT_CAPABILITIES`. A backend that enforces method scope at an API boundary declares it; one that cannot simply does not — the honest `cannot`, expressed as the absence of a capability rather than a claim it has to make and get wrong. This also keeps the *mode* off the fourth-bare-`getattr`-declaration trigger [`sandbox-architecture.md`](sandbox-architecture.md) warns about (a new `enforces_egress_methods` flag would be exactly that), because a `Capability` rides an axis the protocol already has — though the axis grows the declaration surface elsewhere, by the enforceable-token set argued under the backends below.

### Fork 3 — router: the check it already runs

Because the declaration is a `Capability`, the refusal is the one the router already runs. A spec with any method-scoped entry **derives** `Capability.EGRESS_METHODS` into its `requires` at construction, and the existing capability match refuses a backend that lacks it with `SandboxCapabilityNotSupported` — no new exception, no new check site. That match gains exactly one qualification, argued under the backends below: where method-scoped rules survive, it also requires every rule token to be a member of the serving declarer's published token set, so the site and order of the router's checks never move. The egress **mode** still resolves independently (`ALLOWLIST` ∈ `egress_modes`); both axes must pass, so refuse-never-degrade holds on each and a method-scoped spec is never silently served host-wide. The derivation is the "cannot forget" guard: a kind that names methods cannot also fail to require the capability, because it does not write `requires` for this by hand.

### Fork 4 — normalization: core owns the method grammar and nothing else

`EgressRule.__post_init__` validates the **methods only** — the token grammar below, a non-empty tuple or `None`, and the case-sensitive duplicate check. The **host** field keeps today's exact contract: core holds no opinion on host strings, bare or inside a rule, and the kind-level rules stay where they are, unchanged, applying to a rule's host exactly as they do to a bare string today — a kind that refuses a blank, whitespace-bearing or comma-bearing host refuses it wherever it sits. The asymmetry is deliberate: method grammar is vocabulary this design introduces, so core owns it; host grammar predates it and stays owned where it already was.

- **Casing** — the caller's spelling is preserved **verbatim**. RFC 9110 makes a method a case-sensitive token, and this design admits custom verbs, so `get` and `GET` are two distinct methods and uppercasing one into the other would rewrite the rule the caller wrote. Duplicate detection within one host's methods therefore compares **case-sensitively**: distinct tokens are distinct methods. The alternative offered — accept `get` but refuse it as a noncanonical spelling of a *known* method — is refused too, because deciding which spellings are noncanonical means knowing which verbs are standard, which is the verb whitelist this design does not have, smuggled in through the validator. The footgun is documented instead of engineered away: a rule for `get` matches only a literal `get` request, and every mainstream client sends `GET`, so a lowercase spelling of a standard verb is almost certainly a mistake the author owns — the enforcing proxy compares the wire token to the rule token, and does nothing more.
- **Token shape** — each method is a valid HTTP token, the RFC 9110 `tchar` grammar, which rejects whitespace and separators (`/`, `:`, `,`, and the rest) so a malformed entry like `GET/foo` or `GET:foo` is refused, while every real verb is a token and passes. There is still **no verb whitelist**: WebDAV and custom methods are real, and whether a *given* verb is enforceable is the backend's concern, not the vocabulary's. This validates the *grammar*, not membership in a list of known verbs — and it is the only string grammar core takes an opinion on here.
- **Empty methods** — `EgressRule(host, methods=())` is a `ValueError`. `methods=None` means *all* (the bare-string equivalent); a non-empty tuple means *these*; an empty tuple would mean "allow this host for no method at all," which is incoherent — drop the host instead.
- **Unscoped rules collapse to strings — in the spec, not in the rule.** `EgressRule(host, None)` is exactly a bare `host` (all methods), and `methods=None` stays a legal thing to construct: a caller building rules programmatically wants to name a host before it knows whether it will narrow it, and a frozen dataclass cannot hand back a `str` from its own constructor in any case — `__post_init__` returns the instance or raises, and nothing else. The rewrite is therefore **`SandboxSpec.__post_init__`'s**, in the pass it already makes over `egress_allow` to collapse equivalents and refuse conflicts: it rebuilds the tuple, and every `EgressRule(host, None)` it meets is written back as the bare `host` string, which then participates in that same collapse as the bare host it became. So the tuple a backend reads **never contains an all-methods rule object**, and a method annotation survives only where it actually narrows. That is what keeps the capability derivation exact — any `EgressRule` still present after the rebuild carries real methods, so an all-methods entry never forces `Capability.EGRESS_METHODS` — and it is what keeps a backend written before the axis reading plain strings.
- **Scheme** — entries are **schemeless by convention**, and today nothing enforces the convention. No `http://`/`https://` in the vocabulary means nothing a spec spelled precisely can be silently widened across schemes — but a scheme-qualified entry like `https://example.com` passes the kind's current refusals (it is not blank and carries no whitespace or comma) and lands in a spec, where on the shipped backends it is at best a silently dead allowlist entry — the proxy allowlist never matches it — a mistake the author never hears about. The design closes that where host grammar lives: **the kind's refusals grow a scheme check in the adoption wave** — `_validated_hosts` refuses any entry bearing `://`, bare string and rule `.host` alike, one contract for both shapes, in the exact spirit of its existing blank/whitespace/comma refusals — refuse an allowlist that does not say what its author meant. Nothing that worked breaks: such an entry never matched anything on the shipped backends, so the change turns a dead entry into an error the author sees. Direct `SandboxSpec` construction stays unpoliced — core holds no opinion on host strings, and the kind is where authored mistakes are refused, exactly as today. Per-scheme behaviour is a backend's own (hyperlight registers both forms for a bare host, which is its normalization to make, not ours).
- **Duplicate host — collapse equivalents, refuse conflicts.** Hosts are compared **case-insensitively**: hostnames are (the CONNECT proxy already matches its allowlist that way), so `Example.com` and `example.com` are one host and cannot carry two different method sets that a backend lowercasing the name would then silently combine. What that comparison *does* on a repeat is the part worth getting right. Refusing every repeat is not additive — `egress_allow=("example.com", "example.com")` builds a valid `SandboxSpec` today, and a blanket "one entry per host" rule would break specs that work now, on a change whose whole claim is that it breaks none. So equivalent entries **collapse**: duplicate bare strings, and case variants of one bare string, become a single all-methods entry, which is semantically what the tuple already means today (the first spelling survives, since core rewrites no host string). Method-scoped entries collapse by the same standard: equivalence between two entries for one host compares the **set** of method tokens, case-sensitively — order is presentation, not policy — so `("GET", "POST")` beside `("POST", "GET")` is one rule, not a conflict, with the first entry's spelling and order surviving; the comparison is well-defined because each rule's tuple is already duplicate-free under the per-rule check. A `ValueError` fires only where the shapes genuinely **conflict** — two genuinely different sets — and every conflicting shape is one this design newly makes expressible: one host carrying two different method sets, or a bare string beside an `EgressRule` for the same host where the rule narrows. There the ambiguity is real — which one wins is unanswerable — and refusing it is safe precisely because the shape could not be written before.

## What each layer changes

- **`SandboxSpec`** — `egress_allow` widens to `tuple[str | EgressRule, ...]`. `__post_init__` keeps the existing "a non-empty `egress_allow` requires `egress is ALLOWLIST`" guard and does its rebuilding pass over the tuple: it **rewrites every `EgressRule(host, None)` as the bare `host` string**, collapses entries that are equivalent for one host, refuses the ones that conflict, and **auto-adds `Capability.EGRESS_METHODS` to `requires`** when any surviving entry is method-scoped. The guard's message rendering becomes union-aware in the same change: today it `", ".join`s the entries, which a rule object would turn into a `TypeError` before the documented refusal ever formed, so each entry is named by its host — a rule's methods in parentheses after it — and the refusal still quotes what the caller wrote while the error path stays the documented `ValueError`, pinned by a test that a method-scoped rule under `CLOSED` or `UNRESTRICTED` raises `ValueError`, never `TypeError`. Canonicalization lives here rather than in the rule because this is the pass that already rebuilds the tuple, and because a frozen dataclass cannot canonicalize itself into a different type. This is the one place the model derives rather than validates, and it is safe because `requires` is an additive set.
- **`EgressRule`** — a new frozen dataclass in `_protocol.py`: `host: str`, `methods: tuple[str, ...] | None = None`. Its `__post_init__` validates the methods and nothing else, as above; the host carries the contract it carries today, and the rule rewrites nothing — not the host, not itself. Its docstring is where the narrowing-not-closing honesty lives. And it is public API, not a private shape: a deployment writes one and consumers import `maf_sandbox`, never `_protocol`, so the class exports at package level beside `Egress` and `Capability` — `_protocol.__all__`, the package `__all__`, and a row in `TestPolicyVocabularyExports` — as part of step 1's core work.
- **`Capability`** — a new `EGRESS_METHODS` member, opt-in, absent from `DEFAULT_CAPABILITIES`. Declared only by a backend that enforces method scope before TLS.
- **The router** — same check site, same order, one qualification. The capability match it already runs is still the refusal, and when any surviving rule is method-scoped it additionally requires every rule token to be a member — case-sensitively — of the serving backend's declared token set (below). Because `ensure_can_serve` and `acquire` run the same checks, attach preflight and acquire refuse identically, by construction.
- **The kinds** — a deployment reaches this axis through a factory, and today the factory refuses a rule before a `SandboxSpec` is ever built. `codeact_sandbox_spec` and `make_codeact_tools` both type `egress_allow` as `Sequence[str]` (`_tool.py:155`, `_tool.py:222`), and `_validated_hosts` calls `entry.strip()` on every entry (`_tool.py:445`), which an `EgressRule` has no answer to. So the documented feature would be unusable through the repo's one deployment-configurable kind unless the kind widens too: the two factories take `Sequence[str | EgressRule]`, and `_validated_hosts` grows a single `isinstance` branch — a bare string takes today's path unchanged, and an `EgressRule`'s `.host` is checked by the same kind-local rules (blank, whitespace-bearing or comma-bearing refused) with the rule itself passed through intact. The widening runs the whole chain, not just its mouth: `_effective_egress` and `_codeact_spec` widen their signatures to carry `str | EgressRule` through to the spec, and `_tool_description` renders a rule method-aware — the model reads the narrowing as policy, the host with its methods named, never a dataclass repr — with tests part of the same adoption pull request. The kind's **own** half, `_KIND_EGRESS`, stays bare strings: all-methods is its designed posture, and fixing it in code is what stops a deployment widening what the kind itself requires. `_effective_egress`'s `dict.fromkeys` dedup stays equality-based, and the authority on collapse and conflict stays `SandboxSpec.__post_init__`'s pass: a deployment that passes a narrowing rule for a host `_KIND_EGRESS` already names bare sends both shapes through the union, and core's conflict rule refuses the spec — the designed answer to a deployment narrowing what the kind itself requires, arrived at with no new kind code. Bicep needs nothing — its factory takes a mode and no hosts at all. **This is adoption work and sequences with the adoption pull requests below, not with the core release.**
- **The backends** — a backend that serves a method-scoped spec (so, one declaring the capability) sees `str | EgressRule` in `egress_allow` and reads the methods; a backend that does not declare it is only ever handed plain hosts, because the spec's rebuild has already turned unscoped rules into strings and any `EgressRule` surviving it forces the capability. **Declaring also carries a fit check**: every method token in every rule must be one the backend's mechanism can hold **as written**, and a rule the mechanism would rewrite or explode on is refused up front — never normalized, never deferred to a runtime error. Its mechanism is a declaration the router reads, not backend code: a declarer publishes its enforceable tokens as data, `egress_method_tokens: frozenset[str] | None` beside the capability — `None` means every core-valid token, a finite set means exactly those spellings — and the router's membership qualification above is read from it. That keeps the sentence above concrete — whether a given verb is enforceable is the backend's concern, not the vocabulary's, stated once as data instead of enforced in each adapter — and the testing fake declares `None`, or a finite set when a test needs the refusal path. A backend-local check at acquire was weighed and refused because it breaks the attach-time contract: `sandboxed_tool` preflights every spec through `ensure_can_serve` at attach — the refusal [`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md) counts among the stack's gained honesty — and a verdict the router cannot see waves a core-valid token through that preflight only to fail it at first acquire, attach and acquire disagreeing about one spec. Publishing the set puts the verdict where the preflight runs, so attach and acquire cannot disagree. The cost is stated rather than hidden: the token set is a new qualified declaration read, so the declaration surface grows by one — the collapse signal [`sandbox-architecture.md`](sandbox-architecture.md) names, firing again; the *mode* still rides the capability, and collapsing the declaration surface stays that document's concern, not this axis's. The opposite trade was weighed and refused too: making `EGRESS_METHODS` itself promise every core-valid token would keep the surface flat, but the only realistic first declarer could then never declare it — Hyperlight's verb list is finite — and a vocabulary whose first declarer is excluded is dead on arrival. Where the methods have to land is **reuse identity**, and it differs by backend. **docker and wslc** both fold the allowlist into the sandbox name ([`../network.md`](../network.md) records both), so that fold must grow to include the methods, or a `GET`-only and an all-methods sandbox for one host collide into one warm container. **ACAS does not fold the allowlist at all** — its reuse key is `(scope, thread, agent_dir, kind)` and a warm sandbox keeps the policy of the spec that created it — so method scope inherits ACAS's existing changed-allowlist hazard and needs the same fix (a full-policy identity, or a replacement check on reuse), not a fold it does not have. **Hyperlight sits in the same class, and is named because it is the first declarer**: allowed domains are registered before the warm snapshot, and the planned adapter's cache identity is explicit `(key, kind)` plus tool names, no policy fold — so reacquiring the same `(key, kind)` under a different method rule restores the older, possibly broader, policy from the snapshot. The fix is ACAS's — the canonical egress policy, the post-rebuild tuple with its methods, joins the cache identity, or reuse runs a policy-mismatch replacement check — and changed-policy reuse is covered in its adoption tests, because a stale broader policy on the very backend that enforces methods would be the axis refuting itself. None **declares** the capability today: the CONNECT-tunnel pair (docker, wslc) cannot see the method at all, ACAS's L7 proxy could in principle, and the first real declarer is Hyperlight — where the declared set earns its keep at once. Measured against the current wheels, `allow_domain(target, methods)` validates nothing at registration — any token registers — and the mechanism's real rules surface late: matching is case-normalized, so rules `get`, `Get` and `GET` all admit a `GET` request, and a token outside its fixed verb set explodes host-side at first `run()` (`RuntimeError: invalid HTTP method: PROPFIND`). Its `egress_method_tokens` is therefore the uppercase spellings of that verb list, declared by the adapter since there is no registration-time refusal to lean on, and each exclusion is the mechanism's own: a lowercase or mixed-case token stays out of the set because the mechanism would enforce its uppercase rewrite — a different rule than the author wrote — and a token outside the verb list because the mechanism's own answer is the late runtime error the membership check exists to prevent. The refusal itself now falls out of set membership — `get` is not in `{GET, ...}` — decided at the router, not in adapter code. One wrinkle is stated rather than hidden: the wire comparison is case-insensitive too, so a `GET` rule there also admits a hypothetical lowercase `get` request — wider than the literal token by exactly the case axis, a mechanism fact for the adapter's own documentation the way the CONNECT pair's method-blindness is, and unobservable with mainstream clients; an author who needs the literal-case distinction is refused by the only declarer, which is the honest outcome. Also honest: the guest's entire request surface at this version is the injected `http_get`/`http_post` ([`hyperlight-backend-exploration.md`](hyperlight-backend-exploration.md)), so method scope there bounds a surface that is already narrow.
- **Conformance** — a method-scope probe (a `GET` reaches a `GET`-only host, a `POST` to it is refused), extending [#402](https://github.com/sokolaidev/maf-extensions/issues/402)'s outcome probe. It does not ride `run_egress_probes`' curl harness — that harness shells `curl` through `Sandbox.exec`, and the first planned declarer has no `EXEC` at all, only `RUN_CODE` and the injected client — so the probe defines a **subject seam**: the subject supplies *issue a request with method M to this URL*, with an `EXEC`-plus-`curl -X` default for backends that have those, and a declarer without them implements the seam over its own surface (Hyperlight's injected `http_get`/`http_post` cover exactly the `GET`/`POST` pair the probe uses). The probe's fixture contract requires the target to answer 2xx to **both** `GET` and `POST` when reached, and the probe takes **two pre-acquired subjects**, because one sandbox cannot hold both policies: a control subject acquired under an all-methods entry for the target, where a reached `POST` stands as the positive control, and a scoped subject acquired under the `GET`-only rule, where the denial is asserted — the same reason the egress harness requires a denied URL that answers 2xx when reachable: without the control, an endpoint answering 405 to `POST` lets a backend with no method enforcement pass the denial probe. Acquisition stays the wiring suite's, exactly as `run_egress_probes` already receives a sandbox its wiring acquired with the right allowlist, so the shared suite gains no acquisition or factory seam and no cleanup protocol — a factory seam with cleanup in shared code was weighed and refused, because acquisition and disposal live in the wiring suites today and moving them into the shared module would put lifecycle policy where no backend knowledge exists. Its refusal case needs no sandbox at all, because the refusal is the router's: the shared suite asserts it at the router seam — `ensure_can_serve` over a spec bearing a token outside the backend's declared set refuses — in core's unit tests against the testing fake configured with a finite set, and in a declarer's wiring suite against its real declaration, boot-free and cleanup-free. The wiring suite still supplies the out-of-set token — which token falls outside a mechanism is backend knowledge, so core never guesses — but it no longer needs an acquisition seam, which the shared suite could not offer anyway: `ConformanceSubject` exposes only an already-acquired sandbox, and the subject seam above serves the live `GET`/`POST` enforcement probes and nothing else. The probe is `maf_sandbox.conformance` code, so it lands in step 1's core release, where unit tests against the testing fake — which declares the capability and implements the seam trivially — cover the pass and refusal paths both; wiring into a live suite is the declarers' own, each declaring backend's e2e suite adding it with its adoption, the same way `run_egress_probes` landed in core before any backend wired it.

## Sequencing

Fully additive; nothing is blocked on it. The Hyperlight adapter serves host-wide entries under plain `ALLOWLIST` on day one and adopts the refinement when the axis lands — a `GET`-only spec is simply refused on it until then, which is the correct refuse-never-degrade behaviour, not a regression.

**It lands in three steps — a compatibility wave, then a release between core and adoption — because two repository laws leave no other order.** [`AGENTS.md`](../../../AGENTS.md) is explicit on both. A dependency floor may only name a version that exists, and CI installs every built wheel into a clean environment to prove it, so a core addition a dependent imports has to be merged *and released* before the dependent can adopt it — a core wheel built from the same branch still carries its pre-release version, so "land them together" resolves against nothing. And the same gate runs every package's strict pyright on every pull request, so the moment `egress_allow` widens, every shipped reader that types it as strings goes red — runtime capability gating narrows nothing statically, and "core lands first and alone" cannot go green as written. Hence:

0. **Compatibility preparation — one `chore:` per consumer package, before the core minor.** Four shipped readers consume `egress_allow` as strings: docker folds it into the sandbox name — `"allow:" + ",".join(sorted(spec.egress_allow))` (`_backend.py:817`) — and joins it into the proxy env (`_backend.py:948`), wslc carries the same two shapes (`_backend.py:720`, `_backend.py:808`), ACAS builds an `EgressHostRule(pattern=host, ...)` per entry against an SDK pattern typed `str` (`_backend.py:824`), and CodeAct hands the tuple to `_tool_description`'s `Sequence[str]` (`_tool.py:729`). Each moves to a form that type-checks under today's `tuple[str, ...]` and under the widened union alike: the name folds and proxy-env joins render entries through `str()` — `",".join(sorted(str(entry) for entry in spec.egress_allow))` — and ACAS's pattern construction and CodeAct's description call render the same way. The docker and wslc chores carry their test-side reads too — the same strict gate types the packages' tests, and a test was not a lesser touch than a source file, [`AGENTS.md`](../../../AGENTS.md)'s own words at the time — so the `_ALLOW_ID` fold each suite rebuilds (`tests/test_docker_backend.py:1143`, `tests/test_wslc_backend.py:1114`) and wslc's widened variant (`tests/test_wslc_backend.py:1291`) move to the same `str()` rendering. The shims guard the static gate, not behavior: a non-declarer never receives a rule object at runtime — the spec's rebuild turns all-methods rules into strings, and any surviving rule forces the capability the backend lacks, so the router refuses before acquire — and each shim is tightened or retired in that package's own adoption or wiring pull request. `chore:` releases nothing and each pull request touches one package, so the attribution law is kept.
1. **Core lands and releases.** `EgressRule`, `Capability.EGRESS_METHODS`, the `SandboxSpec` plumbing — the widened field, the canonicalizing rebuild, the collapse and conflict rules, the capability derivation — and the conformance probe above, exercised against the testing fake, go in on their own title and ship in a `maf-sandbox` minor.
2. **Adoption follows as separate package-scoped pull requests, behind the released floor.** One has the Hyperlight adapter declare `EGRESS_METHODS`, read the methods out of `egress_allow`, and raise its `maf-sandbox` floor to the release step 1 produced; one carries the CodeAct widening above — the factories and the chain behind them, tests included; and each declaring backend's e2e suite wires the probe in as its own `chore:`. The split is [`AGENTS.md`](../../../AGENTS.md)'s attribution law rather than caution — every file under `packages/<name>/` attributes to that package, so a cross-package pull request mis-announces in two changelogs at once.

> **Since #629, a package's own `tests/` attributes to nobody.** The rollout above is kept as written, but the parts of steps 0 and 2 that split *only* to keep a test out of another package's changelog are no longer required — a shared conformance probe wired into two backends' `tests/` can ride the change it belongs to. Everything the split does for `src/`, `README.md` and `pyproject.toml` still holds. All are gated by the same released floor, and none touches a second package.

**Two alternatives to step 0 were weighed and refused.** A two-release accessor migration — core ships a string-only accessor in minor A, consumers migrate to it behind raised floors, minor B widens the field — buys the same green gate for a second core release plus floor bumps across four dependents, and the repository already knows what one core minor costs its dependents. And a string-compatible representation — an `EgressRule` that *is* a `str` subclass — would pass every shipped consumer silently, which is degrade-not-refuse smuggled into the type system: the exact failure this design exists to refuse, delivered by the class hierarchy instead of a backend.

**So the capability is unclaimed for one release, and that is this repository's own precedent rather than a hole.** `RUN_CODE` and `ATTACHED_IDENTITY` both entered the vocabulary with no backend declaring them and are still listed as *nobody* in [`../capabilities.md`](../capabilities.md); a vocabulary is what makes an honest `cannot` sayable at all, and it has to exist before anyone can decline it. Refuse-never-degrade covers the interval exactly: for that one release a method-scoped spec is refused on **every** backend, because none declares the capability — the correct answer to an ask nothing can enforce, not a silent widening, not a regression against anything that worked before, and not a claim a backend has to make and get wrong. What must never ship unexercised is an *enforcement* claim; the vocabulary that lets a backend withhold one can.
