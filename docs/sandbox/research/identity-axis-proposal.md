# The identity axis: one word, four things, and the order to build them in

> A proposal. It reads every open issue on the identity axis together, separates the four things the word "identity" is spent on, and lays out one design and one implementation order for all of them. It covers the authority issues [#567](https://github.com/sokolaidev/maf-extensions/issues/567), [#566](https://github.com/sokolaidev/maf-extensions/issues/566) and [#757](https://github.com/sokolaidev/maf-extensions/issues/757), and the guest-principal cluster they turned out to share a foundation with: [#741](https://github.com/sokolaidev/maf-extensions/issues/741), [#753](https://github.com/sokolaidev/maf-extensions/issues/753), [#754](https://github.com/sokolaidev/maf-extensions/issues/754), [#792](https://github.com/sokolaidev/maf-extensions/issues/792), [#839](https://github.com/sokolaidev/maf-extensions/issues/839) and [#710](https://github.com/sokolaidev/maf-extensions/issues/710). What it decides graduates to [`../hosts.md`](../hosts.md), [`../capabilities.md`](../capabilities.md), [`../policy-isolation.md`](../policy-isolation.md), [`../tool-call.md`](../tool-call.md) and the backend pages. The argument it grew from is [`two-axis-sandbox-policy.md`](two-axis-sandbox-policy.md) § Identity.

## The problem is a word

The open issues on this axis do not disagree with each other. They talk past each other, because "identity" names four different things in this repository, and each issue is about a different one.

| The thing | What it is | Where it lives today | Which issues |
|---|---|---|---|
| **Authority a host tool exercises** | Whose grants a host-tool body runs under, in the host process | `Identity.APP`, `Identity.USER`, the decorator's leg, `HostToolAggregate.identities`, `denied_identities`, `mint_user_identity` | [#566](https://github.com/sokolaidev/maf-extensions/issues/566) |
| **Authority attached to the sandbox** | A platform identity the guest itself can spend, through platform plumbing | `Capability.ATTACHED_IDENTITY`, a name nobody declares | [#567](https://github.com/sokolaidev/maf-extensions/issues/567) |
| **Material provisioned for one call** | A token handed to a guest for the length of one call, spendable at one audience | nothing; the refusal text that once named it moved to option B | [#757](https://github.com/sokolaidev/maf-extensions/issues/757) |
| **The guest principal** | The uid the guest program runs as: root, a resolved user, or nobody the backend could name | docker's `_guest_identity` and `_ContainerFacts.guest_uid`; acas's `_probe_guest_uid`; nothing on wslc | [#741](https://github.com/sokolaidev/maf-extensions/issues/741), [#792](https://github.com/sokolaidev/maf-extensions/issues/792), [#839](https://github.com/sokolaidev/maf-extensions/issues/839), [#710](https://github.com/sokolaidev/maf-extensions/issues/710) |

A fifth use is only a naming habit. The docs say a sandbox's "identity is `(key, kind)`", and [#753](https://github.com/sokolaidev/maf-extensions/issues/753) says "the identity that would narrow it is already at the call site". That is the sandbox's **name**, the tuple a backend keys it by, and it is what the disposal ladder is missing a rung for. It belongs in this proposal because the guest-principal work and the reclaim capability both need that rung before they can act on one sandbox rather than every sandbox a key owns.

The rule this proposal asks the repository to adopt, in the shape the `tier` rule already has in [`../../../AGENTS.md`](../../../AGENTS.md): **identity is authority.** Say **principal** for the uid a guest runs as. Say **credential** for the material that proves an authority, a token or an environment value. Say **name** or "what a key owns for a kind" for the addressing tuple. Code that already spends the word on a memo key, `_image_identity`, does not rename; prose stops.

## What was read from the installed SDKs and CLIs

Every constraint below was read from the installed SDKs and CLIs rather than assumed. Two of them change the design from what the two-axis record imagined.

- **The ACAS data plane's `exec` takes a command and a working directory and nothing else.** `SandboxClient.exec(command, *, working_directory=None)` in `azure-containerapps-sandbox` 0.1.0b4. No environment. A `user=` keyword is accepted and discarded, as [`../backends/acas.md`](../backends/acas.md) already records. [#757](https://github.com/sokolaidev/maf-extensions/issues/757)'s constraint stands.
- **The ACAS create call takes an `environment` mapping.** `begin_create_sandbox(..., environment=...)` sets variables for the sandbox's life. That is a create-time channel, not a per-call one, and a warm sandbox keeps whatever it was created with. It is the `write_file` objection in another form and this proposal does not use it.
- **A managed identity attaches to the sandbox group, not to a sandbox.** `SandboxGroupMgmtClient.patch_group_identity(name, {"type": "SystemAssigned"})`, and the `aca sandboxgroup identity assign` command. Every sandbox in a group shares the group's identity. The design's `IdentityScope.PER_SANDBOX` is not something the service offers; `SHARED` is what it offers, and `PER_SCOPE` is a deployment that provisions one group per scope.
- **The egress proxy can attach an identity's token to requests for one host.** `EgressRuleAction(type="Transform", headers=[EgressHeader(operation="Set", name=..., value_ref=EgressHeaderValueRef(managed_identity_ref=EgressManagedIdentityRef(identity_type=..., resource=...)))])`, matched by `EgressRuleMatch(host=..., path=..., methods=...)`. The token is minted for a named `resource` and set by the proxy; the guest never holds it. The same header can be sourced from a group secret instead, `EgressSecretRef(secret_id, secret_key)`. This is the single-audience cell the two-axis record designed, provided by the platform rather than composed by this stack, and it is why the in-guest half of C′ is the smaller half.
- **Both container backends can carry a per-call environment.** `docker exec -e K=V` and `wslc container exec -e K=V` both exist, the latter confirmed from the installed CLI's own help. The `exec(env=)` channel is implementable on the two backends a pull request can run, and only ACAS refuses it.
- **A snapshot is taken from a sandbox and a sandbox is created from a snapshot; nothing restores in place.** `create_snapshot` on a sandbox, `begin_create_sandbox(snapshot_id=...)` on the group, `commit` to a disk image, and no restore or revert member. A reset on acas is therefore a delete and a create from the snapshot, under a new sandbox id, and whether that is faster than a create from the disk image is unmeasured.
- **No shipped backend declares `ATTACHED_IDENTITY`, `SNAPSHOT`, `IsolationScope.CALL`, or a per-kind disposal.** `dispose(key)` takes every kind's sandbox on every registered backend, and wslc's registry and acas's labels both already carry the kind that core cannot name.
- **The guest principal is probed on two backends and read from nowhere by core.** docker resolves `Config.User` through `/etc/passwd`, `/etc/group` and `id`, and falls back to `0:0` with a warning when a named user resolves nowhere. acas runs `id -u` once per image and serves an unreadable answer. wslc reads nothing and runs `reclaim` as `--user 0` on the contract that the file plane wrote as root.

## Principles carried over, unchanged

The design below invents no new kind of check. Each piece is one of the repository's existing shapes applied to a new subject.

- **Declared and matched, or declared and resolved, never emulated.** A backend states what it provides; a spec states what it needs; the router serves exactly that or refuses with a named exception. Sharing, widening and loosening are the directions a match exists to catch.
- **Silence has one rule per field, and it is the field's default.** A backend that never heard of a declaration is read the way it was read before the declaration existed.
- **Orderings are data with an exhaustiveness test.** A new scope enum gets a rank mapping beside `ISOLATION_SCOPE_RANK`.
- **A capability gates a method; a fact is established, not declared.** The guest principal is a fact the backend measures on the cold path of `acquire`, which is Decision 3 of [`../guest-platform-and-commands.md`](../guest-platform-and-commands.md) applied to a principal rather than a command. It narrows a declared ceiling; it is never a declaration.
- **Core helps a backend comply and never branches per engine.** Where two backends need the same refusal, core ships the helper that produces it, and each backend calls it with its own facts.
- **A credential never crosses guest to host.** The guest may trigger a host tool and may never choose or supply the principal it runs as. `user_identity` is already a reserved argument for this reason; every new principal below gets the same treatment.

## Pillar A — the guest principal is a fact core can read

```python
class GuestPrincipal(StrEnum):
    ROOT = "root"                  # exec runs as uid 0
    UNPRIVILEGED = "unprivileged"  # exec runs as a non-zero uid the backend has established
    UNKNOWN = "unknown"            # the backend could not say: no probe answered
```

**Where it is established.** By the backend, on the cold path of `acquire`, where docker and acas already probe; wslc gains a probe. The fact belongs to the sandbox it was measured on. A backend that shares it across sandboxes keys it by an immutable artefact identifier, a content digest or a disk-image id, and never by a name: a reference like `python:3.13` can be repointed between two creates, and a memo keyed by it would hand the second container the first image's principal. docker already keeps its facts per container and forgets them when the container goes; acas's memo moves from the spec's image name to the disk-image id it resolves for an imported image, since a name in the group can be re-imported too, while a prebuilt image resolves to its bare catalogue name and to nothing immutable, so its principal stays per sandbox.

**How it reaches core.** `Sandbox.guest_principal` becomes a property on the `Sandbox` protocol. It is a member rather than a `getattr` read, because a runtime fact with a conservative silence rule would make every backend written before it look like an unknown principal, and the whole point of the fact is that the backends this repository ships can answer it. Adding a member to `Sandbox` is a breaking change, and that is the choice this repository already made for `reclaim`.

**What it decides.** Two things an issue today decides ad hoc, and a third it deliberately does not.

1. **Which capabilities the guest can back**, [#741](https://github.com/sokolaidev/maf-extensions/issues/741). acas already refuses `FILES_OUT` and `HOST_TOOLS` at acquire on a non-root image, because its file plane writes as root and the guest can create nothing inside what the file plane made. docker's unresolved-identity fallback is the same shape: the image named a user, the writes land `0:0`, and the guest cannot empty its own call directory. Core ships one helper, `refuse_capabilities_the_guest_cannot_back(spec, *, guest, files_land_as_guest, backend_name)`, and the rule is one sentence: **refuse the writing-guest capabilities when the guest is not established as `ROOT` and the file plane does not land files as the guest; serve `EXEC` with a warning.** `UNPRIVILEGED` is claimed only over an established non-zero uid. A named user the account files did not resolve is not that, since `USER root` is a named user too, so it stays `UNKNOWN` unless the backend observes the uid another way. docker can, and without a shell: the process that keeps every container alive, `sleep infinity`, runs as the image's user, and `docker top` reports its uid from the host, so the principal is read off a process the image already runs rather than off anything the guest is asked to do. That is the observation-not-announcement rule of Decision 3. It holds only where the container's uids are the host's: under a rootless Engine or `userns-remap`, both of which the backend supports, `docker top` reports the host-mapped uid, container root as a high number, and reading it as `UNPRIVILEGED` would license a raised removal on a false premise. So the backend reads `docker info`'s security options once per daemon, and where they name `rootless` or `userns` the process listing establishes nothing and the principal stays `UNKNOWN` unless the account files answer; translating through the process's user-namespace map is not claimed, since on Docker Desktop the daemon's `/proc` is in a VM the host cannot read. The principal probe runs on a rootless Engine as well as a rootful one. wslc has no process listing and stays `UNKNOWN` where its account files do not answer. `UNKNOWN` refuses the same capabilities `UNPRIVILEGED` does, because an image with no shell can still run its own binary through an argv exec and write beside root-stamped inputs. What that changes for acas is the memo, not the rule: an unreadable probe is no longer remembered, so a transient failure costs one refused acquire rather than an image refused for the backend's lifetime. The value itself is what the image's own `id` answers, an announcement rather than an observation, so on acas it is read in the narrowing direction alone: a wrong answer refuses a capability or fails a call and licenses nothing, and no raised removal there rests on it. docker passes `files_land_as_guest=False` only where its stamping fell back to root; acas and wslc always pass `False`. This closes #741 the way #722 closed on acas: a refusal at acquire that holds on every backend, with the `0:0` fallback kept for the one shape it is right for, an `EXEC`-only workload whose whole result is its stdout.
2. **With whose authority a removal may run**, [#839](https://github.com/sokolaidev/maf-extensions/issues/839) and [#710](https://github.com/sokolaidev/maf-extensions/issues/710). The reach rule is unchanged: a raised removal is licensed only over a path with no component the guest could have swapped. The principal supplies one leg of that argument where the check walked nothing: on a backend whose file plane writes as root and whose guest is `UNPRIVILEGED`, every component the file plane created is root's and unwritable by the guest. It does not supply the other leg, the ancestors the file plane did not create. The host-tools launcher runs `mkdir -p` for the working directory as the guest when nothing else created it, so a `work_dir` under a guest-writable ancestor, `/tmp` on every shipped image, is one the guest can create and swap, and acas resolves a linked parent. That leg is a check, and docker already runs it at acquire: `ancestors_are_the_hosts`, one stat per component from `/` down, cached per container. The record makes it the shared helper every root-plane backend runs once per sandbox. acas cannot run it through its data-plane stat, whose payload carries a mode and a type and no owner, so a `0755` ancestor the guest owned would pass, and a guest-answered `stat` is an announcement the observation rule refuses even on a sandbox no input has reached, since an image supplied from outside is exactly the one whose self-description is not trusted. So acas licenses its raised `reclaim` on an engine fact instead. At acquire, before any input, the file plane creates `work_dir` and every ancestor of it that does not already exist, and what the file plane creates is root's by the platform's own semantics. The raised removal is licensed only where the sole pre-existing ancestor is `/` itself, and whether `/` is root's is a fact acas cannot observe and a measurement over the shipped images does not establish for the image a spec actually selects. So it is attested by the host, per artefact the host built and imported: `AcasSandboxConfig(root_owned_disk_images=...)` names immutable disk-image ids, the raised removal is licensed for those alone, and the reclaim suite's live run re-measures each attested image. The license does not rest on the principal, which on acas is an announcement: a guest that is not root can write no component of a root-owned chain, and a guest that is root, whether the image said so or the program gained it, has no authority left to raise and can steer the removal onto nothing it could not have deleted itself, so a false uid changes what the shared refusal decides and nothing about reach. An image not attested, a prebuilt one included since it resolves to no immutable id, is reclaimed as the guest; a guest that owns `/` on such an image can replace the file-plane-created top-level directory and steer a host-authority delete through the linked parent, which is exactly what the attestation exists to rule out. A `work_dir` under any other pre-existing ancestor, `/tmp/x` say, is not raised over: its reclaim runs as the guest over `exec`, where a chain the guest could create is one the guest can empty. The fact is per sandbox, since the chain is created per sandbox and depends on the spec's `work_dir`, and nothing memoises it. wslc cannot run it from its engine: its filesystem path check is answered inside the container, which is why #495 keeps `remove` refused there, and an answer the guest can give licenses a recursive delete carrying root's authority no more than it licenses `remove`. So wslc withholds `RECLAIM` and is cleaned by disposal, a create of about half a second there, until an engine-authenticated stat exists, which is the upstream gap #125 already waits on. #710's measured facts are that check's answer for the default base on acas, root-owned `0755` from `/` down, and they replace the caveat only where the check has run; where it fails, the removal drops to `rm -rf` over `exec` as docker's does, and a chain the guest could create is one the guest can empty. wslc's `remove` stays refused for the reason #495 gives, now with the principal named in the refusal, and #839 closes as a decision rather than a mechanism: the owner of what the file plane wrote is known from the principal and the plane, the owner of the rest cannot be established from that engine, and so nothing raised is licensed on wslc and `reclaim` is withheld beside `remove`.
3. **Nothing about cleanup.** Whether a sandbox stays warm is Pillar B's ladder, and the principal is not an input to it. Root widens the reach of what a call leaves behind; it does not create the category, since a non-root guest writes `/tmp`, its home and its user site-packages just as freely. [#792](https://github.com/sokolaidev/maf-extensions/issues/792)'s default is adopted there for every image rather than keyed on this fact. What the principal still owes the ladder is the acquire-time log line that names the guest beside the rung the call will be cleaned by.

**Proved by.** A conformance probe, `the-principal-the-backend-reports-is-the-one-the-guest-runs-as`: exec a file creation, ask the subject who owns it, and compare to the reported principal. `SandboxEntry` carries no owner and asking the guest would break the observation rule, so the seam is the subject's, `ConformanceSubject.owner_of(guest_path)`, answered from the engine: the tar header on docker, and `None` on acas, whose stat payload carries no owner, and on wslc, so the probe verifies docker and skips the other two rather than asking their guests. The seam is in wave 1's list.

## Pillar B — the cleanup ladder, and the rung below the key

**Proposed, on the maintainer's direction of 2026-09-03: a call leaves nothing behind by default, and warm reuse is earned.** [#792](https://github.com/sokolaidev/maf-extensions/issues/792) asked for this on root images. It holds for every image, because the property at stake is what one call leaves for the next, and root only widens its reach. The framework's end-of-call cleanup is resolved from a ladder, and the cheapest rung a kind and a backend establish together is the one that runs.

```python
class Cleanup(StrEnum):
    RECLAIM = "reclaim"   # remove the call's directory; the rest of the sandbox stays as the call left it
    RESET = "reset"       # restore the sandbox to the state it had before any input reached it
    DISPOSE = "dispose"   # delete the sandbox; the next call creates one

CLEANUP_RANK: Mapping[Cleanup, int]   # weakest first; a host and a spec may raise, never lower
```

**What establishes each rung.** `DISPOSE` is established by construction on every backend, through the rung below the key. `RESET` is established by a backend that declares `Capability.SNAPSHOT` and implements `Sandbox.reset(*, timeout)`: the sandbox returns to the state it had at acquire, before the first `write_file`, so nothing a call wrote or started is there for the next one. `RECLAIM` is established only by the kind's own declaration, `SandboxSpec.confined_to_guest_call_path=True`: every byte the workload writes lands under its guest call path, and nothing it starts outlives the call. With that claim and a backend declaring `Capability.RECLAIM`, removing the call directory is enough. Without the claim the rung does not exist for that workload, which is the whole of "dispose by default": a spec that says nothing is cleaned by disposal.

**Resolved, not matched.** `SandboxRouter(min_cleanup=Cleanup.RECLAIM)` is the host's floor and `SandboxSpec.min_cleanup` the workload's; the effective floor is the stricter, and the router runs the weakest established rung at or above it. `effective_cleanup(spec)` is public beside `effective_isolation_scope`, so `ensure_can_serve` tells a host what every call will cost before one runs. Nothing is refused here, since `DISPOSE` is always established: a host that distrusts a kind's claim raises its floor to `RESET`, and one that distrusts a snapshot raises it to `DISPOSE`. The ladder is not the scope axis. Scope says which calls may share a sandbox at once; cleanup says what a call leaves for the next. At `IsolationScope.CALL` the cleanup is the delete of the call's own sandbox, and the ladder is not consulted.

**The claim is proved where the backend can diff.** Core ships `assert_nothing_left_behind(subject, call)`: on a sandbox no call has touched, fingerprint it, run the workload's own call and its cleanup, fingerprint again, and fail on any difference. A fingerprint is two things, and the subject answers both from its engine: the set of paths changed since the sandbox was created, and the processes running in it. docker answers the first with `docker diff` and the second with `docker top`. A fresh container is what makes the first answer sharp, since a path already marked changed before the call would hide a second write to it, so the probe refuses a subject whose diff is not empty at the start; and a writable mount the diff cannot see, a tmpfs or a volume, is read off `docker inspect` and refuses the probe too. Docker also gives every container an implicit tmpfs at `/dev/shm` that neither the diff nor the mounts inventory shows, so the subject fingerprints it through the engine's own tar surface, `docker cp` of the directory, before and after, and any entry it holds afterwards is a difference; a `--tmpfs` the host added is fingerprinted the same way. What the pair does not see, the probe does not claim: kernel state, open sockets, and the content of a path the call rewrote to its original bytes, which the diff still reports as changed and so fails safe. The in-process fake answers both from its own state. A backend with no diff primitive skips the probe and the claim stands as a claim there. A kind that declares confinement owes this probe in its own suite, on docker, and the claim it establishes is exactly the pair: no path left changed, no process left running.

**Cleanup above `RECLAIM` waits for the last call out.** At `IsolationScope.CONVERSATION` two calls of one message can share a sandbox, and a reset or a disposal under a running sibling is a failed call. So the router keeps an in-flight count per `(key, kind)`, and a `RESET` or `DISPOSE` runs when the count reaches nought. This is [#476](https://github.com/sokolaidev/maf-extensions/issues/476)'s counting alternative, now required rather than optional. It serialises nothing on its own, the one exception being Pillar E's credential-carrying call, which holds its entry exclusively; the finished call's residue stays readable by a running sibling until that one ends, which is the exposure a concurrent sibling has today. `RECLAIM` runs at once, since the call directory is the call's own. **The zero transition is a gate, not only a number.** A count that reaches nought and then awaits the cleanup leaves a window in which a new call of the same process increments, acquires the warm sandbox through get-or-create, and has it deleted underneath it by the cleanup already in flight. So the entry is a state per `(key, kind)`: `serving(n)`; `draining(n)` from the moment the first call out records a cleanup above `RECLAIM`, since the sandbox is condemned from then on and admitting a third call into it while a second is still in flight would hand the newcomer the first call's residue, or its surviving credential, under a default that promises neither; and `cleaning` when the count reaches nought, moved to before the first await. What the transition runs is not one cleanup but the pending ones: each exiting call records the cleanup its own sandbox on its own backend owes, keyed by the backend and the sandbox's `instance_id`, and folded per instance to the strongest rung any of its calls resolved to, and the last call out runs each record once. `Sandbox.instance_id` joins the protocol in wave 1 for this: the backend-issued identifier of the running sandbox, a container id on docker and wslc and the sandbox id on acas, stable for the life of the physical sandbox and new after a reset, which neither a wrapper object, fresh per acquire on every backend, nor a name that folds the egress policy can stand in for. Two calls served by two sandboxes then leave neither's residue behind, and two waiters never race two resets over one sandbox, which on acas would replace its id twice. The entry stays `cleaning` until every record lands, and a record that does not land crosses to the failure path. The state is loop-neutral, because the router and acas both serve more than one event loop and an `asyncio` primitive binds to the loop that first contends it, which is why the router already keeps its disposal locks per loop: the count, the state and the pending records are plain data whose transitions a `threading.Lock` guards, and a waiter registers a future on its own loop that the last call out resolves through that loop's `call_soon_threadsafe`. An acquire that arrives during `draining` or `cleaning` waits for the cleanup to land and then creates fresh; running bodies are never serialised, only entrants from the moment the sandbox is condemned. The failure path already has this shape, since `dispose_unclean` marks the key before its first await and an acquire in flight is refused when the mark appears; the clean path takes the same shape with a wait in place of the refusal, because nothing is wrong with the key. **The count is per router, and the record says what that bounds.** The state lives in the `SandboxRouter` instance and nowhere wider, so two replicas serving one conversation's turns at the same time, or two routers in one process over one engine, each count to nought on their own, and the first to get there deletes the sandbox under the other's call. That is the failure path's hazard today, made routine by a default disposal. No engine here can count acquires across replicas, and a marker inside the sandbox is the guest's to forge, so the design does not pretend to a lease it cannot hold. It states the precondition instead, where [`../tool-call.md`](../tool-call.md) already states the lock's: cleanup above `RECLAIM` at `IsolationScope.CONVERSATION` is sound where a conversation's turns pass through one router at a time, in one process or across replicas, which is what a thread's sequential turns give a MAF host and what today's failure-path disposal already assumes. A process-wide table keyed by the backend object would cover only two routers that share one backend instance, and an identity the engine would recognise across routers is a lease by another name, so the precondition names the router and nothing pretends further. A host that runs one conversation's turns concurrently on several replicas, or through several routers, raises `min_isolation_scope` to `CALL`, where there is no shared sandbox to delete out from under anyone; that is one more reason [#436](https://github.com/sokolaidev/maf-extensions/issues/436)'s backend work matters after this lands. A backend that can hold a lease on its engine may declare one later; nothing here forecloses it, and nothing here claims it.

**Failure is what it was, timed like the rung above it.** A reclaim or a reset that reports failure, or a stop that did not reach the process group, escalates to disposal through the unclean path, with its ledger and its `FailedReclaimPolicy` unchanged. The key is marked unclean at once, so no new call is admitted, and the disposal itself is a pending record like a routine `RESET` or `DISPOSE`, run by the last call out: an immediate delete would take the sandbox from under a sibling still in flight, the hazard the count exists to prevent.

**A sandbox this router did not clean is not trusted.** The gate, the served-by table and the unclean ledger live and die with the process, and `acquire` is get-or-create on every backend: docker reuses a running container under the derived name and acas a sandbox under its, so a router that starts after a host restart, or after a disposal that failed and a process that exited, is handed the last process's sandbox and knows nothing of what it holds, a call that never ended, a cleanup that never ran, or one that failed. It adopts nothing on faith. The router keeps the `instance_id` of every sandbox it has served, and an acquire that answers with an instance it has not seen is an adoption, cleaned before the call runs at a rung that owes nothing to what this router knows, since `RECLAIM` owes everything to it: `Sandbox.reclaim` takes the one call directory the router created under an unguessable name, and stops no process, so a router that holds no record of the last process's calls can neither name their directories nor end their survivors, and a reclaim of the new call's path would leave both. Adoption is therefore a reset where the backend declares `SNAPSHOT` and the engine still holds the sandbox's baseline, which restores the state from before any input and ends every process a call started, and otherwise a disposal followed by one fresh acquire, whose answer is trusted as a create because the disposal landed, whatever rung the call itself resolved to; a failure crosses to the unclean path as any cleanup's does. That costs one create per warm sandbox per process lifetime, from a snapshot or cold, and a warm sandbox is never carried across a process boundary on the strength of a confinement claim; it is what makes an in-process ledger enough: nothing survives a restart that the next process would trust, and a process that died mid-call, where nothing was ever condemned, is covered the same way, which a condemned state persisted outside the process would not be. Two routers over one engine in one process would adopt each other's sandboxes out from under each other, which is the precondition above stated once more.

**What each rung costs on the shipped backends.** `DISPOSE` on docker and wslc is a create of about half a second, which is why the default costs little there. On acas it is a cold create, the path the warm-resume design exists to avoid, and that is where `RESET` earns its rung. The SDK has no in-place restore, but it creates a sandbox from a snapshot. So acas's reset is a snapshot taken at create before any input, and at cleanup a delete plus a create from that snapshot, registered under the same key and kind with a new sandbox id. The baseline has to be findable by a router that did not take it, since adoption resets across a restart and process memory is gone by then, and it must never be taken of a sandbox that has served, since that would preserve the residue a reset exists to remove. So the snapshot is named for the sandbox's derived name, which is stable across resets and across processes, taken once by the router that created the sandbox before its first input, recovered from the engine by that name rather than from memory, and deleted with the sandbox by the disposal that removes it, the reconciliation sweep covering the one a dead host left; an adoption that finds no snapshot under the name disposes rather than snapshots. Whether a snapshot can be named or labelled and listed so is M6's to measure. Whether that beats a create from the disk image, and whether the snapshot brings back a booted VM or only its disk, is measurement M6. If it does not beat it, acas declares no `SNAPSHOT`, takes the cold create, and a warm acas sandbox is the kind's claim alone. Hyperlight's native snapshot is the same rung, and its proposal already names it as the warm-reuse mechanism.

**What this does to the two shipped kinds.** codeact runs model-written code and can claim nothing, so it is cleaned by disposal everywhere, and its fix-round loop pays a create per call until a backend declares `SNAPSHOT`. bicep can claim confinement only once its module cache is under the call path: `bicep restore` writes to the home directory's cache today, so a warm sandbox carries every module a conversation ever restored. The bicep pull request in wave 1 points the cache into the call path, declares the claim, and proves it with the probe. The price is a restore per call, which is what the claim costs and what the warm sandbox was hiding. Sample 13's live check asserts one container across four acquires; it stays true under `RECLAIM`, which is what the claim keeps for bicep.

**The rung below the key.** [#753](https://github.com/sokolaidev/maf-extensions/issues/753) and [#754](https://github.com/sokolaidev/maf-extensions/issues/754) are one change. Every rung above `RECLAIM` ends in a disposal, and a disposal at key granularity takes every kind's sandbox on every backend, so the rung has to exist first.

**The backend member widens.** `SandboxBackend.dispose(key, *, kind: str | None = None, instance_id: str | None = None)`. `None` for both keeps today's meaning: a caller releasing a key means all of it. A kind names what that key owns for that kind, which is the unit every backend already registers and labels, and which on docker and wslc is one container per egress policy the conversation has run under. An `instance_id` names one of those, the physical sandbox a cleanup record holds, and it is the clean path's target: a `(key, kind)` sweep from a routine cleanup would take a sibling instance whose own rung was `RECLAIM` with it. The sweep without an instance stays for release and for the failure path's fallback. Widening the member with a defaulted keyword is a breaking change to the protocol and lands as a core `feat!`, because a backend that does not accept the keyword fails when core passes it, and nothing in the type system marks the gap.

**The router remembers who served a call.** The backend that served an acquire travels with the call's own record, beside the sandbox it acquired, so the cleanup disposes on the backend that served this call and no other. The router's table, `(key, kind) -> {backend, ...}`, holds every backend serving that sandbox rather than one last-written value, because under the per-spec routing this rung is a prerequisite for, two specs of one kind can land on two backends, and a last-writer entry would send the earlier call's cleanup to the later call's backend, killing a sibling and leaving its own sandbox behind. An entry leaves when that backend's disposal lands. It is in-process state with a per-process lifetime, the same as the unclean ledger it sits beside, and the adoption rule above is what makes that lifetime enough. Per-kind disposal narrows to the serving backend when the table knows it and falls back to the fan-out when it does not. The fan-out reaches another replica's sandbox only if the backend answers from its engine rather than from its memory, and today acas's `dispose(key)` consults its process registry alone, so a sandbox created elsewhere is reached by `dispose_scope` and nothing else. The rung therefore comes with an obligation on the member it widens: a backend that labels at create answers `dispose(key, kind=...)` from its engine, selecting by the labels its purge already selects by with the kind label added. That is the sweep docker's `dispose` already runs for a key, and it is the only correct shape there: a container's name folds the egress identity as well, so `(key, kind)` names one container per egress policy the conversation has run under, and a derived name would reach only the one the current policy would build while an older variant stayed up. The registry stays the fallback for a listing that fails. One thing the sweep rests on that the backends do not yet hold: acas composes its labels with the caller's `spec.labels` last, so a caller label named `kind`, or `scope`, `thread` or `agent`, would overwrite the value the sweep and today's purge select on. A backend that sweeps by label writes its reserved entries last, so a collision can never win silently, and refuses a caller label whose key is reserved, at acquire and by name. Until a backend does, the record claims no cross-replica reach for `dispose`, and the backend page says so.

**Two disposal paths, kept apart, and one crossing between them.** The clean path, `SandboxRouter.dispose_kind(key, kind, *, instance_id, timeout)`, which names the instance its record holds, is ordinary cleanup, and it is what the ladder's `DISPOSE` rung and acas's reset both use: a disposal that lands writes no ledger and refuses no key. It is bounded the way `dispose_call` is, because it runs in the call's `finally` and becomes routine under a default disposal, and a backend call that never returned would otherwise hold the call and the `(key, kind)` gate in `cleaning` for ever; a disposal that runs out of time is one that did not land, and crosses over exactly as a refused one does. A disposal that does not land is not clean, whatever path asked for it. `dispose` is best-effort and answers with a `DisposalFailure` when the sandbox may still be there, and a clean path that read past that answer would hand the next acquire exactly the residue the rung exists to remove; so a failed clean disposal crosses to the failure path. Under the default `FailedReclaimPolicy.DISPOSE` that records the reason and refuses the key until a disposal lands; under `KEEP`, the host's one opt-down, the sandbox is kept with the residue in it and the host is told, as a failed reclaim is kept today, and nothing is refused. `KEEP` loosens every rung's failure alike, a credential-carrying call's included, because a host that opts into forensics opts into it knowingly and one policy with one meaning is the shape the router already has. Under the default, success is the only thing that stays ledger-free. The failure path, `dispose_unclean(key, *, kind, instance_id, timeout)`, takes the kind and the instance too, threaded from the call's own record by the cleanup that calls it and persisted in the ledger before the first await, and the ledger entry for a key is a set of pending records, each a backend, a kind and an instance, which the cancellation marks add to as well; a disposal that lands removes its own record and the key reopens only when the set is empty, so a retry that clears kind B's sandbox does not reopen a key while kind A's is still dirty, and a retry deletes the same sandbox the first attempt did; without it a served-by table keyed by `(key, kind)` cannot be asked from a key alone and the failure path would still fan out at key granularity. It narrows its deletion to the serving backend and kind but keeps its refusal at the key. That is the conservative answer to #753's ledger question: a dirty sandbox for kind A does not make kind B's safe to hand out, so the refusal stays wide while the deletion narrows, and the `SandboxUnclean` message names the kind. Narrowing the refusal is a later decision, taken once [#328](https://github.com/sokolaidev/maf-extensions/issues/328) makes a key genuinely span backends.

**`Capability.RECLAIM`.** Declared, the `RECLAIM` rung is available to a kind that claims confinement, and core calls `Sandbox.reclaim` after each call as today. Not declared, the rung does not exist on that backend whatever a kind claims, and the ladder resolves above it. Its silence rule is the backend's and not the spec's, and the two defaults part here. `DEFAULT_CAPABILITIES` stays `{EXEC, FILES_IN}` as the ask a spec makes when it says nothing, and `BackendDeclarations.capabilities` gains its own silence default, `DEFAULT_BACKEND_CAPABILITIES`, that set plus `RECLAIM`, because every backend written before the member existed implemented `reclaim` as a mandatory one and is read as it was. `RECLAIM` is never an ask: cleanup is resolved by the ladder rather than required by a spec, so a spec naming it in `requires` is refused in `__post_init__` and the capability match leaves it out, which is what lets wslc declare its capabilities without it and be cleaned by disposal rather than refused for every default spec, as a runtime-only backend already declares less than the defaults. The router's hand-check, `_refuse_a_sandbox_that_cannot_be_reclaimed`, and the `TypeError` it raises from `acquire` go away, replaced by ordinary capability matching. The capability's docstring states the cost in its own words: a backend that does not declare it has no reclaim-based reuse, so its sandboxes are reset after every call where it declares `SNAPSHOT` and disposed after every call otherwise, and a disposed sandbox is created cold for the next call because `acquire` is get-or-create. `Sandbox.reclaim`'s docstring is rewritten to #754's acceptance text: reach stays the rule; confinement is a best practice rather than a promise; the mechanism and any check it needs are the backend's; a backend that cannot establish safety raises and `FailedReclaimPolicy.DISPOSE` makes that safe; the sentence that licensed the absent check goes. The conformance suite's `run_reclaim_probes` moves onto `_run_suite` with the new capability as its gate, and `tests/test_conformance_coverage.py` loses its note that RECLAIM has no withheld-capability answer.

**Proved by.** `a-disposal-by-kind-leaves-the-sibling`: acquire two kinds under one key, dispose one, and the other still answers `exec`. And the RECLAIM suite, now skipped rather than owed on a backend that withholds the capability.

## Pillar C — a host tool that acts as the sandbox

[#566](https://github.com/sokolaidev/maf-extensions/issues/566) adds `Identity.SANDBOX`: the body runs host-side, under the identity the sandbox was provisioned with, and spends no authority the sandbox was not provisioned with. What it may reach with that authority is wider than the sandbox's egress cell, and the approval paragraph below is where that is paid for.

**Servable under three conditions, each checked where it belongs.** The workload has an identity to act as: one the backend attaches, Pillar D's declaration, checked by the router at attach, or one the host provisioned on the spec, the static case below. The host can mint a token as that identity, `HostToolRegistry(mint_sandbox_identity=...)`, checked at registration the way `mint_user_identity` is. And the identity is one the host can actually assume, which is the host's own fact and not the library's: a user-assigned identity the host resource also holds is mintable by the host through `ManagedIdentityCredential`, by client id or by resource id as the ref's `kind` says; a system-assigned identity on a sandbox group is mintable by nobody but the group, and a registry on such a deployment registers the tool and refuses its call, exactly as a registry without a minter refuses a `USER` tool today.

**The shape follows `USER` member for member.** The minter is called once per run with the run id and the `PrincipalRef` the sandbox acts as, Pillar D's scope-free name for a principal, and its answer reaches the body as the reserved argument `sandbox_credential`, named for what it carries, material, by the rule this record opens with. The shipped `user_identity` argument carries a token too and was named before that rule; renaming it `user_credential` belongs with the vocabulary pull request in wave 2 and is not this record's to decide. One success per run is cached; a failure is not. A guest naming the argument is refused before the mint. `allowed_identities` takes `SANDBOX` as one more opt-in member, which is what the set shape in #396 was kept for. `denied_identities` works unchanged. The kind reads `Sandbox.attached_identity` off the acquired sandbox and passes its `principal`, or the spec's provisioned one, into `HostToolRun(sandbox_identity=...)`; neither being there makes the call refuse, the way a registry without a minter does.

**The static case, and where it lives.** #566 names two provisionings, a platform-attached identity and a static one the host configured, and the second needs no capability: the host decided this workload runs as X, and the guest half of that is Pillar E's call credential carrying X's token to the one host. `CallCredential` carries `identity: PrincipalRef | None`, the principal the material proves, and `SandboxSpec.provisioned_identity` is a read-only property over `call_credential.identity`, derived and never invented, the way `identities` is derived from `host_tools`. One provider therefore owns both paths: the material the guest spends and the principal a `SANDBOX` host tool acts as are one object, so the tool cannot mint as X while the guest holds Y or nothing. The run's `sandbox_identity` is a `PrincipalRef`: the acquired sandbox's `attached_identity.principal` where the backend attaches one and `spec.provisioned_identity` otherwise; a spec carrying both is refused, since a workload has one identity to act as; and a `SANDBOX` tool is refused in `SandboxSpec.__post_init__` unless the spec carries one of the two, the way a surface without `HOST_TOOLS` in `requires` is refused. `also_carries_out` folds `provisioned_identity` for the reason it folds the capability.

**`SANDBOX` raises the surface to approval-gated, as `USER` does.** The authority is the sandbox's own and no wider, but the body spends it from the host's network position rather than from inside the sandbox's egress cell, so the same token reaches every endpoint the identity's grants allow and not only the hosts the spec names. That is a widening in reach even where it is none in authority, and approval is what accounts for it. A host that has bounded the body's reach some other way may still opt down through the kind's `approval_mode`, which is the host's hook.

**Where the host-side token is spent.** In the host's own network position, like every option-B body. The single-audience bound the guest-side channels get from egress does not apply here, and [`../hosts.md`](../hosts.md) says so for `APP` and `USER` already.

## Pillar D — an identity attached to the sandbox

[#567](https://github.com/sokolaidev/maf-extensions/issues/567)'s vocabulary, reshaped by the measurement that the platform attaches identities to groups.

```python
class IdentityScope(StrEnum):
    NONE = "none"                  # nothing attached: the standard's second condition, unrelaxed
    PER_SANDBOX = "per_sandbox"    # an identity this sandbox alone holds, gone when it is
    PER_SCOPE = "per_scope"        # one identity per user or tenant scope
    SHARED = "shared"              # one identity every sandbox the backend serves can spend

IDENTITY_SCOPE_RANK: Mapping[IdentityScope, int]   # narrowest first; sharing is the widening direction

@dataclass(frozen=True)
class AttachedIdentity:                  # what a backend declares, before any sandbox exists
    scope: IdentityScope
    auto_delete_seconds: int | None = None   # the platform-side bound on how long a leaked sandbox keeps the authority; positive
    egress_header: bool = False          # the egress machinery can set the identity's token on an authority-bearing rule

NO_ATTACHED_IDENTITY = AttachedIdentity(scope=IdentityScope.NONE)

class PrincipalKind(StrEnum):
    CLIENT_ID = "client_id"
    RESOURCE_ID = "resource_id"

@dataclass(frozen=True)
class PrincipalRef:                      # a principal, named the platform's way, and which kind of name it is
    kind: PrincipalKind                  # so a minter dispatches on it rather than inferring a format from the string
    reference: str

@dataclass(frozen=True)
class AttachedIdentityRef:               # what an acquired sandbox answers: the principal it holds, and how widely
    principal: PrincipalRef
    scope: IdentityScope
```

**A principal has no scope; an attachment does.** `PrincipalRef` names an identity and nothing else, which is what a host-provisioned credential proves and what a minter is asked to act as. `AttachedIdentityRef` composes it with the sharing the platform gave it. The composition rule below, that a provisioned call credential has no scope, is why the two are separate types rather than one with a nullable scope.

**Two objects, because a declaration and a principal are settled at different times.** `AttachedIdentity` is the backend's declaration, read by the router before any sandbox exists, and it carries what a declaration can: the scope and the bound. `AttachedIdentityRef` is the principal a particular sandbox holds, answered by `Sandbox.attached_identity` after acquire, `None` where nothing is attached. For `SHARED` the reference is the group's identity and every sandbox answers the same one; for `PER_SANDBOX` it is minted at create and differs per sandbox, which is why it cannot live on the declaration. The property joins `guest_principal` on the `Sandbox` protocol in wave 2's breaking change, and it is the typed value Pillar C's kind hands to a run.

**The backend declares what it provides.** `BackendDeclarations.attached_identity: AttachedIdentity = NO_ATTACHED_IDENTITY`. Silence is a claim, like `isolation_scopes`: a backend that says nothing attaches nothing, which is true of every backend in this repository. `Capability.ATTACHED_IDENTITY` stays as the spec's ask, and the router reads it as declared exactly when the scope is not `NONE`. A backend listing the capability while declaring no identity, or the reverse, is refused when the router resolves it, with both fields named. The declaration is settled synchronously from configuration, since the router reads it before any sandbox exists; acas takes an `AcasSandboxConfig(attached_identity=...)` that names the expected principal, its assignment, system or user-assigned, and the resource id of a user-assigned one, and verifies that against the group through the management client on every acquire, warm reuse included. The comparison is on the principal and the assignment and not on the scope, because a group repointed to a different user-assigned identity keeps its scope, its bound and its header injection, would pass a check on those alone, and `Identity.SANDBOX` would then act as the replacement. It is verified because `patch_group_identity` can change the group under a running deployment and a check on the first cold acquire alone would let a later warm acquire serve an identity the configuration never declared, or serve a workload whose declared identity the group no longer carries. A mismatch in either direction refuses the acquire. The read is bounded by the group's change token where the service offers one, so an unchanged group costs a conditional read rather than a full one, and M5 measures both the read and whether such a token exists. The read detects drift; it does not bind. What pins the authority a sandbox spends is the rule itself: for a user-assigned identity every header rule names the identity's resource id, so a group repointed to another identity after the read mints nothing for the old rule rather than minting as the replacement, and a request fails closed. A system-assigned identity cannot be pinned that way, since its rule names only the type and a system identity disabled and re-enabled is a new principal under the same name. acas therefore declares an attached identity only when it is user-assigned, and declines a system-assigned one. It also declares only the scope its deployment can honour: one group serves every scope the backend is handed, so the identity is `SHARED` unless `AcasSandboxConfig(scope=...)` binds the backend to a single scope and every acquire for another is refused, in which case the group's identity is that scope's alone and `PER_SCOPE` holds by construction. Routing scopes to groups is per-spec routing's territory and is not claimed here. A group carrying an identity the configuration did not declare is an ambient identity, and serving it would falsify the micro-VM claim.

**The spec opts in; the host and the spec bound the sharing; the router resolves it.** An attached identity reaches a workload only when that workload's spec requires `Capability.ATTACHED_IDENTITY`. A backend attaching one to a spec that did not require it is refused as ambient, whatever the host permits, because the obligation that every authority channel be spec-declared is a statement about the spec, and because `sandbox_tool_declarations` reads the spec and nothing else. On a group with an identity, every workload served there opts in, and a kind exposes the opt-in on its factory beside `egress_allow`. `SandboxRouter(max_identity_scope=IdentityScope.NONE)` is then a bound and not a substitute: the widest sharing this host will run any workload beside, checked at construction like the floor so a deployment on a group with an identity fails at startup unless the host said so. `SandboxSpec.max_identity_scope: IdentityScope | None = None` lets a workload tighten and never loosen, and a spec that requires `ATTACHED_IDENTITY` must state it, refused in `__post_init__` without one, as it must state its retention bound: `None` is no opinion, and a workload that asks for an identity with no opinion on how widely it is shared would inherit whatever the host tolerates, which is the silent widening a declared-and-matched granularity exists to catch. The effective ceiling is the narrower of the two, and the seventh check refuses a backend whose declared scope ranks above it with `SandboxAttachedIdentityNotPermitted`; the same exception names the ambient case. A spec that asks for the capability on a backend that attaches nothing is caught by the capability match. The readings this produces are the ones the design wants: a workload gets an identity only by asking for it, and gets it only where the backend shares it no more widely than the workload and the host tolerate.

**The three obligations, placed.** *Granularity declared and matched* is the check above. *Every authority channel out of a sandbox is spec-declared* is answered on the egress rule: an attached identity is spent through the proxy's header injection, and the rule that names the host also names the `resource` the token is minted for, so the audience is written where the host is. That rides on the method-scoped `EgressRule` already specified in [`../network.md`](../network.md), which gains an `authority: str | None` leg carrying the resource the token is minted for, the same split between a host and a resource that `CallCredential` makes in Pillar E. An authority-bearing rule names one concrete host: the allowlist admits `*.` wildcards, and a token set on every subdomain a wildcard matches is spendable at every one of them, which is the single-audience cell inverted, so a wildcard host with an authority is refused where the spec is built. The header the token is set on is fixed as `Authorization`, in bearer form, because every resource the platform mints for takes that header and a name field on the rule would be one more knob for nothing; acas turns the leg into `EgressHeader(operation="Set", name="Authorization", value_ref=EgressHeaderValueRef(managed_identity_ref=EgressManagedIdentityRef(identity_type="UserAssigned", identity_resource_id=<the attachment's reference>, resource=<the rule's authority>)))`, the identity selector coming from the backend's declared attachment and never from the rule, which names only the resource; that selector is what makes the pin below real, it is the same value the per-acquire read compares, and what `format` writes into the header is what M2 verifies. Two consequences for that record. Its canonicalisation collapses an unscoped rule to a bare host string, and an all-methods rule that carries an authority must not collapse, or the resource is gone before the backend sees it: a rule collapses only when both `methods` and `authority` are absent, and the derivation that adds `Capability.EGRESS_METHODS` inspects `methods` rather than counting survivors, or an all-methods authority rule would demand a capability nobody asked for and refuse acas over a restriction the spec never made; that derivation and its tests are wave 2's. And the mechanism an authority-bearing rule needs is the proxy's header injection, which the backend declares on the attachment itself, `AttachedIdentity.egress_header`, and not in `credential_channels`: that set is the call-credential channels the eighth check reads, and one set for both would let it admit an acas call credential on the header channel before the members that carry one exist. The seventh check refuses an authority-bearing rule on a backend whose attachment declares no header injection, beside the `ATTACHED_IDENTITY` the spec already requires for the identity itself. Whether an ACAS guest can also reach a token endpoint from inside is measurement M1 below. If it can, that is an authority channel no rule names, and the scope ceiling bounds sharing rather than audiences, so nothing in this design bounds it: acas then declares no `ATTACHED_IDENTITY`, and its acquire-time verification refuses a group carrying an identity as ambient, until the spec can name and bound that channel, which would be a `CredentialChannel` for an in-guest endpoint with an audience list the platform enforces, and the platform offers none. Documenting the endpoint is not an enforcement point. *A finite platform-side auto-delete* binds every scope but `NONE`, and it is stated on both sides: the backend declares `auto_delete_seconds`, refused without one, and a spec requiring `ATTACHED_IDENTITY` states `max_identity_retention_seconds`, refused in `__post_init__` without one, so a workload cannot opt in without saying how long a leaked sandbox may keep the authority, and the seventh check refuses a backend whose bound is longer than the workload tolerates. Both are positive integers, refused where each is built otherwise: a zero or negative bound would pass the retention comparison and bound nothing. And the bound is applied, not only declared: acas today logs a lifecycle configuration that failed and serves the sandbox under the service's defaults, which for a workload that opted in to an identity would be authority with no bound at all, so on a spec requiring `ATTACHED_IDENTITY` a create whose lifecycle policy could not be applied is disposed by the acquire that created it and the acquire is refused. For `PER_SANDBOX` the deletion reclaims the authority itself. For `PER_SCOPE` and `SHARED` the identity outlives the sandbox, since a scope's other sandboxes still spend it, and the deletion ends only this sandbox's ability to spend it; that window is the one the obligation bounds. Tearing a `PER_SCOPE` identity down is the deployment's, which provisioned it, and no member here claims it: `dispose_scope` purges one conversation and must not revoke authority that sibling conversations of the same scope still spend. The bound is an absolute lifetime, counted from creation and enforced by the platform whatever the sandbox does, because a leaked sandbox is one nothing on the host will ever stop. acas does not have that today: its lifecycle policy suspends after idle and deletes after a stop, so the delete interval counts from the suspension and not from the create, and whether a guest that keeps working defers the suspension is unmeasured. That is measurement M7. If idleness is defined by the data plane alone, a sandbox whose host has died goes idle by construction and the sum of the two intervals is an absolute bound for the leaked case, which acas declares. If a working guest keeps the sandbox up, acas declines `ATTACHED_IDENTITY` until the service offers a lifetime counted from creation, which is an upstream ask.

**What information-flow reads off it.** `sandbox_tool_declarations` writes the outbound confidentiality cap only when something can carry data out, and today that is egress or a landing sink. An attached identity is a third way out that need not traverse egress, so `also_carries_out` folds `Capability.ATTACHED_IDENTITY in spec.requires`, which the opt-in above is what makes readable there, and folds `provisioned_identity` beside it. And a `SHARED` identity is a fourth relay for [#793](https://github.com/sokolaidev/maf-extensions/issues/793)'s list: two conversations spending one identity at one service can pass bytes through that service. A host that raises `max_identity_scope` to `SHARED` accepts that, and [`../hosts.md`](../hosts.md) names it beside the sink-root mailbox.

**Composition rules stand.** `Identity.USER` never attaches; the closest the platform gets is `PER_SCOPE`. A provisioned call credential has no scope, because it is call-time material, which is Pillar E.

## Pillar E — material provisioned for one call

[#757](https://github.com/sokolaidev/maf-extensions/issues/757) asks which of four shapes C′ takes. The answer this proposal gives is the first shape with the fourth's honesty: build the vocabulary and the refusals, ship the channel on the backends that can carry it, refuse it by declaration on the one that cannot, and park the second channel behind a measurement.

```python
class CredentialChannel(StrEnum):
    EXEC_ENV = "exec_env"            # handed to one exec as environment; what that process starts inherits it
    EGRESS_HEADER = "egress_header"  # set by the egress machinery on requests to the host; the guest never holds it

@dataclass(frozen=True)
class CallCredential:
    channel: CredentialChannel
    host: str              # the one egress host the material may be sent to
    name: str              # the variable, or the header
    resource: str | None = None   # what the token is minted for, where that is not the host: an audience URI
    identity: PrincipalRef | None = None   # the principal the material proves, when the host provisioned one
    max_lifetime_seconds: int = ...       # the token expires within this, enforced by its issuer; positive, required
```

**A host and a resource are two values.** The egress rule matches a hostname, and a token is minted for an audience that is often a URI rather than that hostname: a storage account's blob endpoint against `https://storage.azure.com/`. One field cannot do both jobs, so `host` is what egress binds and `resource` is what the mint binds. On both channels the host's minter receives `resource` and mints the call's token; on `EGRESS_HEADER` that token is written to the per-sandbox secret and the rule's header reads it through `EgressSecretRef`, never through the managed-identity mint, which is Pillar D's path for an attached identity and would mint as a different principal. `None` means the token's audience is the host itself.

**A name has the grammar of its channel, checked where the spec is built.** For `EXEC_ENV` the name is a POSIX environment variable name, a letter or underscore followed by letters, digits and underscores. For `EGRESS_HEADER` it is an HTTP field name, the RFC 9110 token grammar the egress-methods record already validates a method against. `CallCredential.__post_init__` refuses a name its channel cannot encode, so the eighth check never admits a credential that would fail at the first exec or at the egress API, where the refusal would reach the model as a sentence about something it did not write.

**A credential bounds its own lifetime.** The cleanup ladder ends a call's token only where the host reaches the cleanup; a host that dies leaves a detached child holding an `EXEC_ENV` value and an acas sandbox holding its secret until the platform deletes it, and neither backend offers a deletion the host's death cannot defer. So `CallCredential` carries `max_lifetime_seconds`, positive and required, and the host's minter answers with a `MintedCredential(value, expires_at)` rather than a bare string, so the provider accepts an answer only when `now + skew < expires_at <= now + max_lifetime_seconds`, `now` the host's clock and `skew` a named constant allowing for the issuer's, refusing one already expired as firmly as one that outlives the bound, and never hands the guest a token whose end it cannot see. What the library cannot verify is that the issuer honours that expiry; that stays the host's obligation, and the docstring says so rather than claiming the bound is enforced here. A spec is refused without the bound. What a leaked sandbox holds after that many seconds is an expired token, whichever channel carried it.

**Declared, asked, resolved.** `BackendDeclarations.credential_channels: frozenset[CredentialChannel] = frozenset()`, silence the absence of an answer, refusing a spec that asks and leaving every other spec as it was. `SandboxSpec.call_credential: CallCredential | None = None`. The eighth check refuses a channel the backend does not declare with `SandboxCredentialChannelNotSupported`. docker and wslc declare `{EXEC_ENV}`; acas declares nothing until M4 lands, and is refused rather than served through a command-line prefix that puts the secret in the process table.

**The host is the whole of egress, checked where the spec is built.** `SandboxSpec.__post_init__` refuses a call credential unless `egress is Egress.ALLOWLIST` and the canonical set of hosts in `egress_allow` is exactly one, matching the credential's `host` case-insensitively, whatever methods or authority the rule for it carries. A method-scoped rule for that host only narrows where the material can be spent, and refusing it would refuse the composition wave 2 sets out to serve. And the host is concrete: a `*.` wildcard, legal elsewhere in the allowlist, would send the material to every host the pattern matches, so `CallCredential.__post_init__` refuses one. Not a subset: exactly the one host. The cell is the point, and a second allowed host is a second place the token can be spent.

**The protocol grows one parameter.** `Sandbox.exec(command, *, working_directory, timeout, env: Mapping[str, str] | None = None)`. The contract is about what the backend does, not about where the material ends up: the mapping is handed to that one process at start and to nothing else; the backend never writes it to the sandbox's filesystem, never records it where a listing or an inspect could show it, never puts it in its own client's argv, and never hands it to a later exec. The argv clause is the one the container backends have to earn, since both run the engine's client as a subprocess and a host process listing shows every argument to every uid: docker's `-e NAME` form reads the value from the client's own environment, so the backend sets it on the subprocess's environment and names only the variable on the command line; wslc is measured for the same form in M3, with `--env-file` over a host-side file readable by its owner alone as the fallback where an engine has no name-only form, and it declares the channel only where M3 finds one of those two carriers, withholding it otherwise, since a value on the client's argv is the one host exposure the contract refuses and the existence of `-e` proves only that a value can be passed. What that leaves is stated rather than hidden: the value sits in the client subprocess's environment, and in that fallback file, for as long as the client runs, and both are readable by the host's own uid through `/proc` and nothing else. That uid already holds the token, since the host minted it and keeps it in its own memory, so the bound the contract claims on the host is the process listing and not the host's own uid. M3 measures that bound as stated. A host whose threat model includes its own uid closes it by driving the engine over its socket, where the value travels in a request body and appears in no process's argv or environment; that is a transport this backend does not have and this record does not add. What the program does with it is the program's, and a process it starts inherits it; on both container backends a started process can outlive the exec that started it, so the material is not gone when `exec` returns. That is why the channel is bounded by the cleanup ladder below rather than by this contract. A backend that declares no `EXEC_ENV` channel raises `NotImplementedError` on a non-empty mapping rather than running the program without its material, and the attach gate keeps that unreachable. The host-tools transport passes `env=` to the launcher exec only; the kill exec carries none. `run_code` gains nothing, since a runtime backend with no shell has no environment to hand over, and a `RUN_CODE` credential channel is a later member when a backend wants one.

**The mint is the host's, per call, and it lives beside the kind.** A kind factory takes a provider, `make_codeact_tools(call_credential=CallCredentialProvider(spec=CallCredential(...), mint=...))`, mints once per tool call with the call's own identifier, and hands `{name: token}` to the exec. It is named for the call because that is its lifetime: a kind without host tools has no run, and a kind with one mints for the call and passes the material to the one exec that starts the run. What the program does with the value is the program's, and the program is the model's: codeact renders guest stdout verbatim, so a program that prints its environment hands the bearer to the model, and one that encodes it first hands it past any filter. The channel does not pretend otherwise. The router strips the minted value where it appears verbatim in the stdout and stderr it returns, a courtesy that catches the careless print and no more, and the approval ask says what the surface is: the program will hold a bearer for one host and one resource, may reveal it to the model, and the model may spend it wherever the host's other tools reach until it expires. What is enforceable is the lifetime and the scope, so on `EXEC_ENV` the provider accepts a `MintedCredential` only when its `expires_at` also lies within the call's own deadline plus the skew, the run's timeout for a kind with host tools and the exec's for one without, refusing a longer one as it refuses one that outlives `max_lifetime_seconds`. That bounds the value by the deadline and not by the call, since a call returns when its program does, and a value the model read stays spendable until `expires_at` however early that was; the approval ask says so in those words. A minter that can end it sooner answers with `MintedCredential(value, expires_at, revoke=...)`, an optional awaitable the router calls when the call returns, ahead of its cleanup, and only then is the value dead when the call is; a revoke that fails is logged, and the ask's words already cover it. Wiring one raises the surface to approval-gated, the softening the two-axis record designed: the residual is misuse of the authority at the one legitimate service, bounded in time and in audience rather than hidden. A credential the model must never read has one channel, the header the proxy injects, and that is wave 3's. `also_carries_out` folds it, for the reason it folds an attached identity.

**The bound the channel cannot close, and the rung that closes it.** A program holds its environment, and so does anything it spawns, including a process that outlives the call. At `IsolationScope.CONVERSATION` a concurrent call in the same sandbox runs as the same principal and could read that process's environment, which would make material provisioned for one call material two calls can spend. So a credential-carrying call takes its whole `(key, kind)` entry exclusively, since that entry is what the gate holds before the acquire that names an instance: it is admitted only when nothing is in flight on the entry, holds the entry in `draining` for its duration so no sibling is admitted on any instance of it, and releases it when its cleanup lands. Such calls therefore serialise against every call of their kind in the conversation and not only against other provisions, and `IsolationScope.CALL` is what removes the wait. A later call could still read a survivor's environment, and that is what the ladder answers: a spec carrying a call credential has its cleanup floor raised to `RESET`, since a reset restores the state from before any input and so ends every process a call started, and `DISPOSE` where no reset exists. `RECLAIM` is never enough for a credential, because a confinement claim is a claim and a token is worth more than one. `IsolationScope.CALL` is stronger still, and stays the recommendation for a credential-carrying workload once a backend declares it. M3 measures the survivor case, not only the clean one.

**The parked half.** `EGRESS_HEADER` for call credentials on acas needs a secret per sandbox, and the platform's secrets are group-scoped objects, so that means one group secret named for the sandbox, created at the first provision, referenced by that sandbox's rule alone, and deleted with the sandbox; never one secret shared by every sandbox, since a rule on every sandbox referencing the same one would hand sandbox A's requests the token sandbox B wrote last, across conversations. Whether the group's secret quota and the create latency let a deployment hold one per warm sandbox is M4's to measure, and if the platform cannot, the channel stays unsupported. A secret outlives its sandbox when the host dies before the revoke and the platform deletes the sandbox on its timer but not the secret, so the backend reconciles: on every cold acquire and on every scope purge it lists the group's secrets under its own name prefix and deletes any whose sandbox the service no longer lists, or whose age exceeds the credential's maximum lifetime plus the sandbox's auto-delete bound, whichever comes first; a `reap` entry point an operator can run from outside the host is the same sweep, the shape #808 asks for on the container backends. M4 measures that the sweep finds and deletes an orphan. Within one sandbox no two credential-carrying calls run at once, since Pillar E's gate admits such a call only when nothing is in flight on its entry, so the lease below is the backend's own guard beneath that gate rather than the mechanism that decides concurrency, and it holds unconditionally. Measurement M4 measures the platform beneath the gate: whether the proxy reads the secret's current value at request time on a warm sandbox, and, with two sandboxes each on a group secret named for it, whether each sandbox's requests carry only its own. If both hold, acas declares the channel and the token never enters the guest at all, which is the better cell. The two failures are not one, and neither is recovered by a smaller scope. If a warm update does not reach the proxy, the channel is unsupported: the members below act on a sandbox that already exists, and a token that has to be an input to the create needs material handed to `acquire` for a call-scoped sandbox, with its own cancellation cleanup, a pre-acquire path this record does not design and does not claim. If sandboxes do not isolate their secrets, no scope recovers it either, since a call-scoped sandbox spends a per-sandbox secret too. In both cases acas declares no channel. Either way the channel needs a protocol member the env channel does not, because the provider's `{name: token}` reaches `exec(env=)` and acas implements no such thing: `Sandbox.provision_call_credential(credential, mint, *, timeout)`, which takes the lease first and only then calls `mint` for the value it writes to the per-sandbox secret, so a call queued behind a long one does not spend its token's lifetime waiting, and returns a handle, and `revoke_call_credential(handle, *, timeout)`, which the call's cleanup runs on every exit path; both gated by `EGRESS_HEADER` in `credential_channels`, and the secret deleted with the sandbox. The handle is a lease on the sandbox's one secret, held from the provision until the revoke: a second provision on the same sandbox waits for the first call's revoke rather than overwriting a value the first call's requests are still carrying, since serialising the two members on their own would leave exactly that window open. That is the backend's own serialisation beneath core's gate, defence in depth rather than a second policy, and `IsolationScope.CALL` is what removes the wait for both. That member is wave 3's protocol change, and the channel is not claimed shippable before it exists.

## Pillar F — the control plane

Option A is already true of the protocol: it holds no credential, and a backend authenticates however it authenticates. What is missing is the seam. `AcasSandboxConfig` takes `credential_factory: Callable[[str], AsyncTokenCredential] | None`, called with the caller's scope, read off `CallerContext.current_scope` at the same moment the key is, and the backend keeps one client per `(loop, scope)` where it keeps one per loop today. That is the `CallerContext` path #567 names at the granularity a host can actually exchange for: a token per tenant, minted when that tenant's first acquire arrives on a loop. A scope is caller-derived, so the table is bounded rather than left to grow, and bounded without closing a client under a caller: each entry carries a count of operations in flight, and it is idle exactly when that count is nought. A registered sandbox does not pin its client, and that needs a change in the wrapper as well as in the table: `_AcasSandbox` today holds the SDK's sandbox client and calls it directly, so an eviction would leave a warm wrapper with a closed transport. In this design the wrapper keeps the sandbox id and the scope and no transport, and every operation borrows the scope's client from the backend for its own duration, a per-operation lease that counts the operation in flight and rebinds to a fresh client after an eviction; a sandbox needs a client only while an operation runs, so a tenant whose conversations sit warm with nothing in flight holds no slot. A conversation's purge closes nothing by itself. The ceiling, `AcasSandboxConfig(max_scope_clients=...)`, is per event loop, because the client's transport is loop-bound and the table is per loop already for that reason: eviction and the close run on the owning loop, an idle entry is evicted when a new scope arrives above the ceiling on that loop, and the process-wide bound is the ceiling times the loops the host runs, which for a host with one loop is the ceiling itself. An evicted scope pays one client rebuild on its next operation; a table whose every entry has an operation in flight waits for one to finish for at most `AcasSandboxConfig(scope_client_wait_seconds=...)` and is then refused with the ceiling named, an overflow refusal rather than a wait without bound, since `SandboxBackend.acquire` carries no timeout of its own and a create poll is bounded only by the SDK's polling deadline; a client is never closed under a caller. `aclose` still closes everything. Without that, a long-lived multi-tenant host holds one client, one credential and one connection pool per tenant it has ever served. A per-call exchange is deferred and said so in the disposition below: the SDK client takes its credential at construction, so a credential per call is a client per call, a cost no host has asked for. [#313](https://github.com/sokolaidev/maf-extensions/issues/313)'s private-registry pull is the same seam one step over, and it is not served by it: the SDK's `managed_identity_resource_id` on the image import answers `RegistryAuthFailed` even with `AcrPull` held, by #313's own measurement, and what worked there was a registry username and token. The import credential path is designed from a re-measurement of the service, M8, and #313 stays open rather than assigned to a wave. No core change.

## What this proposal does not do

- **Erase.** An unlink is not an overwrite; `IsolationScope.CALL` and this proposal both leave that where [`../tool-call.md`](../tool-call.md) puts it.
- **Serialise calls** ([#476](https://github.com/sokolaidev/maf-extensions/issues/476)). It counts them, so a cleanup above `RECLAIM` waits for the last call out; nothing queues except a credential-carrying call, which Pillar E holds exclusively on its entry. Declaring `CALL` on a backend stays [#436](https://github.com/sokolaidev/maf-extensions/issues/436)'s, and Pillar E's bound is why it matters more after this lands.
- **Route per spec** ([#328](https://github.com/sokolaidev/maf-extensions/issues/328)). Pillar B's served-by table is the prerequisite #753 named, and this proposal builds only that.
- **Read the stop's pid from anywhere new** ([#463](https://github.com/sokolaidev/maf-extensions/issues/463)). That is the transport's, not the axis's.
- **Negotiate a transport** ([#369](https://github.com/sokolaidev/maf-extensions/issues/369)). One consequence is worth carrying there: a backend-supplied channel's trampoline must resolve through `HostToolRun.call`, or the identity gates above never run on it.

## Implementation order

Three waves. Each core wave is one `feat!` minor, because every dependent pays a release per core minor and two protocol changes in one minor cost the same as one. A wave's core `feat!` cuts a version outside every published dependent's ceiling. Whether a breaking title lands outside them on its own depends on where the ceilings sit at the moment it merges, and they sit two minors up as soon as a dependent adopts, so every wave's core release names its version with `Release-As:` in the squash box, the first minor outside every published ceiling, rather than trusting the arithmetic of the moment; that is the escape the release documentation already describes for exactly this. The widening pull request that ordinarily precedes a core release is not opened for it: a published backend that admitted the new core would be paired with a protocol it does not implement, `dispose` called with a kind it does not accept and members read that it does not have. `check_release_order.py` exits non-zero to say a ceiling excludes the release, and merging over it is the expected move for a deliberate break. Backends and kinds then follow the core release in their own package-scoped pull requests, each raising its floor and its ceiling together to the version that exists, and the samples' floor bump goes last. The in-process fake rides in the core `feat!` of the wave that changes it: `maf_sandbox.testing` is shipped source under `packages/maf-sandbox/src/`, so a separate pull request would need a releasing title and would cut a second core release for the wave. What lands apart is a dependent's own test-suite wiring against the changed fake, since a package's `tests/` attributes to nobody, and where that wiring must precede the change it goes first.
