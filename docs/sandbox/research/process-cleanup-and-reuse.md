# Process cleanup and explicit reuse

> **Accepted design.** The cleanup policy is documented in [tool-call.md](../tool-call.md); process events are documented in [observability.md](../observability.md). This record explains the decision for [#463](https://github.com/sokolaidev/maf-extensions/issues/463).

Deleting a directory, signalling a process group, and taking before/after process snapshots cannot establish that a sandbox is clean. A guest can write elsewhere, leave its group, reparent descendants between observations, and race numeric identifier reuse. No current cleanup mechanism proves complete cleanup. Cgroups add more lifecycle and platform machinery than the present design should own and are outside this change.

The host therefore disposes after each call by default. `SandboxRouter(min_cleanup=Cleanup.RECLAIM)` explicitly accepts reuse with possible residual state. It applies to unconfined kinds too; `SandboxSpec.confined_to_guest_call_path` describes the kind's attempt to confine changes, not proof or permission. A spec may still demand a stronger cleanup floor. `FailedReclaimPolicy.KEEP` separately controls what happens after a cleanup failure. Shared instances drain active sibling calls before disposal, and call isolation still disposes its own instance.

Reuse never skips cleanup. The transport collects the result, checks and attempts to stop its recorded processes on success, timeout, error and cancellation, and independently attempts removal of its transport directory. The call wrapper reclaims the call directory on the RECLAIM path. Actual cleanup failures reach the existing failure policy; successful best-effort cleanup still carries uncertainty.

Launch observations share the run deadline. Process cleanup has one five-second budget for observation, signalling and verification; pre-signal observation can spend at most one quarter of it. Expired or cancelled observations remain visible as unavailable audit records, and cancellation still propagates. Any incomplete or unavailable snapshot marks the run unclean even if a later scan succeeds; each audit event still describes its own snapshot. Directory reclamation has its own bound and still runs after the process budget expires.

The launcher reports the program PID and optional dedicated PGID directly through its output. A trusted shell helper waits until the host has received the complete receipt and releases a fresh start token; it then execs the program without changing the recorded PID. This keeps new guest code from reopening an ancestor's control descriptor before it closes. Standalone `launcher_script` callers retain diagnostic files but receive no signal-authority receipt. The host retains the gated receipt in memory. Guest-writable PID and session files never select a signal target. Numeric identifiers are not stable handles, so observations retain process start ticks with each PID and refuse an observed replacement. A remaining check-to-signal race is explicitly accepted by a host choosing reuse.

Process snapshots are taken before launch, after the launcher receipt, before cleanup and after cleanup. They retain observed ancestry even if a process is later reparented, distinguish preexisting processes and new unattributed processes, and identify zombies separately from running survivors. New processes alone are never authority to kill: concurrent calls and sandbox services can create them. Cleanup retains the last observed metadata for each attributed identity across partial or unavailable scans, while audit snapshots and survivor reports describe only their current observations. Retained targets are checked again immediately before signalling and are batched under the same cleanup deadline. An escaped descendant whose ancestry was never observed cannot reliably be attributed.

The portable Linux collector reads `/proc` through an isolated invocation of the configured guest interpreter. This is guest-observed evidence, not an independent trusted engine measurement: a modified interpreter, proc mount or executable can lie. Every snapshot records that provenance and whether collection failed, was truncated or missed fields. Runtime snapshots do not replace the engine-backed conformance fingerprint. No environment variables are collected. Collection has time, count, byte and field bounds.

Audit events retain PID, PPID, PGID, SID, start ticks, user and group IDs, supplementary groups, username, argv, command, executable, cwd, process name and state, threads, CPU ticks and memory usage when available. They carry instance, call, run and snapshot correlation, phase, timestamp, attribution, recorded signal attempts and observed survivors. Cleanup decisions without a recorded attempt omit the signal; an unavailable descendant-helper result cannot establish whether it signalled. Standard logs contain identifiers, counts and outcomes without commands.

The core observer seam emits the structured records without an OTel dependency. `maf-sandbox-otel` exports snapshot summaries, per-process audit logs and cleanup actions with trace context independently of trace sampling. Commands and paths follow its existing `record_sensitive_data` policy; an audit pipeline requiring commands enables that option. Metrics have only bounded phase/outcome dimensions. Observer or exporter failure must not prevent directory cleanup or change the call result.
