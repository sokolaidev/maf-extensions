# Exfiltration, cross-sandbox movement, and the core's centralised structures

> An exploration: an adversarial reading of the sandbox stack's information-flow surface, asking three questions the shipped documents answer only in passing. First, can a guest move data into the agent host outside the channels FIDES (`agent_framework.security`) gates — through filenames, run outcomes, anything the declarations do not name? Second, can bytes ever move from one sandbox to another? Third, how secure are the centralised data structures in core that every call shares? Everything below was read out of the code as it stands; where a question was already answered on a main document's page, this record says so rather than restating the argument. No decision is proposed — the findings mostly confirm what shipped, and the exceptions are named at the end.

## The threat model this read against

The sandbox exists so that model-written code runs somewhere that is not the host process. The model-facing direction is *in scope and intended*: a kind's whole purpose is to bring a result back, and that result is whatever the guest produced. So "the model can read what the program printed" is not a finding — it is the product. The question that is a finding is the narrower one: **can bytes reach a place FIDES was told they do not go, or reach a reader other than the model whose call produced them?** Three readers exist on the host side — the transcript (the model's context), host state (a sink's destination, a file store, a log), and other sandboxes. The FIDES declarations gate the first two by labelling the tool; the third is gated by nothing called FIDES and has to be held by keying, lifetimes and disposal alone.

## What FIDES gates, precisely

`sandbox_tool_declarations` (`maf.py`) is the whole surface. Two legs reach a host's policy engine off the tool's `additional_properties`:

- `source_integrity` — whether this tool's *output* taints the conversation. `bicep_validate` declares `"trusted"` (a compiler's deterministic diagnostics, from a sandbox with no ambient identity and an allowlist of Microsoft-operated restore hosts). `execute_code` deliberately declares nothing, so the tracker's untrusted default applies: what comes back is whatever a model-written `print(...)` chose to emit, and the conversation is marked for it. Both are pinned by each kind's `TestFidesDeclarations`.
- `max_allowed_confidentiality` — written **only** when the host passed a cap *and* the workload can carry something out: a non-empty `egress_allow`, an output that lands plus a sink, or `also_carries_out` (the host-tool registry leg, which neither of the others can see). The cap gates *whether a call of this tool may run at all* in a conversation above the cap — never the content of what crosses.

That second point is the load-bearing limit of the whole mechanism, and it is worth stating plainly because "gated by FIDES" reads as if something inspects bytes: **nothing in this stack inspects bytes**. FIDES answers two questions — may this result taint, may this call happen — and both are answered from declarations settled at attach time. Everything the guest writes crosses the channels those declarations *label*, and no label narrows a pipe.

## Finding 1 — the overt channels are labelled, capped and honest

Every path bytes take from guest to host was traced, and each is one of four:

| Channel | What crosses | Bound | Labelled? |
|---|---|---|---|
| Tool result (`ExecResult` stdout/stderr/exit code) | Everything the program printed | **No byte cap in the protocol at all** | Yes — taint, per kind |
| Landed artifacts (`FILES_OUT` → sink) | Guest-chosen names, guest bytes | `TransferLimits` per direction (8 MiB/file, 32 MiB total, 64 files by default) | Yes — the `LAND` + sink leg of the cap |
| Host-tool calls (request/response files) | Guest JSON in, host JSON out | Call cap (16/run), per-response and total byte ledgers, refusal echo truncated at 120 chars | Yes — `also_carries_out` + the registry's own stamps |
| Failure sentences (the sanitisation ladders) | Fixed sentences to the model, detail to the log | Sentences are host-authored constants | Not a data channel — that is the point of the ladder |

The failure ladders deserve their own sentence because they are where an exfiltration attempt would most plausibly find a crack. `SandboxToolSession.acquire` orders its catches so that a refusal carrying provider text (`ATTACH_REFUSALS`, caught first — the classes are subclassable, and one inheriting `ValueError` would otherwise take the verbatim branch) is never confused with a message this stack authored; provider and transport detail goes to the log with `error_detail`, and the model receives one of five fixed sentences. `codeact`'s exec path follows the same split. The transport's timeout messages (`_TheRunsOwnTimeout`) are written model-safe at construction and surfaced whole. `HostToolRun.call` sanitises every refusal, truncates guest-chosen echo (`_bounded`), and refuses an unserializable return rather than letting a `__str__` cross. `SandboxUnclean` branches on a code, not a message, and the backend's sentence stays in the log. **No crack was found**: a guest cannot choose bytes that reach the transcript through an error path.

## Finding 2 — the creative channels are real but land inside the tainted position

Two hypotheses were tested specifically, because they are the ones the declarations do not name:

**Data encoded in a filename.** Yes, the bandwidth exists. Under `CodeactOutputs.MANIFEST` the *guest* writes `manifest.json` naming its own outputs; those names pass `validate_artifact_name` (≤255 bytes of UTF-8, no control characters, no traversal — a narrow invariant that refuses a lot but not *this*) and land through the sink, and `_format_landed` then writes them back into the transcript as `- {name} ({n} bytes)`. So a program can push roughly 255 bytes × 8 files of chosen text per call into the model's context through names alone, plus a byte-count side channel of a few digits per file. But observe what this *is*: the same bytes were already in the transcript as artifact content (or could have been — the file body is read and landed beside the name), the call that carried them taints the conversation because `execute_code` declares no integrity, and the model is the reader. The name channel adds no reader and no position the content channel lacks. **Assessment: not a policy hole; a documented-bandwidth footnote.** A host that lands artifacts from untrusted guests while declining to cap `outbound_max_confidentiality` has already accepted the bigger half of this.

**Morse code in failed/succeeded runs.** Also real, and weaker. A guest controls its exit code (0–255), its own success/timeout/refusal outcome, and can shape timing. The outcome ladder and the `fate`/`reach` clauses of a timeout message reach the model verbatim, and `perf_counter` deltas land in logs. But the *sender* is the guest program and the only *receiver* is the model whose code the guest is — one principal. A covert channel needs a second principal; here the second principal would be the host's log, where the detail half of every ladder already goes, and where a one-bit-per-poll timing modulation is drowned by real latency. **Assessment: a covert channel with no covert reader.** The honest framing is that outcome-as-signal is indistinguishable from ordinary program behaviour, and no policy short of refusing to report outcomes could close it.

The one genuinely covert direction worth naming is **guest → off-host**, where the reader is the allowlisted endpoint itself: an exfiltration-shaped `GET` through the egress proxy. That channel is real, is the reason `network.md` insists `GET`-only *narrows* rather than closes, and is gated by the only leg that can gate it — the allowlist and the confidentiality cap over `egress_allow`.

## Finding 3 — bytes do move between sandboxes, in exactly one designed way, and one documented accident

The second question: can data move from one sandbox to another? The routes, strongest first:

**Warm reuse within one conversation — by design, and wider than the call's own directory.** `acquire` is get-or-create, and the sandbox key is `(scope, thread_id, agent_dir, kind)` — never the call. Everything a call writes outside its own `guest_call_path()` is readable by every later call in the same sandbox, and `tool-call.md` states this as the accepted cost: same user, same conversation, not a tenancy breach. Two precisions keep that sentence honest. First, the per-call cleanup that makes warm reuse *safe* is mandatory, not assumed: `reclaim` is behind no capability, the router refuses at `acquire` a backend whose sandbox lacks it, and the backend that most needs the exception serves it anyway — `wslc`'s `remove` is `NotImplementedError` while its `reclaim` runs `rm -rf` as root, because the caller made the directory and no filesystem path check is owed. Second — the correction — **what reclaim removes is the call directory, and nothing confines where the guest *program* writes**. A program that writes to `work_dir`'s root, `/tmp` in the image, or its own `$HOME` leaves those bytes for every later call in the conversation; and on a backend whose `exec` detaches (docker's `HOST_TOOLS`), a daemon spawned by a run that then exited cleanly — no stop needed, so no unclean note — is running when the next call arrives. Within-conversation persistence is therefore "everything the program could reach", not "what the kind wrote", and only the conversation boundary — not reclamation — is what confines it.

**The key is the whole cross-conversation boundary — at the addressing layer, and only there.** Nothing accepts a scope, thread id or path from the model — `SandboxToolSession.key` reads them from the host's request context, `agent_dir` is baked at factory time, and `make_caller_context` takes *callables* precisely so a per-conversation value is never captured. A model-supplied key would be the one direct cross-sandbox reach; there is no path for one. The file store listing is the injection-pinning boundary on the *inbound* half, and it is likewise host-read. What this does **not** mean, and the earlier draft of this record implied: the unguessable name is not a security boundary against a guest already inside. A program in the sandbox can enumerate `work_dir` — or `/`, or `$HOME` — with whatever the image ships (`ls`, `find`, `os.listdir`), and read everything it finds there. The uuid in `guest_call_path()` and the digest in the docker container name are *addressing*: they stop two concurrent calls of one conversation colliding, and they stop two conversations resolving to one container. Against a guest already resident they are nothing — which is fine, because everything a guest can enumerate in *its* sandbox belongs to *its* conversation. The name is a namespace, and namespaces prevent collision, not access; access is what the key holds, and the key holds.

**Backend-level adjacency — contained, with one caveat each.** Docker derives container names from a length-prefixed SHA-256 over the key parts, so `scope="a|b", thread="c"` cannot collide with `scope="a", thread="b|c"` — and the comment is right that the key fields are host request context, making this defence in depth rather than a reachable exploit. Every container is `--network none` (or proxy-topology allowlist), so there is no container-to-container network path between two sandboxes on one daemon. The shared daemon itself is the `container` rung's stated cost: a kernel shared by every sandbox, which the isolation ladder prices rather than hides. `wslc` shares the WSL 2 utility VM across guests the same way, same rung, same price. ACAS is remote and per-sandbox. The caveat: `HOST_TOOLS` on docker detaches — a process one call started outlives it and is observable from the next call *in the same sandbox*, which is the warm-reuse case again, not a cross-conversation one.

**Host-state mediation — the one place guest-to-guest is real, on the host's wiring.** Two sandboxes never share a sink or a store by construction: a sink is host state the *host* owns, and the file store is the caller's listing. The composition question is whether **bytes returning from one guest can become bytes *into* another guest through host state**, and the answer is that the stack permits exactly the compositions a host wires, with no structure in core naming the dangerous ones. Three concrete relays, strongest first. *(1) The sink root as a mailbox.* `make_file_system_sink` wrote `root / artifact.name` with `write_bytes` and, when this was read, **no existence check** — the name invariant confines *where in the root*, not *over what* — and the collision refusal in `collect_outputs` is per-collection, so it never sees an earlier conversation's landing. A host that hands one root to every conversation of a scope has built a mailbox: guest A's manifest names `msg.txt`, the bytes land, and any guest whose model is later persuaded to read the same directory — or whose host sink root is also a served directory — reads them. Sample 07's own README documents the write half *within* one message ("two renders both land `out/diagram.png` and the second overwrites the first — the sink's behaviour rather than this kind's"); nothing widened that check across collections, because nothing in the library knows what a collection shares a root with — and what closed it below refuses the second landing rather than widening the check. *(2) The store as the return path.* `list_all_files` walks the **whole** store, and the listing is the injection-pinning boundary — a file the store holds is, by construction, a file the next call may name as input. Land artifacts where the store serves from and the loop closes: guest A writes, guest B reads, no sandbox ever touched another. Whether a store ever serves sink output is a host composition no check in this repository gates — there is no "these two roots must be disjoint" validation anywhere. *(3) Host tools as the relay.* A sink-declared tool writes host state under guest-chosen arguments; a source-declared tool reads host state back into a later guest. Both legs carry FIDES labels, but a label is not a mediation check — the composition is the host's, taken per tool, with the aggregate carrying each leg's declaration and nothing composing them. **Assessment: no unmediated guest-to-guest path exists — and "mediated" means the host's wiring decisions, not a gate in this stack.** `hosts.md` § *The relays a host can wire* now carries the sentence this record asked for, and `make_file_system_sink(existing=…)` makes (1)'s overwrite a decision rather than a silent `write_bytes` — a signal rather than a control, since refusing the second landing leaves the first readable. (2) and (3) stay words: the library holds one end of each and never both.

**The unclean survivor — the documented accident.** A program a stop did not provably take down can outlive its call, and anything it writes back *after* the removal lands in the sandbox the next call of that conversation reacquires. The framework's answer is disposal-on-unclean (better a failed run than leaked data), the router refuses the key until a disposal lands, and `FailedReclaimPolicy.KEEP` is the host's explicit opt-down. This is intra-conversation, documented on `tool-call.md`, and the one place where "bytes cross a lifetime boundary" is true — which is why the framework's response to it is the strongest action it has.

**The testing fake, for completeness.** `InProcessSandboxBackend.acquire` returns the *same* sandbox whatever the key — a deliberate simplification its own docstring names, meaning two "sandboxes" in a test share bytes freely. It declares `Isolation.NONE` and is a test fixture, but a host that mistakenly registered it in production would have no keying at all. The router's default `MICROVM` floor refuses it unless the host opted all the way down — the floor doing precisely its job.

## Finding 3½ — the sandbox as a bypass of the main agent's own tool policy

A question this audit was asked directly and answers *yes, structurally*: where FIDES (or an approval requirement) refuses a **main-agent tool** that writes to a sink, can the model reach the same effect through the sandbox? Three shapes, each verified in the wiring.

**Confidentiality-cap laundering.** FIDES gates each tool by the declarations it carries, and `outbound_max_confidentiality` on a sandbox tool is **opt-in and off by default** — written only when the host passed a cap *and* the tool carries something out. A host that refuses its main-agent `post_comment` tool for a confidential conversation, then wires `post_comment` into a codeact registry without passing a cap, has attached a tool FIDES will happily call: the guest program reaches it through request files, and the effect lands. `also_carries_out` folds sink-declared and unstamped tools into the cap condition, so the *hook* exists — but the host has to use it, and nothing derives the value.

**Approval laundering.** `sandboxed_tool`'s `approval_mode` defaults to `never_require`; codeact raises the whole surface to `always_require` only when the registry carries an `Identity.USER` tool. The escalation keys on **identity, not sink**: a sink tool running under *app* authority gets no approval gate from this stack, where the same function as a main-agent tool might have carried `always_require`. The parameter is the host's hook, and nothing fills it in.

**Middleware invisibility.** The structural half, stated on `hosts.md` itself: "each host-tool call bypasses whatever middleware the host runs — the boundary sees only the aggregate result." The registry's gates — resolution, binding, caps, the identity allow-list — are all real, but they are *this stack's* gates, not the host's, and per-tool FIDES policy has no expression at the aggregate: `outbound_caps` is carried verbatim and unfolded, one cap per sandbox tool rather than per function. **Assessment: the sandbox is, by design, a lower-gated path to effects the main agent's tools are refused or approval-gated for — the declaration machinery is faithful (per-leg stamps, one-read, sealed registry) but granularity is lost at the boundary and the host must re-derive its policy there itself.**

## Finding 4 — the core's centralised structures are small, mostly immutable, and hold against their threats

Core holds a handful of process-wide structures every call shares. Each was read for poisoning, collision, exhaustion and stale-state risks:

**The router's unclean ledger** (`SandboxRouter._unclean`, a plain `dict[SandboxKey, DisposalFailure | None]`). Unbounded growth is the obvious worry, and it is real but bounded by honesty: an entry exists only while a sandbox holds data nobody could remove, and it leaves when a disposal lands or a scope purge succeeds. A hostile *guest* cannot write to it at all — entries are created by the framework's own cleanup or by `mark_unclean`, from `DisposalFailure` codes folded through `fold_disposal_failures`, whose closed vocabulary (`unreachable`, `timeout`, `refused`, `unlisted`, `unknown`) is enforced by normalisation rather than trusted. A backend's *detail* string does land in it, but the only reader that surfaces anything is `acquire`, which quotes the **code** and keeps the detail in the log — so a malicious backend cannot push text at the transcript through the ledger. The one shape worth noting: `dispose_scope` rebuilds the dict on every successful purge (a comprehension, not mutation-during-iteration), and concurrent access is safe because the reads and writes carry no `await` between them — the same property the disposal-lock comment leans on. **Verdict: sound.** A key count bounded only by failed disposals is a monitoring signal, not a vulnerability.

**The disposal locks** (`weakref.WeakKeyDictionary` of loop → `WeakValueDictionary` of key → `asyncio.Lock`). The weak-on-both-sides design is documented and correct: locks do not accumulate per key, and a contended lock cannot keep a dead loop alive. The disposal-lock discipline (only disposals serialise; `acquire` takes no lock, and re-reads the ledger after its create's await) closes the race a disposal-during-create would otherwise open — the `_refuse_a_key_closed_during_the_create` path is the proof it was thought through. **Verdict: sound.**

**`_CALL`, the per-call ContextVar** (`maf.py`). The record it carries is the only mutable state in the lifetime chain, and its design is argued at length on `tool-call.md`: asyncio contexts are copied per task, so a child reads the right record and cannot reach a sibling's; `owner` guards against one session's body being attributed to another's; `closed` is set before the removal runs so a task outliving the call cannot be handed a path being deleted. The attack this structure would enable — one tool call's body reaching another call's guest path — is closed by exactly those three fields. **Verdict: sound, and unusually well-argued for a ContextVar.**

**The unclean notes** (`_reclaim._UNCLEAN`, a `ContextVar[list[_Note]]`). Same lifetime discipline: opened by the wrapper, closed in the `finally`, and `note_unclean` is a no-op outside a call. Notes are `(sandbox-object, reason)` pairs matched **by identity** in the reclaim, so a call that acquired two sandboxes disposes only the one a note names. The reason strings are host-authored transport sentences, not guest text. **Verdict: sound.**

**The host-tool registry and its ledgers.** The registry is the one door, sealed by `aggregate()` — a late `register` is refused rather than called against policy that never saw it, and a duplicate name is refused rather than rebound, so the callable surface cannot be mutated out from under a derived spec. Declarations are captured at registration (`declaration_for` reads the snapshot, never the function), closing the swapped-stamp race. The `HostToolRun` ledgers (call count, delivered count, delivered bytes) are per-run, checked *before* the tool body runs — the ordering that makes a sink tool's outward effect unrefusable-after-the-fact — and the slot-return on cancellation is in a `finally` keyed on delivery, not outcome, which is what makes a cancelled call consistent. A guest's only writes here are a name and arguments, both validated at the door and both bounded in what they can echo back. **Verdict: the strongest structure in the stack.**

**`InMemoryStore` and the fakes** (`testing.py`). Copied on construction, duck-typed, zero imports — a test fixture with no production reach. **Verdict: sound for what it is.**

The pattern across all of them is worth naming, because it is the actual finding: **core holds no structure a guest can write to, and no structure whose corruption a guest could profit from.** The ones a guest *influences* (ledger entries via failed cleanups, notes via overruns) accept only host-authored codes and reasons, and the ones that carry guest data (a run's request/response files) live in the guest and are policed at the door on the way back. The centralisation risk in this stack is not memory corruption — it is *policy drift* (a registry sealed after the spec was derived, an aggregate taken before registration finished), and every one of those seams has an explicit refusal on it.

## What this record would escalate

Four things, none of them a hole in what shipped, all of them seams worth a tracker if the maintainers agree. Two now have one: the root-image disposal question is filed and the host-composition relays are answered, and this record links them rather than restating them.

1. **The cap's egress half tests `egress_allow`, not `spec.egress`** — already a row on `hosts.md` § Status, marked *open, untracked*. This audit confirms it is the one derivation gap that matters: a hypothetical future kind permitted `UNRESTRICTED` would carry everything out uncapped. It deserves an issue of its own rather than an untracked row.
2. **`ExecResult.stdout` has no byte bound anywhere in the protocol.** The artifact channel is capped three ways; the stdout channel is capped by nothing but the transport's own patience and whatever the model's context window does with a 30 MB `print`. A `max_total_bytes` on exec output would make the two halves of "guest bytes to transcript" symmetric. Today it is bounded in practice by token cost, which is a business bound, not a safety one.
3. **The filename channel's bandwidth deserves a sentence on `hosts.md`.** Not a control — a host that lands artifacts has accepted the content channel, and the name channel adds no reader — but `hosts.md` § sinks argues the confidentiality of *bytes* without noting that *names* cross the same boundary with a 255-byte-per-file budget the caps never count. One honest sentence would close the gap between what the page argues and what a hostile guest can spell.
4. **The host-composition relays and the root-image disposal default are filed**: [#792](https://github.com/sokolaidev/maf-extensions/issues/792) asks whether a sandbox whose guest runs as root should be disposed per call rather than reclaimed, with `reclaim` becoming a kind-declared opt-in licensed by a confinement guarantee; [#793](https://github.com/sokolaidev/maf-extensions/issues/793) carried the sink-root mailbox, the store-fed-by-sink loop and the sink-tool-to-source-tool relay, and shipped the documentation-first fix with the sink refusal beside it. What remains unfiled from this record is the derivation gap Finding 3½ names — a helper that turns a registry into the `outbound_max_confidentiality` and `approval_mode` a host should pass — and it is listed under the mitigations below rather than numbered here, because whether it is library code or a documented checklist is itself part of the question.

## Conclusions — what is good, what is not

**What is good, and worth saying with the same emphasis as the criticisms.** The failure ladders are the strongest part of this stack: every path a backend's or transport's prose could take into a transcript is answered by a fixed sentence, an ordered catch, or a code-not-detail refusal, and this audit tried to crack them and could not. The router's refusal-first posture — five checks before a backend is reached, at construction and again at acquire, refusing rather than degrading on every axis — is what makes misconfiguration loud instead of quietly unsafe. The mandatory, un-gated `reclaim` with disposal-on-unclean gives the framework its one irreversible action and points it at the right target (data retention, not tidiness). The host-tool registry is the best-engineered object here: one door, sealed on aggregate, declarations captured once at registration, ledgers checked before the body runs. The `InProcessSandboxBackend` refusing to serve under the default floor is the ladder working, not a limitation. And the honesty of the documentation is itself a control: pages state what mechanisms *narrow* rather than close, and this record could only be this precise because the docs make falsifiable claims.

**What is not so good, in one sentence each.** The outbound confidentiality cap is opt-in, so the default deployment has a fully declared but entirely unexercised policy leg (Finding 1). The stdout channel is uncapped where the artifact channel is capped three ways — the two halves of the same boundary are asymmetric (escalation 2). Warm reuse is cleaner than its pre-#680 self but still assumes what it cannot check: that the *program* confined itself to the call directory, and that a cleanly-exited run left nothing running (Finding 3). No structure in core can see a host composition, so the three guest-to-guest relays remain legal and invisible to every declaration — named on `hosts.md` since [#793](https://github.com/sokolaidev/maf-extensions/issues/793) and, for the first relay, refused at the second landing — a warning and one guard, where a check on the composition is still what none of the three has (Finding 3). The sandbox is by construction a lower-gated path to effects the main agent's own tools are refused or approval-gated for, and nothing derives the host's middleware policy onto it (Finding 3½). And the two trust asymmetries the docs already name remain true and worth restating: declarations are claims, not controls, and a stamped `sink=None` that lies defeats the aggregate that trusted it.

**The one-line verdict.** The boundaries that exist are well built; the gaps are all of one shape — **a policy that lives on the host's side of a line the library drew deliberately, with the hook supplied but the derivation left to the host** — and every recommendation below is about closing that distance without moving the line.

## Recommended mitigations

### For `maf-sandbox`

Ordered by reach, highest first — each names the finding it answers.

1. **Derive, or at least demand, the outbound cap when a registry carries sinks** (Finding 3½). The cleanest shape: `HostToolAggregate` already holds every sink cap; a helper that turns it into the `outbound_max_confidentiality` (strictest cap the host's own vocabulary can express, or the host's explicit choice) would turn "the host must remember" into "the host must call one function". Bolder and better if the maintainers agree it is honest: *refuse* a sandbox tool whose registry declares sinks and whose caller passed no cap — the same refuse-don't-degrade posture the isolation floor already uses, applied to the one case where silence is a hole rather than a choice.
2. **Bound `ExecResult`** (escalation 2). A `max_total_bytes` on exec output, spec-side and folded into `TransferLimits` the way the host-tool transport already folds its own, makes stdout and artifacts symmetric. The `files_out` caps are the vocabulary; the work is applying them to the channel that has none.
3. **Move the relays from legal to named** — done in [#793](https://github.com/sokolaidev/maf-extensions/issues/793). The must-not block is `hosts.md` § *The relays a host can wire*, and the code half went with it: `make_file_system_sink` defaults to refusing an existing destination, so landing over one is a decision rather than a silent `write_bytes`.
4. **Dispose root-user sandboxes by default** ([#792](https://github.com/sokolaidev/maf-extensions/issues/792)). The pre-emptive form of an action the framework already takes on failure; the issue carries the design question of what a kind's confinement guarantee is worth.
5. **Close the egress-half derivation gap** (escalation 1). One condition — test `spec.egress`, not `egress_allow` — and the untracked row becomes a closed one. Small, and small is the point: it is the only item here that is a bug-shaped gap in a derivation rather than a design question.

### For application developers wiring this stack under MAF

These assume the packages as shipped, and most of them cost one line each. Ordered the same way.

1. **Pass `outbound_max_confidentiality` to every sandbox tool factory, every time** (Findings 1, 3½). The parameter is off by default for reasons the library documents, but the host is the only party that knows its own vocabulary. If the tool carries anything out — a sink, an allowlist, a registry with sink-declared tools — a host that passed no cap has attached a tool its policy engine cannot refuse. Derive the value from the strictest sink the tool can reach, main-agent tools included: the sandbox must not be the loosest path to an effect something else gates.
2. **Set `approval_mode="always_require"` when the registry writes** (Finding 3½). The stack raises approval for `Identity.USER` automatically; it does not for an app-authority sink tool, and approval is exactly what a main-agent tool with the same effect would have carried. The parameter exists; nothing fills it in for you.
3. **One sink root per conversation; never the file store** (Finding 3). `make_file_system_sink(root)` — give each `(scope, thread_id)` its own root, keep those roots disjoint from everything the file store serves, and treat `list_all_files` as what it is: a whole-store walk. The relays need a host composition; refuse to be one.
4. **Read the provenance of the file store before lowering the floor** (Finding 3). Sample 08 already says this in its own wiring comment: with a store attached, the program's input is no longer only what the model wrote, and `min_isolation` should be chosen against where those files came from, not copied from the sample that seemed closest.
5. **Treat the transcript as the sink it is** (Finding 2). Everything a program prints persists into the conversation and, with it, wherever the host persists conversations. A host classifying its data owes the stdout channel the same classification it owes the artifact channel — and until escalation 2 lands, the only bound on the former is token cost.
6. **Keep `FailedReclaimPolicy` at its default** (Finding 3). `KEEP` is an honest opt-down with a documented cost; this audit found the default (dispose on unclean) to be the framework's strongest guarantee, and no host that cares about exfiltration should be the one loosening it.
