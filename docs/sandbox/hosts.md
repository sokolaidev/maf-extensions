# The host boundary

> Everything that crosses between a sandbox and the host that runs it: where artifacts land, which host functions a guest may call, whose authority the resulting work carries, and where a guest path resolves. Sources of record: [`research/files-out.md`](research/files-out.md), [`research/two-axis-sandbox-policy.md`](research/two-axis-sandbox-policy.md), [`research/call-lifetime.md`](research/call-lifetime.md).

A sandbox exists so that untrusted work has somewhere to run that is not the host process, and three of the four subjects here are places that containment is deliberately and narrowly relaxed: artifacts move guest bytes into host state, host tools move host authority into guest reach, and identity decides whose authority that is. They belong in one document because a host reasoning about any of them has to hold the other two — a landing sink changes what an egress-shaped policy leg means, and a host-tool call carries out what neither egress nor a sink can see. The storage base is the odd one: not a relaxation but the ground the other three stand on, and today owned by nobody.

## Where artifacts land

This is the first channel in the stack where **guest-chosen names and guest-produced bytes reach host state**, and everything below follows from that sentence. It is not the mirror of `FILES_IN`: on the way in the host chooses the name and the content and the destination is disposable, while on the way out the guest chooses both and the destination is a transcript, a file store or a blob container that is not.

One capability creates two information flows, and conflating them is the mistake this section is arranged to prevent. Reading bytes the kind itself consumes — a SARIF file parsed into diagnostics — is a **source**, and the question is integrity, already answered by the workload's own `source_integrity`. Landing an artifact in host state is a **sink**, and the question is confidentiality: may a conversation this sensitive cause bytes to be written where they are going? The two are distinguished in the spec rather than left to convention, by `DeclaredOutput.disposition` — `LAND` goes to the host's `OutputSink` and the model gets a reference; `CONSUME` goes to the kind, which parses it, and never reaches the sink. It is a *routing* distinction and nothing more: a `CONSUME` output is stat-ed, capped and counted exactly like a landing one, because it is the same guest, the same filesystem and the same bytes leaving the sandbox. What `collect_outputs` does not do for one is **read** it — that read is the kind's own call, with the kind's own bound. The capability that makes any of it reachable, and the `FILES_OUT` / `FILES_LIST` split behind it, are [`capabilities.md`](capabilities.md)'s.

### The host writes; the library never does

A file store, a blob container, a UI artifacts panel, a scratch directory — the destination is a property of the application, and `maf_sandbox` is stdlib-only by design. The host supplies a callback, which is the pattern `CallerContext` already is:

| Type | What it carries |
|---|---|
| `Artifact` | `name` (validated, relative, derived from the declared output), `content: bytes`, `kind` (`spec.kind`, so a host can route by workload), `media_type` (as the kind declared it, never sniffed) |
| `LandedArtifact` | `name` echoing what was asked for, `display` safe for the transcript, `handle: str \| None` — host-internal, never auto-rendered |
| `NameNormalization` | `NFC` (default) or `NONE` (byte-exact) |
| `OutputSink` | `deliver: Callable[[Artifact], Awaitable[LandedArtifact]]`, plus its `normalization` |

`collect_outputs(sandbox, spec, *, sink=None, outputs=()) -> tuple[LandedArtifact, ...]`, frozen and ordered — a tuple, as `egress_allow` is. It lives in the **stdlib-only core**, not in the MAF glue: it needs nothing from `agent_framework`, and registering `_outputs` in the protocol-module set is what makes the zero-dependency test enforce that automatically rather than by anyone's memory. `make_file_system_sink(root)` ships as the one worked sink, and the refusal is why it exists — a link already sitting in `root` carries a write straight out of it, the host-side twin of the symlinked ancestor every guest path is checked for. The writing is three lines.

**The typed return is a security property, not tidiness.** If `deliver` returned one string and the kind put it in the tool result, whatever the host handed back would enter the transcript verbatim — and for a blob container that may be a SAS URL with a bearer token in the query string, persisted and replayed on every subsequent turn. `display` is what the model sees; `handle` is the host's own reference, and nothing in this library renders it anywhere.

### Everything is pulled and capped before the first `deliver`

A push callback that writes to host state cannot be un-called, so "no partial delivery" is only achievable by collecting the whole set first. The phase order is the contract rather than an implementation detail: what the declaration alone decides — a sink for anything that lands, a valid name for every output, no two landing names that collide — is settled before the sandbox is touched; then every declared output is stat-ed and capped; then every landing one is read; and only then is anything delivered. One consequence is normative: **there is no streaming to the sink.**

The second consequence is weaker than it looks and is worth stating rather than discovering. What is normative is that over-cap bytes are never *delivered*. `max_total_bytes` as a *peak host-memory* bound is best-effort and backend-dependent: it is passed down as `read_file(max_bytes=...)`, so a backend that can stop reading early does — but a backend whose SDK buffers the whole response internally, which the ACAS one does, has already allocated the file by the time this library can look at its length. **Such a backend cannot provide the memory bound at all**; it can only refuse afterwards, which is a delivery guarantee, not a memory one. A host needing a hard ceiling gets it from a streaming backend or from the per-file cap it chooses.

**One residue survives that ordering, and it is a property of the shape rather than a defect.** If `deliver` itself raises on the third of five artifacts, the first two are already in the host's store and nothing can retract them; the exception propagates and the host holds a partial set. Everything the library decides — a bad name, a collision, a breached cap, a missing required output — is settled before any delivery, so this is the *only* path to a partial landing. It is also the strongest argument for a batch `deliver`: one call taking the whole collection would remove the residue entirely, where the per-artifact shape cannot. Left per-artifact until a host argues otherwise.

**A spec with `LAND` outputs requires a sink.** This is structural rather than a per-kind judgement: a tool declaring something that lands with nowhere to land it cannot honour its own spec. The check sits inside `sandboxed_tool`, **after the attach gate**, so a host with no sandbox configured at all still gets `[]` — the unconfigured-host escape wins, exactly as it does everywhere else. Two neighbours ride with it: a spec that declares any output, of either disposition, and does not name `FILES_OUT` in `requires` is refused, because the capability match is the only thing between that spec and a backend with no pull surface; and **`deliver` refuses by raising**, because returning `None` is a silent drop and a `refused` flag on `LandedArtifact` is a check every consumer must remember and one will not.

**A name unknown when the tool is built can still be known before the collection runs**, and that road is declared rather than discovered. A spec sets `outputs_named_at_call_time`, and `collect_outputs(outputs=...)` is refused without it — so a kind cannot quietly collect paths its attach-time declarations never admitted to, which is what keeps every attach-time question (is a sink required, does the cap apply, must the backend serve the pull surface) answerable from the spec alone. `DeclaredOutput` splits `path` from `name` for the same workload: `acquire` is get-or-create, so a kind whose outputs would otherwise persist into the next round needs a per-call directory, and the run id in the guest path is not something the host's namespace should inherit. `path` is what the backend reads; `name` is what the sink receives; both are held to the invariant below, and collisions are keyed on the delivered name.

### Names

The library enforces a **narrow invariant** and no more: relative, no traversal, no separator beyond the declared output's own, no segment that names nothing (`a//b` and `a/./b` are `a/b`, and delivering both spellings would land two artifacts for one file), no control character, bounded length, valid UTF-8. It does not guarantee the name is legal at the destination, because it cannot — legal names differ between a blob container, NTFS and a file store. **Hosts still own their own namespace rules.** Control characters are the one rule that reaches past the guest's grammar and it is not overreach: no filesystem anywhere accepts a NUL or a newline, so refusing them decides nothing a destination might have decided differently.

The length bound is checked against the name **as it will be delivered**, after normalization. NFC is not length-non-increasing — 85 × U+0958 is 255 bytes decomposed and 510 composed — so checking the declared spelling would be checking a different name.

`portable_file_name()` ships as an **opt-in helper**, covering Microsoft's authoritative set and nothing beyond it: `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, **and the ISO/IEC 8859-1 superscript variants `COM¹ COM² COM³ LPT¹ LPT² LPT³`**, all reserved with an extension too (`NUL.tar.gz` is `NUL`), plus `< > : " | ? *`, ASCII 0–31, and trailing dots and spaces. The superscripts are the entry that justifies shipping it at all — Windows reads them as digits, `echo test > COM¹` fails to create a file, and no host writing its own list will think of them. The set stops exactly at the documented one: `COM⁴` (U+2074) is not a digit to Windows and is a legitimate filename, and a helper that guesses beyond the spec starts mangling names that were fine.

Names are NFC-normalized before `deliver` sees them, because it is the one form all three filesystems recognise alike. `NameNormalization.NONE` disables **only the rewrite** — the narrow invariant still applies, and collision detection still compares normalized forms. We compare normalized and write what was asked for.

**Case-only collisions are refused across one collection**, since `Diagram.png` and `diagram.png` are two files on Linux and one on Windows and default macOS, and `collect_outputs` has every name in hand before it delivers any of them — the host receives artifacts one at a time and can never see the collision itself. The comparison is **lowercase, not casefold**: casefolding maps `ß` to `ss` and `ﬁ` to `fi`, so `Straße.png` + `Strasse.png` and `ﬁle.png` + `file.png` would each be refused as one file when they are two on Linux, NTFS and case-insensitive APFS alike. A cap that fails a whole collection has to be right about why.

**Never-overwrite is a contract clause, not a library guarantee** — the host does the writing, so the library cannot enforce it.

### The sink is structural, and that is why it is not declared

It is tempting to give the landing callback a role decoration like a host-tool call, or to stamp it as a sink automatically. Both are wrong. A host-tool call's role is genuinely ambiguous — source, sink, both, or neither — which is why its decorator makes every leg explicit. **A landing callback has no ambiguity**: data moves guest → host state, always. It cannot be a source. There is nothing to infer, so nothing to auto-infer. What is *not* structural is how confidential the destination is, and that is the one value the library refuses to invent.

### The confidentiality cap: one value, one source, no fold

`sandbox_tool_declarations` writes `max_allowed_confidentiality` only when the host passed a cap **and** the workload can carry something out: `bool(spec.egress_allow)`, or the spec declares an output that lands *and* a sink is attached, or a caller asserts `also_carries_out` for a flow the spec cannot show. The sink half exists because a landing sink falsifies the original premise — "a sandbox with no network cannot carry anything out of the conversation" is false once guest bytes reach host state with egress closed. Both halves of the second clause are load-bearing: a sink is ordinarily *one object handed to every sandbox tool a host builds*, so its presence alone says nothing about whether this workload sends anything down it, and capping a spec that declares no outputs or only `CONSUME` ones would gate calls for a flow that does not exist. A spec setting `outputs_named_at_call_time` satisfies the clause exactly as a declared `LAND` output does.

**The egress half reads the allowlist payload, not the mode.** `bool(spec.egress_allow)` is true of exactly one posture — an `allowlist` run that names hosts — so a spec running `unrestricted`, which reaches anything and names nothing, is *not* capped, and neither is an `allowlist` run with an empty list. The derivation predates the mode axis ([`network.md`](network.md)) and was never moved onto `spec.egress`. Until it is, a host that wants the cap on an unconfined workload writes it itself, the way `maf-sandbox-codeact` already writes one for a registry the spec cannot see.

**There is one value from one source, and nothing anywhere folds two.** The cap is an opaque string in the host's own vocabulary with no ordering, and this repository requires an ordering to be data with an exhaustiveness test, as `ISOLATION_RANK` and `INTEGRITY_RANK` are. `OutputSink` carries no cap of its own to be combined.

The host-tool registry does not fold either, and this is worth stating plainly because the source of record still describes a strictest-over-sinks fold as something the registry does. `HostToolAggregate.outbound_caps` is `frozenset(d.sink for d in declarations if d.sink is not None)` — **every declared sink cap, verbatim and unfolded** — because more than one distinct cap is the host's to reconcile against its own, never this package's to guess between. The registry, the `require_declared` gate and the seal all exist and shipped with the host-tools contract; the fold is the one part of that sentence that is absent, and deliberately.

The two paths meet in exactly one place, and no longer by hand. A registry can carry something out with **no landing artifact and no egress to say so** — a host-tool call is the flow — which is the one leg the spec-side derivation cannot see. So `maf-sandbox-codeact` passes `also_carries_out` when its surface has outbound caps or serves undeclared tools, and the derivation folds that one fact into its single rule rather than the kind writing a cap of its own. Which keeps the condition in one place, and means a key the rule learns later reaches this tool too. **Supplying both a sink and an explicit `declarations=` is refused** rather than resolved by precedence: an explicit mapping is written verbatim, so the pair would attach a tool whose declarations know nothing about its sink, with the cap silently absent instead of the one the host chose.

### What artifact landing is not

**It is not `HOST_TOOLS`.** Nothing inside the sandbox calls the landing callback; the kind calls it host-side after the run, so the no-host-tool-call property a CodeAct-class kind rests on survives intact. A host wanting a hard stop denies `FILES_OUT`.

**It is not a second write path into the file store.** A kind that lands artifacts where the agent's own file tools write has given model-written code an unapproved `file_access_write`, and one that can overwrite has given it a way to influence a *different* kind on the next call. `(key, kind)` sandbox identity separates sandboxes; it does nothing about host state they both touch.

**It does not change backend selection.** The router resolves a backend by name or position and checks the isolation floor; the capability match happens afterwards and **raises** rather than choosing a different backend. A host whose only backend lacks `FILES_OUT` gets an exception out of its agent factory, not a quietly-unattached tool. See [`policy-isolation.md`](policy-isolation.md) for the four checks and [`backends/README.md`](backends/README.md) for who serves what.

## Host tools: calling, outward

Calling host functions from inside a sandbox is the CodeAct pattern's differentiator and **the one capability where trust crosses outward**. The function body runs in the host process with the host's privileges, driven by model-written code, and each host-tool call bypasses whatever middleware the host runs — the boundary sees only the aggregate result. It ships as six layers.

| # | Layer | What it is |
|---|---|---|
| 1 | **Nothing is callable by default** | `HostToolRegistry` starts empty; every reachable function is one a developer explicitly registered |
| 2 | **A one-time, suppressible warning** | The experimental-warning shape, naming the property that surprises people: host-tool calls bypass the middleware chain |
| 3 | **A role-explicit decorator with no defaults** | `@sandbox_tool(source=..., sink=..., identity=...)` — each leg answered, each leg's `None` a considered "not that role". `source` is `SourceIntegrity`; `sink` is the host's own confidentiality vocabulary, verbatim; `identity` is `Identity` |
| 4 | **Per-leg aggregate derivation, over the relevant subset** | `result_integrity` is the weakest tier over *sources only* — a sink-only or pure tool must not drag the result to untrusted, and a registry with no sources has no integrity opinion at all. `outbound_caps` is every sink cap, verbatim and unfolded. Any `Identity.USER` tool sets `requires_approval` |
| 5 | **`require_declared`, the one door, and the seal** | The bridge resolves names *exclusively* through the registry, so registration is the only way in — and registration is where the declaration is captured, read once and never again. Enforcement fires at registration (raises: a host configuration error) and again at call time. Taking the aggregate **seals** the registry, so a later `register` is refused: mutation is answered by making it ineffective rather than by re-gating against it, which could never have caught a stamp swapped for another complete one. With the gate off an undeclared tool fails safe — untrusted source, `Identity.APP`, and `has_undeclared` on the aggregate so a host sees the degrade without diffing the folds |
| 6 | **Router-level denial** | `denied_capabilities={Capability.HOST_TOOLS}`, `denied_identities={...}` — for a posture that wants a hard stop rather than awareness |

Declarations are carried claims; enforcement is the host's middleware. A host without `agent_framework.security` loses nothing structural — registry, warning, gate and denials all function identically — and gains classifications that are ready the day it turns enforcement on. Declaring `source=trusted` protects nothing by itself; a claim without a reader is documentation, and the docs say so.

### The transport an `EXEC` backend can implement honestly

`host_tool_calls_over_exec(sandbox, run, layout, *, timeout, ...)` runs the guest program **detached** and supervises it until it exits, carrying calls as request and response files over `EXEC` + `FILES_IN` + `FILES_OUT`. `FILES_LIST` is deliberately not required. The kind writes its program and a generated shim into a fresh per-run directory; the supervisor writes the launcher, starts it, and polls.

**The shim is a convenience, not a control.** It runs in the guest, where model-written code can read, edit or bypass it, so every check it appears to make is decoration. Argument binding therefore happens **host-side, at the registry's one door**: `inspect.signature(...).bind(**provided)` proves names and arity, and anything deeper is the tool body's own duty because the body is host code. A callable whose signature cannot be read at all is not called.

The remaining bounds are the same shape — host-side, at the one door, and knowable before anything runs. A **per-run host-tool-call cap**; a per-run delivered-response count and byte budget, and a per-response ceiling, all reusing `TransferLimits`. Every one is checked *before* the tool body is called, because a sink tool's body does its work in the host process, and refusing after it has already acted means the effect happened, could not be reported, and reads to the model like something to retry. The transport's own framing counts against all three, so a per-response cap that cannot hold one byte inside that framing refuses outright rather than promising a response nobody could be handed. The supervisor removes the transport's own directory on every exit path; the run's working directory is left for the caller, which collects artifacts from it and reclaims it afterwards.

**One sentence to read before registering anything, because a declaration reads like a control and is not one: `Identity.APP` is not the safe option, only the declared one.** It is the application's full authority — for a deployed host, its workload identity with every grant it holds — and the only real bounds on it are the emptiness of the registry and the host-tool-call cap. Least privilege for host-tool calls comes from what a host registers, never from what it declares.

`Identity.USER` is **declarable but not servable**. Declaring it must be possible so a registry can be written honestly and refused loudly; serving it must not be until per-run token minting, an audience-within-egress check and the ephemeral `exec` env channel exist, or a host ships model-orchestrated user authority before anything bounds it. Registering one raises the whole `execute_code` surface to approval-gated; calling one is refused with those prerequisites named in the sentence the guest sees.

### Which backends serve it, and on what evidence

`HOST_TOOLS` is the one capability member with **no method behind it**, so what a backend asserts by declaring it is narrower than what the rest assert — narrow enough that both declaring backends spell it out at the declaration. The claim is that **`exec` detaches**: a process started by one call outlives it and is observable from the next, which is the whole of what the launcher-returns-at-once, exit-code-file-is-the-only-witness design rests on.

`maf-sandbox-docker` declares it because the container is the sandbox and stays up between calls. `maf-sandbox-acas` declares it because the microVM does — and that is the backend where it could not be taken on faith, since every call is an HTTP round trip to a remote control plane rather than a local daemon. Each measures it against the real thing in its own e2e rather than reading it off an SDK. It is **not** a claim about the image: the shipped launcher wants `sh`, `nohup`, `printf`, `mv`, `mkdir`, `rm` and `kill`, and a kind wants whatever interpreter it names, none of which a backend chooses, since `spec.image` does. That gap is the guest-platform axis's, and it is the same gap `EXEC` already has. `maf-sandbox-wslc` serves neither this nor `FILES_OUT`, so it cannot carry the transport at all.

A host-tool call carries the identity of the run it served: `HostToolRun` has a documented `run_id`, stable across the run and loggable, so an observer keys a per-run ledger or a trace on it rather than inferring the boundaries from latency.

## Identity — whose authority sandbox work carries

The token exchange is host plumbing in every case; what differs is **where the resulting authority is exercised**.

- **A. Control plane.** Backend configs take a **credential factory** — a callable read at call time, the `CallerContext` pattern — so acquire and dispose run under the app's identity or a per-request exchanged one, the protocol indifferent to which.
- **B. Host-tool calls acting as the user — recommended for user authority.** The body runs host-side and reaches the host's on-behalf-of plumbing; the credential never enters the sandbox, only results do. The decorator's `identity` leg is what makes it declarable, and any `Identity.USER` tool raises the aggregate to approval-gated.
- **C. In-guest provisioned credentials — vocabulary only, discouraged.** The declarations and refusal machinery exist so the pattern can be refused, audited and reasoned about. Hard-refuse under untrusted taint.
- **C′. The single-audience egress cell — the designed benefit case.** A logged-in user's on-behalf-of call runs inside a sandbox running `Egress.ALLOWLIST` with `egress_allow` *exactly* the target service: token audience **=** the one host the mode permits, so the token is spendable only at its audience, the response leaves only through the middleware-visible tool result, and attacker-shaped influence has nowhere else to go. That is network-enforced least privilege the host process cannot provide, since host-side only middleware stands between a confused tool body and the open network — so the taint softens to approval, the residual being misuse of the user's authority *at the one legitimate service*, bounded and visible. The token rides a **per-`exec` ephemeral channel** (`exec(..., env=...)`, a protocol addition not yet made) and never `write_file`, which persists across warm reuse, shows up in listings, and can echo back out.
- **D. Platform-attached, sandbox-scoped identity — recommended for service authority.** A per-sandbox managed identity exercised through platform connectors, so token material exists in nobody's code. Not the forbidden ambient: the micro-VM standard bars reaching identity that belongs to *someone else*, and an attached identity is the sandbox's own — declared, least-privilege, disposed with it.

Three obligations come with D, and each closes a way the pattern would otherwise be quietly weaker than it reads:

| Obligation | Why |
|---|---|
| **Granularity is declared and matched** — `IdentityScope.SHARED \| PER_SCOPE \| PER_SANDBOX` | A backend that would silently share where the spec asked for partitioned is refused. Sharing is the widening direction, and the widening direction is the one a match exists to catch |
| **Every authority channel out of a sandbox is spec-declared** | Platform connectors need not traverse the sandbox's network path at all, so `egress_allow` alone does not bound them — this is exactly the seam where [`network.md`](network.md)'s guarantees stop |
| **A spec carrying `ATTACHED_IDENTITY` must set a finite platform-side auto-delete**, refused otherwise | It time-bounds the worst case — how long a leaked sandbox retains authority when every host replica has died. Purge stays never-fail-the-delete, but failed *authority* reclamation is loudly observable: disposal now reclaims authority, not just compute |

Two composition rules. **`Identity.USER` never attaches**: managed identities are workload identities, and the closest D gets is `PER_SCOPE`, an identity per user or tenant whose RBAC is that user's resource partition. And **a provisioned user token has no `IdentityScope` at all** — it is call-time material, per-sandbox-per-run by construction, dead before the sandbox is.

**What is built today is the vocabulary and its enforcement points, not the plumbing.** `Identity`, the decorator's mandatory identity leg, `SandboxSpec.identities` derived from the registry's aggregate, and `denied_identities` on the router all came forward with the host-tools contract rather than waiting for the identity step. `ATTACHED_IDENTITY` exists as a capability name and no backend declares it.

`IdentityScope`, A–D's plumbing, and C′'s prerequisites are open, and they are three unrelated things wearing one number. Only the last has a live consequence: the refusal a `USER` host-tool call already returns is a promissory note that names those prerequisites in the sentence the guest reads, so it is the half worth scheduling against.

## Where the storage base comes from

A guest path is relative to something, and today that something is owned by nobody. A workload declares `work_dir` in its spec, no backend reads it, no backend creates it, and the protocol does not promise it exists. Every kind then composes absolute paths from a base the stack only hopes is there.

> **A backend allocates the storage base and resolves every path against it. Kinds address everything relative to that base and never compose an absolute path.**

It is the only shape that serves a backend whose store has no filesystem under it: such a backend cannot honour a POSIX base a workload invented, but it can resolve a relative name however its store works. It also matches the surface as it already stands — every `Sandbox` method takes a `working_directory`, and five of the six take a path to resolve against it. `work_dir` reaches a sandbox object exactly once per call, as that argument, because no sandbox object knows the spec: one holds an SDK client, another a runner and a container name, the in-process fake a dict.

**The override is first-class, not an escape hatch.** A kind shipping an image that pre-populates the base needs the base to be exactly where the image put it: bicep's `bicepconfig.json` is copied to a fixed root and found only by walking *up* from the file being compiled. So the override belongs on the spec, beside the image it travels with — `None` means the backend chooses, a value means *this image requires this exact base*.

Two dependencies, both real work. The first is closed: **`write_file` takes a working directory and participates in confinement**, so the asymmetry where the in-door accepted an absolute path the read surface would have refused is gone, and every path-taking method now refuses one that escapes. What has not moved is the base those paths are relative to.

The second is the open question. **Something still needs a real absolute path inside the guest.** The host-tool transport puts the shim's directory on `PYTHONPATH`, which the interpreter resolves against nothing — so either the launcher works relative to its own working directory, or the protocol gains a resolution step. `guest_call_path()` is correct either way: a path relative to a base is still a path, so nothing renames when the base moves.

`work_dir` stays **guest-native** in the meantime, and not by preference. A kind derives absolute paths from it and passes them into `exec`'s argv, and a backend cannot find a path inside an opaque argv without parsing arbitrary command lines — an argv *sequence* protects against quoting, not against paths within the arguments. The call-lifetime model this sits inside, and the reclamation that follows from it, are [`tool-call.md`](tool-call.md)'s; the capability that gates confinement rather than deletion is [`capabilities.md`](capabilities.md)'s; what a kind may assume about either is [`kinds/README.md`](kinds/README.md)'s.
