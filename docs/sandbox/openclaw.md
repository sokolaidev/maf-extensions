# Shared MCP workload service

The shared service exposes operator-selected workload operations through MCP to OpenClaw, MAF and other qualified clients. Each client owns agent turns and tool authorization; the service owns transport sessions, execution admission and cleanup. Workload bindings supply the input, execution and result contracts for individual kinds.

## Service and workload boundaries

The service is reusable host infrastructure. Adding a kind must not require changes to authentication, MCP session management, admission, cancellation routing or process ownership. A trusted startup composition registers workload bindings and their resources explicitly; it does not scan installed kinds, accept module names from clients or expose an arbitrary execution dispatcher. Discovery lists only successfully configured tools with unique stable names and concrete input/output schemas. Registration is fixed until a drained restart; duplicate names or an unsupported policy fail startup before readiness.

| Layer | Responsibility |
|---|---|
| Shared service | FastMCP/ASGI transport, authentication, request/session limits, global admission, call identity, cancellation supervision, readiness and shutdown ordering. It does not import Bicep, Terraform or draw.io implementations. |
| Workload binding | Named MCP operations and schemas, bounded input preparation, calls to the existing kind factory through the router, and bounded result/artifact projection. It receives trusted call context separately from model arguments. |
| Startup composition | Operator-selected bindings, router/backend resources, images, egress, timeouts, file stores and output sinks; retained cleanup scopes and resource lifecycle callbacks. Docker is the first configured backend, not a transport requirement. |
| Existing kind and backend packages | Workload behavior and sandbox execution through the existing protocol/router contracts. They acquire no FastMCP or HTTP dependency. |

The registration contract must declare input and serialized output limits, an operator-selected call deadline, required host capabilities, and resource ownership before a tool can be advertised. Shared supervision wraps every execution and holds admission until the binding task and resource cleanup settle, including after errors or repeated cancellation. Resource startup/recovery and shutdown hooks belong to the application lifetime, run once per registered resource rather than per MCP session, and unwind already-started resources if later initialization fails. Cleanup failure makes the whole service unavailable in this first version. Bindings retain their kind's completion, verdict and artifact semantics; the transport must not invent a Bicep verdict or successful result for another kind, and must not report success after uncertain cleanup.

The owner directory identifies the service deployment. Startup composition associates its retained owner with stable backend cleanup scopes, independent of MCP sessions and model arguments. Resource recovery preserves unrelated owners. The first Bicep binding preserves the prototype's existing owner format and scope so switching transport can recover prior containers. Adding or removing a resource mapping must reconcile its retained resources before readiness; generating a new scope is not a migration strategy. The Bicep deployment uses one Docker resource with local exclusive ownership.

The Bicep binding preserves the [stdio prototype](../../samples/experimental/openclaw_bicep/README.md)'s tool name, snapshot digest, compiler configuration/image identity, closed networking and result projection. Its in-memory source store and 120-second call deadline are binding policy, not assumptions in the shared transport. Other kinds register their own operations without forcing their inputs into Bicep's file-list schema. They still require bounded schemas, host policy and independent qualification. Artifact-producing kinds need an explicitly configured sink and bounded delivery/read contract; persistent kinds need trusted conversation ownership, retention and recovery rules. An MCP session ID is not durable conversation identity. Registering a callable alone does not satisfy those contracts.

The Bicep deployment exposes only the Bicep binding. Two small test bindings with distinct schemas and results must exercise the same registration and supervision path to prove the boundary without enabling another workload in that deployment. One global active call remains the limit across all registered tools; adding a second binding does not add a second admission slot. Automatic plugin discovery, remote tenancy, parallel scheduling and a new generic kind API are outside this service contract.

## Bicep operation and result contract

The first binding exposes exactly `bicep_validate(files)`. It validates every supplied `.bicep` and `.bicepparam` file as one source set; there is no entry-point selector, auxiliary JSON/text input, formatting, deployment, shell, arbitrary compiler flag or downloadable output. Local modules and parameter references must be included in that set. Discovery and the typed models in [server.py](../../packages/maf-sandbox-mcp/src/maf_sandbox_mcp/server.py) define the wire schemas; the HTTP and stdio bindings share them.

The request object contains only `files`, an array of 1–8 objects containing only string `path` and `content` fields. Names are relative ASCII slash-separated components, at most 200 characters overall and 64 per component. Traversal, absolute/drive paths, device names, duplicate case-folded names and file/directory overlaps are refused. Source must be valid UTF-8 without NUL, at most 64 KiB per file and 256 KiB total. Raw input checks supplement the generated JSON Schema: character counts do not establish UTF-8 byte limits. No rejected source is staged into a sandbox.

The adapter copies accepted strings into an immutable, sorted snapshot and a fresh in-memory file store for that call. `source_sha256` hashes UTF-8 compact JSON of the sorted `[path, content]` pairs, with non-ASCII content preserved. `config_sha256` hashes the exact UTF-8 operator configuration bytes; `image` carries the selected immutable image identity. These fields identify the submitted snapshot and policy, not a workspace's current contents.

| Result field | Contract |
|---|---|
| `completed` | Boolean; true only when the kind produced its completed validation result and cleanup is confirmed. |
| `verdict` | `valid` or `invalid` only for a completed call; otherwise null. Compiler errors can be a completed invalid result. |
| `status` | `ok`, `incomplete`, `timeout`, `error` or `cleanup_failed`; mappings below apply to admitted calls that return a structured result. |
| `diagnostics` | Untrusted text, at most 16 KiB UTF-8. Overflow removes completion/verdict and returns a bounded explanation; it does not present a truncated success. |
| `source_sha256`, `config_sha256`, `image` | Snapshot, compiler-policy and immutable image identities. Digests are attribution metadata, not host-enforced information-flow authority. |
| `cleanup` | `confirmed` or `failed`; cleanup uncertainty suppresses any verdict and poisons admission. |

| Outcome | Structured result and MCP behavior |
|---|---|
| Valid or invalid completed compiler result | `status=ok`, `completed=true`, corresponding verdict and `cleanup=confirmed`; invalid is not a transport failure. |
| Unprepared registry module, unreadable compiler report, incomplete compiler phase or diagnostic overflow | `status=incomplete`, `completed=false`, null verdict; confirmed cleanup is still required. A missing submitted local module can instead be a completed compiler error with verdict `invalid`. |
| Service request deadline | Cancellation is requested and work/cleanup are drained; a returned result has `status=timeout`, false completion and null verdict. A compiler-phase timeout can instead be reported by the kind as incomplete. |
| Unexpected framework result shape or execution failure | `status=error`, false completion, null verdict and bounded generic diagnostics; compiler text cannot manufacture completion or a verdict. |
| Unconfirmed cleanup | `status=cleanup_failed`, `cleanup=failed`, false completion and null verdict, even if compilation previously completed. New work is refused until explicit recovery. |
| Busy, unavailable session/service, unknown tool or malformed arguments | Bounded MCP/tool or protocol refusal as appropriate, without claiming a `ValidationResult` or allocating new workload resources. |
| Explicit cancellation, lost response or session shutdown | A structured result is not guaranteed to reach the caller. Transport acknowledgment and client-task completion are separate from supervised guest cleanup; an unknown result is not silently replayed. |

For structured returns, `error`, `timeout` and `cleanup_failed` set MCP `isError`; an incomplete compiler result is represented by its explicit completion/verdict fields. `structuredContent` is authoritative. The SDK-style JSON text mirror preserves one projected content item through the qualified OpenClaw path; it is not a second result. Both transports use the same Bicep projection.

### Host policy and filesystem boundary

Trusted startup selects an immutable local image ID or repository digest, compiler configuration/cache, backend, state directory, bearer credential and resource budgets. The Bicep composition explicitly admits `Isolation.CONTAINER` and call scope through `SandboxRouter`; it does not lower the router's default policy globally. A host requiring stronger isolation must select and qualify a compatible backend. The configured Docker limits are 1 GiB memory, one CPU, 128 PIDs and all Linux capabilities dropped. Compiler phases have 15-second deadlines; lifecycle commands use 10 seconds, cold image pulls 30 seconds, the owned-scope sweep 30 seconds and request cancellation 120 seconds. Settlement can exceed these cancellation deadlines.

Bicep uses `Egress.CLOSED`, the operator's prepared cache configuration and `--no-restore`. The prepared AVM profile contains selected pinned modules, not the whole registry. The host must keep credentials out of the image because compiler functions can read guest files. The adapter returns diagnostics only and makes no general guest-filesystem secrecy claim.

Inline names never select host paths. There is no host workspace mount or host file bridge, and the in-memory store cannot carry host symlinks, reparse points or hardlinks. Caller mutation after admission does not change the copied snapshot. This removes those host-path races from the admitted source surface; it does not qualify a future filesystem-backed provider. Configuration, token and retained owner files are trusted operator inputs outside agent-writable directories, not hostile file inputs protected by a new no-follow bridge. Any workspace/file/artifact extension must satisfy #1639/#1641's confinement and replacement-race acceptance before admission.

### Framework and installation decision

Use SDK-bundled FastMCP and the existing Bicep kind's MAF-backed tool callable, without a model-running agent or a separate `fastmcp` distribution. The adapter reads the fixed leading framework completion/verdict fields and refuses unknown shapes; it never searches diagnostics for authority. This is an explicit compatibility dependency, not a new public framework-neutral result API. Splitting core's MAF dependency or introducing such an API needs a separately justified consumer requirement and is not required for this first tool.

The supervised source installation uses Python 3.12+, uv, reachable Linux Docker, a prepared immutable image and the trusted compiler/owner/token files described in the [operator guide](../../samples/experimental/openclaw_bicep/README.md). `uv run --script` installs declared dependencies, while the adapter modules themselves still come from the checkout. The qualified historical baseline is OpenClaw 2026.9.7, MAF core 1.19.0, MCP 1.28.1, core/Bicep/Docker 0.46.0/0.22.0/0.24.4 and Uvicorn 0.54.0. Capture the full resolver manifest: the source sample's ranges do not pin every transitive package or force MAF 1.19.0.

[`maf-sandbox-mcp`](../../packages/maf-sandbox-mcp/README.md) delivers #1898 as an installable wheel and fixed `maf-bicep-mcp` entry point, preserving runtime/binding separation. Its [installed-worker qualification](research/openclaw-gateway-qualification.md#installed-worker-qualification-2026-10-13) records clean installation outside the checkout, MAF 1.20.0 compatibility, real Gateway/console behavior, owned cleanup and a bounded network denial probe. The preceding source-only recipe and historical baseline remain separate evidence. SDK private session access, Uvicorn protocol hooks, the MAF projection and image changes require renewed evidence for the affected contract. Publication remains a separate maintainer action.

## Process and transport

One independently supervised Python process serves stateful Streamable HTTP at a fixed operator-selected `http://127.0.0.1:<port>/mcp` endpoint. It uses SDK-bundled `mcp.server.fastmcp.FastMCP` with `mcp==1.28.1`, JSON responses to POST requests, and separate MCP sessions for each connected client. It has no event store or replay of completed results. SDK-managed GET streams remain supported for client compatibility. Stateless HTTP is excluded: a cancellation notification must reach the same MCP session that owns its request.

The operator starts the service separately from OpenClaw. OpenClaw's `mcp.servers.bicep` definition uses `transport: "streamable-http"`, the fixed URL and an operator-provisioned authorization header; it does not launch the Python worker. MAF uses `MCPStreamableHTTPTool` against the same endpoint. The bounded two-session [Gateway qualification](research/openclaw-gateway-qualification.md#two-session-http-execution-2026-10-05) uses OpenClaw 2026.9.7 with its TypeScript SDK 1.30.0 and MAF core 1.19.0 with Python MCP 1.28.1. This pin also passed the HTTP session, cancellation, retirement, MAF-client and Docker regression tests; the earlier MCP 1.26.0 results remain historical. Other versions require their own evidence. Stdio remains the script's default; HTTP is explicit opt-in. The two modes are mutually exclusive for the same owner directory.

The ownership lock, registered backend resources, workload bindings and global admission slot belong to the outer ASGI application lifetime. They are constructed once, before transport sessions, and are released after all work settles. FastMCP's per-session server lifetime cannot own these shared resources. There is exactly one ASGI worker, no automatic code reload and no independently initialized worker pool. Startup persists the retained owner state and sweeps only that deployment's scope before accepting connections. A second service process using the same state directory refuses startup.

## Authority and admission

All clients represent one trusted local operator with uniform policy. Authentication uses a random bearer credential with at least 256 bits of entropy, held in operator-controlled storage outside agent workspaces and supplied through trusted client configuration. The service reads its credential and the immutable operator policy for every registered binding at startup. It authenticates every MCP HTTP method before session allocation, parsing or dispatch; missing or invalid credentials receive 401. Rotation drains and restarts the service and reconnects clients. Logs exclude credentials, source contents and raw session IDs.

The listener binds only IPv4 loopback. An exact Host allowlist includes the selected address and port; all requests carrying an Origin header are rejected with 403 for this non-browser deployment. Wildcard origins, redirects, reverse proxies, external listeners and remote multi-tenancy are outside this design. Loopback authentication does not establish isolation from a compromised process running as the same OS user. These rules implement a local deployment contract, not an OAuth authorization server.

MCP session IDs and JSON-RPC request IDs route messages; they do not authorize filesystem access, select an owner or identify an OpenClaw agent. The adapter associates each active call with the authenticated transport session and request ID, independent of tool arguments. Duplicate live request IDs within one session are rejected before SDK dispatch. Numeric and string IDs remain distinct, including during cancellation. The adapter translates typed client IDs to private SDK stream keys, preventing collisions with the pinned transport's string-keyed request map and reserved GET stream; JSON responses restore the original client ID. Equal IDs in different sessions remain independent. A leaked session ID cannot replace the bearer credential, and clients sharing that credential are not mutually distrustful tenants.

One service-wide admission slot permits one tool call at a time across all bindings. Contention returns a bounded MCP tool error without a workload result; it creates no queue or sandbox. The active slot remains held through cancellation and disposal. Each admitted call receives host-minted call identity and isolated call state; the Bicep binding keeps its fresh in-memory file store and immutable source/result contract. Image selection, backend, egress, configuration and resource limits remain operator-owned; Bicep retains closed guest networking. Session closure never sweeps shared backend scopes; only the global owner does, after active work settles.

## Bounded transport sessions

The session adapter owns a registry capped at eight records, including initializing and closing sessions. Allocation is atomic and occurs only for a valid authenticated initialize request without a session ID. Unknown IDs receive 404; malformed initialization and ordinary requests without an initialized session allocate nothing. A full registry returns 503 without creating another SDK transport. The service removes a retired record only after its transport and any associated call have settled. Idle sessions expire after 15 minutes without an authenticated client request; an open GET stream alone does not refresh this timer. Active work is never evicted to make room.

The pinned SDK retains explicitly terminated transport records, so HTTP mode uses an encapsulated session-manager integration that bounds both the adapter registry and SDK state. A cap on a second dictionary alone is insufficient. The [experimental HTTP adapter](../../samples/experimental/openclaw_bicep/workload_http.py) owns the SDK transports directly and runs FastMCP's underlying server; it does not create the default retaining manager or a redundant outer registry. Private SDK access is isolated, documented against 1.28.1 and covered by churn/retirement tests. FastMCP defaults alone do not bound retained session state.

Each POST is limited to 2 MiB before JSON parsing, counting streamed/chunked bytes as well as Content-Length; exceeding it returns 413. Request-body assembly has a 10-second deadline. The HTTP server permits at most 32 accepted connections and 16 KiB of request headers per request; the adapter allows at most 16 simultaneous POST body readers and one GET stream per session. Cancellation and DELETE must remain usable while a workload is busy. Admission checks occur before expensive schema processing, and every rejected request releases its transport budget. Slow readers, excessive headers and connection churn are explicit acceptance cases; this local service does not claim resistance to denial of service by its OS owner.

## Cancellation, shutdown and recovery

An explicit MCP cancellation applies only to its transport session's matching request. It requests cancellation of that call and retains the existing repeated-cancellation drain. A protocol acknowledgment does not release admission or prove workload termination. A bare HTTP disconnect does not cancel work: the caller's result may be lost, while the service continues supervising the call. The binding's configured request deadline (120 seconds for Bicep) triggers a cancellation request if the call has not settled. Cancellation settlement and cleanup can take additional time, during which admission and ownership remain held. Gateway turn cancellation must be qualified through the client's actual MCP notification path. A service-side deadline is a fallback, not a hard maximum container lifetime.

DELETE marks that MCP session closing, rejects new work from it and requests cancellation of its associated call before transport retirement. The response acknowledges session retirement, not completed sandbox cleanup. Closing an idle session leaves another session's active call untouched. Losing a GET stream has no process-lifetime effect. An idle-session expiry uses the same retirement path. Control requests and cleanup run without holding a registry lock across waits, so a closing session cannot prevent another client's cancellation or admission checks.

Graceful service shutdown stops admission, retires transport sessions, drains the active call, verifies the final owned-scope sweep, then releases the process lock. Cleanup uncertainty poisons global admission and requires recovery; a clean-looking MCP connection cannot override it. Failed session retirement retains its capacity reservation, reports a diagnostic without session or source details, and retries once per second while global admission remains poisoned. Shutdown waits for that retirement to settle before releasing resource ownership. If draining hangs, the service retains ownership and reports that it is not ready. A supervisor must not start a replacement while the lock is held. Forced process death can leave a container, which the next owner reconciles after acquiring the retained lock. No independent watchdog or hard recovery deadline is claimed.

Gateway restart/reload affects its client sessions, not the service process. Service restart invalidates all old MCP session IDs, which receive 404; clients establish new sessions. A client does not silently replay a tool call whose outcome became unknown. A deliberate retry is a new call; for Bicep it validates a newly submitted snapshot, even if its bytes match. The service stores no cross-call source or result history. Policy changes use a drained service restart. Retained ownership cannot be moved to another backend endpoint without operator reconciliation. The [bounded lifecycle execution](research/openclaw-gateway-qualification.md#reload-restart-and-withheld-result-execution-2026-10-05) qualifies hot reload, idle Gateway process replacement, graceful service restart and one withheld completed result returned as a transport error. The [selected active-service crash execution](research/openclaw-gateway-qualification.md#active-service-crash-and-retained-owner-recovery-2026-10-06) establishes compiler survival after forced service exit, retained-owner cleanup of a deliberately paused orphan before readiness, and reconnection without replay. The [startup cleanup-refusal execution](research/openclaw-gateway-qualification.md#startup-cleanup-refusal-and-explicit-gateway-recovery-2026-10-06) also qualifies refusal while a paused orphan cannot be cleaned, followed by retained-owner recovery and an explicit idle Gateway restart to rebuild discovery. Later recorded cases qualify post-completion cleanup-confirmation refusal, selective active/idle deletion and the bounded discovery recovery below. Subsequent [connection-loss](research/openclaw-gateway-qualification.md#docker-connection-loss-and-retained-resource-recovery-live-result-2026-10-10) and [daemon authorization-denial](research/openclaw-gateway-qualification.md#daemon-authorization-denial-and-retained-resource-recovery-live-result-2026-10-11) runs qualify selected real Docker cleanup failures; the closure audit separates remaining requirements from broader interruption cases. Windows retains the prototype's process-restart recovery limit; host-crash durability remains separately unqualified.

Service readiness and Gateway discovery are separate observations. With pinned OpenClaw 2026.9.7, both [capacity refusal](research/openclaw-gateway-qualification.md#delayed-discovery-recovery-without-restart-live-result-2026-10-08) and [initial service absence](research/openclaw-gateway-qualification.md#initial-service-absence-and-two-session-recovery-live-result-2026-10-08) recover without restarting Gateway in the selected executions. After the service is ready and the startup cooldown has elapsed, a new turn triggers catalog refresh but still returns the stale-catalog error; a separately submitted turn then executes work. The checks use a 35-second margin, not a guaranteed recovery deadline, and verify that failed turns are not replayed. Recovery from poisoned resource cleanup remains a separate condition requiring the service recovery described above.

The [accelerated idle-expiry execution](research/openclaw-gateway-qualification.md#accelerated-idle-expiry-and-active-session-isolation-live-result-2026-10-09) qualifies the existing sweeper with a two-second fixture threshold, restored to the 900-second default after one idle registration drains. An active compiler and its MCP session survive; subsequent work reuses that session and reconnects the expired one with a fresh identity. The expired transport receives HTTP 404 on GET/DELETE before reconnection. The [default-duration execution](research/openclaw-gateway-qualification.md#default-15-minute-idle-expiry-live-result-2026-10-09) separately qualifies the unchanged 900-second policy while A receives periodic new calls. B expires after 900 seconds of measured transport inactivity, then reconnects for new work without replay. Accepted control notifications can refresh that clock without running a workload. Broader timing races and prolonged churn remain unqualified.

The [Docker connection-loss cleanup case](research/openclaw-gateway-qualification.md#docker-connection-loss-and-retained-resource-recovery-live-result-2026-10-10) requires real CLI connection refusal, independent evidence of retained resources, refused admission in both sessions, and removal before replacement readiness. Recovery preserves ownership and does not replay aborted work.

The [Bicep HTTP/MAF ownership execution](research/openclaw-gateway-qualification.md#bicep-http-ownership-and-independent-maf-closure-live-result-2026-10-11) qualifies equal-ID/repeated cancellation, active response-only connection loss and independent active/idle MAF closure. In the pinned MAF client, an outstanding call can remain pending until its request timeout after service cleanup and transport retirement; hosts must manage their awaiting client tasks separately from guest ownership.

## Acceptance before enabling multiple Gateway sessions

The real workload cases below qualify the Bicep binding. The service-boundary case uses test bindings and does not qualify additional production kinds.

| Case | Required observation |
|---|---|
| Service and binding boundary | Register two test bindings with distinct schemas/results and verify discovery, duplicate-name refusal and missing-capability refusal before readiness. Hold A in one binding; B in the other receives busy without execution. Exercise cancellation routing and drain, result/size bounds, partial startup rollback and cleanup failure across both. Core service modules must not import concrete kinds or backend implementations; Bicep keeps its existing schema and projection. |
| Two real Gateway sessions | Both discover only the authorized validator and independently produce valid, invalid and incomplete results with matching input/config/image identities and one projected content item. Use published Python dependencies and the pinned OpenClaw installation. |
| Shared admission | Hold A inside compilation; B receives busy with no extra container. After A's confirmed cleanup, B succeeds. No fairness or parallel compilation is promised. |
| Cancellation isolation | Send equal JSON-RPC IDs from two transport sessions. A cannot cancel B's matching ID. Cancel A repeatedly during active compilation and disposal; busy remains until A settles, then B succeeds. |
| Session closure | Closing idle A preserves active B. Closing active A retires only A, keeps the global slot until cleanup, and leaves B connected. Exercise both MAF close and OpenClaw disposal. |
| Disconnect semantics | Drop only the HTTP response stream and observe continued bounded supervision. Separately abort a Gateway turn, capture the MCP cancellation notification and verify exact-container cleanup; do not infer notification delivery from a disconnected socket. |
| Restart and reload | Reload one client's configuration, restart Gateway, and gracefully restart the service. Verify invalidated IDs/reconnection, no implicit request replay, preserved unrelated owners and successful later calls. |
| Authentication and framing | Reject missing/wrong credentials on POST, GET and DELETE; bad Host/Origin; malformed bodies; oversized Content-Length and chunked bodies; duplicate live IDs and ordinary uninitialized requests. No rejection allocates a sandbox or leaks submitted bytes. |
| Resource bounds | Fill all eight records, including initialization/retirement races; ninth initialization fails without allocation. Cycle at least 100 sessions, verify SDK and adapter records return to zero after retirement, exercise idle expiry, slow bodies and GET/connection limits. |
| Failure and recovery | Inject cleanup failure and repeated cancellation; all clients observe refusal until recovery. Kill the service with an active container, then restart with the same owner and verify startup cleanup. This selected crash case does not complete the whole interruption matrix. |
| MAF compatibility | Two real `MCPStreamableHTTPTool` instances discover and call with static authorization headers, preserve structured-result projection and close independently. Repeat with the exact published dependencies selected for the implementation. |

Acceptance uses a deterministic provider and host-observed results, transport messages and container identities. It makes no claim about LLM reasoning, prompt-injection resistance, information-flow enforcement in OpenClaw or unattended operation. The [research record](research/openclaw-integration.md#multi-session-lifecycle-decision) contains the option comparison and the smaller transport probe that informed this design.

## Installed Bicep conformance runner

The repository-local [runner](../../scripts/openclaw_conformance/__main__.py) qualifies the fixed `installed-bicep-windows-v4` profile against an explicitly selected candidate. It installs OpenClaw 2026.9.7 and the published `maf-sandbox-mcp` 0.1.0 wheel into a fresh external directory, verifies every installed Python wheel and npm dependency payload against its locked archive, including native files, and freezes a complete runtime file inventory. Installer-generated launchers and metadata are listed separately and bound by that inventory; they are not claimed to be archive payloads. Preflight, installed checks and postflight reject changed, missing or additional files. It also verifies installed imports and records complete dependency, host, image and configuration identities. The historical MAF 1.20/core 0.48 qualification is a different candidate; the published worker requires core 0.50 and its compatible MAF range.

Use a private external directory, Node compatible with the pinned OpenClaw release, uv, and a reachable Docker daemon running Linux/amd64 guests. Pull the selected immutable prepared Bicep image first. Preparation reaches package indexes; the deterministic campaign needs no model account and does not deploy Azure resources. Linux is deliberately outside this profile.

```powershell
$prepared = Join-Path $env:TEMP ('oc-install-' + [guid]::NewGuid().ToString('N'))
$campaign = Join-Path $env:TEMP ('oc-campaign-' + [guid]::NewGuid().ToString('N'))
$image = 'ghcr.io/sokolaidev/maf-extensions/bicep-avm@sha256:b3f14b266052def3f7b5a7b6ca4fb38f06acdff0e99e7df2437dd4f0c6b0b82e'
uv run --no-project --python 3.13 python -m scripts.openclaw_conformance prepare --output $prepared --image $image
uv run --no-project --python 3.13 python -m scripts.openclaw_conformance run --prepared $prepared --manifest "$prepared/candidate.json" --output $campaign
uv run --no-project --python 3.13 python -m scripts.openclaw_conformance evaluate --bundle "$campaign/evidence" --plan "$campaign/plan.json" --manifest "$prepared/candidate.json"
```

Check each command's exit status before continuing. `prepare` refuses an existing installation directory and writes `candidate.json` only after installation checks. `run` requires a new output directory, freezes its plan before observations and writes an atomic summary on failure as well as success. `evaluate` takes the expected plan and candidate separately from the evidence bundle; a report cannot remove required groups or choose its own expected identity. Keep these expected inputs trusted. Hashes bind recorded bytes, not their truth; the runner and independent host observers remain part of the qualification trust boundary.

The finite campaign retains the existing 43 transport cases and 109 SDK retirements, five Bicep/MAF ownership cases, two Gateway sessions each receiving valid/invalid/incomplete results, a prepared-module compiler call, configured/input refusal, worker import guards, paired reachable/closed TCP probes, and independently observed cleanup. Direct ASGI, socket, installed compiler and Gateway observations retain separate attribution. Python audit guards observe selected worker import effects, including delayed/late-exit controls; they are not an OS sandbox or a new OpenClaw credential/non-full-plugin qualification. The Gateway uses a local deterministic provider, with no model-reasoning claim.

Keep the entire preparation and campaign directories private: they contain service credentials, temporary configuration, locks and diagnostics. The bounded `evidence/` records, expected candidate and plan are intended for sanitized retention after inspection; raw logs, dependency-lock command comments and provider state are not public artifacts. Each group has a unique attempt ID and its own bounded artifact. The evaluator requires the exact expanded transport case IDs and independently checks response-loss attribution; installed worker and npm bytes are checked again after runtime probes. Failed attempts remain in their own directories. Do not retry into an existing directory or relabel a previous report. Missing controls, mismatched artifacts, skips, incomplete cleanup or emergency purges cannot qualify the profile. The supervisor owns only its recorded processes/containers and verifies an unrelated sentinel survives; no daemon-wide pruning occurs.

Changing runner/adapter bytes, dependencies, the host/engine, image or configuration requires a new candidate and campaign. Preparation records both the full dependency versions and hashed locks; preserve those private locks when reproducing an exact resolution. A passing report does not authorize publication, production adoption, unattended recovery, arbitrary filesystem access, native MXC, credentials, or another platform. The [bounded actor-loss campaign](research/openclaw-gateway-qualification.md#bounded-actor-loss-qualification-2026-10-20) qualifies #1973 on its separately recorded candidate; conditional Windows/MXC file-boundary qualification remains #1974.

## Bounded actor-loss profile

The additional `owner-loss-windows-v1` profile selects one unbroken control, all twelve Gateway/external-caller/worker combinations at pre-admission, observed compiler execution, completed-but-undelivered response and owned-container removal barriers, and two worker-recovery refusal controls. The external caller is a separate process sending HTTP to the Gateway; killing it leaves the Gateway alive. A pre-admission caller or Gateway loss can therefore still admit one call. Missing client delivery never establishes that compilation did not happen.

The [fault runner](../../scripts/openclaw_conformance/owner_loss.py) requires a complete installed-Bicep baseline for the exact same candidate, verifies installed bytes before and after the campaign, and freezes its own required cases and deadlines before starting. Every case owns separate processes, worker state and a sentinel resource. Fault injection terminates the identified actor through a retained Windows process handle after proving membership in the fixture's job. Final job termination and leftover removal are independent harness cleanup. They do not count as worker self-recovery.

Recovery retains the locked deployment owner, starts a fresh worker and requires confirmed cleanup before readiness. Token rotation is an explicit operator action. The profile tests old-token refusal separately from old-session refusal, including cancellation and DELETE while a fresh compiler call remains active. Surviving-worker settlement requires the target request's terminal record and an inactive service snapshot; `/ready` alone is insufficient. Gateway sibling checks reuse a session established before the fault. Replacement workers use new sessions. The large workload used to observe an active compiler may finish with an incomplete verdict; its recorded result must still confirm cleanup and exclude cancellation. Separate simple control and sibling calls must produce valid results.

Connection-unavailable recovery uses a private Docker context with an unreachable reserved loopback endpoint. Removal-denied recovery uses the existing [dedicated authorization daemon](research/openclaw-gateway-qualification.md#daemon-authorization-denial-and-retained-resource-recovery-live-result-2026-10-11), with its pinned image, locally compiled Go authorization plugin, mutual TLS and exact target/client/nonce correlation. It requires Go and the profile's already-pulled Docker-in-Docker image. The privileged disposable daemon is a scoped test control, not a stronger isolation claim about the parent engine. Its resources and the main worker's resources have separate cleanup observers.


Check each exit status. A failed case remains failed; the runner proceeds to independent cases only after confirmed harness cleanup. An interrupted child or failed parent supervisor cannot turn a child report into a pass. Repeated runs use fresh directories and distinct attempts. All required cases, both recovery controls and cleanup must pass before the evaluator emits `qualified_for_profile`.

If only the qualification sources change, `python -m scripts.openclaw_conformance.owner_loss bind --prepared <installation> --manifest <old-candidate.json> --output <new-candidate.json>` verifies the retained installation and writes a new candidate bound to the committed runner. It establishes no qualification. Run a fresh installed baseline with the new manifest before using it for faults; an old baseline cannot be transplanted to the new candidate.
