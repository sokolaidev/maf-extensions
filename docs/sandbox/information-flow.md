# Information flow

> What a kind is allowed to claim about the result it hands back, and why the claim is not about who wrote the bytes. The framework's vocabulary, the one rule that decides every declaration, what its input-label join does not establish, and the rules a kind is held to. The decision is recorded in [#774](https://github.com/sokolaidev/maf-extensions/issues/774); [`hosts.md`](hosts.md) owns the sink and identity legs of the same seam.

A tool result is persisted into a conversation and read back by the model on every later turn. If it carries text an attacker shaped, the conversation now contains an instruction the model may follow — and the framework's information-flow module exists to notice that and stop it. A sandbox is what makes the work safe to *run*; this document is about what is safe to *say* about the answer.

## What the framework tracks

MAF's information-flow module (`agent_framework.security`, FIDES) attaches a label to every tool result and carries a running label for the conversation. A label has two independent axes:

- **Integrity** — `trusted` or `untrusted`. Where the content came from, not whether it is correct. Standing guidance a package emits is trusted even when it is wrong; a compiler's diagnostic is untrusted when the template it describes was model-authored, however accurate it is. The axis exists to say whether content could carry an instruction an attacker chose, so provenance is the test and truthfulness is not.
- **Confidentiality** — `public`, `private`, `user_identity`, ordered. How far the content may travel. This suite never orders or folds confidentiality values; they are the host's own vocabulary, carried verbatim ([`hosts.md`](hosts.md)).

Labels combine by most restrictive: one untrusted input makes the combination untrusted. Integrity is a ratchet — once untrusted content becomes visible in a conversation, the conversation stays untrusted, and the policy middleware then refuses every later tool that has not opted in to running in one.

**A word this repository does not use for an integrity value: *tier*.** It already means the grounding level here — `T0` is the model checking its own work, `T2` is compiler truth — and it separately means FIDES's label-propagation priority, below. An integrity value is a **label**, or a **level** where "label" would collide with the framework's `ContentLabel` object. Confidentiality is the exception the rename leaves alone: where a document says "a host's confidentiality tiers" it is describing the *host's* own vocabulary, which this suite carries verbatim and never orders.

## Where a label comes from

FIDES resolves a result's label by a strict three-tier priority, and *tier* is its word for that priority rather than for any value:

| | Source | Used when |
|---|---|---|
| Tier 1 | per-item `security_label` on each returned item — the whole label, **both axes** | always wins if present |
| Tier 2 | the tool's `source_integrity` declaration | no per-item labels |
| Tier 3 | the join of the call's input argument labels — its **integrity** only; confidentiality comes from the tool, never from the join | neither of the above |

With none of the three, the result takes the middleware's `default_integrity`. That is `untrusted`, it is the fail-safe direction, and it is what this suite relies on — but it is a constructor argument on `LabelTrackingFunctionMiddleware` and on `SecureAgentConfig` rather than a constant, so what a kind gets for saying nothing is a host's setting. Measured landing on *trusted* against a host that moved it ([`research/laundering-into-the-file-store.md`](research/laundering-into-the-file-store.md)).

**Tier 2 replaces tier 3; it does not floor it.** A tool that declares `source_integrity` instructs the middleware to disregard what it knows about that call's inputs. This is the single fact every declaration in this suite turns on, and it is why the question a kind has to answer is mechanical rather than a matter of judgement.

## The rule

**A kind may declare `trusted` only where its result does not derive from input the framework has not established as trusted.**

Authorship is not the test. That a package formatted the string, or that a first-party compiler emitted it, says nothing about the trust of what it was formatted *from*: a compiler is deterministic about a template the model wrote, and its diagnostics quote that template's identifiers back verbatim. Freedom from influence is not the test either, at least not as a separate one — it is what derivation measures.

Three questions settle a **`trusted`** claim. When an `untrusted` declaration has to be explicit rather than left to the join is decided separately, below:

1. What are the result's actual sources — every channel that reaches it, not only the arguments: the file store it reads, an allowlisted host the program may fetch from, a host-tool registry it may call back through.
2. Is each of those established at least as trusted as what this tool is about to declare?
3. What of them survives into the result — as text, as a number, as the presence of a line?

**The join is a lower bound on the first question, never the answer to it.** Where it says something weaker than the declaration, the declaration is suppressing what the framework knows. Where it says nothing, the framework knows nothing — and a source it never observed is still a source. So a trusted labelled argument does not license the declaration on its own: it settles one channel and is silent about the rest.

A **`trusted`** declaration is honest only where every surviving source clears question 2, or question 3 answers *nothing*. Read "clears" strictly: a source is cleared by being established **as trusted**, and a source established as *untrusted* is the opposite of cleared — the registry fold answers either way, so establishment on its own settles nothing. Of the sources in *What the input-label join does not establish* below, the file store and an allowlisted host establish nothing at all in either direction. A host-tool registry is the exception: its fold does establish the integrity of the tools registered in it, and a kind that serves them can read it — but it settles that source and no other, so a registry folding to `trusted` clears one source while the store behind the same call stays unestablished. Neither shipped kind clears *every* surviving source, so neither may declare `trusted`; both declare nothing today, and moving them to an explicit `untrusted` is [#840](https://github.com/sokolaidev/maf-extensions/issues/840).

**Declaring nothing is a supported answer, and it is a delegation rather than a fail-safe.** It is not an omission to be filled in later; it hands the question to the input-label join, which is where a workload running model-authored code belongs. Note what that does and does not promise. The join propagates whatever labels the arguments carry, so a call with a trusted labelled argument yields a *trusted* result; where it finds no labels at all the result takes the host's `default_integrity`. What keeps every kind here on the untrusted answer today is that every value they take is a plain unlabelled string and that no host in front of them has moved that default — a property of their signatures and of a deployment, not a guarantee of the rule.

**So declaring nothing is not universally safe, and two separate routes launder exactly as a false `trusted` would.** A kind whose visible arguments carry a trusted label, while an unestablished source still reaches its result out of band, gets a *trusted* result out of tier 3 — with no declaration written anywhere, and the rule above broken all the same. A kind on a host that raised `default_integrity` gets one out of the no-labels branch, and **that route asks nothing of the kind's signature**, so no shape of arguments defends against it. Both are measured ([`research/laundering-into-the-file-store.md`](research/laundering-into-the-file-store.md)). Where an unestablished source may survive into the result, a kind therefore declares `untrusted` **explicitly, for the whole tool**: an explicit `untrusted` is a tier-2 declaration, so it overrides the join and the default alike, and it puts the claim where the framework reads it instead of in a comment beside an argument that is not there. Not per item — an untrusted per-item label carries a confidentiality this suite has none to give (below), while the tool-level declaration leaves the confidentiality resolution alone. Delegating is an answer only where the delegate cannot answer trusted, and a kind reading content out of the agent's file store cannot establish that, because neither route is its to control.

## What an untrusted result actually costs

Less than it appears, and the difference decides whether a kind can afford to be honest.

FIDES hides an untrusted result by default: the item is replaced by a variable reference the model can pass to another tool without reading, and **hidden content does not taint the conversation's integrity** — only what stays visible does. Its *confidentiality* still counts: the framework folds a hidden item's confidentiality into the conversation, so a hidden item labelled above a sink's cap can still close that sink. Nothing in this suite writes a result-side confidentiality of its own, and a per-item label carries one whether a kind meant it to or not — which is why the split below labels as few items as it can. From a clean conversation, then, an honest untrusted declaration keeps the conversation's integrity clean and costs the model its sight of the result.

**Hiding is a first-taint protection, not a redaction.** It applies only where all of four conditions hold: `auto_hide_untrusted` is on, the item is untrusted, the tool is not `inspect_variable`, and **the conversation is still trusted**. The last is the one that decides how far the paragraph above reaches. Once anything has tainted the conversation, hiding stops: a later untrusted result is visible, and the model reads it. So the trade holds while the conversation is clean and lapses when it is not, and a host that admits this workload into an already-untrusted context gets neither half of it — not the hidden result, and not the clean conversation it was protecting.

Where a host has turned hiding off, the untrusted result is visible from the first call, the conversation goes untrusted, and the policy middleware refuses subsequent tools that have not opted in. Both behaviours are the framework's, measured against `agent-framework-core` 1.13.0 and 1.16.0 — the floor this suite declares and the newest published at the time of measuring — whose `agent_framework/security.py` are byte-identical to each other. The declared range `>=1.13.0,<2` admits any later 1.x, which no measurement here covers. The reproducer is in [#774](https://github.com/sokolaidev/maf-extensions/issues/774).

That trade — a clean conversation against a blind model — is the whole difficulty. Splitting the result narrows it rather than dissolving it: it rescues whatever a kind can say without reference to the call, and leaves everything derived from the guest program on the wrong side of it. For a kind whose product *is* the derived half, `bicep_validate` above all, the trade is unchanged for the part the caller wanted, and a host that needs the model to read it is choosing taint.

## One result, two labels

A result is not uniformly derived. `execute_code` withholding its streams returns an exit status the guest chose beside a fixed sentence naming the recovery route; `bicep_validate` returns the compiler's diagnostics, and the same shape would put standing guidance beside them. Collapsing those into one label forces a kind to be either dishonest about the derived half or useless about the half that derives from nothing.

So a kind returns **items, each carrying its own label**, and the rule above is applied to each item separately.

**An item may be labelled trusted only where its value *and its presence* are both independent of every source not established as trusted** — the same test as the rule above, applied per item rather than per result. A source the framework established as *untrusted* counts against the item exactly as an unestablished one does; what licenses the label is establishment **as trusted**, never establishment as such. "Guest-controlled" would be too narrow: a value the store decided, with no guest program involved at all, is unestablished just the same. Authorship does not qualify it — that test is rejected above and it is no more valid per item than it was per result. A diagnostic count, an exit status, a stream size and a presence bit all derive from something unestablished, and moving one into an item of its own changes the granularity rather than the derivation. Presence is the half that is easy to miss: a line emitted only when the program failed carries one bit of unestablished information whatever its text says, so a constant sentence qualifies only when it is emitted unconditionally — on **every** return path, refusals and error surfaces included, and true on all of them. No sentence any shipped kind renders meets that today.

What survives as trusted is therefore narrow — standing guidance the kind emits on every return path, saying nothing about this call. That is less than it sounds like it should be, and it is not the whole of what [#769](https://github.com/sokolaidev/maf-extensions/issues/769) measured: that issue's failing program left the model an exit code and nothing else, and what it asked for was the exit code, the stream sizes, the landed-output list **and** a sentence naming the route. Standing guidance is the only one of the four this rule lets a kind keep visible, so the split preserves the recovery route and not the diagnosis. Everything computed from the call sits beside it carrying no label of its own, which is how it takes the call's — untrusted, for a kind that declares nothing and whose arguments carry none — and is hidden while the conversation is still trusted. The label is the kind's claim, the hiding is the framework's response to it, and only the first is unconditional.

This is tier 1, and it is what a kind reaches for whenever its result mixes the two. In core it is `sandboxed_tool`'s widened return type — a body answers with a `str` or with a list of items — and `labelled_result_item`, which builds one of those items with the framework's own label serialization rather than a dict literal.

**A per-item label carries confidentiality as well, and this suite has none to give.** Tier 1 replaces the whole `ContentLabel`, not its integrity alone, and `ContentLabel` defaults confidentiality to `public` — so an item labelled for derivation and nothing else arrives *public* whatever the call would otherwise have been. Confidentiality values are the host's own vocabulary, carried verbatim and never ordered or folded here ([`hosts.md`](hosts.md)), so a kind cannot invent one. The integrity reasoning above is therefore only half of what a per-item label has to get right.

**The other half is answered by not labelling.** An item carrying no label of its own takes the call's — the tool's `confidentiality` declaration, or the middleware's `default_confidentiality` where the tool declares none — and the result's combined label is the *most restrictive* across every item. So a result that leaves one item unlabelled keeps the call's confidentiality whatever the labelled ones said, and no kind ever names a value it does not have. Measured on 1.13.0 and 1.16.0, against a tool declaring `confidentiality: private`:

| Result | Combined | Conversation after | Model sees |
|---|---|---|---|
| one string, no label | untrusted/private | trusted/private | hidden, whole |
| guidance + diagnostics, **both** labelled for integrity alone | untrusted/**public** | trusted/**public** | summary visible, diagnostics hidden |
| guidance labelled, diagnostics **unlabelled** | untrusted/private | trusted/private | summary visible, diagnostics hidden |
| the same, with the confidentiality coming from the middleware default instead | untrusted/private | trusted/private | the same |

Only the second row loses the classification, and it is the one shape `sandboxed_tool` refuses: a list whose every item carries a label has nothing left to carry the call's. `labelled_result_item` refuses `untrusted` for the same reason from the other end — an untrusted item is precisely the one holding what the call produced, so `public` on it is a claim about content a kind cannot classify, and that item's own label is what `inspect_variable` reports once it is hidden. Where the input-label join might answer trusted, the untrusted claim belongs to the whole tool as `source_integrity="untrusted"`, which leaves the confidentiality resolution alone.

## What the input-label join does not establish

The rule above is what a kind is held to. These are the reasons it cannot be checked automatically, and a kind writer has to know both.

**Two different things keep the join uninformed, and only one is invisibility.** `execute_code` takes its model-authored program *directly*, as `code: str` on every variant; `bicep_validate` and codeact's `files=` take store-relative names. The join sees all of those — they are arguments — and finds nothing to label, because a plain string carries none. Separately, the *content* behind a name is read from the agent's file store inside the tool body, which the join never sees at all. Visible-but-unlabelled and out-of-band are different failures with the same outcome here, and a kind writer needs both: the first is fixed by labelling arguments, the second cannot be. In either case it collects nothing, and the framework takes its separate no-labels branch straight to the untrusted default — reached because nothing was inspected rather than because anything was traced. Note which way that branch points: joining an empty set of labels would return *trusted*, so the fail-safe here is the branch, not the join. A kind therefore labels what it emits from what it knows about its own construction, not from what the framework traced for it.

**The store is the channel that cannot be repaired from the outside, and content reaches it already stripped.** `AgentFileStore` takes a `str` and returns a `str`: there is no parameter for a label, no return channel for one, and no per-path metadata, so the store does not decline to carry a label — the type it holds cannot hold one. That is what separates it from the argument side, where a caller *could* pass a labelled value and be believed. And the framework fills it: a model that passes a hidden variable reference as the `content` of the host's file-write tool has that reference expanded into the real bytes **before the write tool's body runs**, so what lands in the store is content the framework was hiding a moment earlier, carrying nothing. A kind then reads it by name and answers from it. The whole chain has been run — hidden content, through `file_access_write`, into the store, out through a tool shaped like `bicep_validate`, and back into the conversation stamped trusted — in [`research/laundering-into-the-file-store.md`](research/laundering-into-the-file-store.md).

**So the ruling for this channel is narrower than the rule above, and it points at the declaration a kind writes rather than the one it omits.** A kind whose result may derive from content it read out of the store may not declare `trusted`, and may not rely on declaring nothing either, because the two routes in *The rule* above are both open to it and neither is its to close. It declares `untrusted` explicitly, or labels the affected items untrusted per item once that is available. Neither shipped kind does today; both declare nothing and land on the untrusted answer by the shape of their signatures, which is [#840](https://github.com/sokolaidev/maf-extensions/issues/840)'s to fix. Letting the store carry a label — so that a kind is handed the labels of the files it was named, and this stops being a claim it makes unaided — is [#841](https://github.com/sokolaidev/maf-extensions/issues/841).

**Egress and host tools widen the derivation without widening the signature.** A program that may reach an allowlisted host, or call back through a host-tool registry, derives from whatever those returned. The registry's own folded integrity is available as `HostToolAggregate.result_integrity` — the weakest level over the registered sources, with an unstamped tool failing safe to untrusted ([`hosts.md`](hosts.md)) — and a kind that serves host tools reads it rather than assuming its own construction still describes the result.

**A rewritten argument is knowable exactly, and only with a host's help.** The framework substitutes hidden content into an argument before a kind's body runs, and hands the body the result with no record of the substitution. A kind can *infer* which arguments were rewritten by comparing them against the payloads the framework has stored, and `positions_holding_hidden_content` does exactly that when it has nothing better — but inference over stored payloads is conservative by construction, so a short stored payload makes an untouched name report too, and what it compares depends on how a payload happens to be stored and reduced. `argument_provenance_middleware` removes both. A host wires it beside the information-flow middleware, and the answer comes from the framework's own record of the arguments as they arrived: an entry differing from the spelling the caller gave *at the same position* is one the rewriting produced. Exact, independent of payload shape, and one record per call rather than one per process. It reads that record from a metadata key the framework does not publish, though, and this suite accepts every `agent-framework-core` 1.x — so a compatible minor could rename it and this would stop answering. What it must not do is stop answering *quietly*, and two things see to that: a divergence alarm in the suite, which fails at upgrade time here, and the call itself, which is read for a second key the same middleware writes alongside the first. One key without the other says a middleware ran and its record is gone, so the tool warns once and **fails closed** — naming every position it was asked about rather than quoting one the framework may have rewritten. That tell is read from the call's metadata rather than from the framework's accessor on purpose: metadata travels with the context, so it still answers on the worker thread a synchronous body runs on, where the accessor is a thread-local and there is no fallback to degrade to either. Retiring both needs a provenance API the framework publishes, which is [#826](https://github.com/sokolaidev/maf-extensions/issues/826). Order does not matter — the two middleware share one call context. It also answers a narrower question, which is the security difference between the two: the record is about *this call*, so it tells a caller only what it already knew, while the inference is about the store, so a value that merely matches hidden content is reported even where nothing was rewritten — and a caller that chooses the value can watch which way the refusal renders and learn that its guess sits inside something hidden.

**Position by position, and both directions matter.** The comparison is per entry and the answer names entries, never values, because a caller controls every one of them. Matched against the record as a whole, a rewritten entry would be excused by an equal value the caller placed at another position — and the hidden content would be quoted straight back. Answered with values rather than positions, a caller's own guess would be reported as rewritten because an equal entry elsewhere was — and watching its own refusal stop quoting it would confirm the guess. Two spellings of one channel, closed by the same rule: `positions_holding_hidden_content` returns the positions in the list it was handed, and a caller indexes them rather than asking whether the answer contains a name. What neither answer hides is the *length* of a value it declines to repeat.

## What the shipped kinds declare

| Kind | Declares | Because |
|---|---|---|
| [`bicep`](kinds/bicep.md) | nothing | the diagnostics quote model-authored Bicep, and the file name in every location is a string the model chose |
| [`codeact`](kinds/codeact.md) | nothing | what comes back is whatever a model-written `print(...)` emitted, and withholding that text does not remove the guest from what remains |

Both reach the untrusted fallback, because their arguments carry no labels for the join to propagate and because no host in front of them has moved `default_integrity`. Neither of those is a claim either kind makes, which is why both should be saying `untrusted` outright — [#840](https://github.com/sokolaidev/maf-extensions/issues/840). Under per-item labels both split the same way: standing guidance that says nothing about the call is labelled trusted and stays visible, while everything derived from it — the diagnostics, the exit status, the counts and sizes — is left unlabelled, takes the call's untrusted label, and is hidden for as long as the conversation is still trusted.
