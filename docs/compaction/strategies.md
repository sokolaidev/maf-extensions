# The strategies

Five compaction strategies and one supporting middleware, the fifth a composition of two of the others. This page says what each one does, what its defaults are, how it is wired up, and where it fails. The [front door](README.md) has the problem they answer and the measurements; the [research record](research/strategies-as-designed.md) has the design argument as it was written.

## The break-even every default is derived from

With `p` the input rate, `c` the cached rate, `R` the tokens an edit removes, `B` the tokens behind the edit and `T` the turns still to come, an edit pays when `R > B(p − c) / (p + T·c)`. At the measured prices and twenty remaining turns the right-hand side is 29% of `B`, and `B` is nearly the whole prompt for an edit near the head. Every threshold below is that formula solved for one of its terms: the minimum-gain floor is it solved for `R`, the user-turn band share is it solved for `T`, and the composition's chain target is it applied to the chain's own earliest edit.

Two consequences run through every strategy. Decisions are made from a message's *position*, never from the conversation's current size, so the same prefix compacts to the same bytes on every later turn and stays cached. And shortening is preferred to removing, so the conversation stays legible and the edit stays local.

## `AnchoredCompactionStrategy`

Keeps a fixed number of head groups and tail groups verbatim and shortens the tool results in the band between them. Each banded result is trimmed to a share of the ceiling set by its position counting from the head, `max_input_tokens × band_share ÷ (position + 1)`, so a result keeps the same allowance on every pass. Only if shortening leaves the prompt over the ceiling does it remove whole groups, oldest first, and only as a last resort does it shed assistant narration. It never touches user turns. Defaults: three head groups, four tail groups, a band share of 0.25, narration collapse on.

In-place tool-result shortening keeps the compatibility `result` field and the provider-facing `items` text in sync. By default, anchored trimming and removal of recorded table rows skip results containing any non-text item or text item carrying metadata (including security labels, annotations, and provider state); whole-group exclusion still follows each strategy's existing rules. On a later pass, each strategy also repairs stale bare-text `items` when `result` already carries its compaction marker, including after history reload and below the current compaction threshold. The repair retains the existing compacted result and skips metadata-bearing items; unmarked field differences are left alone.

The optional `rewrite_result_text(content, text) -> bool` hook lets a host shorten labelled or mixed results under its own metadata policy. It operates on a copy, rewrites text items and returns `True`, or declines with `False`. The library validates the joined text, synchronizes `result`, and retains the original non-text objects in order, including their media costs. The host preserves or conservatively merges text metadata and updates provider raw state when it understands that representation. Minimum-gain projections can discard hook changes; hooks must be deterministic and have no external effects. The record strategy uses the hook for partial row removal and forwards it to its default fallback; an explicit fallback keeps its own configuration. See the [hook example and contract](../../packages/maf-compaction/README.md#shortening-labelled-tool-results).

A message another strategy has marked *preserved* is skipped by all three removal paths. Preserved is not excluded: the message is still sent and counted in full, so a pass can end over the ceiling with everything removable gone. That is the intended outcome; the strategy stops on "nothing moved" rather than looping against a band it may not touch, and an honest overflow the caller can see beats a silent loss.

Where it fails: when tool results are smaller than their allowance it plans nothing, and lowering the share does not rescue a small payload, since the whole payload is then under the break-even. Past the window it keeps the conversation admissible at the cost of the values it trims. Measured at 1.5 times a 120,000-token window it kept 40 of 53 facts on one model and 31 on the other; at 3 times, 13.

## `MinimumGainAnchoredCompactionStrategy`

The anchored strategy with a floor. Before mutating anything it projects the collapse it is about to perform and declines if the saving is below `min_gain_fraction` of the tokens the collapse puts back on the meter, the included prompt from its earliest rewrite to the end. The default is 0.29, the break-even rounded up. The floor does not apply when the prompt is already over the ceiling, where shortening is what keeps the conversation admissible rather than an optimisation. `declined_collapses` counts the refusals, so a run that never fired and one that fired to no effect can be told apart.

The turns still to come divide the formula and nobody knows them at decision time: ten remaining turns need 43% of `B` and forty need 17%, so a workload with conversations shorter than the twenty the default assumes should raise the floor.

## `ToolResultAnchoredSummarizationCompactionStrategy`

The one strategy that carries information forward instead of discarding it, in two phases split across a middleware and the strategy.

`ToolResultRecallMiddleware` reads the conversation size on each call's way out. Past `trigger_fraction` of the ceiling, or once `max_groups_before_record` tool groups have accumulated since the last record, it pins the *next* request to a single tool, `recall_earlier_tool_results`, whose description asks the model to write down every value from earlier tool results that later work could depend on. The tool echoes that text back as a tool result. If a client exception names `tool_choice` in its message or explicit cause chain, recall is retried with `auto`, only the recall tool advertised, and a temporary user message appended after the final tool result or user question, and later recall requests use that mode. Hosts can select it up front with `supports_tool_choice=False`. The prompted message is removed from middleware-owned lists after completion, failure or cancellation; ordinary calls recover the caller's tools and options. Stale messages flagged `_maf_recall_prompt` are removed at middleware entry and after downstream history loading, before compaction and sending. Hosts persisting or displaying copied agent message lists must filter that flag too, including on checkpoint replay; middleware cannot clean independent copies retroactively. The strategy then finds the record in the loaded history and drops the tool groups in front of it that the record demonstrably carries.

A session stops requesting recall after two consecutive forced responses lack the recall call, after two consecutive value-free records or blank forced responses, or immediately when a forced request fails outside the unsupported-pin fallback. The failed request is retried once with the caller's original options and output cap; another failure propagates. Forced streams, including prompt fallback, are buffered so failed updates cannot reach the caller. Cancellation and framework abort signals propagate without another retry. The middleware exposes `pin_disabled`, `recall_disabled`, `pin_disabled_reason`, `value_free_record_streak`, `ignored_forced_calls` and `failed_forced_calls`. The reason distinguishes `"unsupported"` (prompt recall continues) from `"ignored"`, `"failed"` and `"value_free"` (recall stops). Every disablement transition emits a module WARNING with the bound session id and reason. An ignored-request warning also distinguishes prompted from pinned recall and reports whether the final response contained another tool call, text, both, or neither; it includes no response content. Both streaks, the disabled flag, reason and identities of evaluated records survive session restores. A record quoting any target value resets the value-free streak while recall is enabled; a nonblank record with no eligible target values leaves it unchanged. Forced list/object values are normalized to text before execution, including in buffered updates. Blank text and empty structures advance the streak even without eligible targets, but the tool emits no record marker for them and grants no removal authority. Existing records remain usable, and once recall stops the composition stops waiting for a new one before proceeding through the user half and configured fallback/overflow policy. The [provider-support note](../../packages/maf-compaction/README.md#provider-support-for-forced-recall) specifies the exception match, retry bounds, diagnostics and reporting/reset contract.

Value-free backoff judges a record against distinctive target tokens retained before compaction can shed their groups. The pending basis survives session restores and is consumed when the next recall answer arrives; it does not grant coverage or removal authority. Consolidation replacements do not count as recall answers, and unjudged outcomes survive replay and session restores. Without a saved basis, the remaining eligible groups provide it. The record strategy's `last_record_value_judgment` distinguishes `has_values` and `value_free` from `no_candidates` and `no_values`; unjudged records also emit an INFO diagnostic without conversation content.

Coverage is measured in values, not in tool names. For each candidate group the strategy extracts the distinctive tokens of its results, whitespace-delimited, punctuation stripped, at least four characters and one digit, compared with their case, and calls the group covered when the record quotes at least `coverage_share` of them, 0.8 by default. A group the record does not cover is first held out of the fallback's reach while the strategy asks the middleware for another record, and preserved for good once asking stops helping. A prompt that cannot then be brought under the ceiling overflows loudly, which is preferable to the quiet loss it replaces.

Large string-result groups exceeding `record_target_tokens` can release individual pipe-delimited Markdown table rows containing a distinctive value when a record quotes each row verbatim under matching column headings. The remaining text and headings stay verbatim, with a marker explaining the omitted rows. This partial credit leaves whole-group `coverage_share` unchanged; code fences, rows containing backslashes, non-string results and records quoting only bare values remain ineligible. Match the strategy's target to `make_recall_tool(target_tokens=...)`, distinct from the forced response cap. A target of `None` disables partial removal and the target-based diagnostic while retaining whole-group coverage. Duplicate rows under matching headings anywhere in the loaded tool results remain because their source is ambiguous. `groups_held_unreachable_coverage` on either strategy counts held groups whose estimated cheapest required value text exceeds that target on the last record pass. The estimate sums per-value token counts and excludes formatting, labels and other groups; it diagnoses budget pressure rather than proving impossibility. Partial row removal does not earn another forced record: the retry chain remains bounded by whole groups retired. Later batch records can still release rows from settled groups. Partial credit can reduce duplicate text without freeing a whole group, and uncovered material can still reach the composition's overflow policy. Loaded history recomputes the same row decisions against its records.

The fallback behind a record also holds tool groups after the newest record: those groups could not have been covered when it was written. This leaves assistant narration as the removable material. The no-record give-up path runs the ordinary fallback instead, so its result measures the fallback rather than preservation by a record. `groups_kept_uncovered`, re-force and preservation counters distinguish partial coverage from that give-up path.

Records repeat by default. Above the size trigger, a repeat waits for `min_groups_before_repeat` new tool groups, four by default. This bound does not force below the trigger; `max_groups_before_record` remains an independent trigger. A re-force chain retries only its original uncovered targets while making progress, settling groups that arrive during the ask without opening another chain for them. A record covers what existed when it was written, so the middleware asks again once a new batch has accumulated, and re-arms on new *material* rather than on size, since the size that fired the trigger never goes away: the record is added to the conversation, and preserved. Every record is preserved, so records accumulate as a floor under the prompt; this strategy never merges them, because an older record is the sole account of the groups behind it. The composition does, as a last resort.

Defaults: a trigger of 0.6 and a give-up line of 0.9 of the ceiling, past which the strategy stops waiting for a record and hands the conversation to its `fallback`, an anchored strategy. The record is written by a model reading the tool payload and degrades with the bulk it is given, so the trigger wants to be early; the give-up line is far enough above it for the record, which arrives one call late by construction, to land. The record is asked for at a stated target of 2,000 tokens and capped at 4,000 on the forced call alone, two separate bounds because a cap truncates a tool call inside its arguments rather than making the model aim for a size.

Four constraints the design holds to. The record must be a tool result the provider issued, since a client-minted call is refused by routes that track tool calls server-side. The middleware adds no stored message; prompt fallback uses an ephemeral trailing message that counts towards the request budget but not user-turn or fallback group anchors. The recall tool cannot be hidden from the model, so `RecallGate` keeps it inert unless the middleware armed it. And the forced call's reply is bounded by two numbers, the target and the cap, not one.

Where it fails: the quality of the record decides the row. On a model that writes a record naming every value, the strategy keeps every fact and runs 32% under an unlimited model at 1.5 times the window. On a model whose record covers two of six tool groups, the uncovered groups are preserved, the prompt cannot be brought under the ceiling, and the conversation overflows: two seeds of five at 1.5 times the window, every seed at 3 times. It also cannot touch user turns, so a conversation whose bulk is user text outgrows it.

## `UserTurnAnchoredSummarizationCompactionStrategy`

The mirror of the record strategy on the other half of the conversation. Past `trigger_fraction` of the ceiling it takes the user turns between a fixed head and a fixed tail, sends them to a summariser client, and puts the summary back in their place as a single *user* message, linked to the turns it replaced through the framework's own summary annotations. It reads nothing but user groups, so it and the tool-side strategies measure independent things.

Defaults: one head turn and one tail turn, since the first turn carries the task and the last is the live request; a trigger of 0.8, later than the record strategy's because a summary costs only a broken prefix and wants to fire as late as it can; and a `min_band_share` of 0.1, the break-even solved for turns, which refuses a pass whose band is worth less than a tenth of the prompt. For a band that fits in one request, the share bounds the pass count: a band regrows only from new user turns, so the prompt must grow by `1 / (1 − f)` before the band is worth the share again, one pass per 11% of growth at the default. A pass whose band holds only the strategy's own earlier summary does nothing.

`max_summary_input_tokens` caps the estimated size of each summariser request, including its instructions and numbered transcript. It defaults to half `max_input_tokens`, with a minimum of one, and can be set for a summariser with a different input budget. The tokenizer supplies the estimate; reserve provider overhead and output space separately. Once the eligible band clears the minimum share, the pass takes only its oldest whole turns that fit, leaving newer turns for later passes. The selected prefix must contain a new user turn, so recompaction does not spend a request on an earlier summary alone. If no eligible prefix fits, the oldest turn is retained without truncation or a request; the strategy does not skip ahead past it. Prefix sizing checks otherwise-unprobed candidates before declining, because tokenizer counts need not grow when text is appended. Partial folds likewise take the oldest summaries that fit, require at least two, and preserve later boundaries and their text. These limits can leave the conversation above the main input ceiling.

Set `summary_timeout_seconds` to a positive finite number to time out each user-summary or fold request. A timeout cancels the request and counts as a failure; the client must honour cancellation, and cancellation cleanup can extend the elapsed time. Configure `max_consecutive_summary_failures` (a positive integer) together with `summary_backoff_seconds` (positive and finite) to skip fresh requests after that many consecutive failures. Exceptions, empty replies and rejected oversized summaries contribute to the streak. After the cooldown expires, the next eligible request retries; another failure renews the cooldown, while a fresh accepted summary resets the streak. Cached answers still replay during cooldown without resetting it. `user_summary_skips`, also exposed by the composition, counts withheld requests separately from `user_summary_failures`. All three settings default to `None` (off). Session snapshots retain the failure streak and a wall-clock cooldown deadline, so the cooldown follows a session across replica changes, restarts and stack-cache eviction when the host persists its state. Older snapshots default to no failures or cooldown. Expired deadlines or deadlines more than the configured backoff ahead are discarded, limiting the effect of clock differences between hosts. These settings cover user bands and user-summary folds, including emergency folds; record merges/rewrites and media-description hooks retain their own policies. A skipped or timed-out summary leaves its source material intact, and the composition continues to its configured overflow policy.

`summary_mode` decides what a pass does with the summary the previous pass left. `recompact`, the default, re-reads it, so one message stands for everything behind it. `boundary` never re-reads it: the summary is preserved as a boundary, the next band starts after it, and the prefix up to the newest boundary is byte-identical on every later pass, at the price of one standing summary per pass. `fold` is the boundary mode with a bound: once the ordinary band is declined, the oldest summaries that fit the request budget are collapsed into one only if at least two fit and that selected prefix repays the break by the same formula. Summaries left for later passes do not contribute to that profitability check; the composition's emergency folds instead require only a smaller replacement. The three modes have not been separated by measurement, so the default stays where it is.

A summary remains a user message because the next pass selects user groups: an assistant summary would be invisible both to recompaction and to boundary discovery. Replacement uses the framework's summary links in both directions and excludes the originals with a reason. Hosts must retain the links and text marker through storage; preservation marks alone do not identify boundaries and are re-applied on each pass. In `recompact` mode the summary stays unpreserved so the next band can include it.

The framework compacts loaded copies before the model request and stored history after the turn. The strategy remembers recent summariser requests, answers and summary ids, replaying the same replacement on stored history without another summariser call or counted compaction. Identical text from new sources reuses the answer under a fresh summary id and counts as another compaction or fold. Both lists then carry the same replacement, avoiding a second cache break on the next request. `remembered_requests` defaults to one; a composition using boundary or fold mode requires at least two because one pass can request a band summary and a fold. `user_summaries_replayed` counts replays, including a retried request or another model request that loads the same history.

The summariser is a trust boundary sharper than the framework's own: its output stands in for the user's turns, which is the half a model treats as instructions. Point it only at a service trusted as much as the primary model. What the summary keeps of the turns is not something the benchmark can measure, since its planted facts live in tool results.

Where it fails: alone, everywhere past the window, since it cannot reach the tool half. Measured alone it disqualifies on every seed at 1.5 and 3 times the window on both models. It is the composition's second half.

## `ToolResultAndUserTurnAnchoredSummarizationCompactionStrategy`

The two summarising strategies over one conversation. It owns no selection rule and removes nothing itself; what it adds is an order, one line for both halves, and a last-resort chain.

The record half runs first and records every new batch of tool results. The user half is judged at the same line, the record half's trigger, against the prompt *as the record half left it*, in whichever `summary_mode` the caller built it with; the composition does not set or require one, and the measured row used the boundary mode. It acts only if tool compaction was not enough, since its edit sits just behind the head and breaks nearly the whole cached prefix. The bound `take_reforce` wiring shares the middleware's configured repeat, size and group-bound trigger with this wait without consuming the request. While a record is due or already requested and still has time to arrive, the user half is not judged at all: the record half compacts in two steps, ask on one pass and drop on the next, and a user half judged on the asking pass would summarise the user turns, take the prompt under the line, and leave the middleware with nothing to ask for. The wait expires after two model responses with no record, so a model that never records cannot leave the conversation uncompacted.

Then, only while the prompt is still over the input budget, a chain: merge the oldest active records that fit into one; merge the oldest standing user summaries that fit into one; rewrite the record harder, up to `harder_attempts` times, two by default; then the record half's fallback, with every tool group no record covers held so it may drop narration only; then the overflow policy. The default `overflow_policy="shed"` releases only the record phase's holds and removes whole unrecorded groups until the message budget is met, warning with the lost message IDs. `overflow_policy="raise"` retains those groups. Both raise `CompactionBudgetExceeded` before returning an oversized prompt if the remaining protected material cannot fit. Records, external holds, fixed anchors and call/result pairing remain protected; the host must reserve budget for tool schemas and provider overhead. Once started the chain works down to a target rather than to the budget, removing `chain_gain_fraction` of the tokens behind its earliest edit, 0.29 by default, so the next turns have room before the chain is needed again. Every replacement is kept only if it is non-empty and smaller than what it replaces, and nothing is checked against content, because an overlap check fitted to one workload's values would reject correct paraphrase on another. A refused request is remembered and not asked again while what it would rewrite is unchanged.

Record merging and rewriting use the user half's summariser client and `max_summary_input_tokens` limit. Each request includes only the oldest whole records that fit its own instructions; a merge requires two, a harder rewrite one. Newer records stay in place, and an oversized oldest record is retained without a request. The chain continues to its remaining steps and the configured overflow policy when bounded requests cannot free enough space. The client reads only the selected records. Asking the agent for a merge would send the over-budget prompt the chain is trying to reduce. A replacement is a preserved assistant message with the record marker and package metadata, so it is recognised as a record without inventing a provider tool-call id or entering the user band. Size acceptance compares both the candidate and the old record bodies in that same message form; counting the original tool-call arguments too would reward removing a duplicate copy without shortening the record. Record merging precedes user folding because its earliest edit is usually later in the prompt and breaks less of the cached prefix.

Last-resort shedding decisions are remembered by message ID and replayed on stored history and session restores, even when the restored list is below budget.

The framework runs a strategy twice per call, over the copies sent on the call and over the stored history, and the two lists need not reach the same step. Every decision the chain makes is therefore kept for the run and put back on every list that holds what it changed, before the chain decides anything new; `decision_state` and `restore_decisions` expose that state so a harness that replays a conversation can carry it along.

Record-merge and rewrite refusals are keyed by their numbered record-body transcript and source count, both identical on the loaded and stored lists. A change to either makes the request eligible again. Restore discards legacy refusals without source counts because their shrink decision cannot safely apply to colliding multiline sources. Refused user folds remain among the user half's remembered requests until a new band summary changes what the fold would read. Chain counters distinguish accepted replacements, rejected or skipped requests, failed summaries, fallback use, targets reached or missed, and replayed decisions; the [benchmark flags](cachebench.md) expose these alongside both halves' counters.

Where it fails: poor record coverage can make the default shedding policy lose unrecorded values to fit the message budget. Strict mode retains those groups and raises `CompactionBudgetExceeded` if the prompt remains too large; either policy raises when protected material alone cannot fit. The historical measurements predate budget enforcement: at 3 times the window on the model whose records leave groups uncovered, one seed of five overflowed after 172 fallbacks; the other four ran 30-56% under the control, and the mean the one seed drags to +79% is that seed. Those measurements do not qualify the current overflow policies. Both parts' costs are spent, an agent turn for the record and a summariser call for the summary, so inside the window it is a few percent dearer than not compacting.

## Wiring

Every strategy implements the framework's `CompactionStrategy` and attaches wherever the framework takes one: `create_harness_agent`'s before and after strategy, or a `CompactionProvider` on a plain `Agent`. The record strategy and the composition also need the recall tool registered and `ToolResultRecallMiddleware` installed, with the same tokenizer and ceiling as the strategy; the [package README](../../packages/maf-compaction/README.md) shows both. `find_nested_strategy` finds the record half inside a composition, since a composition is not an instance of its parts and a plain `isinstance` would leave the middleware uninstalled, which is a row that waits, falls back and reads as a model that refused to comply. `record_text` reads the record a conversation holds, for diagnostics. The three summarising strategies, `RecallGate` and the middleware keep one conversation's decisions on the instance. Direct wiring creates the stack and agent per session; the middleware raises if a second session reaches it.

### Serving many sessions

One shared agent uses `SessionCompactionRegistry(build)` with a fresh `CompactionStack` per session, one `SessionCompactionProvider`, one `SessionToolResultRecallMiddleware`, and one `make_session_recall_tool(registry)`. `CompactionStack` binds the record strategy to its recall middleware even with `reforce=None`, so value judgments, target capture and the two-record value-free back-off remain active independently of re-forcing. Re-force trigger and feedback hooks are bound only when `reforce` is configured. `AgentSession.state` owns the JSON-safe snapshot; the bounded cache only saves stack construction. Every phase restores state, including cache hits, and persists it on exit. The provider takes its session from the hook arguments, the middleware from its chat context, and the recall tool from its injected function context; a context variable exposes the stack only while that phase runs. The model never supplies the session identity.

With `create_harness_agent`, set `disable_compaction=True`, pass the provider through `context_providers=`, and move it immediately after the history provider, where the harness places its built-in compaction provider. After hooks execute in reverse order. Framework 1.20 loads history per model call, so provider `before_run` sees no loaded history: use `SessionToolResultRecallMiddleware(..., compact_before=True)` and `SessionCompactionProvider(..., before=False)`. The chat middleware supplies a strategy bound to the explicit session for deferred streaming execution; the provider compacts persisted history after the turn. The [shared-agent example](../../packages/maf-compaction/README.md#serving-many-sessions) shows the complete wiring and provider placement.

The snapshot includes record decisions and outstanding re-force asks, the chain's waits and content-keyed kept or refused replacements, shed IDs, remembered user requests and folds, pending recall flags and the armed gate. User compaction and fold counts travel because they allocate summary IDs; the other counters remain process-local diagnostics. The existing `ChainDecisions` and `RecordDecisions` replay values gain `to_dict()` / `from_dict()` without widening what their existing restore methods replace. `CompactionStack.to_dict()` is the full session snapshot. Kept folds and record replacements retain source counts to avoid rendering every possible prefix during replay; older snapshots without counts learn them on matching replay. Record snapshots store each transcript, source count and answer together; legacy transcript maps migrate on restore. Refusals persist source counts too, while ambiguous legacy refusals are retried. This keeps decisions for colliding multiline transcripts with different source counts separate. Exact transcript equality still validates each replacement. It contains conversation text and grows with retained content decisions, so its storage and retention policy follows history.

The host saves and restores the framework's whole session between requests, uses the same stack configuration on every replica, and serializes requests for a given session across replicas. Concurrent distinct sessions are supported. Cache eviction does not discard session state, and unsupported snapshot versions or stack kinds raise. Writers emit snapshot version 5 with versioned record identities, media descriptions and media-aware summary replay keys. Readers accept compatible versions 1 through 5 and migrate legacy transcript-keyed folds to summary-ID keys. Legacy composed decisions whose `anchor` or `declined_behind` uses an unversioned `call:` identity are rejected before state is applied: that identity cannot uniquely recover the occurrence needed to preserve a pending recall wait. Continue those sessions with their original reader or explicitly rebuild compaction state from retained history after reviewing the pending decisions; do not automatically clear the state on failure. Legacy snapshots without those identities remain readable. Older builds reject version-5 snapshots; replicas sharing that session must support the new schema. Distributed locking, external persistence and atomic storage of a response with the session remain the host's responsibility.

## Media handling

Media-bearing user turns stay verbatim unless the user strategy has a `describe_media` hook. Preservation covers the entire turn, including its surrounding text, and applies in all three summary modes. Explicit host preservation takes precedence over the hook. Unknown non-text content types also stay verbatim: the strategy does not infer that a part it cannot interpret is expendable.

Every strategy, recall middleware and composed budget check uses the same message-accounting path. Framework `data`, `uri` and `hosted_file` parts, including media in function-result items, receive a fixed estimate of 1,024 tokens per part by default. `MediaTokenEstimator` overrides image and other-media costs independently, or accepts a pure `estimate_media(content) -> int` callback for provider-specific estimates. Costs must be positive integers. The underlying tokenizer counts text and message structure; a small marker replaces each media payload before its estimate is added. The estimator measures neither URL length nor base64 length as media usage. Repeated annotation, forced recounts and previously cached framework counts do not accumulate the estimate. These are configurable budgeting estimates, not measured provider token usage or a guarantee that a request fits a provider's window. Reserve overhead separately. `count_tokens` remains a text counter; `count_message_tokens` exposes the media-aware single-message estimate to hosts, while external framework token gates retain their own accounting.

The optional asynchronous hook has the shape `describe_media(content, message) -> str | None`. It receives copies of the selected media part and its complete user turn so the host can interpret the media in context. The package does not download media or choose a vision service. The hook supports images, audio, video and documents represented by the three media content types; whether a particular format can be described is the host's responsibility. Returning `None` declines that part. The strategy invokes it only for eligible band turns, preserves part order, and labels each returned description as inferred context rather than a user instruction. Both services must be trusted with the supplied content; a description is a lossy interpretation, not a replacement for retaining original media in host storage.

A pass stops preparing further turns when a description fails, is empty or exceeds the summarizer input budget, or when its prepared transcript reaches that budget. Cancellation propagates. Successful descriptions are reused even if another part fails or the summarizer later refuses the request. The oldest fitting prefix still obeys `max_summary_input_tokens`, including instructions and description markers; the source turns are excluded only after a nonempty, smaller summary is accepted. Original media behind an excluded turn remains the host's storage responsibility. The hook's own request size, timeout, service access and output generation are controlled by the host.

Description identities include the source message ID, ordered content and surrounding text. Successful descriptions and media-aware summary replay keys persist with the session so the before-call and after-turn views, cache eviction and replica switches reuse the same decisions. Different media cannot borrow a summary solely because their accompanying text or generated descriptions match. Fingerprints avoid duplicating media bytes in the compaction snapshot; descriptions remain conversation data and follow its retention policy. A host must use stable message IDs and immutable or versioned media references, and keep hook configuration stable across restores. A URL whose remote bytes change under the same reference cannot be detected without fetching it; use a new reference or reset compaction state when its contents change.

Preserved media remains part of the budget. If protected material cannot fit, the composition raises `CompactionBudgetExceeded` under either overflow policy. The host must reduce protected context or use a larger budget; silent image loss is not an overflow policy.

The [live image verification record](research/media-live-1878.md) measures description, compaction, session replay and provider usage on synthetic images; its scope does not extend to other media or providers.

Recall records bind to local call occurrences, not globally unique service call IDs. An id-less legacy result must have exactly one unanswered matching declaration. Hosted calls, ambiguous matches and duplicate results cannot establish coverage. With legacy declarations, durable message identity distinguishes repeated service call IDs; a repeated service ID without either occurrence or durable message identity is conservatively refused. IDs shaped like the framework's generated `msg_N` positions are never treated as durable, even if a caller supplied one; use `Content.id` or a different stable message-ID format to disambiguate repeated legacy calls. Matched record text alone authorizes removal, including when unrelated marked results share its message. A record span containing any unrelated content is retained intact during consolidation, since that content is absent from the summarizer's input. Call/result pairs spanning separate groups are retained together; sequential complete pairs with id-less results remain removable when each result has one unanswered declaration. Invalidating a legacy anchor does not complete a pending recall wait, even when an older record becomes the newest valid one. The wait ends on a demonstrably newer completed record or its normal response bound; an invalid anchor still grants no removal authority.

## Request resilience

The composition reserves outgoing instructions and tool schemas per call and can leave an additional `estimate_margin` for tokenizer error. Its history-storage phase keeps the configured budget. A sending-budget refusal during post-call recall bookkeeping queues no new pin and preserves the completed response; before-call enforcement is unchanged. Recall waits through tools-disabled calls, validates forced arguments before returning them to the framework, and can bound a complete forced response with `forced_call_timeout_seconds`. Internal records explicitly retain values regardless of user-facing reply-format instructions; re-asks name missed results in a temporary tool description, and `records_without_values` reports records that quoted no distinctive target value.

User-summary `summary_input_policy="chunk"` covers an oversized eligible band through stable whole-turn chunks and bounded merges. Completed chunk answers survive in the session snapshot; one deadline and failure-cooldown event cover the whole pass. Optional summary chat options apply to user summaries, chunk merges, standing-summary folds, record merges and record rewrites. They share one retirement state after a failed attempt and an unconfigured retry. These mechanisms are exercised by scripted clients; they do not establish live provider recall quality or tokenizer accuracy. The [package configuration guide](../../packages/maf-compaction/README.md#per-call-request-budgets-and-chunked-summaries) specifies defaults, wiring and limits.

## What none of them do

Inside the context window nothing here beats not compacting: the best strategy costs within 3-8% of the control, inside the seed spread, and the whole conversation stays cached. Past the window the composition keeps every fact and is cheaper than an unlimited model, except on gpt-5.6-luna at three times the window, where it costs more and overflows on one seed of five; the rest either lose facts or overflow. None of them measures what a user-turn summary kept of the turns. All of them call `agent_framework._compaction`, the framework's private compaction helpers, for grouping, token annotation and the exclusion flags, so the dependency is pinned to one minor and re-read before the pin moves.
