# Terraform and OpenTofu validation images

> **To build, try, check or deploy an image, see [USAGE.md](USAGE.md).**

This page describes what the validation images contain and the rules their inputs follow.

[image.json](image.json) owns the base-image digest, platform, engine versions, download URLs, archive checksums and profile mappings. The Python [builder](build_image.py) reads that file and passes matching version metadata to Docker; [install.py](install.py) reads the same file inside the build and verifies the downloaded binary's reported version. Each image holds one engine. The initial platform is **Linux amd64**. The `builtin` profile has an empty provider mirror and supports built-in resources and local modules. The `random` profile reads its providers from the corresponding `dependencies.terraform.json` or `dependencies.opentofu.json` manifest, and the builder copies the selected manifest into the image. Downloads happen during image construction; validation has closed egress. Default tags name the engine version and the profile; a `--tag` override does not change the binary version.

Both image and profile manifests require an integer schema identifier of `1` and reject duplicate JSON keys at every depth. Provider names and prerelease versions use the same manifest grammar in preparation and image builds. Provider prerelease identifiers are nonempty, dot-separated, and lowercase. Engine pins also accept uppercase ASCII prerelease letters and preserve their spelling, for example `1.16.2-RC.1`. Core version numbers and numeric prerelease components reject leading zeros; nonnumeric identifiers such as `01a` remain valid. Provider archives must target `linux_amd64`. Profiles also reject repeated provider source/version/platform identities before any download. There is no automatic latest-version lookup.

## Image identity

The image carries Docker/OCI labels `org.opencontainers.image.version`, `ai.sokol.maf.engine` and `ai.sokol.maf.engine.version`, including the actual verified binary version. `/opt/maf-terraform/engine.json` also records the engine, executable, version, platform, archive digest, binary digest and profile; it remains the launcher's runtime identity record. A missing/mismatched version build argument or a binary reporting another version fails the build. Derived prepared images inherit these labels from their base and rewrite `engine.json` to profile `prepared` with the prepared receipt's `manifest_sha256` and `policy_sha256`. A prepared mirror holds the providers unpacked: the engine links each provider into the call instead of copying its bytes, and the launcher refuses a call that was served by copying. The one regular file it allows below the call's providers directory is the empty file OpenTofu locks beside a link it made, named for that link.

The base is Python 3.13.15 slim pinned by digest in `image.json`. The installer checks every downloaded archive before extracting it, preserves engine license notices, and leaves provider licenses inside their mirror archives (in a prepared image they are unpacked beside the providers). [runner.py](runner.py) verifies the recorded binary identity and version before executing a request. Deploy the resulting image by immutable digest; a deployment owns its trusted image and provider selection.

The launcher also accepts the fixed `format` mode used by the kind's opt-in `terraform_format` and `opentofu_format` tools. It runs only `version -json` and `fmt -recursive -no-color`, returning complete changed files within the 128 KiB output bound; no providers, modules, or initialization are needed. Rebuild the base images and every derived prepared image to adopt this launcher. The prepared receipt pins its digest as `reader_sha256`; an old receipt cannot be reused with a replaced launcher.

## Approved dependency preparation

The request restrictions in this section apply to `terraform_dependencies.py`. The image installer's `random` and custom profiles use the existing checksum-verified `urllib` downloads; they consume provider URLs and digests but do not enforce manifest redirect policy, address restrictions, or the preparer's resource limits. For those guarantees, build `prepared.Dockerfile` from a trusted empty-mirror base, as [USAGE.md](USAGE.md#build-a-prepared-image) shows. Its first stage runs the CLI and is the only step with network access. Every later step runs with `RUN --network=none`, so unpacking, verification and the offline probes cannot reach the network, and the host needs no Python to prepare. Base-image and engine-binary acquisition remain separate trusted image-build inputs.

The repository tool [terraform_dependencies.py](../../scripts/terraform_dependencies.py) prepares additional dependency profiles using a host-owned manifest. This is build tooling, not a public Python package API or a guest-facing download service. Run it through its CLI after `uv sync --locked`; the CLI supervises a worker under one 30-minute wall-time limit, including DNS and archive processing. The CLI has no worker mode; its parent launches a private Python entry point against temporary output. Worker refusals return fixed policy decision codes to the CLI; arbitrary worker diagnostics are discarded, and unclassified failures report `preparation-failed`. A refusal also names the artifact it stopped on: the worker records that artifact's position in the manifest before each download, plus the HTTP status where a response carried one, and the CLI reads the identity and URL back out of the manifest it validated itself, so nothing an upstream server sent reaches the message. The position is recorded rather than raised, so an unclassified failure and the supervisor's deadline also name the artifact preparation had reached, through the inventory pass as well as the downloads. It is cleared once no artifact is being worked on, so a failure writing the receipt or in the CLI's own publish step names nothing rather than the last artifact to have finished. The tool executes neither engines nor providers on the host. Validation still has CLOSED egress.

The example manifests pin the existing engine-specific `random` provider archives and the standalone `random_string` module example from HashiCorp's `v3.7.2` commit. The module graph is a single leaf, recorded separately from the provider lock. The selected upstream module files are preserved, including its UTF-8 configuration and ancillary import script; preparation and validation never execute that script. The module archive digest was reviewed and pinned from the immutable commit archive, not authenticated by a release signature. Provider digest pins carry forward the image guide's approved SHA256SUMS values. A provenance string is an operator assertion; the preparer verifies the pinned digest and does not verify signatures or establish signer trust.

The base must be a trusted builtin-profile image built from the same checkout. The build refuses a base whose launcher differs from the one preparation read configuration with, a nonempty base mirror, an engine mismatch, changed ZIP bytes, and any missing, additional, or digest-mismatched provider archive; it then unpacks every verified ZIP into the image, restores each extracted file's `0o755` mode, checks every extracted file against the receipt's `files` digests, and fails unless the `h1` recomputed over the unpacked tree equals the receipt's. The published mirror holds unpacked providers, which the engine links into the call and never copies. A supplied lock whose provider hashes are `zh:`-only is no longer verified against the unpacked mirror, while `h1:` hashes still are. Tags in the local examples are conveniences: deployments must use the resulting immutable image ID/digest. Preparation publishes only after complete success. The `prepared` build stage holds its output alone; export it to preserve it in trusted artifact storage, where writable directory permissions alone do not make it immutable. A build given that directory as the `prepared` context uses it instead of preparing again. Stage module files by the receipt's inventory and check their hashes, as the example does. The example rejects non-relative paths and resolved paths outside the module directory before reading; staging requires stable, trusted artifact storage. Do not mix unrelated provider mirrors into the image.

### Manifest and request contract

Only trusted host configuration supplies the manifest. Never construct it from guest URLs or attach the preparer as an agent tool. `schema` is exactly `1`, `engine` is exactly `terraform` or `opentofu`, and unknown fields and duplicate JSON keys are refused. The provider list requires full `hostname/namespace/type` source identity, exact version, target platform, and an artifact. A module entry requires a name, immutable 40- or 64-hex revision, archive subtree and full local graph: directory keys map module-call names to their resolved relative directory targets. `.` is the root. Every configuration directory and edge must match, be reachable and be acyclic. HCL and JSON are supported; duplicate keys at every depth of module JSON are refused before graph inspection. In a local module bundle, remote/dynamic module sources, override files, mixed engine file precedence, hidden directories and hidden files other than `.terraform.lock.hcl`, state and variable files (regardless of suffix casing), links and non-text module payloads are refused. Registry sources belong in `registry_modules`, described below; there is no recursive public registry/Git resolver.

Every artifact requires an exact `url`, trusted ZIP `sha256`, and a bounded `provenance` reference. Optional `redirects` lists at most three exact subsequent HTTPS URLs; every listed hop must occur before the final response. Alternatively, an exact GitHub release URL can carry its decimal `github_repository_id`; only its first HTTPS response may supply one signed redirect to `release-assets.githubusercontent.com/github-production-release-asset/<repository-id>/<asset-id>`. That capability belongs to this artifact transfer, expires with the transfer, and grants no guest authority over the CDN. Further redirects are refused. Signed queries are accepted only on this server-issued redirect, have a bounded fixed key vocabulary, reject duplicate fields and decoded controls, and never enter receipts or diagnostics.

All ordinary URLs must already be canonical ASCII HTTPS with lowercase DNS host and implicit port 443. Paths are exact and allow only ASCII letters, digits, `_`, `-`, `.`, `~` and `/`; empty/dot segments, percent encoding, duplicate separators, userinfo, explicit ports, backslashes, fragments and caller queries are refused. No prefix rule broadens an ordinary URL. Requests are fixed GETs with `Host`, `User-Agent: maf-dependency-preparation/1`, `Accept: application/octet-stream`, `Accept-Encoding: identity`, and no body. Caller methods, headers and bodies are unsupported fields. Cookies, authentication, environment proxies, CONNECT and service discovery are unused. Every redirect receives the same checks. The transport rejects private, link-local, multicast and transition-address routes, checks all DNS answers, then connects to a checked numeric address with TLS hostname verification and no second DNS lookup.

Limits are 4 MiB manifest, 64 provider archives, 16 module archives, 512 registry module packages, 64 MiB per download, 2 GiB accumulated downloads, 32 KiB raw response head (status lines, headers and interim responses combined), 4,096 ZIP entries in a provider or module archive and 65,536 in a registry package archive, 1 GiB expanded data per provider archive, 8 MiB expanded module data (for a registry package, its baked files only), 256 files per module bundle, 64 graph nodes, and 256 inventory records below one registry module call. Provider archives are checked in chunks rather than held in memory. The worker and parent share a fixed 30-minute maximum; malformed or incomplete data never publishes an output. Complete SHA-256 verification precedes archive parsing. ZIPs are read as bounded data and never extracted by archive paths on the host. Receipts contain artifact identities, digests, each provider's per-file digests and `h1:` package hash, graph/file inventories, bounded decisions and the complete policy hash, omitting transfer URLs and response content. The receipt records the canonical manifest digest separately from a versioned `policy_contract` containing the preparation implementation SHA-256, the SHA-256 of the launcher whose parser it reads configuration with, and effective limits. `policy_sha256` binds both. Implementation text is normalized to LF before hashing, so checkout line endings do not change identity; any source edit or limit change does. Preserve the identified implementation with the receipt. Runtime warm reuse remains unsupported.

### Registry module graphs

Use `registry_modules` for registry sources such as Azure Verified Modules (AVM). Authored configuration keeps its `source` strings, `version` constraints and lock file. Nothing is rewritten to a local path. The guest still has no registry access: the base CLI configuration disables module registry discovery for `registry.terraform.io` and `registry.opentofu.org`, and egress stays CLOSED. Registry modules are Terraform-only; the preparer refuses them in an OpenTofu manifest.

Two AVM manifests are committed. [dependencies.terraform-avm.json](dependencies.terraform-avm.json) is the catalog: every `avm-res-`, `avm-ptn-` and `avm-utl-` module in the `Azure` namespace at its newest release, with the nested modules and providers they need. [dependencies.terraform-avm-network.json](dependencies.terraform-avm-network.json) pins only `Azure/avm-res-network-virtualnetwork/azurerm` 0.22.2 and its nested `Azure/avm-utl-interfaces/azure` 0.6.0. `terraform-live.yml` builds the small one; the catalog is built by an operator.

#### Package rules

Each entry names a package `name` (`<module>-<system>-<version>`), a `source` with its registry host, an exact release `version`, the 40-hex `revision`, and an `artifact` whose URL must be the codeload archive of that revision. One source may appear at several versions. `graph` maps each baked directory to its calls. A local call is `{"local": "<directory>"}`. A registry call is `{"registry": "<package name>"}`, or `{"registry": "<package name>", "dir": "<subdirectory>"}` for a source ending in `//<subdirectory>`. Every directory must be reachable through local calls from `.` or from a directory another package calls. Registry references must be acyclic.

Preparation reads configuration with the launcher's own parser in [runner.py](runner.py), so it accepts the files the launcher reads at run time. Override files merge the way Terraform merges them: module arguments merge into the base block, and a `required_providers` entry replaces the entry with the same local name. Preparation requires the declared edges exactly. Each registry call must name its package's source and subdirectory, and carry a version constraint that admits the package version. In each directory, some pinned version of each required provider must satisfy all of that directory's constraints, and every resource, data or ephemeral type needs a pinned provider. Constraints use `=`, `!=`, `>`, `>=`, `<`, `<=` and `~>` over release versions; a one-part `~>` is refused because the module and provider libraries read it differently.

Only baked files are checked: the non-hidden files in declared directories. `.tofu` files are skipped, because Terraform ignores them. Other archive entries, such as examples and tests, are never read.

#### In the image

The receipt records each package's file digests and `inventories`: for each baked directory, the module manifest records Terraform writes below a call to it. The prepared image copies the files to `/opt/maf-terraform/registry/<name>/` and refuses any missing or extra file. Before the image is published, the build runs offline `init` through the launcher for every package that no other package calls, and once for each rank of provider versions, so every pinned provider version is installed once. It runs four probes at a time, prints every probe that failed, and fails if any did. It also refuses a mirror whose files are not executable, because a dropped executable bit would otherwise fail only later, at `validate`.

At run time the launcher reads the staged project's module calls, follows local calls inside the project, and writes `modules.json` records for registry calls a baked package can serve. It picks the newest baked version the call's constraint admits. A call to `<source>//<subdirectory>` is recorded as Terraform records it: with that source and the package's subdirectory. The record keeps the authored source spelling, and Terraform still compares it and the version constraint with the configuration. A call the launcher cannot read, an unbaked module or version, a constraint it cannot decide, a missing child or provider, or a lock checksum mismatch fails initialization, so validation is INCOMPLETE.

### Generating a manifest

Hand-maintained pins do not scale, so the committed prepared manifests are generated by [scripts/terraform_manifest.py](../../scripts/terraform_manifest.py) from the policy file beside each. [USAGE.md](USAGE.md#build-an-image-with-azure-verified-modules) shows how to refresh one and build the image. A policy names only what a human decides:

- `engine`: `terraform` or `opentofu`. It decides the registry every address resolves against, and the engine the manifest declares.
- `providers`: the provider addresses a manifest may pin, each with a version bound.
- `registry_modules`: modules to bake, each with a version constraint. Generation fails if one of them cannot be baked.
- `catalog` (optional): a namespace and name prefixes. Every matching module is a root at its newest release. Its `exclude` list leaves named modules out, with a reason.

Registry modules are Terraform-only, so an OpenTofu policy carries an empty `registry_modules` and no `catalog`; the generator refuses either before it makes a request, and its manifest pins providers alone. [dependencies.opentofu-providers.json](dependencies.opentofu-providers.json) is that manifest: the Azure `azapi` and `azurerm` providers beside `local`, `null`, `random`, `time` and `tls`. An operator builds that image, as with the catalog; `terraform-live.yml` builds a prepared image of each engine from `dependencies.terraform.json` and `dependencies.opentofu.json`. `registry.opentofu.org` serves the same provider protocol as `registry.terraform.io` and decides which artifact each pin takes: the six HashiCorp providers here are OpenTofu's own rebuilds, while `azapi` 2.12.0 is the Azure release the Terraform manifests pin, with the same digest. Every request names this client, because `registry.opentofu.org` refuses one that arrives without a `User-Agent` of its own.

Each root bakes at the newest release its constraint admits, never a prerelease. Each nested call bakes at the newest release its own constraint admits, so one source can bake at several versions. For each root, the generator pins the newest release of each provider that the policy bound and every requirement in that root's module tree admit, which is the version the engine selects for it. It also pins the newest release under each policy bound. Provider digests are cross-checked against the release `SHA256SUMS` the registry names, and GitHub-hosted providers carry their repository id. A module's revision is the commit the registry download names.

A catalog root that cannot be baked is left out, and the manifest's `excluded` list records why. Causes include a provider the policy does not approve, a call to a module outside the policy, a call without a version, a module name longer than Terraform's 64-character limit, and any refusal from the preparer's own checks, which the generator runs on every package. A committed pin can also go stale, because the registry withdraws a module the manifest already names: preparation then refuses `response-status` 404 for that artifact. That 404 is not proof on its own — an archive URL also 404s when a repository is renamed or its history rewritten — so a withdrawal is established by asking the registry and the repository as well, and only then does the pin belong in `excluded`, or in the policy's `catalog.exclude` when it should stay out of a later regeneration. Nothing is written until a dry run of the real preparer has proven every pin against downloaded bytes; then the generator prints which pins moved. `--check` fails instead of writing when the committed manifest no longer matches the policy, which suits a CI guard.

Generation is deterministic, so the committed manifest's diff is the review surface. Generated provenance records where each value came from and carries no date; the commit does. The preparer verifies bytes, not signatures, so a reviewer still reads the module code at each new commit. The catalog policy approves the HashiCorp, Azure, Microsoft and `integrations/github` providers AVM modules use. It does not approve the community providers `chilicat/pkcs12` and `lonegunmanb/ephemeraltls`, which need their own review. The `random` profile manifests are not generated: each pins one provider beside its engine version and changes only when the engine does.

## Verification

The deterministic package tests need neither Docker nor installed engine binaries. `tests/test_terraform_dependencies.py` covers TLS receiver controls, policy refusals, artifact integrity, graph verification and archive bounds. The receiver accepts the negative controls under unrestricted requests before the preparer refuses them. DNS-private refusal tests are separate from the local TLS receiver, whose dial address and trust root are deliberately replaced by the test fixture. `tests/test_terraform_runner_modules.py` checks how the launcher reads module calls and builds records, without an engine. The `live_build` tests in `tests/test_terraform_image_build.py` build and check custom provider profiles for both engines.

The engine suite, `packages/maf-sandbox-terraform/tests/test_terraform_docker.py`, runs real CLI calls against the two `random` profile images, checks the daemon after each call, and also executes [test_runner.py](test_runner.py) inside each Linux image to exercise bounded pipes, deadlines, environment isolation, and lock behavior.

The prepared suite, `tests/test_terraform_dependencies_docker.py`, runs for both engines against a prepared image and its exported preparation. It verifies provider/module initialization, correct and mismatched readonly locks, missing dependencies, source nonmutation, daemon-observed network mode and disposal. A separate Docker receiver accepts direct HTTP and raw CONNECT controls over bridge networking before the identical controls are denied inside CLOSED adapter sandboxes. This is Docker evidence; ACAS and WSLC have not been live-qualified for this preparation profile.

The AVM images have their own suite, [test_terraform_avm_offline.py](../../tests/test_terraform_avm_offline.py). It runs against the catalog image or the small network image. Each backend runs the same calls through the Terraform tool: exact and `~>` pins, a local wrapper module, a correct lock, and five failures that must render INCOMPLETE for their named cause. Every sandbox first proves it cannot fetch the registry discovery document. On Docker that is `--network none`; the Docker leg also checks the same probe succeeds on a bridge network. A Docker-only case runs the launcher inside the image against a provider-only root and proves `init` served the provider by links into `/opt/maf-terraform/mirror`, with no copied bytes. ACAS CLOSED denies at a TLS-terminating proxy: DNS and TCP succeed and the request returns 403, so the probe checks for retrieved content rather than a connection. Each ACAS call creates one billable sandbox that the router disposes. `terraform-live.yml` runs the Docker leg after merge and on a schedule; ACAS runs only when an operator supplies those values.
