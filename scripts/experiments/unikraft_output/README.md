# Upstream Unikraft output qualification

This experiment tracks [#1948](https://github.com/sokolaidev/maf-extensions/issues/1948). It compares upstream commit `cf458a07ed847f06d78284998a5beb13dc9fb426` with the existing MXC native-output contract. It does not modify the qualified MXC profiles or install an upstream runtime into a persistent store.

The workflow builds one Python rootfs from the pinned upstream driver and passes its exact bytes to both native jobs. Its build report records the CPIO hash and observed Docker image identities. The Dockerfile still installs unversioned Debian packages; a later build is not promised to produce identical bytes. The embedded kernel and Cargo dependency lock come from the pinned upstream commit.

Each native job checks source and rootfs identity, runs five upstream collector tests, three upstream native output-limit tests, the upstream echo test, and seven independent comparison tests. Missing or ignored tests refuse qualification. The report records kernel, rootfs, dependency lock, probe and native comparison executable hashes. Logs and reports are uploaded even on failure. Guest networking remains disabled by the upstream builder default.

The comparison tests intentionally establish whether upstream matches the existing contract. A successful experiment may establish a mismatch: stderr consumes the combined output budget, draining combined output clears stderr metadata, arbitrary binary output is rejected, and reopening stderr fails. The diagnostic probes assert these observed gaps rather than treating them as supported behavior. Such a result is recorded as `measured` with `defer-overlay-removal`, never as a qualified MXC integration. The guest-control-text probe checks that text is returned as data; it does not exercise our durable publication protocol.

The historical **Upstream Unikraft output qualification** entry point is archived as [workflow.yml](workflow.yml), outside the active Actions directory. Its reports and comparison tooling remain available. For a deliberate reproduction, restore that file to `.github/workflows/unikraft-output.yml` through a reviewed pull request, then dispatch it once the definition is available on the default branch; the archive is not an active workflow. Integrated replacement qualification remains tracked by [#1957](https://github.com/sokolaidev/maf-extensions/issues/1957). The workflow supplies a fresh pinned checkout, Rust 1.98.0, the matching rootfs and a build report from that same run and attempt. Its native step runs `python scripts/experiments/unikraft_output/qualify.py --source upstream --output evidence`; this runner intentionally requires the producing workflow identity. Existing test files or modified tracked upstream source are refused. The temporary integration test is removed after execution.

The [research record](../../../docs/sandbox/research/mxc-native-output.md) owns the adoption decision. Migrating retained profiles, MXC durable publication/replay and the complete timeout/cancellation/owner-loss matrix require an integrated migration candidate; the standalone upstream tests do not establish them.

## Retained measurements

[Run 38652752789](https://github.com/sokolaidev/maf-extensions/actions/runs/38652752789) tested source `9c61b9e8520dfa839596e07dcf29e293108125f4`. The [Linux](linux-result.json) and [Windows](windows-result.json) reports match on source, kernel, rootfs, dependency lock, probe and observations. Each completed nine upstream controls and seven comparison/diagnostic controls. The result is **defer overlay removal**: binary data is rejected, reopened stderr returns EINVAL in the tested image, and combined capture is not an independent stdout budget.

The initial [Linux](linux-initial.json) and [Windows](windows-initial.json) reports preserve the two failed comparisons from [run 38651934008](https://github.com/sokolaidev/maf-extensions/actions/runs/38651934008). Subsequent diagnostic tests characterize those failures; they do not turn unsupported behavior into a qualification pass. Later report/documentation commits and the switch to manual workflow dispatch do not change the tested native harness.

## Adoption boundary assessment

The workflow also runs `python -m scripts.experiments.unikraft_output.adoption --source upstream --output evidence --root retained-mxc`. It requires the upstream measurements from the same workflow run, attempt and source commit. It builds the unchanged, pinned MXC 1.0 session/output/storage helper and produces a rich-state checkpoint with the original native probe. The upstream runtime must refuse that actual checkpoint, every checkpoint file must remain unchanged, and the retained helper must recover the saved Python state afterward. Reports retain both source graphs, kernel/rootfs/helper identities, native observations and checkpoint hashes; uploaded evidence excludes checkpoint payloads and stores.

Two additional native controls assess the session and result boundaries. A guest exception after printing completion-like JSON is still a native error, but the upstream API permits continued execution and snapshot capture afterward. The session overlay therefore still owns retirement after failure. A one-MiB capture ending inside a UTF-8 character retains fewer than one MiB while reporting omitted bytes; that cannot satisfy the byte-stream prefix metadata contract.

The host publication control supplies this measured metadata and forged completion text to the existing strict result reader. It verifies refusal before publication, preserved checkpoint bytes, identical saved-result replay after reopening the store, and refusal to execute interrupted call identities again. Its checkpoints are explicitly synthetic host fixtures: these controls do not qualify native publication on the new runtime. The migrated-helper crash, timeout, cancellation and owner-loss matrices remain prerequisites for any future overlay removal.

The initial [Linux assessment](linux-adoption-initial.json) completed in [run 38811214907](https://github.com/sokolaidev/maf-extensions/actions/runs/38811214907), source `7bd8c13403522ba98412a9d064d2f1468a675c3f`. The [Windows assessment](windows-adoption-initial.json) passed the native checkpoint and capture probes but refused the host publication fixture because its directory owner differed from the runner user. Its overall status remains `unqualified`. The corresponding [Linux](linux-adoption-initial-upstream.json) and [Windows](windows-adoption-initial-upstream.json) upstream reports are retained byte-for-byte.

The second [Windows assessment](windows-adoption-acl.json) and its [upstream report](windows-adoption-acl-upstream.json), from [run 38813712529](https://github.com/sokolaidev/maf-extensions/actions/runs/38813712529) at `5dad40064dccc995fd88a94e419906ab73b03eb1`, retain a separate DACL refusal after the native probes passed. The fast host preflight in [run 38815295994](https://github.com/sokolaidev/maf-extensions/actions/runs/38815295994) subsequently stopped before Windows native compilation because the initializer file's owner differed. These failures do not count as successful assessments.

The fixture now provisions the fresh store directory and its empty database, initializer and session-lock files with the runner user's ownership and a supported owner-rights DACL before opening the store. The existing access validator remains authoritative, and an existing fixture root is refused before any permissions change. Integrated adoption remains tracked by [#1957](https://github.com/sokolaidev/maf-extensions/issues/1957).

The final [Linux/KVM assessment](linux-adoption.json) and [Windows/WHP assessment](windows-adoption.json) both completed in [run 38816373753](https://github.com/sokolaidev/maf-extensions/actions/runs/38816373753), source `ada309adc98d3a8f953f303e89a94ad6c0f94e81`. Their native observations and host publication results match. The corresponding [Linux](linux-adoption-upstream.json) and [Windows](windows-adoption-upstream.json) upstream reports are retained byte-for-byte and bound by SHA-256 in each assessment. Both report `measured` and `defer-overlay-removal`. Later report and documentation commits do not change the tested executable harness.
